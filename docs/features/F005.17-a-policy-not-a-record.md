# F005.17 — A TXT at the name is not a policy

> Parent: [F005 — Mail sending (Resend)](F005-mail.md) · filed by helpdesk, intercom #27208, 2026-09-09 · **depends on [F005.15](F005.15-one-level-beside.md)**.

**Status:** Backlog · affected version 0.10.1

## The gap

`verifySendingDomain` checks SPF, DKIM and MX. It does **not** check DMARC.

Grep finds exactly two mentions of the word, both inside a single comment at `src/verify.ts:261`:

```
// send.webhouse.dk has SPF but no DKIM and still PASSES DMARC, because
// _dmarc.webhouse.dk defaults to relaxed alignment and SPF alone carries it.
```

So the author **reasoned about the DMARC record** — knew it exists, knew it decides whether a half-configured domain still delivers — and never looked it up. The comment is the evidence that the gap was seen and left open.

## Why it is more than deliverability

Resend does not require DMARC, so leaving it out was defensible. But:

> Without a DMARC record the **receiver** has no policy to fall back on, and a forged mail from the customer's own domain has nothing stopping it.

For a multi-tenant product onboarding customer domains — which is exactly what helpdesk is building — that is a security property, not a nicety.

They have had to write a ~90-line layer on top (`apps/core/src/mail/domaene.ts`) that calls us and then resolves `_dmarc.<domain>` itself. That is the drift the reuse rule exists to prevent, and they filed it instead of keeping it.

## The two details that change the implementation

Both measured by helpdesk, both worth more than the feature request itself.

### 1. The suggested fix must be `p=none`, never `p=reject`

A new domain with no traffic history starting at `p=reject` **rejects legitimate mail if any one link is wrong** — invisible to the sender, visible to the customer's user.

Our `missing` array carries the fix text, so this is our sentence to get right. F005.15 already established the principle in the other direction: a fix that does not fix costs trust. A fix that actively breaks the customer's mail costs more.

### 2. A TXT at the name is not a policy

`_dmarc.<domain>` can answer with something else entirely — a `google-site-verification`, say. helpdesk requires the `v=DMARC1` prefix, case-insensitive, and has a test for precisely that: **a TXT that exists but is not a policy yields `missing`, not `ok`.**

Without it, *"the name answered"* is enough to pass. That is a green for the wrong reason, and it is the same shape as [F035.14](F035.14-the-preview-must-stay-readable.md)'s preview case — a value that matches the *location* of the thing you want without being the thing.

The case-insensitivity is not decoration: the RFC does not mandate a case, so a case-sensitive check reports a valid policy as missing — a false alarm, which is how a check gets switched off.

## Three states, unchanged

helpdesk's error-code split matches what this package already does, and it stays explicit:

| resolver error | state |
|---|---|
| `ENOTFOUND`, `ENODATA` | `missing` |
| `ESERVFAIL`, timeout, anything else | `unknown` |

Their sentence for why: *"alarmerer vi på vores egen resolver der er nede, lærer folk at ignorere alarmen."* An `unknown` never counts toward `ok`.

## Depends on F005.15 — and the dependency is the interesting part

[F005.15](F005.15-one-level-beside.md) fixes **where** we look for SPF and MX: Resend puts them on `send.<domain>`, and we currently look at the apex.

**DMARC is different again.** The policy always lives at `_dmarc.<domain>` — never under the send subdomain. So the obvious mistake, once F005.15 has moved two lookups to `send.`, is to move this one with them.

Adding DMARC first would mean writing a fourth lookup into a function whose lookup locations are about to change, and then re-deciding all four at once. Do F005.15 first; this card then adds one lookup to a settled shape, with an explicit assertion that it did **not** follow the others.

## Reuse

Nothing to check — this extends a function this repo owns, in the fleet's single mail primitive. helpdesk filing it rather than keeping their 90 lines is the reuse rule working; the card's job is to make their layer deletable.

## Non-goals

- **Judging the policy's strength.** We report that a policy exists, not whether `p=none` is strong enough for this customer. That is the customer's posture decision, and a package that grades it will be wrong for someone.
- Parsing the full DMARC record (`rua`, `pct`, `sp`, alignment modes). The prefix answers the question this check asks.
- Checking DMARC on anything but the sending domain.

## Rollout

Minor, additive — a new field. **But `ok` changes meaning for real domains:** a domain that reports `ok` today and has no DMARC record will start reporting `false`. That is the fix working, and the release note must say so in those words, or consumers gating on `ok` will read it as the package having become noisy.

helpdesk removes their local layer in the order [F005.16](F005.16-nothing-broken-leaves-the-house.md) established: published → verified against their real tenant domain → **then** the copy goes. Not before — their layer is rejecting today, and deleting it while ours only reports would be a silent regression.
