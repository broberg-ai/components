# F038.47 — Discovery's errors reach Upmetrics

## Motivation
The daily Upmetrics standing order (27/10) found components with 0 open issues — the day after F039.10's outage, when every DB-backed route on discovery.broberg.ai answered 500 for 25 minutes (26/10, 13:42–14:10 dansk tid). broberg-discovery has `UPMETRICS_DSN` and `UPMETRICS_API_KEY` as Fly secrets, but `apps/discovery/server.ts` never initialises `@upmetrics/sdk`: errors go only to the `@broberg/logger` line. A repo that sends nothing cannot close its own issues, and an outage nobody's dashboard sees is found by a peer instead (helpdesk found that one).

## Scope
- `init({ dsn: process.env.UPMETRICS_DSN, environment, release })` at boot, only when the DSN is set.
- In `app.onError`: keep `errorLogger(log)`, and also report the error to Upmetrics (message + stack + route + status), never headers or body.

## Non-goals
- No client-side SDK (Discovery's pages are server-rendered).
- No change to response shapes.

## Architecture
A tiny `reportError(err, ctx)` seam in server.ts that is a no-op without a DSN and calls the SDK's capture otherwise; tests inject a fake.

## Dependencies
`@upmetrics/sdk` (latest), the existing Fly secrets.

## Reuse
The fleet's error hub is Upmetrics via `@upmetrics/sdk` (CLAUDE.md, «Upmetrics — error + incident observability»); no @broberg package wraps it. `@broberg/logger` stays the log sink.

## Rollout
Test + ship dark → commit → the discovery workflow deploys → send one test event → see it via GET /api/issues → resolve it.
