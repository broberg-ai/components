# F053.11 — `readPeriod` answered "could not read it" with the same value the consumer uses for "never expires"

**Status:** In progress · **Epic:** F053 (`@broberg/stripe`) · **Written:** 2026-09-08
**Ordered by:** Christian, 2026-09-08 — «Stripe manglen skal selvfølgelig bygges»

## Motivation

`readPeriod()` returns `{ start, end }` where `end: null` means **"I could not read it"**. The package README says so in as many words, and says the reader must never treat it as "no expiry".

sanneandersen stores that value in `subscriptions.current_period_end`, a column where `null` **already** means something else:

```
null = "gift, deliberately no expiry"     → access forever is CORRECT
null = "could not read it"                → access forever is WRONG
```

Their access rule (`access.ts:51`) is `or(isNull(currentPeriodEnd), gt(currentPeriodEnd, now))`, and it cannot tell the two apart, because the difference was never written down anywhere.

**That is not their bug alone.** The package hands them the exact value that collides, and then documents that they must not let it collide. *A warning is not a guard* — their own sentence about their `console.warn`, and it applies to our README too.

### Measured, by sanne, on production 2026-09-08

- 6 subscription rows. One paying (Malene, `2026-09-27`), five gifts with `null`. **No wrongful access today.**
- The **update** branch is already defended: `readPeriod(sub).end ?? sub.currentPeriodEnd ?? null` — an event without a period no longer erases a date we know.
- The **create** branch is not: `currentPeriodEnd: periode.end` is written raw, with a `console.warn` beside it.

So the exposure is real, currently unrealised, and one unreadable payload away.

## Scope

**Make the unreadable case unstorable by accident.** `readPeriod` returns a discriminated union, so `end` does not exist on the failure branch and cannot be written to a nullable column without the consumer deciding what to do:

```ts
export type PeriodRead =
  | { ok: true;  start: number | null; end: number }
  | { ok: false; reason: "no-subscription" | "no-period-field" };
```

`ok: false` carries **no `end` at all** — not `end: null`. That is the whole design: the failure branch must not be shaped like the success branch, or a consumer can keep reading `.end` and get `undefined`, which stores as `null` again.

**Breaking, so 0.4.0.** Measured before choosing: the only consumer in the fleet is sanneandersen, three files. Keeping the old shape alongside the new one was rejected — the old shape *is* the defect, and an opt-in safe variant is the bypass this repo has been bitten by before ("the guard existed and was bypassed").

### Non-goals

- **Not fixing sanneandersen.** Their create branch is in their repo and touches a live payment path with a real paying subscriber; that needs Christian's own order to *them*. We ship the package and the recipe.
- Not touching `readSubscriptionId` — its `null` has only ever meant one thing.
- Not throwing. These run inside a webhook handler; an exception means the event is never acknowledged and Stripe retries forever.

## Reuse

Nothing to reuse — this is the fleet's own Stripe chokepoint. Checked Discovery for a second payment primitive: `@broberg/stripe` is the only one.

## Acceptance criteria

1. `readPeriod` returns `{ ok: true, start, end: number }` on every shape it reads today — item-level, top-level, and the mixed case. Asserted per shape, so the migration cannot quietly narrow what we can read.
2. `ok: false` carries **no `end` property at all**. Asserted with `"end" in result === false`, not with `end === null` — the point is that the field is absent, not nullish.
3. A consumer that writes `result.end` straight into a nullable column **fails to compile**. Asserted with a type-level test that must produce an error on the union.
4. The two failure reasons are distinguishable: no subscription object vs a subscription with no period field anywhere. One test each.
5. **Mutation-proven:** collapsing the union back to `{start,end}` with nullable `end` must redden a NAMED test. A green absence-check is worth nothing until it has been seen to fail.
6. README carries the migration in three lines, and states plainly that `ok:false` means *unreadable* and never *no expiry* — the sentence that is the whole incident.
7. Published as 0.4.0, and sanneandersen is told with the recipe. **Their adoption is NOT this card's AC** — it is theirs, on Christian's order.
