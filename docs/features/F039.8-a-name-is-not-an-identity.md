# F039.8 — A name is not an identity

**Status:** Backlog · **Epic:** F039 (Discovery auto-enrollment) · **Written:** 2026-09-01

## The problem

Discovery keys every enrollment on a **session name**. Session names are not
unique, and never were.

Raised by buddy, with measurements rather than a preference:

1. **Two sessions named `sanne` are running right now.** Nothing in an enrollment
   record distinguishes them — and nothing distinguishes them *historically*
   either, so an adoption reported last month cannot be attributed to the right
   one after the fact.
2. **`cardmem` points at three different repos** through session-name inheritance
   (their F116.3). One roster row already answers for three codebases, and every
   reuse-gap served to those sessions is computed against a merged population.
3. **`cardmem_session_start` already carries `repo` as `owner/name`.** The unique
   key is present at the moment of enrolment and is thrown away.

## Why this is the same failure as F039.7, one level down

F039.7 was about a gap that could not tell *"has not adopted it"* from *"has
never told us anything"*. This is the same merge underneath it: two **different
repos** arriving as one row, and the answer reading as a confident fact about
whichever one you happened to ask about.

The asymmetry is what makes it worth fixing rather than tolerating:

- a **split** identity makes a gap look too long — annoying, and *visible*;
- a **false merge** makes it look right while crediting the wrong party — and
  nothing about the output says so.

And it has already produced a wrong answer in this repo. I mapped `fd-sundhed`
onto `fds` on name similarity; buddy measured that `fds` is
`webhousecode/fysiodk-aalborg-sport`, **a different customer**. My own FLEET
roster said so — I had edited that file and not read it.

## A third mechanism — claimed, not confirmed (2026-09-02)

The session in the sanneandersen repo reported: *"denne session hedder i øvrigt
`sanneandersen-9a` i dag, ikke `sanne` — navnet skiftede mellem to sessioner i
samme repo, mens repoet ikke har flyttet sig en tomme."*

If true, that is a **third** way a name stops identifying a repo, distinct from
the two already recorded:

| | mechanism | what breaks |
|---|---|---|
| 1 | **inheritance** — one session hands a name to another | credits the wrong session |
| 2 | **simultaneity** — two sessions hold one name at once | no inheritance to trace; both are valid senders |
| 3 | **rename** — the same repo's session is renamed over time | yesterday's and today's enrolments never join |

Mechanism 3 is the worst for a *historical* roster: 1 and 2 confuse who reported
something now, 3 silently splits one repo's history in two.

**Measured against the live API the moment it was reported:**

```
sanne             -> resolved sanne, 6 enrolled, merged_from [uuid, sanneandersen]
sanneandersen     -> resolved sanne, 6 enrolled
sanneandersen-9a  -> resolved ITSELF, 0 enrolled, gap_confidence never_reported
```

So a fresh enrolment under the new name opens a third row — and F039.7's own
disclosure would tell a well-reporting repo that it *"has never self-reported
anything"*: true of the NAME, false of the REPO. The disclosure is correct and
misleading at the same time, which is this epic's shape exactly.

**But the alias was NOT added, and that is the point of this section.**

Adding `"sanneandersen-9a": "sanne"` turned `apps/discovery/server.test.ts` red:
every non-UUID alias must be **owner-confirmed**, and a session's word about its
own name is a third category the guard deliberately does not accept. The guard is
right — it exists because `fd-sundhed` was once merged onto `fds`, a different
customer, on name similarity.

And the check paid for itself immediately. `buddy list_sessions` reports the live
session on m1 as **`sanne`**, not `sanneandersen-9a`. So the rename is either not
in effect, already reverted, stale in one of the two registries, or the reported
string is a cardmem project slug rather than a buddy session name — and *which of
those* is unresolved. One more identity question that a repo slug would not have.

**Consequence for this card, not a new one:** the alias map is now the thing being
argued against. Three entries exist for one repo, every rename needs a fourth, and
the entry that would have been needed today could not be added without the owner.
That treadmill is the argument — not a reason to loosen the guard.

## The fifth mechanism, and it settles the card (2026-09-02)

sanne reported that their session calls itself `sanneandersen-9a` while messages
addressed to `sanne` still reach it, and framed it as *"the name a session
REPORTS is not the set of names that ROUTE to it"*.

**Then I ran both directories from THIS session, and it is sharper than that.**
It is not one session's self-report against my measurement. It is **two
directories I can read from one seat, disagreeing about the same peer at the same
moment:**

```
buddy list_sessions   m1: cardmem, trail, fd-sundhed, super, components, buddy, cms, sanne
ListAgents            sanneandersen-9a [7c19f6] · interactive · tmux sanne:@1902.%1910
```

Same peer. Same instant. `buddy` says `sanne`; the harness says
`sanneandersen-9a` — and the tmux window it names is `sanne`, which is
evidently what buddy is reporting. Neither is lying and neither is stale.

**So no name is authoritative, because there is no single directory of names.**
Which name a repo "has" depends on which directory you ask, and a roster keyed on
a name has silently picked one directory without saying so. That is the argument
this card was reaching for; everything above it is a symptom.

### And simultaneity is no longer a relayed claim

In the same output, first-hand:

```
cardmem [225887]  ·  bg           ·  started 2d ago
cardmem [22df4f]  ·  interactive  ·  started 3d ago
```

**Two live sessions with the identical name, in my own peer list, right now.**
cardmem told me this in the abstract earlier; here it is measured, and it means a
message to `cardmem` is addressed to a set, not to a session — while an
enrolment filed under `cardmem` is recorded as if it were one.

### What this changes in the design

Nothing below needs rewriting — it makes the existing design *required* rather
than preferable:

- `repo` (`owner/name`) is the only identifier all three id-spaces agree on. The
  harness ref (`7c19f6`), cardmem's session id (`19e59c29`) and the name are
  three separate spaces for one thing, and sanne could not determine who assigns
  the `-9a` suffix. Neither could I.
- **The alias map cannot be rescued.** An alias maps name → name, so it inherits
  the ambiguity it is meant to resolve: adding `sanneandersen-9a` would have been
  *true in one directory and unused in the other*, with both live.
- A name stays as a **display label**, and the API should say which directory a
  label came from rather than presenting it as identity.

**No alias was added.** sanne asked for none, has 0 enrolments under the new
name, and continues reporting under `sanne` — the right call, and the guard in
`server.test.ts` would have refused it anyway.

## Design

- `POST /api/enroll` accepts `repo` (`owner/name`) and stores it. The roster is
  keyed on the repo; the session name becomes a **display label**.
- `GET /api/sessions/:session` keeps working, and its response states which
  repo(s) the answer covers — so a merged answer cannot be mistaken for a
  single-repo one.
- A row with no repo reported reads `repo: null` **with a note**. It must never
  fall back to the session name and look resolved.

## Non-goals / constraints

- **No naked cutover.** Session-name enrolment keeps working for every repo
  already enrolled until each has re-enrolled. Replace, prove, then remove.
- **The key binding must not break.** Trust-on-first-use stays per session, so a
  repo re-enrolling under its slug uses the key it already holds. Getting this
  wrong locks repos out of their own roster.
- **Never infer a repo from a name.** That is the error already made here once.
  Only an explicit `repo`, or an owner-confirmed alias.

## Verification

The test that matters is the one that is impossible today: two enrolments from
the same session NAME with different repos must produce **two rows**, and
mutating the key back to name-only must turn it red. Everything else is
regression cover — every repo currently in the roster still gets its correct gap
before, during and after.
