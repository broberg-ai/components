# F016.7 — Scrolling inside a popover closes it

## Measured, not reasoned

A panel with an inner list, registered with `makeOutsideClickHandler`, dispatching
a `scroll` event on the **inner** element:

```
onClose called: 1        (should be 0)
```

## Why

```ts
doc.addEventListener("scroll", onScrollOrResize, true);   // capture
...
const onPointerDown = (e) => { if (isOutsideAll(e.target, getEls())) onClose(); };
const onScrollOrResize = () => onClose();                 // ← never asks
```

Capture-phase listening is **correct and deliberate**: scroll events do not
bubble, so capture is the only way to catch an ancestor scroll container — and a
fixed-position portal must close when the page scrolls beneath it, or it floats
away from its trigger.

But capture also catches every scroll from every **descendant**, and
`onScrollOrResize` closes unconditionally. The pointerdown path asks
`isOutsideAll`; the scroll path does not. **Same file, two guards, one of them
missing.**

## Who this already hurts

Not hypothetical, and not the bell:

- **`CustomSelect`** — any option list long enough to scroll closes itself the
  moment the user scrolls it. That is this package's flagship control.
- **`DatePicker`** — same, if the month grid overflows on a short viewport.

Nobody has reported it. That is worth saying out loud rather than treating as
evidence it does not happen: **a select that closes while you scroll reads as a
slip of the finger, not as a bug worth filing.** The absence of reports is what
this kind of defect looks like from the outside.

## Found by the reuse check, which is the point

F074.4 (the shared notification bell) needs outside-click for a panel that is
**portalled** and has a scrolling list of ~10 rows. The house rule says look for a
shared primitive before writing one, so I did.

And `isOutsideAll` taking an **array** of elements is exactly right for a portalled
panel — which is precisely what cardmem got wrong locally: they guarded on a single
`rootRef`, and once the panel was portalled to `document.body` every click *inside*
it was judged "outside", swallowing every desktop click.

**The shared primitive is better than what any of the four apps wrote by hand.** It
just has this one hole, and the bell would have fallen into it on day one.

## Extend, never work around

A local scroll-guard inside the bell would:

1. leave the defect in production for `CustomSelect` and `DatePicker`, and
2. make it the fourth hand-rolled outside-click in a fleet that owns a good one.

So the fix goes here.

## The fix

`onScrollOrResize` asks the guard that is already in the file. Not a second
predicate written beside it — `isOutsideAll`, the same question the pointerdown
path asks.

Resize stays unconditional: a window resize has no target inside anything, so
asking would be noise.

**No option, no flag.** A popover closing when you scroll its own list is wrong in
every app that has ever mounted one; it is not a preference a consumer should have
to discover.

## Reuse

This card *is* a reuse-check result — see above. Nothing external is involved;
`isOutsideAll` is already exported from this package and needs no new dependency.

## Non-goals

- Changing the capture-phase listener to bubble-phase. That would trade this bug
  for the one the code was written to prevent.
- Touching the pointerdown path. It already asks the right question.
