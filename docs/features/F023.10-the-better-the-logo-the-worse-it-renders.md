# F023.10 — The better the logo you supply, the worse it renders

**Status:** Ready · **Epic:** F023 (`@broberg/mail-core`) · **Written:** 2026-09-03

## What happened

Reported by vn-leker, verified in our source, and it **reached Christian's inbox
today**.

`index.ts:153` builds the logo and gives it no width attribute:

```html
<img src="…" alt="…" style="display:block;margin:0 auto;max-width:180px;height:auto;border:0;">
```

`ShellOpts` carries `logoUrl` and `logoAlt` — **no size**. The gap cannot be
closed from the caller's side: any source wider than 180px renders at 180px, and
the only way out is to abandon the slot entirely, which is what vn-leker did.

## The measurement

cms delivered the mark at **480×480** — 2× for a 40px mark, their decision and
the right one. The shell rendered it **180px on a 520px card**, a third of the
width. Christian opened it in Gmail: *«Alt for stort logo»*. It did not read as a
preference; it read as a fault.

## Why it keeps biting: the trap is asymmetric

**The better the source you supply, the worse the result.** A 96px file would
have looked fine. Shipping a retina asset — doing the right thing — is what gets
punished. So this does not hit the careless consumer; it hits the careful one,
and it will hit the next careful one the same way.

## The half a naive fix misses

Setting the width **only in `style`** leaves Outlook rendering the mark at its
full file size: Outlook's Word engine ignores CSS dimensions on an image. A fix
that looks correct in every client the author can check is wrong precisely in the
one that cannot be corrected afterwards.

That is the third time on this epic that the same shape has produced a defect —
the footer fill, the mid-tone text, and now the logo. Each was correct where it
was written and wrong where it was read.

## Reuse

Checked Discovery (`?q=email+image`, `?q=responsive+image`, `?q=logo`).
`@broberg/media-transform` resizes images server-side (HEIC→JPEG/WebP, responsive
variants) and is genuinely adjacent — but it is **the wrong layer** here. The
defect is not that the file is too large; it is that the *markup* does not say
how wide to draw it. Pulling `sharp` into a string-rendering package to solve a
missing attribute would be a heavy dependency for a number.

Worth saying to consumers, though, and it goes in the README: `media-transform`
is the right tool for **producing** the asset at a sane size; `logoWidth` is how
you **draw** it. They are complementary, not alternatives.

## Design

```ts
logoWidth?: number   // default 180
```

```html
<img src="…" width="56" style="display:block;margin:0 auto;width:56px;height:auto;border:0;">
```

**Attribute AND style.** The attribute is what Outlook reads; the style is what
everything else reads. Neither alone is sufficient.

**No `height` attribute**, and this is a correction to the proposal as filed.
vn-leker suggested `height="${w}"` alongside — correct for their square mark, and
wrong for this package, which serves non-square logos. A forced square distorts
them in exactly the client that honours attributes. `width` + `height:auto`.

## Non-goals

- Not resizing the image. See **Reuse** — that is `media-transform`'s job.
- Not changing the placement. F023.8's README records the centred slot as a
  deliberate shared choice that a consumer dropped their own variant for; this
  card changes the **size**, not where it sits.

## Verification

- **Negative control first:** `logoWidth` omitted → byte-identical to 0.4.0's
  logo block, asserted against a snapshot captured from the **previous** build.
  A snapshot regenerated from the new source compares the new code to itself.
- The reported case as a test: a 480px source asked for 56px renders `width="56"`.
- No `height` attribute is emitted.
- **The mutation that matters:** drop the width ATTRIBUTE, keep the CSS. That is
  the shape of the fix a careful author would ship after testing in Gmail and
  Apple Mail, so it is the one the suite has to catch.
