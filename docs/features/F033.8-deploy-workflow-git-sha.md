# F033.8 — The shared deploy workflow cannot tell a register WHICH version it deployed

> Parent: [F033 — Deploy provider core](F033-deploy-provider-core.md) · sibling of [F033.7](F033.7-fly-server-deploy-workflow.md), which built the workflow this story repairs.

## Motivation

On 2026-08-19 the `trail` session measured why their Upmetrics deploy-register showed nothing useful. Their CI deployed with `flyctl deploy --remote-only --config fly.toml .` — no `--build-arg GIT_SHA` — so their boot-time report script posted `sha:"unknown"` and `deploy_id:"unknown-trail-docs"`.

They fixed their own workflows. Then I read ours, and **`fly-server-deploy.yml` has the identical hole**:

```yaml
flyctl deploy --remote-only --config "$CONFIG" $APP_ARG $DF_ARG
```

No build-arg. No sha. Ever. This is the workflow the fleet is told to adopt for deploying a server app to Fly.

### Why an empty sha is worse than no report at all

The register contract — **our** design — is `deploy_id = sha-site`, idempotent. Idempotency exists so a re-reported deploy is not counted twice. But nobody asked what happens when the sha is *empty*:

1. `unknown-<site>` is a syntactically valid id.
2. It is accepted and written **once**.
3. Idempotency then **refuses every later write** — including the correct one after CI is fixed.

So a forgotten build-arg does not produce a gap. It produces a **permanent wrong row that reads as a healthy report**. An app that never reports is visible in a register; an app reporting `unknown` looks like it is working.

That is this week's recurring failure form, again: **a claim that fails GREEN is never contradicted by use.** Ongoing use — which corrects almost everything else — is exactly what cannot correct this.

> The register-side guard (refuse a report whose sha is empty/`unknown`, rather than accept and lock it) was filed with `upmetrics` the same day (#21489). It is theirs, not ours: a contract cannot know its input is empty; only the register can decline to write the lie down. This story is strictly the **producer** half.

## Scope

Put the commit sha into the build, and document the half we cannot do for the consumer.

**In scope**
- `--build-arg GIT_SHA=<7-char sha>` on the deploy step, unconditionally.
- A usage-comment addition stating the build-arg is build-time only, and naming the two Dockerfile lines a consumer needs (`ARG GIT_SHA` / `ENV GIT_SHA=$GIT_SHA`).
- Discovery infra-tip updated so an adopting repo learns this *before* it wires a register.

**Non-goals**
- A general `build_args` passthrough input. Not requested, and speculative configurability is exactly what Rule 2 forbids. One value is needed; one value is passed.
- Making the workflow *report* a deploy. It builds and deploys; reporting belongs to the app's own boot script.
- Fixing trail. They fixed themselves; this is our copy of the same defect.
- The Upmetrics-side guard (#21489).

## Two halves — and only one is ours

A `--build-arg` exists **during the build only**. Passing it does not put anything in the running container. Unless the Dockerfile declares the arg and forwards it to an env var, a consumer wires our workflow, sees a green deploy, and still reports `unknown`:

```dockerfile
ARG GIT_SHA=unknown
ENV GIT_SHA=$GIT_SHA
```

trail's Dockerfiles already carried both lines, which is the only reason their one-line CI fix worked. A consumer starting from ours has no such luck — so **the workflow must say it**, or this story reproduces the very failure it repairs, one layer out.

## Measured before designing

The design rests on one assumption, so it was tested rather than asserted (docker, this machine, 2026-08-19):

| Question | Result |
|---|---|
| Does `--build-arg GIT_SHA=abc1234` fail a Dockerfile with no `ARG GIT_SHA`? | **No — exit 0.** Docker warns about an unconsumed arg; the build succeeds. |

That is why the arg is passed **unconditionally** with no new input: it cannot break an existing consumer.

**Short form, deliberately.** `${GITHUB_SHA::7}` matches what `git rev-parse --short HEAD` prints, which is what local `ship:*` scripts use. Same commit deployed from CI or from a laptop then yields the **same** `deploy_id` — one release, one row. A full-length sha here would silently create two rows for one release, which is the same class of quiet wrongness this story exists to remove.

## Consumers

`happy-little-place` (`.github/workflows/ci.yml`) is the one known adopter, found by a local filesystem grep.

**The consumer list is not proven complete.** `gh search code` was tried first and returned empty — but a control query for a string guaranteed to exist also returned empty, so that search answered nothing at all. Recording it as silence rather than as a zero.

## Reuse

Checked Discovery before writing this. There is no `@broberg/*` package that owns "pass a version into a container build" — this is a GitHub Actions workflow components already owns (F033.7), and the fix belongs in it. Nothing to adopt, nothing new to publish. The related capability, deploy-event reporting, is Upmetrics' surface and is reached via its documented endpoint, not via a package.

## Rollout

One commit to `.github/workflows/fly-server-deploy.yml` plus the Discovery tip. No version to publish — consumers pin `@main`, so they pick it up on their next run. No consumer action is required for the build to keep working; consumers that *want* the sha at runtime add the two Dockerfile lines when they wire a register.
