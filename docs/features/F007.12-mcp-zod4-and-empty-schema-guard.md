# F007.12 — Zod 4 support + never emit a silently-empty inputSchema

> Story under **F007 — @broberg/mcp** (epic closed 2026-06-25; this is a consumer-filed follow-on defect).
> Filed by **beacon** (#18984, escalated #18985). **Blocks beacon F014** (4 stories, paused).

## Motivation

`packages/mcp/src/tools.ts:43` converts a tool's input shape with `zodToJsonSchema(z.object(tool.inputSchema))` from `zod-to-json-schema@^3`, and `peerDependencies.zod` is `^3`.

`zod-to-json-schema@3` only understands Zod 3's internal representation. Given a **Zod 4** object it finds nothing and returns an empty envelope **without throwing**. beacon measured it (zod 4.4.3, zod-to-json-schema 3.25.2 — the versions the package itself resolves):

```
zodToJsonSchema(v4) => {"$schema":"http://json-schema.org/draft-07/schema#"}
z.toJSONSchema(v4)  => {"type":"object","properties":{...},"required":["query"],...}
```

The consequence is not a build error. A tool registered through `defineTool` with a Zod 4 shape reaches the MCP client with **no declared inputs**: the model sees a tool that takes nothing, sends whatever it likes, and nothing validates it. The server starts, the tool lists, the call "succeeds". As beacon put it — a guard that cannot fire looks exactly like a guard that passes. An exception would have been far better.

beacon is 100 % Zod 4 because one Zod object drives REST validation, the generated OpenAPI, the MCP tool inputs and the SDK types (their PLAN.md §6.2). They cannot drop to Zod 3 without abandoning that single-source contract, and they correctly refused to hand-roll transport/tool-registration — so they rolled their half-built package back and filed this instead.

## Scope

1. **Widen the peer** to `"zod": "^3 || ^4"`.
2. **Runtime-detect the converter** in `toToolListEntry`: if `typeof z.toJSONSchema === "function"` (Zod 4 emits draft-2020-12 itself — exactly what MCP wants) use it; otherwise fall back to `zodToJsonSchema` (Zod 3). One `if`, no new dependency.
3. **Escape hatch** — add `inputJsonSchema?: Record<string, unknown>` to `ToolDef`. When set, skip conversion entirely and emit it verbatim. This also serves anyone holding a JSON Schema that never came from Zod.
4. **Kill the silent-empty mode** — after conversion, if the input shape was non-empty but the result has no `properties`, **throw** a named error. This is the part that matters most: it makes the defect impossible to reproduce quietly on any future Zod/converter combination, independent of 1–3.
5. README: document `@modelcontextprotocol/sdk >= 1.12` as a **required peer that is not auto-installed** (a new consumer currently discovers this only when the server won't boot).

### Non-goals

- **Not** a Zod-4-only rewrite. beacon recommended dropping `zod-to-json-schema` for `z.toJSONSchema()` outright; we disagree — `@broberg/mcp` already ships to **cardmem** and **xrt81** on Zod 3, and removing the Zod 3 path is a breaking change for live consumers to fix a problem that an additive branch solves. We take beacon's option (b) plus their (1) and (3), not (a).
- No change to `dispatchTool`, the transports, auth, or the audit envelope.

## Architecture sketch

```ts
function toJsonSchema(shape: RawShape): Record<string, unknown> {
  const obj = z.object(shape);
  const out = typeof (z as any).toJSONSchema === "function"
    ? (z as any).toJSONSchema(obj)                       // Zod 4, draft-2020-12
    : zodToJsonSchema(obj, { $refStrategy: "none" });    // Zod 3, draft-07

  // The guard — version-independent, and the real fix.
  if (Object.keys(shape).length > 0 && !hasProperties(out)) {
    throw new EmptyInputSchemaError(...);   // never ship a schema-less tool
  }
  return out as Record<string, unknown>;
}
```

`toToolListEntry` returns `tool.inputJsonSchema ?? toJsonSchema(tool.inputSchema)`. An empty shape `{}` stays legal (a tool that really takes no arguments) — the guard is keyed on *shape non-empty but output property-less*.

## Dependencies

None new. `zod-to-json-schema` stays for the Zod 3 path.
