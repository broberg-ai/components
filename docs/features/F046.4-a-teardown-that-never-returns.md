# F046.4 — a teardown that never returns

**Status:** In progress · **Epic:** F046 (`@broberg/lens-engine`) · **Written:** 2026-09-11 · **Filed by:** cardmem

## The report, and why it is a good one

cardmem measured rather than suspected: `closeBrowser()` did not return in `apps/lens-cloud/src/pdf.test.ts` on macOS. They first assumed a slow shutdown and raised bun's 5 s timeout to 30 s — it hung the full **30 007 ms**. They told us the number *and* that their first fix had been wrong.

They also did the thing the reuse rule asks for: they bounded it at 10 s **in their own test**, printed a warning that a Chromium may still be running, and filed the gap instead of patching the package around the problem.

And they named the consequence that matters more than the bug:

> a local gate that is habitually red for a reason you learn to ignore is a gate you stop reading — and that is exactly how a genuinely red CI sat unnoticed here for two commits.

## What I measured, and how it changed the fix

**It does not reproduce here.** Same Mac, through the package's own API:

```
node   getBrowser 267 ms · drove a real page · closeBrowser RESOLVED after 24 ms · isConnected false
bun    getBrowser 259 ms · drove a real page · closeBrowser RESOLVED after 33 ms · isConnected false
```

So **bun-vs-node is not the difference** — that was my first guess and it is wrong. Reporting "works on my machine" here would have sent a real defect back to its finder as their problem.

The difference that *is* there: their file is `pdf.test.ts`, and the engine has **no PDF path at all** — `pdf` appears zero times in `packages/lens-engine/src/`. The engine returns PNG bytes. So the PDF work is their code, driving a page it got from our `getBrowser()`, and a page wedged mid-operation (a pending `page.pdf()`, a download, a `beforeunload`) is a documented way to make `browser.close()` block.

**That does not let the package off**, and this is the point of the card: whose page wedges is a detail. A shared engine must not be able to take a consumer's teardown hostage.

## Two defects, both ours

### 1. Unbounded

```ts
if (browser.isConnected()) await browser.close();
```

No bound. Any wedged page hangs the caller forever. cardmem's own second suggestion is the correct primitive and is what this card builds — a bounded form that **resolves `false`** rather than hanging, so a consumer is *told* "a Chromium may still be running" instead of never being told anything. Otherwise every consumer invents its own race, and cardmem already had to.

### 2. A success-shaped non-answer, inside the function under discussion

```ts
const p = _browser;
_browser = null;      // ← cleared BEFORE the await
if (!p) return;
const browser = await p;
if (browser.isConnected()) await browser.close();
```

While the first call is stuck, `_browser` is **already null**. So:

- a **second** `closeBrowser()` returns immediately having closed nothing, and looks like success;
- the next `getBrowser()` sees `null` and launches a **new** Chromium beside the wedged one.

cardmem's 10 s bound puts them in exactly that state: the process accumulates browsers, and every later close answers instantly and convincingly. **The bound alone would make this worse, not better** — which is why AC#7 requires a mutation for the state-restore separately from the one for the bound.

### And a third, in the same family

`catch { /* already gone */ }` swallows a **rejection**, so a close that FAILED is indistinguishable from one that worked. Noted in the code today as "already gone"; that is one of the cases, not all of them.

## Reuse

Discovery checked before the fix, per F217 — `discovery.broberg.ai/api/search` for
`browser teardown`, `timeout bound promise`, `playwright`.

**Nothing to adopt, and that is the expected answer here:** the only fleet package
that owns a browser lifecycle *is* this one (`@broberg/lens-engine`, F046). The
search returns `@broberg/soundkit` (browser audio) and `@broberg/mail` on keyword
overlap alone — neither has anything to do with closing a Chromium.

**Build, in the package that already owns it.** The bound belongs *inside*
`closeBrowser()` rather than in a shared "bounded promise" helper, and the reason is
the whole card: a race a consumer wraps around the call cannot restore `_browser`,
so it fixes the hang and leaves the accumulating-browsers defect in place. cardmem
had already written exactly that wrapper. A generic timeout utility would have let
every consumer keep re-deriving the same half-fix.

**The reuse that did happen is the other direction:** cardmem consumed the fix by
upgrading to 0.10.0 and dropping their local wrapper, instead of the fleet growing a
second copy of it. That is AC#7.

## Design

```ts
closeBrowser(): Promise<boolean>                       // unchanged for existing callers
closeBrowser({ timeoutMs }): Promise<boolean>          // resolves false at the bound
```

- `true` — the browser is closed (or there was nothing to close).
- `false` — the bound was reached, or the close rejected. **A Chromium may still be running**, and the caller now knows.

On `false` the engine **restores** `_browser` to the pending handle rather than leaving it null, so a second call does not lie and `getBrowser()` does not start a rival browser.

`void` could not express any of this, which is exactly why the consumer had to build a race by hand.

## What this does NOT fix, stated so nobody reads more into it

It does not fix whatever wedges cardmem's page. I have not reproduced that and it may well be in their PDF path. What it removes is the **unbounded** failure mode and the **false success** — and the bounded return is what will let them see the wedge at all: a `false` with a reason names a situation their 30 s hang could not.

## Rollout

Ship, then cardmem verifies on the machine that reproduces before dropping their 10 s wrapper — published → proven there → then the workaround goes. **Their Mac is the only known reproducer, so AC#8 cannot be closed from here.**
