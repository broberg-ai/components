# F038.5 — Search: adding a word to a query makes infra tips DISAPPEAR

> Story under **F038 · Discovery API**. Self-found during the weekly inventory
> sweep on 2026-08-10, while checking that tips folded in that same hour were
> actually reachable by the people they were written for.

## The measurement

Probed live against `discovery.broberg.ai/api/search`, five queries:

| query | infra hit |
|---|---|
| `fastly` | **npm** ✓ |
| `fastly negative-cache` | **npm** ✓ |
| `negative-cache fastly` — *same words, reordered* | **NONE** ✗ |
| `caret` | **npm** ✓ |
| `caret minor` — *both words in one npm tip* | **NONE** ✗ |

Adding a word to a query **removes** results. That is the opposite of what a
search box teaches you to expect, and the failure is silent: the endpoint
returns `200` with a well-formed, plausible response.

## Why this matters more than a normal search bug

The fleet rule is *reuse before you build*, and this endpoint is the thing every
session is told to consult first. An empty result here is not read as *my query
was shaped wrong* — it is read as **we do not have that**, and the next thing
that happens is a repo hand-rolls a duplicate. The sweep this bug was found in
existed precisely to prevent that.

It is also the same shape as everything else the fleet has chased this week: a
check that cannot report failure. A search that returns nothing looks exactly
like a search that found nothing.

## Root cause

`apps/discovery/server.ts:157`

```ts
const platformMatch = (full: string, curated: string, ql: string): boolean => {
  if (full.toLowerCase().includes(ql)) return true;            // whole query, verbatim, in order
  const words = new Set(curated.toLowerCase().split(/[^a-z0-9]+/).filter(Boolean));
  return tokenize(ql).some((t) => words.has(t));               // per-token — but NOT over tip text
};
```

The caller passes two different haystacks (`server.ts:317`):

- **full** = `name + role + notes + all tip text + kw` → matched only as one
  contiguous substring of the entire query.
- **curated** = `name + role + kw` → the only haystack that gets per-token
  matching. **Tip text is not in it.**

So tip text is reachable by a single word (a one-word query is a substring), or
by a verbatim multi-word phrase — and by nothing else. Two words that both sit
in the same tip, in the wrong order, match nothing.

The split is not an accident and should not simply be collapsed: `curated`
exists so that a common word like `mail` does not match every group whose tips
happen to mention mail in passing. Widening token-matching to `full` would
trade a silence bug for a noise bug.

## Approach

Add one **additive** rule, keeping both existing ones:

> If the query has **≥2 tokens** and **every** token appears somewhere in `full`,
> it matches.

- AND-across-all-tokens keeps precision — a group must contain *all* the words,
  not any of them.
- Restricting it to multi-token queries protects the single-common-word case
  entirely: `mail` on its own behaves exactly as it does today.
- Purely additive, so no query that works today can stop working.

## Non-goals

- No ranking/scoring for infra (components already rank; infra is a filter). Out
  of scope.
- No stemming, fuzzy matching, or synonym expansion.
- **No per-tip keyword padding.** Adding `caret`/`semver` to the npm group's `kw`
  would make today's probe pass and drift again the moment someone writes the
  next tip. Fix the matcher.

## Verification

RED first — the whole point of this story is a check that could not fail, so a
fix trusted on a green run would be self-defeating. The reordered-`fastly` test
must be demonstrated failing against the current matcher before the change
lands, then the same five live probes re-run after deploy.
