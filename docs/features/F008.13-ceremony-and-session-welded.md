# F008.13 — the ceremony and the session are welded together

**Status:** Ready · **Epic:** F008 (`@broberg/auth`) · **Written:** 2026-09-05
**Asked by:** the trail session, who did the homework and refused to hand-roll it
without our word.

## The question

Trail's owner wants Face ID on his iPhone. Their auth is `control_users` +
`oauth_identities` + `magic_links` + `sessions` — no Better Auth anywhere, and
**`sessions.id` *is* the cookie value**. They asked whether our passkey support
can run the ceremony **alone** — challenge/verify plus credential storage —
while they issue their own `trail-session` row exactly as today.

*Bring your own session.*

## Measured in `@better-auth/passkey@1.6.23`'s own dist — not read off the docs

### 1. `verify-authentication` creates a session unconditionally

`index.mjs` ~461-470, after the WebAuthn assertion verifies:

```js
const s = await ctx.context.internalAdapter.createSession(passkey.userId);
if (!s) throw APIError.from("INTERNAL_SERVER_ERROR", UNABLE_TO_CREATE_SESSION);
const user = await ctx.context.internalAdapter.findUserById(passkey.userId);
if (!user) throw new APIError("INTERNAL_SERVER_ERROR", { message: "User not found" });
await setSessionCookie(ctx, { session: s, user });
```

No flag, no option, no branch. **The ceremony cannot complete without Better Auth
writing its own session row and setting its own signed cookie.** So "bring your
own session" is not a supported mode of that plugin. Trail read it right.

### 2. The `afterVerification` hook is not the opt-out it resembles

It fires **before** that block, so a consumer genuinely can mint their own row
there — and then the request carries on and creates a **second** session with a
**second** cookie anyway. That is two session systems on one login.

Worth naming as a shape rather than a detail: **a hook that runs at the right
moment is not the same as an opt-out**, and it is easy to read as one. Anyone
evaluating this from the type signature alone would conclude it works.

### 3. Registration requires a Better Auth session *already*

The registration verify path reads:

```js
const session = requireSession ? ctx.context.session : await getSessionFromCtx(ctx);
if (session?.user?.id && userData.id !== session.user.id) throw NOT_ALLOWED_TO_REGISTER;
```

A user must be signed in **to Better Auth** before a passkey can be added.
Trail's own `trail-session` is invisible to it.

## Why trail's option (b) is not the escape it looks like

Mapping `user.modelName` onto `control_users` does kill the two-user-tables fear.
But (3) means the **session** model has to be mapped too — and Better Auth then
becomes the writer of their session rows, with its own `token` field and signed
cookie. Their `sessions.id` *is* the cookie; that changes. And their Lens-mint
(F198) inserts a session row directly, so it breaks.

That is the same blast radius as the full migration they were trying to avoid,
concentrated on the one table they can least afford to move.

## Why (c) is right in substance and wrong as a local build

`@simplewebauthn/server` against their own `passkeys` table with an FK to
`control_users` **is** the clean shape. It is also the shape every other repo
with its own sessions will reach for — and each one will independently hit the
trap we closed only today:

> `@better-auth/passkey` hardcodes `requireUserVerification: false` in **both**
> ceremonies. A hand-rolled copy that follows the reference gets a passkey login
> that never checks a biometric actually happened, and it looks perfect.

One repo hand-rolling this is a workaround. Three repos hand-rolling it is the
drift the shared inventory exists to prevent. So the gap is **ours**, and the
answer to trail is "don't build it, we will" — not "go ahead".

## Scope

A ceremony-only entry point, `@broberg/auth/passkey-core` (name TBD in review):

```ts
const pk = createPasskeyCeremony({ rpID, rpName, origin, requireUserVerification, store });

await pk.registration.begin({ userId, userName, existingCredentials })   // options + challenge
await pk.registration.finish({ response, challenge, userId })            // { credentialId } | throws
await pk.authentication.begin({ userId })                                // options + challenge
await pk.authentication.finish({ response, challenge })                  // { userId } | throws
```

- **Returns the verified user id and nothing else.** No session, no cookie, no
  `user` object. The consumer mints its own session — that is the whole point.
- **Carries the F008.12 guard.** `requireUserVerification` defaults to `false`
  for the same reason it does there, and when `true` it fails closed on a
  missing `userVerified` in **both** ceremonies.
- **`store` is injected** — challenge put/consume and credential CRUD. The
  consumer owns its tables; we never create one.

### Non-goals

- **Not a replacement for the Better Auth passkey plugin.** A greenfield Better
  Auth app should keep using it; this is for repos that already own sessions.
  Two entry points, one guard, no fork.
- **Not session minting, in any form.** The moment this issues a cookie it has
  reproduced the defect it exists to remove.
- **Not a credential store.** We define the interface; the consumer's database
  holds the rows.

## The thing that must not happen

**A ceremony API that verifies and then quietly does something with the result.**
The value here is that `authentication.finish` answers exactly one question —
*which user just proved possession of this credential, and did the device verify
them* — and leaves everything after that to the caller. Every convenience added
on top of that answer is a step back toward the welding this card is about.

## Reuse

Discovery checked (`/api/search`): `passkey`, `webauthn`, `face id`,
`fingeraftryk`, `biometri`. `@broberg/auth` is the only hit and it is ours, so
this is an extension of an existing package rather than a new one — the outcome
reuse-first is supposed to produce when a consumer files a gap.

`@simplewebauthn/server` is already in the tree transitively via
`@better-auth/passkey`; this makes it a direct dependency of the new entry point.

## Consumer

trail (`apps/admin-server`, control.db) is consumer #1 and asked for it. They are
**not** to build option (c) locally; that is the message back.

## The store interface, constrained by measurement (trail, 2026-09-05)

Trail read their own source files rather than recalling them, and five of the
findings decide the shape of `store`. They are recorded here because each one is
a way the obvious interface would be **wrong in a way that passes every test we
would write ourselves**.

### 1. `userId` is an opaque string. No format. Not one format.

Three write sites in `control.db`, **two live formats**:

```
u-<hex8>            invite.ts:152        the normal way a human gets in
usr_lens_<hex8>     lens-session.ts:49   the synthetic Lens principal
oauth.ts:297-301    creates NO user — rejects with email_not_registered
```

So `userId: string`, no UUID validation, no prefix assumption. Their sentence is
the one to keep: **a store that validated the shape would reject their Lens
principal and nothing else** — it would break on precisely the one user nobody
tests with.

### 2. The store must never create or update a user — there is no such method

`control_users.organization_id` is `NOT NULL` with an FK to `organizations`. A
passkey registration **cannot lawfully create a user** there: no org exists to
hang it on, and *which* org is a business decision (invite / onboarding), not
something an auth ceremony can derive.

So the interface is credential CRUD plus lookup by `credentialId`, full stop. It
carries **no `findOrCreateUser`, no user upsert, no user object at all.** Their
framing is exact: *"if the interface has a findOrCreateUser, it is the one method
we have to refuse to implement."* An interface with a method a consumer must
refuse is a broken interface, not a flexible one.

### 3. Nothing user-shaped in the interface either

`control_users` has **no `emailVerified` and no `updatedAt`** columns. Better
Auth's user shape assumes both. Any field we borrow from that shape forces a
migration on the one table holding every customer's account.

Combined with (2) the conclusion is stronger than "make them optional": **the
store never sees a user at all**, so the question does not arise. `userName` for
the WebAuthn `user.name`/`displayName` is passed by the caller at
`registration.begin`, never read from a table we do not own.

### 4. A passkey belongs to the USER, never to a tenant

A user belongs to one organization but can hold memberships in several tenants
(`control_memberships`), with the active tenant chosen per request via a
header/cookie. Scope a credential to anything tenant-shaped and the same person
on the same phone gets a key that works in one workspace and not the other.

**cb is in two tenants today, so this would hit the owner first.** No tenant
column, no tenant argument, not optional — the credential is keyed by
`credentialId` and carries `userId`.

### 5. The three session write sites stay untouched — which is the design working

`auth.ts:107` (magic-link), `oauth.ts:317` (Google), `lens-session.ts:79` (the
F198 Lens-mint). The mint is the fragile one: it INSERTs the row directly and
returns `{name:'trail-session', value: sessionId}` to `@broberg/lens`, because
their sessions are unsigned and **the cookie value *is* `sessions.id`**.

Anything that gave the session row a separate token field breaks it. A
ceremony-only API cannot, because it never touches a session — that is the whole
argument for this shape, restated from the consumer's side.

### Green field

**No passkey / credential / webauthn table exists in `control.db` today** (their
measurement: 0 hits across `apps/admin-server/src`). We define the shape and they
have nothing to migrate.

### Their negative control is already written

trail's F249.1 drives an assertion with the **UV flag CLEAR** through CDP's
virtual authenticator (`isUserVerified: false`) and requires it to be REFUSED. A
green login proves nothing about the guard without it — the same trap this card
names for a hand-rolled copy, caught on their side before we shipped a line.
