# F007.15 — tools/list says whether a tool only reads

field #2880 (12/10 2026): Scout attaches only connector tools with `annotations.readOnlyHint === true` (scout's D-eacfbe). @broberg/mcp 0.7.0 knows `kind: 'read' | 'write'` (default read) and enforces it, but `tools/list` sends no MCP annotations, so every app on the package looks like it has no read-only tools: `{"ok":false,"error":"no_read_only_tools"}`.

## Fix
- `toolAnnotations(tool)` = `{ ...tool.annotations, readOnlyHint: (tool.kind ?? "read") === "read" }` — one function, used by both registration paths.
- **readOnlyHint is derived, never set.** `kind` is what the write-guard enforces; a hint that could disagree with it would let a write tool advertise itself as read-only to exactly the client that trusts the hint to decide. So the optional `annotations` field on ToolDef takes title / destructiveHint / idempotentHint / openWorldHint only, and readOnlyHint is applied last.
- Low-level `registerTools`: `toToolListEntry` adds `annotations`.
- High-level `registerOnMcpServer`: `server.tool(name, description, shape, annotations, cb)` (SDK overload, available in the ^1.12 range).

## Not changed
The gate (`dispatchTool`/`toolDenial`) and the per-principal list filter (F007.13) are untouched.

## Reuse
This is the shared package itself (@broberg/mcp); MCP's own ToolAnnotations shape.

## Rollout
Minor 0.8.0 (tools/list output gains a field — additive). Clean install vs 0.7.0; report to field, scout informed.
