# F079.1 — the headless core

> First story after Christian's GO. First consumer is **fd-sundhed**, as an internal admin chat for Owner + Admins — which is exactly why this story is the authorization contract and not the widget.

## The line this core exists to make unwritable

cms measured it in their own 64-tool chat this week:

```js
const usable = tools.filter(t => !t.permission || hasPermission(user, t.permission))
```

`!t.permission ||` — **a tool that declared no permission passed.** 60 of their 64 declared none. A read-only user was handed **61 tools, 30 of them mutating**.

It reads exactly like a permission check. It *is* one, for the four tools that declared something. For the rest it was an open door, and the default pointed the wrong way.

So: `permission` is **required**, enforced twice — the type rejects a literal without it, and `defineTool()` throws at construction, because a dynamically built registry has no compiler. No default. No `||`.

## The second half, from sanne

> **"A tool that can act must not decide whether it may."**

Their `book_appointment` calls an endpoint that answers `consent_required` — proven with raw calls bypassing the UI. The core enforces the structural half: **a tool's `run()` receives only what the consumer put in `ctx`.** The module never hands a tool engine or database access, so the consumer's existing routes stay the gate.

That is also *why* cms's defect could exist: their tools called `getAdminCms()` directly and skipped every `requirePermission` on the HTTP layer. The filter was the only gate, and the filter had a hole.

**Denied tools are invisible, not refused.** A tool the caller may not use is never offered to the model — so it cannot be proposed — and is refused again at execution if the name arrives anyway. Two gates on purpose.

## "I cannot look that up" must not collapse into "no"

The sharpest failure in the whole survey. Christian asked Eir whether Sanne sells anything, and **Eir said no** — confidently — because the shop tool was missing.

The model was not confused. It was blind and sounded certain. A missing capability became a false statement about the business.

So the core contributes a prompt fragment that makes the honest answer reachable, and a test asserts a blind model says *"I can't look that up"* rather than asserting a negative.

## The model is injected, never imported

Consumers call `@broberg/ai-sdk` (fleet rule) and hand the core a function. Two reasons, and the second was bought today:

1. The core stays testable against a fake model — a full tool round with no network and no key.
2. **It carries no version pin.** F061.2 found `@broberg/logger` promising it *"cannot leak a secret"* while pinned to a `secret-scan` four minors stale, because a caret on `0.x` locks the minor. A core with zero `@broberg` dependencies cannot rot that way, and buddy's sentence is the reason it matters: *a package cannot know its promise has become untrue because of something underneath it.*

## Streaming from the first version

Not an enhancement. trail measured **13.1 seconds** average response — on the fastest tier. A non-streaming core would have to be rewritten rather than extended, so the loop yields frames from the start: `text` · `tool-call` · `tool-result` · `error` · `done`.

A throwing tool produces an error frame the model can see and recover from; the stream continues to `done`. Same rule `@broberg/device-stats`'s middleware follows — a broken sub-part degrades the answer, never the request.

## Not in this story

Adapters (F079.3), retrievers (F079.2), the widget (F079.4), spend caps (F079.5), retention (F079.6). This is the contract everything else is an adapter over.
