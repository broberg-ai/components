# F023.8 — The shell contradicts the measurements I wrote into it two hours earlier

**Status:** Backlog · **Epic:** F023 (Mail Templates) · **Written:** 2026-09-03

vn-leker adopted `mail-core` 0.1.0 today and reported back after **Christian read
a real test mail in his own inbox**. Four findings. I verified every one against
our source before agreeing — the line numbers below are ours.

## 1. The one that reached an inbox

`signOff(line1, line2, sign)` puts `font-size:20px` on the **third** argument
(`index.ts:299`). The big slot is last, and the order is fixed.

vn-leker's signature is name-then-title. Mapping `(farewell, name, title)`
rendered

> **CEO & Founding Partner · WebHouse ApS** larger than *Christian Broberg*

in the mail Christian opened. He spotted it on the screenshot before they did.

The API could not express their signature, so the mapping was forced — and a
forced mapping produces a confident wrong answer, not an error.

## 2. The footer is a flat fill

`index.ts:153` — `bgcolor` + `background`, both `backdropColor`.

fd-sundhed measured card **and** footer both becoming `#484848` in Outlook iOS:
the zone stopped existing. What carried it for them was a coloured **rule**, not
a fill. Ours has a rule — `rgba(0,0,0,0.08)`, a near-invisible black alpha that
disappears in exactly the client this is about.

## 3. Footer text runs on `opacity:0.65`

`index.ts:154`. **A mid-tone by another name**, and *"no mid-tones"* is
fd-sundhed's whole conclusion — their old `#8486a6` failed WCAG in **light** mode
before anyone mentioned dark. An opacity also cannot be corrected by a
`[data-ogsc]` rule the way a colour can.

## 4. A contradiction I shipped myself, two hours ago

```ts
const cardBg = b.cardBg ?? "#ffffff";     // index.ts:49 — exactly white
```

Meanwhile the comment I committed in F023.7 lists **`#fffffe`-instead-of-`#ffffff`**
among the three light-forcing techniques the shell uses. **It does not use it.**

Several clients treat *exactly* white as "invert me"; one step off slips the
recognition and no eye can tell the difference. The measured **zero** was for
Outlook iOS specifically — this is the technique that works *elsewhere*, and my
own comment claims we do it while the code does not.

That is the sharpest finding in the report: a comment describing a behaviour the
code does not have is worse than no comment, because the next reader stops
looking.

## Not a gap — recorded so nobody "fixes" it

`renderShell` centres the logo at `max-width:180px`. vn-leker had a 40px mark
beside the sender name and **dropped their own for ours** — *«et delt udtryk er
mere værd end vores variant»*. Deliberate, and it goes in the README.

And Christian's correction to them, which belongs with it: **the mail carries the
SENDER's identity, and the sender is not always the repo the template lives in.**
A consuming repo must not wrap `logoUrl`/`accentColor`/`fontSerif` in a constant.
vn-leker's own brand defines `logoUrl: null` and their builder THROWS on it — so a
missing mark is visible to them rather than arriving as a broken image at the
customer.

## Constraints

- **Additive.** `signOff(line1, line2, sign)` keeps working exactly as it does
  today; three repos call it, and a silent re-ordering would move the emphasis in
  mail already in production.
- The footer fix must be the one fd-sundhed **measured** — a coloured rule
  carrying the zone. A different flat colour is the same failure with a new value.
- **No fourth light-forcing technique.** Three are measured at zero in Outlook
  iOS. `#fffffe` is on the list because it works in *other* clients.

## Verification

The footer test is the one worth designing: render with `cardBg` and
`backdropColor` set to the **same** value — the state fd-sundhed measured — and
assert the zone is still distinguishable. A test using different colours passes
without touching the failure.

## Reuse

Checked Discovery before building (`?q=email+shell`, `?q=signature`,
`?q=contrast`). Nothing in the `@broberg/*` roster owns a mail signature block or
a contrast-checked colour pair — `@broberg/theme` holds design tokens for **web
surfaces**, and a mail cannot use CSS custom properties at all (Outlook does not
resolve `var()`), so borrowing it would produce a mail that renders unstyled in
the client this whole card is about.

So the work stays in `mail-core`, which is itself the shared package for exactly
this: the four defects here were found because a consumer adopted the shared
shell instead of hand-rolling their own. The reuse decision was made when the
package was created; this card is the shared thing getting better because
somebody used it.
