# F039.7 — A gap that cannot say it was never told anything

**Status:** In progress · **Epic:** F039 (Discovery write-layer) · **Written:**
2026-09-01 · **Filed by:** super, in the weekly inventory sweep

---

## Why this is not a dashboard bug

**The gap list is a session's reuse to-do.** `cardmem_session_start` serves it at
boot as `discovery_reuse`, and the reuse-first house rule in every repo's
`CLAUDE.md` tells the session to act on it.

So a wrong gap does not sit quietly in a dashboard. **It tells a working session
to go and build something it already has.**

`apps/discovery/server.ts:388`:

```ts
const gap = available.filter((a) => !have.has(a.package) && !owned.has(a.package));
```

`have` comes from the session's enrollments. An empty `have` is indistinguishable
from a session that has adopted nothing.

## Three ways it answers confidently and wrongly

### 1 · Never reported ≠ not adopted — **super's**

Their words: the roster *"cannot tell 'does not use it' from 'never told us it
uses it'. Both land as an empty `enrolled` and a fat gap list."*

They had been using `@broberg/ai-sdk` **since 2026-08-29** — two generator folders
calling `createAI()` + `ai.image()` against Recraft, the thing every Super and
Aidan logo was made with. Their gap listed 49 packages, **at least one of which
was false**. Self-corrected through `POST /api/enroll`, read back to confirm:
gap 49 → 48.

### 2 · One repo, two identities — **measured here, and bigger**

The session identity is **free text with no normalisation**:

```
fd-sundhed   14 packages      fds            2  (lens, ai-sdk)
sanne         4 packages      sanneandersen  1  (cms-inline-edit)
2e155461-2619-43c2-9056-2ce1184ad5ad   bodymap
f9b691fd-dd83-4641-bf7d-a6b957f5166c   stripe
```

`sanne` and `sanneandersen` hold **disjoint** sets, so each one's gap falsely
lists the other's adoptions as unadopted. Two sessions enrolled under a raw
session-UUID instead of a repo name — those rows are **invisible to that repo
forever**, and the repo's own gap is inflated by exactly them.

22 sessions have any enrollment at all. Every other name in the fleet gets the
maximal gap by default.

### 3 · Correct and still misleading — **buddy's**, and the one with teeth

`buddy → @broberg/secret-scan 0.5.0 · uses` is **accurate**, and it looks healthy.
But 0.5.0 is the version whose announced-axis JSON leak was patched in 0.7.x.
Measured by them on 0.5.0's function surface: `{"password":"hunter2"}` passes
through `redactSecrets` unchanged and `hasAnnouncedSecret` answers `false` —
indistinguishable from clean text.

Their sentence: **"a gap view cannot tell an OLD VERSION from an OLD VERSION WITH
A KNOWN HOLE."**

## The common shape

All three are **two different facts arriving as the same answer**, and the merge
always lands in the reassuring direction. This repo has now hit that shape five
times in twenty-four hours across four different surfaces. It is not a
coincidence; it is what an un-modelled failure state looks like from the outside.

## Derivable today — and what must never be guessed

| | |
|---|---|
| `enrolled.length === 0` | **a fact the server already holds.** never-reported is separable NOW |
| "package X is genuinely unused" | **not derivable, ever.** Label the CONFIDENCE, never invent the state |
| identity aliasing | separable with an **owner-curated** map. Inferring it from string similarity would merge two real repos on a bad day — `sanne` and `sanneandersen` look alike and are one; two others could look alike and not be |

## Design

**1 · `gap_confidence`.** `"never_reported"` when the session has zero
enrollments, `"self_reported"` otherwise — plus a sentence saying what the gap is
worth, so a consumer rendering the payload verbatim cannot present an unverified
list as a to-do list.

**2 · An owner-curated alias map.** A lookup on either name returns the **union**
of both identities' enrollments **and names which identities it merged**. A
silently merged answer is a new way to be confidently wrong.

**3 · Tell cardmem before it ships.** They read this endpoint for
`session_start`. A field nobody renders is the same as no field.

## Not in scope, and why

**buddy's third case — flagging a release as security-relevant — is a separate
story.** It needs a per-release severity marker the roster does not have, and it
changes what a row MEANS rather than how confident the gap is. Filed as its own
thing rather than folded in here, because bolting it on would make this card's
test surface twice as large for a different failure. Recorded so it is not lost.
