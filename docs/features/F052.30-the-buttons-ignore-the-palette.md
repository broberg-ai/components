# F052.30 — The buttons ignore the palette

**Christian:** *"@broberg/bodymap skal nok være lidt mere modulær så den app der
kalder componenten kan overstyre farver og knapper og den slags — men det er I
måske ved at implementere?"*

## Measured before answering

| | |
|---|---|
| **2D** (`react.tsx`) | 27 uses of `var(--bmap-*)`; the hex literals are the CSS-variable **defaults**. Genuinely themeable. |
| **3D** (`three.tsx`) | **13 hex literals in inline styles**, no variable layer. A consumer palette cannot reach them at all. |

So: the **body** is themeable, the **panel chrome** is themeable, the **controls
are not**.

## The embarrassing half, and it is the larger half

**Three of the four colours already exist in `chrome` and are simply not read.**

| line | literal | token that already exists |
|---|---|---|
| `262` | `border: "1px solid #e2e8f0"` | `chrome.border` |
| `262` | `background: "#fff"` | `chrome.panelBg` |
| `789` | `color: "#1e293b"` | `chrome.text` |
| `795` | `color: "#64748b"` | `chrome.mutedText` |

That is not a missing feature. It is the palette being **ignored by the controls**,
in a component whose selling point is that a consuming app themes it. Set
`ui.border` today and it reaches the card but not the buttons inside the card.

And `#64748b` is worse than the others: **F052.19 already replaced that exact
colour** for failing AA at 4.34:1 on the badge background. It survived here because
that sweep read the `defaultUi` object and never looked at the inline styles — a
claim narrower than it appeared.

## The one genuinely missing token

`#0e8f8a` — the teal on the selected intensity button and the active sex toggle —
is **not in `BodymapPalette` anywhere**.

`palette.selected` is not it. That is the colour of a **mark on skin**; the accent
is the colour of an **active control**. Collapsing them would mean a consumer
cannot have a teal mark and a navy button, which is a normal thing to want.

So today every consumer, whatever their brand, gets our teal on their buttons.
fd-sundhed's app is dark navy. sanne's is not teal either.

Two smaller ones: `#f6c9c9` (the remove button's border — pink, hardcoded, sitting
next to a `chrome.danger` that *is* used for the same button's text: half the
control themed, half not), and the quality pill's active `#1e293b`.

## What this card is not

**Component slots** — letting the app pass its own `<Button>`. That is a real
question and a bigger one, and it is exactly where *"prop-soup nobody dares
change"* starts.

Named as an open question for Christian rather than folded in:

- **Tokens first**, because they are unambiguously right and fix the brand
  mismatch today.
- **Slots designed before we know which controls consumers actually want to
  replace is speculation** — and the F074 epic already has a worked example of
  getting this split right (share the shell, keep `renderRow`).

## The contrast trap this opens

Stated here rather than discovered later: today the shipped white-on-teal is
asserted at build time. **The moment a consumer supplies their own accent, nothing
checks whether their text still passes AA** — and this component runs on a
public-health surface where AA is a legal duty.

We cannot measure their colour for them at build time. We *can* give them the
function — that is **F001.10** (export `contrastRatio` from `@broberg/theme`,
filed today after finding that four repos each hand-rolled the WCAG formula).

So the README says the hole exists and points at the tool. Silence would be worse
than the hole.

## Reuse

Discovery searched `theme`, `palette`, `design tokens`, `button`.

- **`@broberg/theme`** — deliberately not adopted, same reasoning as F052.29: this
  component takes a consumer-supplied `BodymapPalette` precisely so a consuming app
  can pass its own tokens in. Binding to `@broberg/theme`'s variables would make it
  *require* that package rather than cooperate with it.
- **`@broberg/ui-controls-core`** — not applicable; these are plain buttons, not
  selects or popovers.

The reuse that actually applies is **internal and is the whole card**: four tokens
that already exist in this package, unused by the code that needed them.

## Non-goals

- Component slots (see above).
- Touching the 2D renderer's CSS-variable layer. It works.
- A dark mode. Consumers set tokens; the package does not decide themes.
