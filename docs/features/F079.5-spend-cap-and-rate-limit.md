# F079.5 — Spend cap + per-visitor rate limit, and the number the cap reads

> Parent: [F079 — `@broberg/chat`](./F079-chat.md)

## Why this is architecture and not a setting

A public chat is **an open LLM-spend faucet on a surface where strangers decide the volume**. The first consumer (fd-sundhed's internal admin chat, Owner + Admins) is authenticated, which is exactly why this story is *not* being built first — but it must exist before anything of ours is exposed publicly.

*"Must exist before the first public deploy, not after the first bill"* only means something if it is **enforceable**. So a public-mode configuration missing a ceiling or a limit is **refused at construction** — the same shape as `can` in the core and the strategy in [F079.9](./F079.9-history-management.md).

## ⚠️ The first blocker is not the prices — it is our own seam

Measured before writing a line of the cap:

```
$ grep -rn "usage\|cost\|spend" packages/chat/src/
src/history.ts:107:  // costs the conversation.
src/http.ts:79:    // still spends money on a surface where the stranger decides
```

Two prose comments. **Zero code.** `ModelEvent` yields `text` and `tool-call` and nothing else, so the core never learns what a round cost — the number is discarded one layer below the guard that would read it. The price question below is real, but it is the *second* blocker; a cap cannot be built on a figure the contract throws away.

So this story adds an **additive** third variant:

```ts
| { type: "usage"; provider: string; model: string; costUsd?: number; … }
```

Additive because a `ModelFn` that never yields it must keep working. And **now** rather than later: cms has not swapped engines yet, so the contract change costs nothing today and would cost a migration next month.

### And the trap the AC did not originally cover

`costUsd` is optional, which means **"not reported"** is a state the guard will meet in the real world — every `ModelFn` in the fleet today yields no usage at all. A cap that treats *no number* as *within budget* is a ceiling that can never be reached and never says why.

> That is this week's defect pointed at ourselves. A consumer sets a limit, sees no error, and concludes they are protected.

So the guard has **three** answers, not two: *within budget* · *over budget* · **could not measure**. The third refuses. `unmeasurable_cost` is its own reason, distinct from `spend_cap`, for the same reason rule 6 exists.

## ⚠️ The number a spend cap reads is not yet trustworthy

This is the whole reason the card exists before the code.

ai-sdk's F040 audit found that **openai, deepseek, gemini and vertex cache automatically**. No money is lost there — the provider already gives the discount — but **the SDK's reported price was too high**, because it neither read their cache figures nor held cache prices for them.

> That figure is exactly what a budget guard reads. **A cap built on it trips early, on a bill nobody ran up.**

**`0.32.0` fixed gemini and vertex**, measured rather than assumed, with the inclusion semantics decided per provider instead of carried over from Mistral:

```
promptTokenCount 11408   cachedContentTokenCount 11242   → subtract
live through ai.chat:    $0.003424 → $0.000388
```

Prices came from Google's own page that day, and each row's `version` string names the source and date — **so a stale rate is visible rather than assumed current.**

**`openai` and `deepseek` are still unverified.** There is no key for either on that machine, so neither the rate nor the inclusion direction could be measured, and ai-sdk **wrote nothing rather than writing it from memory** — which is the correct call and the reason we know.

### So the cap is built *after* two facts, not around them

1. **Inert, never permissive, on an untrusted provider.** On openai/deepseek the cap **refuses** rather than allowing. Our own rule from [F079.8](./F079.8-policy-seam.md), applied to ourselves: an unanswerable question reads as *unanswered*, never as *within budget*.
2. **Never assume a discount that has not arrived.** Gemini's implicit caching is **opportunistic**: in the live run only call 2 hit, while calls 3–6 missed on the identical prefix — where Mistral's key-based caching hit every time. The ceiling is computed on what was actually billed. *A saving you report correctly is not a saving you promise.*

**And we do not estimate their cost locally.** A spend cap built on a number we invented is worse than no cap, because it would be **believed**.

## Reuse, not re-roll

| Need | Package |
|---|---|
| Per-visitor rate limit, `Retry-After` | `@broberg/apikey` |
| Bot wall on the open endpoint | `@broberg/forms-turnstile` |

**Turnstile is asserted server-side**, with a raw call bypassing the widget — a browser-side token is a courtesy, not a control. sanne proved their booking consent the same way, and it is why theirs holds.

## Reaching the ceiling is an answer

The visitor is told plainly that the assistant is unavailable right now, as a **typed frame** — never a provider error, never a silent stop.

And it is **distinct** from *"the model failed"* and from *"I could not look that up"*. Merging them is what this epic's rule 6 exists to forbid: **a failure beneath the chat keeps its own state all the way up.**

## Non-goals

- Not billing, invoicing or per-tenant accounting. A ceiling, not a ledger.
- Not the instruction's own size — that belongs to whoever writes the prompt.
- Not authentication. `getCaller` in [F079.3](./F079.3-adapters.md) already refuses an unauthenticated request before the model is touched.
