# F008.9 — Dark-ship stops at the import graph

> Story under **F008 · @broberg/auth**. Filed by **torrent-search-api**,
> 2026-08-17, with a measurement.

## The report

```
bun add @broberg/auth            # clean Bun project, Bun 1.3.14
→ error: Cannot find module '@better-auth/passkey'
  from node_modules/@broberg/auth/dist/index.js
```

They use no passkeys, configure none, and have no `passkey` key in their config.
The package still will not load.

**Their framing is the finding, and it is better than the bug report:**

> Vores dark-ship-doktrin er rigtig — *"en metode uden secrets registreres
> aldrig, aldrig et crash"*. Det gælder for KONFIGURATIONEN. Det gælder ikke for
> import-grafen — modulet dør før nogen config er læst.

Dark-ship is a property of the **configuration** today. It is not a property of
the **import graph**, and the import graph runs first.

## Re-measured here — and the defect is broader than reported

Their domain was narrower than the bug, because their repo already had Drizzle
installed. In a genuinely empty npm project:

```
npm i @broberg/auth@0.1.2 better-auth
  → ERR_MODULE_NOT_FOUND: Cannot find package 'drizzle-orm'
+ npm i drizzle-orm
  → ERR_MODULE_NOT_FOUND: Cannot find package '@better-auth/passkey'
+ npm i @better-auth/passkey
  → imported OK
```

**Two** load-bearing peers, not one. This is the reason to reproduce a report in
a clean environment rather than in the reporter's — the same lesson `greppable`
learned when three of four defects came from repos that were not even consumers.

## The sharp version of the defect

It is not *"there is a static import"*. It is that **the manifest contradicts the
code**:

```jsonc
peerDependenciesMeta: {
  "drizzle-orm":          { "optional": true },   // ← not optional
  "@better-auth/passkey": { "optional": true },   // ← not optional
}
```

The package tells the installer *"you do not need these"*, then hard-requires
both at module load. npm and bun believe the manifest, install neither, and warn
about nothing. `dist/index.js` lines 1–4 are the whole story:

```js
import { betterAuth }     from 'better-auth';
import { drizzleAdapter } from 'better-auth/adapters/drizzle';   // pulls drizzle-orm
import { magicLink }      from 'better-auth/plugins/magic-link';
import { passkey }        from '@better-auth/passkey';           // direct
```

Same shape as everything else this week, one layer further out: **a declaration
that says one thing while the behaviour does another, and nothing checking that
the two agree.**

## Blast radius — measured, so the design choice is not a judgement call

| | who is affected |
| --- | --- |
| `config.passkey` | **nobody.** No repo in the estate passes it. |
| the `drizzle` re-export (`src/index.ts:62`) | **autodoc**, one import line: `import { createAuth, drizzle as authDrizzle } from "@broberg/auth"` |

## Why this is not a two-line fix

`buildAuthOptions` and `createAuth` are **synchronous**, and `buildPasskeyPlugin`
needs the `passkey()` factory at call time. A lazy `await import()` inside it
would make the whole chain async — **a far worse break than the one being
fixed**. So the fix is structural (a subpath entry), not a swapped import
statement.

## The shape of the fix

**The core entry imports `better-auth` and nothing else optional. Every optional
peer lives behind its own subpath**, so installing the package costs exactly what
you use.

## The guard is the point

A CI job that installs the packed tarball in a clean directory with **only its
non-optional peers** and imports **every** declared entry. It must be shown RED
against 0.1.2 before it is trusted, and it must enumerate the entries from the
manifest rather than from a hand-written list — a wrong list silently shrinks
what was looked at, which is how this got shipped in the first place.

## What works, recorded because it was reported unprompted

- `mountAuth` on Hono: one line, no cast, against `bun:sqlite` + Drizzle.
- Magic-link dark-ship: without `RESEND_API_KEY` it is simply not registered, and
  `configuredMethods()` tells the UI which buttons are real. *"Præcis den rigtige
  form."*

The doctrine is right. It just needs to reach one layer further down.
