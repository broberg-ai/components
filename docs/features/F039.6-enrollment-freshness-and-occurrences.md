# F039.6 — The roster answers confidently about something it has not measured since last time

> Story under **F039 · Auto-enrollment service (Discovery write-layer)**. Raised
> by four independent peer measurements on the same day, 2026-08-10, during the
> weekly inventory sweep.

## What four repos reported, independently, in one hour

| repo | what the roster said | what was actually true |
|---|---|---|
| **cardmem** | `@broberg/lens-engine 0.1.2` | `apps/agent` on `0.4.1`, `apps/lens-cloud` on `^0.1.1` — **three** different answers |
| **beacon** | 2 packages, `secret-scan 0.1.7` | 5 packages, `secret-scan 0.1.8` |
| **torrent-search-api** | `enrolled: []` | `@broberg/ai-sdk` in **production** since 8 Aug |
| **buddy** | one version | `^0.10.4` · `^0.21.1` · `^0.21.1` in one monorepo — a real type break |
| **buddy** (again, after checking their own row rather than nodding) | 1 package | **5 packages** — four had no row at all |

None of these are bugs in the enroll endpoint. It did what it was asked. The
problem is the shape of the question: **an enrollment is written once and then
believed forever.**

cardmem put it best, and it is the same sentence the fleet has been writing all
week about different systems:

> an enrollment that is never updated is the same form as everything else we have
> chased today — it answers confidently about a question it has not measured
> since last time.

## Why it matters beyond tidiness

The reuse-gap handed to every session at `cardmem_session_start` is computed from
this data. So the roster is not a report anybody reads for fun — it is the input
to *what should this repo adopt next*. Three failure modes fall out:

1. **False "up to date".** A monorepo with three pins reports one and looks clean.
2. **False "not adopted".** torrent-search-api ran a package in production while
   the roster said they had nothing.
3. **Gap as noise.** torrent-search-api is deliberately framework-free; 42 of
   their gap entries can never apply, so the list stops being a to-do and starts
   being something you scroll past. A gap you learn to ignore is worse than no
   gap.

## Three changes

### 1. Occurrences, not a version

A repo reports every place it uses a package — path/app label + version — and
`/api/sessions/:session` shows all of them. buddy's monorepo is the acceptance
case: three pins must render as three rows, because that difference is exactly
what broke their build.

### 1b. The partial row — and why freshness alone cannot catch it

buddy checked their own row instead of nodding at the finding, and turned up a
**fifth** case that is a different failure mode from the other four:

```
Discovery said:      1 package   (@broberg/secret-scan 0.1.4)
Actually in use:     5 packages
```

Four had **no row at all**. Not a stale version — nothing. And that is worse than
`enrolled: []`:

> A repo with an empty roster looks obviously unsettled. A repo with exactly one
> correct row looks **settled**. The partial case is more dangerous than the
> empty one, because it does not invite a check.

This has a direct design consequence, and it is the reason this section exists:
**a per-row `updated_at` can never detect it.** buddy's single row was fresh and
correct. A row that was never written has no timestamp to be old. So the
freshness check, built the obvious way, would report green for exactly this
shape — the same class of instrument failure the whole week has been about.

The signal only exists **outside** our own data: compare against the repo's real
`package.json`. Which is another argument for reconcile over push (below).

### 2. Freshness, stated honestly

An enrollment carries a last-confirmed timestamp and goes **stale** past an
agreed age. Stale means *nobody has confirmed this lately* — not *this is wrong*.
It is never deleted and never silently corrected: an aged-out record that gets
deleted turns a known-uncertain answer into a confident empty one, which is the
bug we are fixing, wearing a different hat.

### 3. Not-relevant, set by the repo itself

Per repo, per package, set **by that repo**. Never a central decision about what
somebody else needs — components does not get to decide that torrent-search-api
will never want a theme.

## Open question — settle before building

Do repos **push** all occurrences, or does Discovery **reconcile** against the
repo? F039.4 (reconcile-to-repo) already covers half of this. Building both
halves of the same answer is how two sources of truth get created — pick one
first.

**Leaning strongly toward reconcile**, for two reasons that are not the same
reason:

1. A push is another thing a session must remember, and the entire defect above
   is what happens when remembering is the mechanism.
2. buddy's sharper version, from their own partial-row case: **a push can only
   ever report what the sender KNOWS it uses.** They did not know they were using
   four packages with no row — it was not reluctance, nobody had asked their
   `package.json`. A push model can never surface what was never thought of.
   Reconcile can.

The second argument is the decisive one, because it is exactly the failure mode
this story exists to fix.

## Non-goals

- Not touching the TOFU key model (F039.5 covers reset).
- No auto-enrollment by scanning repos without their key — reads stay public,
  writes stay keyed.
- Not resetting live data. Several repos have already reported in; migrate.
