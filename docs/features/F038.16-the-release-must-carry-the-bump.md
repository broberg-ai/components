# F038.16 — "Remember to bump the roster" failed twice in one night

**Status:** Ready · **Epic:** F038 (Discovery) · **Written:** 2026-09-07

## The measurement, and the second row is the argument

| when | what |
|---|---|
| 6 Sep ~21:00 | The Discovery deploy had been **red for twelve consecutive runs** since 5 September — three roster rows behind npm, **two of them published by this session** without bumping the roster. Nothing had shipped in that window. I fixed it, wrote it into F038.15's evidence, and named the lesson. |
| 7 Sep ~10:30 | I published `@broberg/pwa 0.4.0` and **did not bump the roster.** Caught only because I ran the check by hand while thinking about something else. |

```
@broberg/pwa   roster 0.3.0   npm 0.4.0
```

**Four hours** between paying for the lesson and repeating it — same session,
same night. That is not carelessness a reminder fixes. It is the shape the
Harness-kontrakt already names:

> *a gate does not depend on an agent remembering anything.*

## What exists, and why it is not enough

`check-roster-versions.mjs` runs in the `check` job and blocks the deploy, so the
fleet is never *told* a wrong version. That is why this is a 2-pointer and not an
incident.

But it is a **detector, not a preventer**, and it fails in the expensive
direction: the next Discovery deploy is blocked, so an unrelated and correct
change cannot ship either. That is precisely what the twelve red runs were — the
roster was wrong, and the punishment landed on everything else.

## The asymmetry that makes it worth automating

**The information needed to bump the row is already in the hand of the thing
doing the publish.** `publish.yml` knows the package and the version, because it
is the job that tagged and published them. Requiring a separate step to copy a
number the pipeline already holds is the same shape as F054.7's hand-written
option list: a second copy of a fact that has an owner.

## Scope

- `publish.yml` bumps `ver` in `scripts/inventory-data.mjs` after a successful
  publish, regenerates `docs/`, and commits — in the same run.

### Non-goals

- **Not touching role text or `desc`.** Only `ver`. npm can prove a version
  exists; it cannot prove what a package now does. Unchanged rule from the weekly
  sweep.
- **Not removing the detector.** A bootstrap publish from a laptop still drifts,
  the automation covers only the OIDC path, and the check is also what proves the
  automation works.

## The failure direction to design against

A publish that **fails** must not bump the row — the roster would then name a
version npm does not serve. That is the webpush precedent and it is worse than
being behind: a session is told to install something that does not exist.

## Reuse

None — this is Discovery's own release wiring, in the repo that owns both halves.

## What shipped

**`scripts/bump-roster-version.mjs`** — the bump, as a script the release calls.
10 tests on synthetic roster text (so no case depends on what the real file
happens to hold today) plus one against the real roster, and 4 mutations.

**The `roster` job in `publish.yml`** — derives `<slug>-v<semver>` from the tag,
so all 39 tag prefixes share one shape and a new package needs no edit.

### Why it has no `needs:` on 39 jobs, and that is not laziness

A skipped job propagates as skipped, so a fan-in over 39 conditional jobs would
need `if: !cancelled()` plus per-job status inspection — machinery that can drift
from the jobs it watches, which is the same class of defect as the thing being
fixed.

**It asks npm instead.** It waits up to five minutes for the registry to actually
serve the version, then bumps. A publish that FAILED leaves npm without it, the
script refuses, and the roster is untouched.

> The guard is the same thing the roster is *claiming* — which is why it cannot
> drift from it.

An unreachable registry **skips** the bump rather than failing the release. Not a
verdict on anything, and `check-roster-versions` catches it on the next run.

## The race, found reviewing my own card

Two packages can release at once — I published `pwa` and `theme` the same night.
Both roster jobs then check out the same `main`, both commit, and the **second
push is rejected** as non-fast-forward. The job goes red and that release's row
is never bumped: precisely the guarantee this card makes, lost in the one case
where two of them are being made at once.

The retry **re-derives from a freshly fetched `main`** rather than rebasing a
commit built on a stale one. The regenerated `docs/` conflict line-for-line with
the other job's, and a CI rebase conflict is a no-bump wearing a red X. Re-running
is safe because the bump is idempotent: on a roster already naming the version it
changes nothing and exits 0.

### And exit 2 had collapsed back into exit 1

`bump-roster-version.mjs` distinguishes *npm says this version does not exist*
(a verdict — refuse) from *npm is unreachable* (not a verdict — skip). Run bare
under `bash -e`, both fail the step identically, so the distinction the script is
built around **stopped existing at its only call site**.

> That is the same defect F038.15 fixed one workflow over, four lines below the
> guard that defines the outcomes. I wrote the guard and then called it the way
> the guard exists to prevent.

It also brought the card's own AC#4 evidence back into line: it claimed "an
unreachable registry SKIPS rather than failing" while a path existed where it did
not. The claim was broader than the code; now they agree.

## Five claims a comment cannot prove

`scripts/test-roster-bump-workflow.mjs`, wired into `pnpm test`. Each was
**proven red by mutating the workflow**, because a green absence-check is worth
nothing until it has been seen to fail:

| mutation | result |
|---|---|
| `publish.yml` gains a `branches:` trigger | ✗ the TAGS-only check, alone |
| `check-roster-versions` removed from `check` | ✗ the detector check, alone |
| `deploy` stops depending on `check` | ✗ the `needs:` check, alone |
| the registry probe replaced by `if true` | ✗ the registry check, alone |
| the retry stops re-fetching `main` | ✗ the re-fetch check, alone |
| recovery becomes a `git pull --rebase` | ✗ the rebase check (+ the re-fetch one) |
| the `set +e` wrapper removed | ✗ the exit-2 check, alone |

One named failure each — so a red says which decision died. The rebase mutation
reddens two, honestly: removing the fetch is part of what it does.

**The instrument was wrong before the code was.** The new loop-slice bounded on
the FIRST `done` in the job — which belongs to the *wait* step's own `for … done`,
about 1,200 characters earlier. `slice(2927, 1714)` returns an empty string, so
every `includes()` on it was false. It failed in the red direction this time and
one debug print found it. A different ordering of the two loops and it would have
passed while measuring nothing at all.

## What is deliberately NOT removed

`check-roster-versions.mjs` stays in `check`, and `deploy` still `needs` it. The
automation covers the **OIDC path only** — a bootstrap publish from a laptop
still drifts — and the detector is also the only thing that would show *the
automation itself* had stopped working. Removing it removes the alarm **and** the
evidence.

## What is still unproven, and why it is not laziness

Two acceptance criteria demand a **real release** through the job — AC#2 says so
in as many words: *"PROVEN ON A REAL RELEASE, not a dry run."* Neither is met.

Measured 2026-09-07: all 45 shipped packages' local version equals npm, 0 behind
0 ahead. No release is due. Three packages hold unreleased `src/` changes — `cron`,
`greppable`, `mail` — and all three are comment or rename only, read from the
commits rather than their titles.

Manufacturing a patch to close them was rejected: an npm version is permanent, and
this project's Decision Register requires a release report to consumers on every
`@broberg/*` publish — which a no-change patch has nothing to fill.

They close on the next genuine publish, and they close **loudly in both
directions**: `check-roster-versions` still gates the Discovery deploy, so a row
that fails to move turns it red exactly as it did for the twelve runs that
motivated this card.

## What this does not fix

The bump lands **after** the publish, so there is still a window in which npm is
ahead of the roster. It is minutes rather than hours, and it closes without
anyone remembering — which was the whole complaint. A roster that is briefly
behind is the failure mode we already tolerate; a roster naming a version nobody
can install is the one we do not, and that is the direction the registry probe
protects.
