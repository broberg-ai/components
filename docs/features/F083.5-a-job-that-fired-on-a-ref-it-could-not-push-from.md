# F083.5 — the job fired on a ref it could not push from

**Status:** In progress · **Epic:** F083 (the roster reads the fleet's real manifests) · **Written:** 2026-09-10

## Motivation

`fleet-deps.yml` is the unattended job that keeps `discovery.broberg.ai` honest: it reads every fleet repo's real `package.json`, rebuilds the derived docs, and commits the result **only when the graph actually moved**. F083.3's whole premise was Christian's «et continuerligt job der vedligeholder for dig» — no session, no Mac, no human memory in the loop.

Today it went red fourteen times in six hours, and every one of those reds was the job doing exactly what it was built to do.

```
[detached HEAD 3f96b00] chore(fleet): refresh the dependency graph
 5 files changed, 36 insertions(+), 20 deletions(-)
fatal: You are not currently on a branch.
##[error]Process completed with exit code 128.
```

The scan ran. The graph had moved. The commit was made. And then it had nowhere to put it.

## Root cause

The trigger:

```yaml
on:
  schedule:
    - cron: "17 4 * * *"
  workflow_dispatch: {}
  push:
    paths:
      - "scripts/scan-fleet-deps.mjs"
      - "scripts/fleet-graph.mjs"
      - ".github/workflows/fleet-deps.yml"
```

`on.push` with a `paths:` filter and **no `branches:`**. GitHub does not evaluate path filters for **tag** pushes — so every `<pkg>-v*` release tag starts a full fleet scan.

Measured on this repo's own data rather than recalled from documentation: the tag `mail-v0.13.1` points at commit `d164f8e`, which touched

```
packages/mail/package.json · packages/mail/src/verify.ts · packages/mail/test/mutations.mjs
packages/mail/test/verify.test.ts · packages/secret-scan/package.json
scripts/inventory-data.mjs · turbo.json
```

— none of the three paths the filter names. The job ran anyway. That is the measurement; the documented behaviour is merely consistent with it.

On a tag push `actions/checkout` leaves the work tree on a **detached HEAD**, so a bare `git push` has no upstream branch to resolve and exits 128.

## Why it hid for hours

Four of today's eighteen tag-triggered runs were **green**: `deploy-core-v0.2.0`, `mail-v0.11.0`, `secret-scan-v0.8.0`, `deploy-core-v0.2.1`.

They were green because the graph had not moved, so the step exited at `no change` or `only the timestamp moved` — **before** reaching the push. The defect fires only on a run that has something to commit. A guard shaped by the report would have looked at the four passes and concluded the job was fine on tags; the failure state and the success state are the same code path diverging one line early.

## The cost is the noise, not the red X

The scan itself is unaffected: the daily 04:17 UTC run checks out `main` as a branch and lands its commit normally. What was lost is the **signal**. `fleet-deps` exists to tell us, with nobody watching, when the fleet's dependency graph moved. Fourteen reds in six hours on a job that is red by construction is how a check stops being read — and the next genuine scanner failure would have arrived inside that noise, indistinguishable.

This is the fleet's own "red that stopped carrying information", arriving from the other direction: not a check that has been failing for months, but one that starts failing on every release and will look normal within a week.

## Design

### 1. The fix — one line

```yaml
  push:
    branches: [main]
    paths:
      - "scripts/scan-fleet-deps.mjs"
      - "scripts/fleet-graph.mjs"
      - ".github/workflows/fleet-deps.yml"
```

A tag push no longer starts the job at all, which is correct on its own terms: a release tag says nothing about the fleet's dependency graph, and re-scanning 28 repos because someone published a patch was waste even in the runs that passed.

The `schedule` and `workflow_dispatch` triggers are untouched, and both resolve to the default branch, where `actions/checkout` creates a real local branch.

### 2. The seal — the class, not this instance

`scripts/test-workflows-parse.mjs` already runs inside the fleet-deps job itself **and as CI step 6 of `test.yml`**, which `publish.yml` calls via `workflow_call` — so it already blocks a release. What it did *not* run in is the LOCAL `pnpm test`, which is the command a session reads to decide «green gate → ship». Adding it there costs 70 ms and stops a session getting a green locally and a red in CI for the same tree. It gains one assertion:

> **A workflow containing a BARE `git push` must not be reachable from a tag push.**

Tag-reachable = has an `on.push` trigger AND either names `tags`/`tags-ignore`, or names no `branches`/`branches-ignore` at all.

### 3. Why the rule is not "do not push from a tag-triggered workflow"

`publish.yml` is tag-triggered **by design** and pushes a roster bump to `main` on every release. It is correct, and it is correct for a reason the guard must be able to see:

```bash
git fetch --quiet origin main
git checkout --quiet -B main origin/main   # ← makes a branch out of a detached HEAD
...
git push origin main                        # ← explicit refspec
```

So the discriminating property is the **bare** push, not the tag trigger. A rule that banned all pushes from tag-triggered workflows would redden `publish.yml`, and a guard that reddens correct code gets switched off.

### 4. What the guard deliberately does NOT prove

It does **not** prove that `git push origin main` will succeed. That depends on a preceding branch checkout, which lives in shell text the guard does not read. The guard is written to say so in its own output, because a guard whose claim is broader than its test is the shape this repo has already been bitten by three times: the check passes, and the passing is read as covering more than it does.

## Non-goals

- Rewriting `fleet-deps.yml`'s commit step to be branch-safe the way `publish.yml` is. It is not needed once the job stops firing on tags, and adding a second mechanism would leave two things to keep in agreement.
- Auditing every workflow in the fleet's other repos. This repo's guard covers this repo; the pattern is worth a Discovery tip, not a cross-repo sweep from here.

## What the second negative control found — written down because NC1 alone would have shipped it

The plan above called for one negative control: remove `branches:` and watch the guard redden. It did, and it named the file. On that evidence the seal looked finished.

The **second** control is the one that earned its keep. Making `publish.yml`'s push bare — a mutation planted specifically to redden — left the guard **green**:

```
### NC2 — publish.yml is tag-reachable: make its push BARE and it must redden
  mutation applied, matches: 1
  EXIT=0                                   ← wrong
```

The first predicate constrained what came **before** `git`:

```js
/(^|[;&|\n]|\bthen\b|\bdo\b|&&|\|\|)\s*git\s+push\s*(?=$|[\n;&|)]|#)/m
```

`if git push; then` — `publish.yml`'s own shape — has `if ` in front, which is in no branch of that alternation. So the guard could not see the single most likely way a real workflow writes the defect.

What matters is only what comes **after**: if the command ends there, nothing told git where to push.

```js
/(?<![\w./-])git\s+push(?:\s+-{1,2}[\w-]+)*[ \t]*(?=$|[\n;&|)#])/m
```

Ten cases, both directions, including `git push -q` → true and `git push origin main` / `if git push origin main; then` → false.

This is the repo's own recurring shape, from the other side: **a positive control with a blind spot.** NC1 proved the guard could see the trigger axis. It said nothing about the push-shape axis, and a guard that passes one of two axes looks exactly like a guard that passes.

The restore after each mutation came from a **byte copy saved to the scratchpad before mutating**, never from `git checkout --` — the fix was uncommitted at the time, and `checkout --` restores HEAD, not the work. Both files were read back with `cmp` afterwards and were byte-identical.

## Rollout

Two commits, because they are two different facts: the regenerated Discovery pages (derived output whose source had already landed), then the trigger line + the guard + the local-gate wiring, with this plan-doc. The negative controls ran **before** the commit, not after — a guard nobody has seen fail is not evidence of anything, and in this case the second one changed the code.
