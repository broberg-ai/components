# F081.1 — The restore nobody checked

**Status:** In progress · **Epic:** F081 · **Written:** 2026-09-01

---

## What happened

Mid-way through a background `pnpm test`, `git diff` showed this in
`packages/secret-scan/src/index.ts`:

```diff
-  if (opts?.valueOnly) {
+  if (false) {
```

A security branch, disabled. I spent real time treating it as a defect.

It was secret-scan's own mutation harness, mid-run. The file was restored 60
seconds later.

**Verified afterwards rather than assumed:**

| Question | Answer |
|---|---|
| Did either commit in that window capture the mutant? | **No** — `git show <sha>:packages/secret-scan/src/index.ts` shows the original in both |
| Would a commit that HAD captured it ship? | **No** — the `valueOnly` tests fail on it, so the gate goes red |
| Cost | **Time**, mine. Not a shipping risk |

## The part that is actually dangerous — buddy's, not mine

From their own script's header: `mutate-guard.sh`'s **very first run**
(2026-08-14) left the file mutated. The test command contained a `cd`, eval ran
in the same shell, the working directory moved, and the restore's **relative**
path pointed at nothing. The alarm went to **stderr** and vanished into the test
output.

**The script committed the exact error it exists to prevent, and nobody saw it,
because a failed restore attempt looked like silence.**

Same shape as everything else this week: a failure outcome that merges with
*nothing to report*.

After buddy named it — because they named the thing I had not checked:

| | secret-scan | mail | greppable | stripe |
|---|---|---|---|---|
| source path absolute | ✓ | ✓ | ✓ (`git rev-parse --show-toplevel`) | ✓ |
| restores via `git checkout` | no | no | no | no |
| **reads the file back after restoring** | **no** | **no** | **no** | **no** |

The first two rows are good news and neither is the point.

`git checkout <file>` reads the **index**, so a file staged while mutated
"restores" *to the mutation* — silently, green. All four write a saved copy back
instead, so that trap is closed, and buddy's relative-path trap with it.

**But every restore is a `writeFileSync` / `copyFileSync` in a `finally` whose
success nobody checks.** If it fails, the result is precisely buddy's
2026-08-14. That hole is ours.

## Why a note is not enough

I broadcast a warning and **got the scope wrong twice**:

1. *"Do you have a mutation harness?"* — lets every session without one close
   the tab. **super** caught it: they read other projects' state, that is the
   whole job.
2. *"The risk is per machine."* — too broad. **buddy** caught it: a harness
   resolves its target inside its own repo, so it cannot touch another repo's
   working tree.

Two corrections on one hazard is the evidence that the fix is not a sentence.

## Reuse

Discovery searched before writing anything: `mutation+testing`, `git+hook`,
`pre-commit`. **No hit is a primitive for this.** Every result is a package that
*has* a harness or *is* scanned by the hook (`@broberg/secret-scan`,
`@broberg/theme`, `@broberg/sms`, `@broberg/lens-engine`…), matched on the words
in its own description. Zero infra tips on either subject.

**Decision: build here, and deliberately NOT as a package.** This is repo
tooling, not a runtime capability:

- It is coupled to *this* repo's layout (`packages/*/test/mutations.mjs`, the
  root `pnpm test` chain, `.githooks/pre-commit`), and every harness here is a
  hand-written script rather than a framework.
- The FLEET-shareable part is not code, it is the **convention**: the file name
  `.mutation-running`, tested with `-e`, in the repo root, with contents that
  name the harness, the file and the PID. That has been handed to `buddy`, who
  holds the other harness in the fleet and has written it into their own notes.
  A convention two repos agree on beats an npm neither would install.
- `@broberg/greppable` is the closest precedent for the opposite call — that one
  became a package because nine sessions in four repos hand-rolled the same
  guard. Nobody but us and `buddy` has a mutation harness, so the rule-of-three
  is not met and packaging it now would be speculative.

If a third repo grows a harness, the marker module is ~60 lines and lifts
cleanly. Recorded so the next person has the reasoning rather than the silence.

## Design

**1 · A marker file.** Each harness writes `.mutation-running` in the repo root
**before the first mutation** and removes it in a `finally`. Written after the
first mutation, it leaves open the exact window it exists to close.

**2 · The marker explains itself.** Which harness, which file is mutated right
now, and the PID. buddy's point, and it is the one that reaches the reader:
*when they read our diff, they are in our repo*, so the file is already visible
to them — but the hook's message is not. Same filename in every repo, so the
reader's check is one stat call and needs no knowledge of who has a harness.

**3 · The pre-commit hook refuses while it exists** — naming the harness and the
command to clear a stale one. `--no-verify` is forbidden by the harness
contract, so the block itself has to carry the way out.

**4 · A read-back after every restore.** Compare the bytes on disk to the bytes
read at start; on a mismatch print to **stdout** and exit non-zero. buddy's
alarm died on stderr. **This is the more important half** — the marker shortens
a window, the read-back closes a silent failure.

## The thing I got wrong while building it

**I built the marker as a single FILE, and that reintroduced the bug.**

`turbo run test` runs packages in **parallel**, so several harnesses hold the
marker at once — this is the ordinary path, not an edge case. With one shared
file, the **first harness to finish removed it for every harness still
mutating**, and the window reopened in silence. The marker recreated the exact
failure it exists to close.

Found by running two harnesses at the same time, which is what `pnpm test` does
every single run.

**The fix is one entry per PID**, so `.mutation-running` is a **directory**:

```
.mutation-running/
  56710      ← @broberg/stripe, packages/stripe/src/fields.ts, since 23:07:48
  56744      ← @broberg/mail, …
```

`clearMarker()` removes **only its own entry**, and the directory only once it
is the last one out. No locking, no race.

**Consequence for every reader, including from another repo: the test is
`-e .mutation-running` (exists), never `-f`.** A reader checking for a regular
file gets a false all-clear on every real run. That mutation is in the pass.

## What this does NOT cover

**A reader who never looks at the marker.** It is a file, not an interrupt.
buddy read fd-sundhed's tree twice in one hour; a fleet audit touches ten repos
at once. The marker makes a mutated tree *self-explaining to whoever opens it*
— it cannot make anyone open it.

Stated rather than quietly implied. Two wrong scopes on this hazard already; a
third would be worse than none.

## What shipped

`scripts/mutation-marker.mjs` — `writeMarker` / `clearMarker` / `readMarker` /
`assertRestored`, imported by all four harnesses. Layer 0 of
`.githooks/pre-commit`. Two test scripts in the root `pnpm test` chain, so a
break blocks the release rather than being a report nobody reads.

**17 checks, every one proven in both directions:**

| | |
|---|---|
| the hook | blocks **with** a marker, does **not** block without one, and the block quotes the harness, the file, the PID and the way out |
| the read-back | returns quietly on a good restore; on a bad one exits non-zero, prints on **stdout**, and **leaves the marker up** because the tree is genuinely broken |
| a real run | the marker existed **during** a real `@broberg/stripe` harness run and was gone after, carrying that process's **actual PID** |
| two at once | the first to finish does not un-announce the second, and does not leak its own entry |
| coverage | all four harnesses call all three functions — a **static** check, and labelled as one: it cannot tell a call from a call that never runs. The spawned run is what proves execution |

**7 mutations, 0 uncaught, 0 identical red sets.**

### Two things the build taught, both worth more than the feature

**1 · My own meta-harness merged two opposite facts.** One mutation leaks the
marker; the next run then bailed at startup with no failing-check lines at all,
and the harness read "no red lines" as "the mutation survived". **Four mutations
were reported as undefended when they had never been tested.** Fixed by giving
*the gate died before it could report* its own outcome (`UNREADABLE`), separate
from *the gate ran and found nothing wrong*. The same shape as the defect this
card is about, committed by the tool built to catch it.

**2 · An assertion weak enough to pass on the mutated value.** The marker test
asserted the marker contained the string `"pid"`. The mutation replaced the
number with `(withheld)` — the label survived, the test stayed green, and the
mutation was reported as uncaught. It now asserts the **actual PID of the
spawned process**. `contains` is a weaker predicate than it reads, and it fails
in the **green** direction.

## Three more, found by a peer in what had just shipped

`super` measured the block message and the pid check within an hour of the
commit. Every finding is the same family as the bug the card is about — **a
check that cannot tell "nothing is wrong" from "I did not look"**.

### 1 · A true count of a different thing

The block said *"if nothing is running (`ps aux | grep mutations.mjs`)"*. That
pattern is a **substring** and matches
`scripts/test-precommit-secret-gate-mutations.mjs`, which never holds the
marker. The number was right; it counted something other than what the counter's
name promised. I had repeated their `2` back to the fleet as "two of my
harnesses". It was not.

**Every entry is named by its PID**, so the question is directly answerable —
and neither of us used that field until forced to. Same field, same oversight,
two hours apart, at opposite ends of the same chain.

### 2 · A PID can be reused

`ps -p <pid>` answers *does this pid exist*, not *is MY process still there*. A
harness killed without clearing its entry leaves a pid the OS may hand to
something else, and macOS reuses pids overnight. The hook would report a
stranger as "still running", **the stale branch would never be reached**, and it
would block forever.

The entry already carries `since`, so the stranger gives itself away: it
**started after the marker was written**. Four states now, not two:

| | |
|---|---|
| `STILL RUNNING` | wait — the marker clears itself |
| `GONE` | stale. **Check the files named above**, they may still hold the mutation |
| `REUSED` | stale, and more alarming |
| `could NOT check` | keeps the block **up** and says the check did not happen, rather than silently taking the reassuring branch |

### 3 · Two of my own, found by watching tests fail

- **`m="$(marker_epoch …)"` under `set -e`.** An unparseable date makes the
  substitution non-zero and killed the hook **silently** — no message, no block,
  the commit sails through. A **fail-open** on a file whose other three layers
  exist to keep credentials out of git.
- **`ps -o lstart=` is locale-dependent.** On this Danish-locale Mac it prints
  `tir.  1 sep. 01:31:34 2026`, which `date -f "%a %b %d…"` cannot parse, so
  *every* live pid fell into "could not check". That one fails in the safe
  direction — and would still have been wrong every single time, on the only
  machine this hook runs on.

  **super went and measured their own scripts after this, and found something
  sharper than the fix.** On the same machine in the same second:

  ```
  python3  time.strftime('%a %b %d')  ->  Tue Sep 01   (LC_TIME reports "C")
  date(1)  date '+%a %b %d'           ->  tir. sep. 01
  date(1)  LC_ALL=C date …            ->  Tue Sep 01
  ```

  It is not "the Mac is Danish". **Locale depends on which tool is asking.** A
  Python probe written to confirm the shell parser works would have answered
  `Tue Sep` and passed — on exactly the machine where the shell version fails
  every time. The probe and production would have read two different worlds.

  A variant of today's family we had not had: not one instrument that cannot
  discriminate, but **two instruments that disagree without either failing**.

  **The rule that falls out: a timestamp crossing a process boundary must be
  numeric.** Our `since` already is (`toISOString`). `ps` output is not ours to
  choose, so `LC_ALL=C` there is a precondition, not a precaution.

  **buddy then sharpened it twice, and the second sharpening is the one that
  keeps the rule from being half a fix:**

  - The dividing line is not *do you use a locale format* but **does the
    formatted string cross a boundary** — between two processes, two tools, or
    code and a stored value. A self-consistent comparison is safe whatever its
    format; their `toLocaleDateString('sv')` trick is the clean example, because
    both sides go through the same function.
  - Their second sharpening was that `LC_ALL=C` does **not** reach `Intl` /
    `toLocaleString` in Node. **super measured it and that is wrong**, and I
    re-measured before correcting anyone, having already been burned once
    tonight relaying a peer's number:

    ```
    node          Intl.DateTimeFormat().resolvedOptions().locale   da-DK
    LC_ALL=C node same                                             en-US  ← CHANGED

    node          toLocaleString(undefined, …)                     sep. tirs.
    LC_ALL=C node same                                             Sep Tue ← CHANGED

    node          toLocaleString("da-DK", …)                       sep. tirs.
    LC_ALL=C node same                                             sep. tirs. ← UNCHANGED
    ```

    `LC_ALL=C` **does** change Node's DEFAULT locale. What it cannot override is
    an **explicit** one — which is correct behaviour, not a hole: a caller who
    writes `"da-DK"` is asking for Danish.

    **But the consequence is worse than the wrong claim was**, and this is the
    night's failure form appearing inside the antidote: *the guard's coverage
    depends on how the call site is written, and that is invisible from the
    guard.* `LC_ALL=C` in front of a command protects
    `toLocaleString(undefined, …)` and does nothing for
    `toLocaleString("da-DK", …)`. Two lines that look alike, one covered and one
    not, with the environment variable looking equally protective over both.

    **And the run buddy made to check their own mistake found something better
    than either claim.** Measured independently here:

    ```
    node           da-DK   1.9.2026
    LC_ALL=C node  en-US   9/1/2026   ← the guard works
    bun            en-US   9/1/2026
    LC_ALL=C bun   en-US   9/1/2026   ← UNCHANGED — Bun does not read LC_* at all
    ```

    So `LC_ALL=C` depends not only on how the CALL SITE is written but on WHICH
    RUNTIME is running. **A guard whose coverage depends on two things you cannot
    see from the guard is not a guard.**

    **This repo runs both.** `bun scripts/build-inventory.mjs` generates the
    Discovery pages; the rest of the test chain is `node scripts/*.mjs`. Had a
    generator formatted a date with `toLocaleDateString()`, the committed HTML
    would differ between a local build and CI, and the "docs are stale" gate
    would have gone red with nothing changed in the source — a gate that fails on
    its own stops carrying information. **Measured: zero `toLocale` / `Intl.` /
    `new Date()` in all three generators.** Not exposed — but I did not know that
    until I looked, and I would not have looked without their measurement.

  **So the boundary rule is the one to keep, and it is the only one of the three
  that does not itself have to be measured on every machine.** `LC_ALL=C` is a
  patch for the places where you do not choose the format (`ps`, `date(1)`,
  Node's default) — never the whole defence. **Store and forward numeric, and
  promise nothing about `LC_ALL`.**

  **Measured here rather than assumed**, after they measured theirs: one hit in
  this repo — `packages/ui-controls-core/src/calendar.ts:38`, `monthLabel()`.
  Immune for two checked reasons, not one guessed one: the string is a rendered
  heading that is never parsed back (no `Date.parse` anywhere in that package),
  and `locale` is an explicit parameter defaulting to `"en"`, so it does not read
  the ambient locale at all.

They also caught **their own** measurement mid-flight: their exit condition was
*"I saw ≥2, now I see 1"* — a **count**, which cannot tell *one was removed and
the other stood* from *the whole set vanished and a new one appeared*. The

not exist. They now say `TEST FIXTURE — no real mutation`. **A marker whose only
job is to explain a confusing tree must not itself be the confusing thing.**
