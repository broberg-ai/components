# F005.6 — The send receipt must survive the request that made it

> Story under **F005 · @broberg/mail**. Filed by xrt81 on 2026-08-11 with a live
> incident behind it.

## What happened

xrt81 sent a club onboarding mail with a 1.2 MB PDF to **14 real recipients**.

- All 14 iterations ran. 14 magic-link tokens were created.
- The server log held **zero errors**.
- The HTTP response carrying the Resend ids was lost to a 10-second socket
  timeout in their own API layer.

The ids existed server-side for a moment and were then gone, because the only
place they ever lived was a **return value**. Their `RESEND_API_KEY` is
send-only, so `GET /emails` answers `401 restricted_api_key` and they cannot
reconcile afterwards either.

So: fourteen mails to real club members, no errors anywhere, and no way to know
whether a single one arrived. They correctly refused to re-send blindly.

## Why this is the package's problem, not theirs

Their sentence is the whole argument:

> Lige nu er vores eneste kvittering et HTTP-svar der kan gå tabt — det er
> præcis den slags mangel der bør bo i pakken, ikke i 17 repos.

Measured in `packages/mail/src/index.ts`, the exported surface is
`createMailer`, `createMailerFromEnv`, `mailAllowed`, `buildFrom` + types. There
**is** a `logger` config — but it fires only on **skipped** and **failed** sends.
A fully successful send emits nothing at all.

That is exactly backwards for this purpose, and it is this week's recurring
shape one more time: **the successful path is the silent one.** A batch that
works perfectly leaves no evidence it happened; only failure leaves a trace.
The package header says it *owns DELIVERY only* — and a delivery primitive that
cannot say what it delivered is incomplete.

## The change

One additive hook:

```ts
createMailer({
  onResult: (entry) => { /* { id, to, ok, error?, at, skipped? } */ },
})
```

Called **at send time**, per recipient, for every outcome — success, failure and
ship-dark skip. The consumer decides where it lands (their DB, an event log, a
file). Nothing about the surrounding request can then take the receipt with it
when it dies.

## Non-goals

- **The package does not become a datastore.** No DB, no queue, no retry engine.
  The sink is a hook; persistence is the consumer's.
- No change to what `send()` returns. Purely additive; existing consumers keep
  working untouched.
- Delivery *status* (delivered / bounced / complained) is **not** this story —
  the send response cannot know it. That is F005.7 (webhook receiver).

## Design notes

- **Fail-soft, always.** A throwing sink must not fail the send; a slow sink must
  not delay it. Wrap it, never await anything unbounded. A receipt mechanism
  that can break the thing it observes is worse than no receipt.
- **Skips must be recorded too.** Ship-dark is a real outcome. If a no-op leaves
  no entry, then "nothing was sent" and "nothing was recorded" look identical —
  the same defect class in a new place.
- **Per recipient, not per batch.** xrt81's case is a loop of 14; an aggregate
  entry would not have told them which of the 14 to worry about.
