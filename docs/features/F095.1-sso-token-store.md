# F095.1 — Tokens server-side i @broberg/sso

Se F095. Dette er en auth-kæde (load-bearing): forsegles med tests der går røde, før noget bygges ovenpå.

## Design
- `interface TokenStore { get(sid): Promise<TokenSet|undefined>; set(sid, t): Promise<void>; delete(sid): Promise<void> }`, `TokenSet = { accessToken, refreshToken?, expiresAt }` (expiresAt fra `expires_in` i token-svaret; mangler det, fra access-tokenets `exp` hvis JWT, ellers +5 min).
- Sessionen får `sid` (tilfældig, 128 bit). Tokens gemmes ALDRIG i cookien — cookien er signeret, ikke krypteret, og læses af browseren.
- `completeLogin` returnerer allerede tokens; `ssoRoutes({ tokenStore })` gemmer dem i callback.
- `getAccessToken(c)`: henter, fornyer ved udløb (≤30 s margin) via `grant_type=refresh_token` mod discovery's token_endpoint, gemmer nyt par (refresh-rotation respekteres). Fejl → slet + navngiven SsoError.
- Logout (lokal + backchannel «Log ud overalt») → `tokenStore.delete(sid)`.
- `memoryTokenStore()` som standard-reference med én advarsel: tab ved genstart, ikke delt mellem maskiner. Appen leverer sin egen i drift.
- Bagudkompatibelt: uden tokenStore uforandret adfærd.

## Sikkerhed
Refresh-token er lang levetid og højest værdi; det må aldrig nå browseren eller en log. Tests asserter fravaer i Set-Cookie og i fejlbeskeder.

## Reuse
Udvider @broberg/sso (ejer BID-integrationen). Ingen ny afhængighed.
