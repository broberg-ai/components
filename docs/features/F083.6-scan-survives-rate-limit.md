# F083.6 — The daily scan survives GitHub's rate limit, and the page stops changing every hour

## Why
Measured 22 Oct 2026. The daily `fleet-deps` job failed two days running: `gh: API rate limit exceeded for user ID 486755`, 73 of ~79 repos recorded as failed. The token's 5,000 requests/hour are shared with every fleet session using the same GitHub user, so a busy morning starves the scan. The job correctly refused to commit a broken graph — but nothing retried, so the FLEET section went stale.

Second-order damage: when stale, `docs/inventory.html` renders `⚠ STALE … 52h ago`. The `discovery` workflow regenerates the docs and fails if they differ. One hour later the text reads `53h ago`, so every Discovery commit goes red on a check meant to catch a forgotten rebuild. main was red on 01daf5be for that reason only.

## Scope
1. `scripts/scan-fleet-deps.mjs`: recognise GitHub's rate-limit answer (403/429 with 'rate limit' / `x-ratelimit-remaining: 0`), wait until the reset time (capped so the job stays inside its 20-minute timeout), retry. Other errors stay errors.
2. `scripts/build-inventory.mjs`: drop the relative `Nh ago` from the generated HTML. Keep the absolute timestamp and the STALE marker. The output becomes a pure function of its inputs.

### Non-goals
- A separate GitHub token for the scan (env/secret change — owner's call; an option if waiting is not enough).
- Rendering age client-side.

## Architecture
Retry wraps the single `gh api` call helper in the scanner; clock + sleep injectable for tests. Builder: delete the hours fragment.

## Reuse
No `@broberg/*` package owns GitHub API rate-limit handling; this is internal CI scripting in components.

## Rollout
Commit → fleet-deps runs on push (path filter covers the scanner) → green run commits a fresh graph → discovery deploy green.
