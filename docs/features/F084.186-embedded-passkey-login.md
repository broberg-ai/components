> **Kontrakten — målt af bid 6/11 2026 i broberg-id src/embedded-login.ts (#48995), citeret:**
> 1) `POST /embedded/passkey/start`: body `{client_id, code_challenge (43 tegn base64url), code_challenge_method:"S256", nonce? (≤200), end_user_ip? (≤64, kun ved Basic), redirect_uri? (skal være registreret, ellers 400 invalid_redirect_uri)}`. Ingen state. Svar 200 `{flow_id, frame_url, expires_in:600}`; `frame_url = ${issuer}/embedded/passkey-frame?flow_id=…`. Nonce gemmes på flowet og lander i id_token.
> 2) Rammen poster til forælderen med targetOrigin = forælderens origin, kun hvis den står på klientens liste (origins ∪ frameOrigins): `{type:"bid-embedded-passkey", flow_id, ok:true}` eller `{…, ok:false, error:"not_found"|"cancelled"|"failed"}`. Lyt kun på `event.origin === "https://id.broberg.ai"`.
> 3) `POST /embedded/passkey/complete`: body `{flow_id}`; samme godkendelse som start (Origin på listen eller Basic). Ikke fly. Svar 200 `{next:"done", code, passkey_setup?}`; før nøglen er bekræftet 400 invalid_request. Koden bindes til redirect_uri fra start, hvis den er givet og registreret.
> 4) `https://app.fysio.work` står i embeddedClient.origins for fysio-work-app (sat af bid 6/11; CORS 204 målt). Listen sættes af BID.
> Designet (verifier + nonce på serveren, kun code fra browseren) passer med BID, som det er.

## Motivation
fysio.work (F006.29, ejer-godkendt mockup, #48990) vil have passkey-login indlejret på app.fysio.work, ikke en omdirigering til id.broberg.ai. Klienten er `fysio-work-app` med `clientAuth: "fly"`. bid har målt (#48989), at `/embedded/passkey/start` og `/complete` kun godtager browserens Origin eller Basic client_secret, ikke fly, så passkey-ceremonien må køre i browseren. Uden en fælles del skriver fysio.work en lokal kopi af OAuth-kode, hvilket er præcis den drift, @broberg/sso findes for at forhindre.

## Sikkerhed: hvorfor serveren holder verifier og nonce
fysio.works første forslag var, at browseren laver PKCE-parret og sender `code` + `code_verifier` til serveren. Så kan en angriber lave sit eget passkey-login, tage sin egen code + verifier og få et offers browser til at poste dem: offeret ender logget ind på angriberens konto (login-CSRF) og lægger måske sine data dér. Rettelsen er den kendte: serveren laver verifier og nonce, binder dem til denne browser i en forseglet httpOnly-cookie, og browseren får kun challenge + nonce. En code fra et andet flow kan så ikke byttes, fordi verifieren ikke passer, og nonce-tjekket fanger resten. fysio.work godkendte det (#48993).

## Scope
- Server (`client.embeddedPasskey`): `begin()` → `{ challenge, nonce, flow }`; `complete({ code, flow })` → `LoginResult` via den eksisterende `exchangeCode` (samme token-godkendelse, også fly; samme nonce-tjek).
- Browser (`@broberg/sso/embedded-passkey`, nyt subpath): `start` → iframe → `complete`, giver kun `{ code }`. Godtager kun beskeder fra issuerens origin. Fejl og afbrydelse er typed; intet hængende promise.
- Hono-adapteren: et eksempel i README på de to ruter (begin, complete), der sætter den normale session.

## Non-goals
- UI: fysio.work tegner selv knappen og fejlbeskederne (deres mockup).
- Passkey-registrering — BID's egen side.
- Ændringer i BID. Kan kontrakten ikke bære en server-holdt nonce, tages det med bid, ikke omgås.
