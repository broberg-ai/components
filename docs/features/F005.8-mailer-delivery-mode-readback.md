# F005.8 — A mailer must say what it will actually do

> Story under **F005 · @broberg/mail**. Filed by **cms** on 2026-08-17, out of a
> question about upgrading rather than a bug report. Ordered built by Christian
> the same day.

## How it surfaced

I warned cms that `@broberg/mail` 0.1.0 defaults `live` to `!!apiKey`, so any
environment holding a Resend key sends to **real** recipients — the defect that
hit two repos independently and produced the breaking 0.3.0 fail-safe.

They checked in a minute and came back with: **no, and not by luck.** Their
wrapper sets `live` explicitly, with a comment describing precisely that trap.
They did not take their own comment on faith either — they read 0.1.0's `dist`
in their `node_modules` and confirmed the nullish coalescing lets their explicit
`false` win.

Then they asked the question this story comes from:

> *"Vi sætter `live` ud fra NODE_ENV, IKKE via MAIL_LIVE-secret. Er det en
> fuldgyldig vej i din nye model? Vil helst ikke opdage forskellen på prod."*

## What I measured before answering

```ts
const live = config.live === true;                                  // index.ts:175
if (config.apiKey && config.live === undefined && !config.disabled) // index.ts:178
```

**Their path is fully valid.** An explicit `true` from any source counts;
`MAIL_LIVE` is read only by `mailerConfigFromEnv()`, a helper they do not use.

**And the warning never fires for them** — it is gated on `config.live === undefined`,
and they always pass a boolean. That is correct: the warning exists for people who
*forgot* the field.

## The problem, which is not the one they asked about

By being explicit, they have opted out of the only signal the package has — and
swapped one silent failure for its mirror image:

| | before 0.3.0 | cms today |
| --- | --- | --- |
| risk | accidentally **live** | accidentally **not live** |
| effect | staging mass-mails real users | prod delivers to allowlist only |
| warning | — | **silent**, because `live` is `false`, not `undefined` |

Their gate now hangs on `NODE_ENV` being exactly `"production"` inside the running
container. A new base image, an overridden env, a typo — and prod mail quietly
stops reaching real recipients. No error. No log.

## The gap is mine, not theirs

```
node -e 'const x = createMailer({apiKey:"re_x", live:false}); console.log(Object.keys(x))'
  → mailer keys: [ 'send' ]
```

**The resolved decision is not readable.** A consumer doing exactly the right
thing — setting `live` explicitly — has no way to verify what the mailer
concluded. A test can prove the logic; only a startup check catches an
environment that lies about itself.

## The change

One additive field on the returned mailer:

```ts
export type DeliveryMode = "live" | "allowlist-only" | "disabled" | "no-key";

const mailer = createMailer({ /* … */ });
if (isProd && mailer.mode !== "live") {
  throw new Error(`mail gate is closed in production: ${mailer.mode}`);
}
```

### Why one field and not a boolean `live`

This is the load-bearing design decision. **Three** separate conditions stop this
package from delivering — `live === false`, `disabled === true`, and a missing
`apiKey` — and all three return the same success-shaped `{ ok: true, skipped: true }`.

So a `live`-only readback would let a consumer write

```ts
if (isProd && !mailer.live) throw new Error("…")   // passes while mail is stone dead
```

and have it **pass** on a mailer with no API key at all. That is a false green
*inside the readback built to prevent false greens* — the exact shape of every
other defect found this week. One field, carrying the reason, with exactly one
thing to assert on.

### Precedence

The states overlap, so the order decides what a consumer is told. It follows what
actually happens at send time, not what reads nicely: **no key** and **disabled**
beat `live`, because `send()` returns early on both before the allowlist gate is
ever consulted.

## Non-goals

- **`mode` is resolved once, at creation.** It is not re-evaluated per send, and
  it does not observe a config mutated afterwards.
- **No change to `send()`.** Purely additive; a consumer on 0.4.0 upgrading to
  0.5.0 changes nothing.
- **The adjacent gap is deliberately left out**, and named here so it is not
  lost: `MailResult.skipped` has the identical defect one layer down. Its own doc
  comment reads *"intentionally NOT delivered (disabled / no key / not
  allowlisted)"* — three reasons collapsed into one boolean, so a consumer cannot
  tell a ship-dark no-op from a blocked recipient. That deserves its own card;
  bundling it here would widen the release cms is about to take.

## Rollout

1. Build + tests, red first against 0.4.0.
2. Ship **0.5.0** via the `mail-v*` OIDC tag; verify by installing in a clean dir.
3. Tell cms the version — they asked, and they are about to run the
   0.1.0 → 0.4.0 upgrade, so this folds into one planned task instead of two.

## The rule this instantiates

When a shared package is missing something you need, **extend it — never work
around it locally.** cms could have written their own boot check and nobody would
have known. Instead the question surfaced a real gap and the whole fleet gets the
answer. Same path `@broberg/webpush` took to `sendSilent()`.
