# F041.3 — The contract moved four times in a day, and the only detector was a person

> Story under **F041 — `@broberg/cron`**. Follows F041.1 (build + publish 0.1.0) and F041.2 (xrt81 pilot).

## What arrived

cronjobs reported four changes to their public API in a single day (intercom #23362), at Christian's explicit request. Everything they sent is live and prod-verified, and their `openapi.json` is public, authless and updated in the same commit as the code.

## Measured here before writing anything

Two of their four claims land on us. One does not. Recording the one that does not matters as much as the ones that do — *"we checked and it was fine"* and *"we never checked"* are indistinguishable a week later.

| Their claim | Us |
|---|---|
| `connectTimeout` is new | **Real.** 0 occurrences before regen, 2 after |
| status gains `deferred` + `missed` | **Real.** Ours said `success\|failure\|timeout\|running\|skipped` at four sites — a consumer typed from our package could not represent the server's own output |
| timeout cap 120000 → 600000 | **Does not apply.** `grep` for `120000`, `120_000`, `"120 s"` across `src` + README: nothing. openapi-typescript does not emit numeric constraints as types, so we never encoded a cap to be wrong about |
| partial update reset 8 fields | **Server-side, already fixed.** Our `createJob()` was the vector; their read of `setEnabled()` is correct — it uses the toggle endpoint, not a partial PUT, so it was never exposed |

## ⚠️ The finding is the fifth one, and it is ours

`npm run gen` pulls the live spec **once, by hand**. Nothing afterwards notices when the contract moves.

> Four changes landed in a day, and the only reason we know is that somebody on the other side chose to write to us.

That is a signal which exists only while a person remembers to send it. Christian's sibling rule says a shared inventory cannot know it has gone stale — only the owner of the thing it describes can. Here **we are the reader**, the spec is public and always fresh, and drift is therefore detectable without asking anyone. Depending on the writer's goodwill when the answer is one HTTP GET away is the actual defect.

### Three outcomes, not two

The usual trap, in the usual place. The check must separate:

| | |
|---|---|
| **in sync** | exit 0 |
| **DRIFTED** | exit 1, naming what changed |
| **could not ask** | its own code, its own message |

A network failure must not read as in-sync (a green that never looked), and must not read as drifted either — **a red that fires on a flaky connection is a red that gets ignored, and then the real drift is ignored with it.** That is not hypothetical: this repo has a memory entry for a check that failed for months and stopped carrying information.

## Two things a consumer cannot deduce from the types

**`externalId` uses a COLON**: `repo:job-name`, followed by 13 of 15 fleet jobs. Nothing on either side normalises it, so a deviation **creates a duplicate job instead of updating one** — and from the call site, *"upsert missed"* and *"upsert updated"* look identical. Only `201` versus `200` separates them, and nobody reads that. A convention that lives nowhere in code is a convention that will be broken.

**`connectTimeout` defaults to `null` on purpose.** It bounds how long we wait for a response to *begin*, and `fetch()` resolves at the response headers. For a job that computes first and answers afterwards, time-to-header **is** work time — so a short default would kill exactly those jobs. Set it only when the endpoint answers promptly. The gain is real where it applies: buddy's ingest job answers in 201 ms, and with `timeout=120 s` it hung for the full two minutes through a 16-second outage, burning its entire retry budget on one dead attempt. **Long patience makes a job more fragile, not more robust.**

## The partial-update note, stated in both halves

It is now safe to send a minimal spec — server-side defaults apply only on creation (their F008). **And a consumer should still send full configuration**, so its job does not depend on server behaviour it cannot see.

The incident is worth naming because it hit the pattern we ourselves recommend: an idempotent re-registration by `externalId`, run by every integration on every deploy, silently cleared all tags, reset timeout/retry/timezone, turned a POST job into a GET — and **re-enabled a deliberately paused job**, every single time.

## Non-goals

- Not wrapping the two newly key-authed routes (`/api/logs`, per-job notifications) in the client. Worth doing, but it is its own story with its own AC — folding it in here would hide a new feature inside a maintenance card.
- Not normalising `externalId` for the caller. Documenting a convention is honest; silently rewriting someone's identifier is how you create the duplicate you were trying to prevent.
