# F038.26 — the Discovery CI check logs in with a BID ticket (WIF), and the two GitHub secrets go

Christian 12/10: «Opret GitHub-secrets til Discovery og tag en snak med BID om det ikke burde klares med WIF». The secrets were created the same night (DISCOVERY_SESSION/DISCOVERY_KEY) and live-fresh went green for the first time since Discovery closed on 8/10 (run 38185345692). But a long-lived key in GitHub is exactly what BID tickets exist to remove.

## What already works
ticket-probe.yml (F084.154) gets a ticket from GitHub OIDC → BID token exchange (RFC 8693) with no stored key and reads Discovery's fleet layer with it (proven 10/10). BID's rule is bound to that ONE workflow file.

## What BID builds (broberg-id #2907)
A rule takes a LIST of workflows plus an optional branch lock (checked against workflow_ref) — today it is one workflow per (client, audience) and the branch is not checked at all, which is a hole they close in the same change. Our rule becomes [ticket-probe.yml, inventory-fresh.yml] on refs/heads/main, scope discovery:read.

## Our side
1. live-fresh job gets `permissions: id-token: write`; check-live-fresh.mjs tries `fetchTicket({ audience: "discovery", scope: "discovery:read" })` first, falls back to the secrets, and logs which door it used (never the ticket).
2. When BID says the rule is ready: prove `door: ticket` on a real main run.
3. Then delete the two secrets, remove the fallback, prove green again. Replace, prove, then remove — no naked cutover.
