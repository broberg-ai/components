# F038.11 — The new guard goes red on every release by construction

**Status:** Backlog
**Parent:** F038 — Discovery
**Found:** 2026-08-29, by watching F038.10 run twice on the day it shipped

---

## The measurement

| run | trigger | package | roster | npm | result |
|---|---|---|---|---|---|
| 33265390801 | `workflow_run` after publish | `@broberg/theme` | 0.4.0 | 0.5.0 | RED |
| 33266404033 | `workflow_run` after publish | `@broberg/notifications` | 0.3.0 | 0.4.0 | RED |

Both reds were **correct**. Both were fixed by the next push. That is the problem.

## Why it happens

A release is two acts that cannot be simultaneous:

1. **tag + publish** — npm now serves the new version
2. **roster bump** — this repo now names it

Between them the roster is *behind* npm. `discovery` fires on `workflow_run`
when `publish` completes — **inside that window, every time.** So from now on
*every* release produces one red `discovery` run that is correct, expected, and
self-healing within minutes.

## Why that is worth a card rather than a shrug

**A check that fails predictably and is always fine trains the reader to skip
it.** Once that has happened, the failure this guard was actually built for — a
roster nobody ever bumps — arrives looking identical to the routine one.

That exact failure has already cost the fleet: Discovery pointed at
`@broberg/webpush` 0.2.1 for three days (the version whose icon path renders
nothing on iOS, silently) and it cost xrt81 a full day.

And this repo learned the neighbouring lesson the *same morning*: `test` was red
for eleven consecutive runs and blocked nothing, because no publish job carried
`needs:` (F080.3). Eleven chances to notice, eleven missed. A red that stops
carrying information is not a smaller problem than a missing check — it is the
same problem wearing a green-looking history.

## What I already tried, so nobody repeats it

**Bumping the roster in the same commit as the package does not work today.**
I attempted exactly that before ordering the commits the way I did: the push runs
*before* npm serves the version, so the guard correctly reports the roster is
**ahead**. And *ahead* is the more dangerous direction — it names a version
nobody can install.

So the guard is right in both directions and the release has **no green path
through it**. Two commits is a workaround I have now performed twice; it is not a
design.

## The shape of the fix

**"Ahead" needs a third reading.**

| state | evidence | verdict |
|---|---|---|
| ahead | a release tag for that package + version on this commit | **PENDING** — a publish is in flight |
| ahead | no such tag | RED — names a version nobody can install |
| behind | — | RED — the fleet is told to install an old version |
| unreachable | — | warning, not a failure (F038.9's rule, unchanged) |

A release then becomes: **one commit** (package bump + roster bump + regenerated
docs), **one tag**, a *pending* push that does not go red, and a **green**
`workflow_run` once npm serves it.

### The constraint that keeps this honest

**The pending window is bounded by EVIDENCE, never by time.** Tie it to a release
tag present on the commit — not to a sleep, a retry budget, or a grace period. A
timer would excuse a roster that is stale for a completely unrelated reason, and
that is precisely the case the guard exists for.

**And the stale-deploy block must survive.** Both red runs correctly *stopped*
Discovery from deploying a roster that was behind npm. Whatever replaces this must
keep that half; buying quiet by tolerating "behind" on the `workflow_run` trigger
would let a stale roster ship, which is the whole defect.

## Deliberately not in this card

**Deriving `ver` from npm at build time.** It is probably the right long answer —
the roster hand-copies a number the registry already owns, which is the
hardcoded-value rule applied to data instead of code, and a derived value cannot
go stale. But it changes what the roster *is* (rows exist for unpublished and
planned packages, and the build would then need the registry reachable), so it is
a decision to take on its own merits, not a side effect of a CI fix.

## Rollout

1. Prove RED in **both** directions against the current implementation — ahead
   with no tag, and behind with no publish. Neither must pass before the pending
   path exists.
2. Add the PENDING outcome, gated on tag evidence.
3. Change the release procedure to one commit + one tag.
4. Demonstrate on a real release: no red `discovery` run, both run URLs quoted.
5. Mutation pass — removing the tag-evidence requirement must redden the
   no-tag-ahead test, with a receipt that each mutation applied.
