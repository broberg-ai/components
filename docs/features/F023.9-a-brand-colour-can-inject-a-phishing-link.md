# F023.9 — A brand colour can inject a phishing link into a transactional mail

**Status:** Ready · **Epic:** F023 (`@broberg/mail-core`) · **Written:** 2026-09-03

## What was proven

Not reasoned about — run against the **built** package, 3 September 2026:

```js
renderShell({ accentColor: `#0f7391" onmouseover="alert(1)" x="`, … })
//  <td bgcolor="#0f7391" onmouseover="alert(1)" x="" style="background:#0f7391" …>

renderShell({ accentColor: `#fff;"></td></tr></table><a href="https://phish.example">Log ind her</a><table><tr><td x="`, … })
//  the anchor is in the rendered mail, verbatim
```

An attribute breakout **and** a full tag injection. The attack does not need
script: a `Log ind her` link inside an otherwise genuine, correctly-branded
transactional mail is the entire payload, and every client that strips `<script>`
still renders the anchor.

## Seven sites, zero escaping, zero validation

| line | site |
|---|---|
| 174 | `border-top:1px solid ${accentColor}` — **added by F023.8, i.e. by me** |
| 176 | `color:${accentColor}` on the footer link |
| 228 | `bgcolor` + `background` on the accent bar |
| 288 | `color:${opts.accentColor}` in `eyebrow()` |
| 300 | `border-left:3px solid ${opts.accentColor}` in `noteBox()` |
| 426 | `bgcolor` + `background` on the `cta()` button |
| 442 | `border-left` in `factBox()` |

`escapeAttr` **exists in this very file** (line 19, `= escapeHtml`) and not one
brand value goes through it. `isDark()` runs a hex regex — but only to choose
light-vs-dark text; a non-matching string returns `false` and is interpolated
verbatim. **The one function that inspects the shape of a colour discards what it
learned.**

## Why this is reachable now, not theoretically

The README says every brand value is caller-supplied, and in a single-tenant repo
it is a constant in a config file — there is no attacker in that picture, and the
code is not wrong for what it was built for.

What changed is the deployment model:

- **xrt81** already resolves branding **per tenant from a database**.
- **cardmem's template store** is being built this week.
- The F023 epic's own brief describes *DB-backed multi-tenant override*.

The moment a tenant sets their own accent colour, this is user input reaching an
HTML attribute in a mail sent to **other people**. The assumption did not become
false by anyone being careless; the product moved underneath it.

## Reuse

Checked Discovery before proposing a fix (`?q=html+escape`, `?q=sanitize`,
`?q=colour+validation`). `@broberg/secret-scan` and `@broberg/cms-inline-edit`
both carry sanitisation, and **neither fits**: secret-scan redacts credentials
from text, and cms-inline-edit sanitises rich-text HTML for a browser. Neither
validates a CSS colour token, and neither should — a colour grammar is a
different predicate from an HTML sanitiser, and borrowing one for the other is
how a tokeniser mismatch gets introduced (cms measured exactly that failure on
`[^>]*` two days ago).

So: **build it here, in mail-core, and keep it internal** — it is ~30 lines and a
fleet package for "is this string a CSS colour" would be a package nobody
remembers exists. If a second consumer ever needs it, it graduates then.

## Design

**Reject, do not escape.** An escaped non-colour renders as literal garbage
inside a `style` attribute — the mail still leaves the building and still looks
broken to a real customer. A thrown error fails at the *caller*, where someone
can see it, instead of at the *recipient*, where nobody can.

```ts
assertColor("accentColor", value)   // throws naming the field
assertFontStack("fontSans", value)
```

The colour grammar must accept what designers genuinely pass — `#rgb`,
`#rrggbb`, `#rrggbbaa`, `rgb()`/`rgba()`, `hsl()`/`hsla()`, and the CSS named
colours. **Rejecting a legitimate `rebeccapurple` would push consumers into
working around the guard, which is worse than not having it.**

`fontSans`/`fontSerif` need their **own** rule. A font stack legitimately
contains quotes and commas — `'Segoe UI'` — so the colour grammar cannot be
reused, and the dangerous characters there are `<` and `>` and a quote that
closes the attribute, not the comma.

## Non-goals

- Not a general HTML sanitiser. `bodyHtml` is documented as caller-escaped and
  stays that way; widening this card into "sanitise everything" is how it stops
  shipping.
- Not a fleet package. Thirty lines, one consumer.

## Verification

- The two payloads above, **verbatim from this document**, must throw.
- The negative control is the half that proves the guard is a guard: seven
  legitimate values must pass. Without it, a reject-everything stub scores the
  same as a correct implementation.
- Drive the site coverage from the **field names**, not a hand-written list of
  seven line numbers — a line-number list goes stale the next time this file is
  edited, and staleness here reads as coverage.
- Mutation: removing the guard on any single field must redden a distinct test.
