# F005.10 — Handing `MAIL_FROM` straight to the domain check produces a confident false alarm

> Parent: [F005](F005-mail-sending-resend.md) · follows [F005.9](F005.9-sending-domain-readiness.md), filed by its first consumer within the hour.

## The seam

moovyy adopted `verifySendingDomain()` the hour 0.6.0 shipped, wired it at boot beside the `mode` gate, deployed to prod — and hit the join.

**`MAIL_FROM` is an address, not a domain.** Theirs is `Moovyy <noreply@send.broberg.ai>`. Hand that straight to the check and every lookup goes to a name that cannot exist, all three come back NXDOMAIN, and the report announces that the domain is missing SPF, DKIM **and** MX — about a domain that demonstrably *has* its DKIM.

That is a **confident false alarm**: precisely the outcome the whole check was built to avoid, and precisely the thing that gets a boot check switched off. It simply arrives from the glue instead of from the logic.

## Why it belongs in the package

Three lines every consumer writes identically — and the wrong version **produces no error.** It produces an alarm that looks right. Anything with that signature belongs in one place.

moovyy wrote a local `domæneFor()` with the negative control included, then told us rather than leaving it there. That is the reuse rule working in both directions: they extended nothing locally that should live centrally, and they did not file the card on our behalf either.

## The trap inside the fix

**Normalising quietly would be this same bug wearing a different coat.** If the function silently accepts an address and reports on the domain without saying so, a consumer who passes the *wrong* thing — a URL, an empty string, a display name with no address — gets a clean-looking report about something they never asked about.

So two rules constrain the implementation:

1. **`report.domain` carries what was ACTUALLY looked up**, never the string that was passed in. The normalisation is visible in the output.
2. **Unparseable input is refused, not guessed.** A plausible-looking domain invented from `https://example.com/x` or from a bare name regenerates the exact defect this card exists to remove.

## Forms accepted

The three that actually appear across the fleet's `MAIL_FROM` values:

| Input | Domain |
|---|---|
| `send.broberg.ai` | `send.broberg.ai` |
| `noreply@send.broberg.ai` | `send.broberg.ai` |
| `Moovyy <noreply@send.broberg.ai>` | `send.broberg.ai` |

## The standard the message has to keep meeting

moovyy's production log after adopting:

```
❌ send.broberg.ai: INCOMPLETE — deliverability is degraded (spam-folder risk), not necessarily blocked. missing 2 record(s).
❌   SPF — add TXT on send.broberg.ai: "v=spf1 include:amazonses.com ~all"
❌   MX  — bounces cannot come back; add MX on send.broberg.ai: 10 feedback-smtp.eu-west-1.amazonses.com
```

Their read of why that matters, kept because it is the design brief for every message this package emits:

> *Det er ikke en advarsel man skal researche — det er en advarsel man kan handle på. Jeg brugte en formiddag på at nå frem til præcis de to linjer.*

Also confirmed in production: **the `ENODATA` branch is the one firing for them** — the exact branch that would have stayed silent had only `ENOTFOUND` been mapped. The thing moovyy insisted on before it shipped is the thing carrying the signal.

## Non-goals

- Validating that the address itself is deliverable. This resolves a domain; it does not judge a mailbox.
- Reading `MAIL_FROM` from the environment inside the check. The consumer passes what it uses — an implicit env read would hide *which* value was verified, which is the same silent-normalisation trap one level up.

## Reuse

Nothing to adopt: this is a correction to a function `@broberg/mail` shipped hours earlier, in the package that already owns it.

## Rollout

Additive patch/minor. Existing callers passing a bare domain are unaffected — asserted, not assumed.
