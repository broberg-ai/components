# F081.5 — A slow gate is a bypassed gate

**Status:** Backlog · **Epic:** F081 (mutation-harness safety) · **Written:** 2026-09-01

## The number

Measured from the `test` workflow's own run durations, successful runs only:

```
before F081.2  (2026-08-31)   251s · 187s · 225s     median ~225s   (~3¾ min)
after  F081.2  (2026-09-01)   675s                                  (~11¼ min)
```

Three times slower. **+7½ minutes on every push.**

The cause is not mysterious. A mutation harness re-runs its package's whole test
suite once per mutation, and F081.2 wired six previously-unrun harnesses into
`turbo run test`:

```
lens-engine 27 · webpush 13 · notifications 12 · theme 11 · mail-identity 7 · pwa 4
```

74 extra full-suite runs.

## Why this is not just a performance ticket

The Harness-kontrakt's reasoning applies to the gate itself. Its rule is *never
bypass the gate* — and an 11-minute wait on every push is precisely the pressure
that produces a bypass. A bypass is never announced.

This repo already has the precedent, and it is in this workflow's own comments:
`test` had been failing for **eleven consecutive runs** when
`@broberg/notifications 0.3.0` was published, because no job depended on it. A
gate people route around reaches the same place as a gate nothing depends on.

## What this is NOT

**Not an argument to unwire the six.** They found real defects the day they were
switched on, and F081.2's whole finding was that a harness nothing runs looks
exactly like coverage. The question is **when** they run, not **whether**.

## Options, none chosen

| | | |
|---|---|---|
| a | keep it | 11 min is survivable; turbo already caches unchanged packages |
| b | per-package | mutation harness runs only when that package's `src` changed |
| c | nightly | the slowest (lens-engine) moves out, required before a *release* rather than before a *merge* |

**The trap in (b), stated because it is the one that would bite:** "this package
did not change" is not "nothing that affects it changed". A shared dependency bump
would skip exactly the harness that would have caught it.

## Constraints

- Never unwire a harness to make the gate fast.
- Any skip must be **discovered from the diff**, never a hand-written list of
  which packages are slow — a hand-written list is what hid six harnesses for
  months.
- **A skipped harness must be named in the gate output.** A silent skip is
  indistinguishable from a pass, which is the failure this entire epic is about.
- The release path still sees every harness. Nothing publishes on a gate that
  skipped its own mutation harness.

## Verification

Re-measure with the same method — successful `test` workflow durations,
before/after — so the result is a number, not an impression. And attribute the
7½ minutes **per harness** first: the mutation count is a proxy, and a proxy is
how you optimise the wrong one.
