# F081.5 — A slow gate is a bypassed gate

**Status:** Backlog · **Epic:** F081 (mutation-harness safety) · **Written:** 2026-09-01

## The number

Measured from the `test` workflow's own run durations, successful runs only:

```
before F081.2  (2026-08-31)   251s · 187s · 225s     median ~225s   (~3¾ min)
after  F081.2  (2026-09-01)   675s                                  (~11¼ min)
```

Three times slower. **+7½ minutes on every push.**

The cause is not mysterious. A mutation harness re-runs its package's whole test
suite once per mutation, and F081.2 wired six previously-unrun harnesses into
`turbo run test`:

```
lens-engine 27 · webpush 13 · notifications 12 · theme 11 · mail-identity 7 · pwa 4
```

74 extra full-suite runs.

## Why this is not just a performance ticket

The Harness-kontrakt's reasoning applies to the gate itself. Its rule is *never
bypass the gate* — and an 11-minute wait on every push is precisely the pressure
that produces a bypass. A bypass is never announced.

This repo already has the precedent, and it is in this workflow's own comments:
`test` had been failing for **eleven consecutive runs** when
`@broberg/notifications 0.3.0` was published, because no job depended on it. A
gate people route around reaches the same place as a gate nothing depends on.

## What this is NOT

**Not an argument to unwire the six.** They found real defects the day they were
switched on, and F081.2's whole finding was that a harness nothing runs looks
exactly like coverage. The question is **when** they run, not **whether**.

## Options, none chosen

| | | |
|---|---|---|
| a | keep it | 11 min is survivable; turbo already caches unchanged packages |
| b | per-package | mutation harness runs only when that package's `src` changed |
| c | nightly | the slowest (lens-engine) moves out, required before a *release* rather than before a *merge* |

**The trap in (b), stated because it is the one that would bite:** "this package
did not change" is not "nothing that affects it changed". A shared dependency bump
would skip exactly the harness that would have caught it.

## Constraints

- Never unwire a harness to make the gate fast.
- Any skip must be **discovered from the diff**, never a hand-written list of
  which packages are slow — a hand-written list is what hid six harnesses for
  months.
- **A skipped harness must be named in the gate output.** A silent skip is
  indistinguishable from a pass, which is the failure this entire epic is about.
- The release path still sees every harness. Nothing publishes on a gate that
  skipped its own mutation harness.

## Verification

Re-measure with the same method — successful `test` workflow durations,
before/after — so the result is a number, not an impression. And attribute the
7½ minutes **per harness** first: the mutation count is a proxy, and a proxy is
how you optimise the wrong one.

## Measured — the saving is real (3 Sep 2026)

Job-level durations, successful `test` runs only, queue time excluded:

| run | date | harnesses skipped | job |
|---|---|---|---|
| 33636850919 | 2 Sep | 0 | 479s |
| 33744951598 | 3 Sep 10:33 | 0 | 632s |
| 33749244613 | 3 Sep 11:21 | 0 | 659s |
| **33751554517** | **3 Sep 11:47** | **10 of 10** | **256s** |

The last row is commit `616d8f58`, the first push since the selector was wired
that touches only one package (`packages/mail-core/`). The skips are **counted**
— `grep -c 'SKIPPED  test/mutations.mjs'` gives 10 there and 0 on the others —
not inferred from the clock. AC#2's disclosure requirement is what makes the
saving auditable instead of merely asserted.

Not a controlled A/B: the baseline commits did different amounts of other work.
The claim the numbers support is the narrow one — on a single-package push, ten
of ten harnesses skipped and the gate finished in 256s.

## The test read the job's environment instead of its own (3 Sep 2026)

The `mail-core-v0.2.0` tag push went **red and blocked the publish**, and the
cause was in `scripts/test-mutations-if-changed.mjs`, not in the selector:

```js
env: { ...process.env, GITHUB_EVENT_BEFORE: base },   // inherits GITHUB_REF
```

The selector reads exactly three variables — `GITHUB_REF`, `GITHUB_REF_TYPE`,
`GITHUB_EVENT_BEFORE` — and the fixtures controlled only the third. On a **tag**
push the job's own `GITHUB_REF=refs/tags/mail-core-v0.2.0` reached every fixture,
so all of them answered `scope: RELEASE — every harness runs` and five checks
that expect a skip went red.

**The expensive half is the other direction.** The one check guarding the
dangerous case — *"a TAG push runs the harness even with an empty diff"*, added
after run 33636438450 skipped all ten and reported green — **passed on that run
for the ambient reason.** Its own `GITHUB_REF_TYPE: "tag"` was redundant; the
environment had already decided. On the single run where that check mattered, it
proved nothing.

It was caught by its neighbour, which exists for precisely this:

```
CONTROL: base at HEAD and no tag ⇒ gamma skips
  → the control did not skip, so the tag case below proves nothing
```

That sentence was written as a guess about how the check could rot. It named the
real failure on the first run that produced it.

**Fixed** by `fixtureEnv()`, which blanks all three variables before applying the
case's own. **Proven** by restoring the leak on a copy and re-running under
`GITHUB_REF=refs/tags/…`: 6 red, reproducing the CI failure line for line plus
the new check. Under the same tag condition with the fix in place: 13 green.

**The new check is the guard, not the fix** — it sets the release variables in
the *parent* process and requires an unrelated package to still skip, so the leak
cannot return quietly.

**Released as 0.2.1, not 0.2.0.** The tag `mail-core-v0.2.0` is on the remote at
the broken commit; moving it needs a force-push, which is the owner's order to
give. A version number is cheaper. npm confirmed to hold only `0.1.0` — the
failed gate meant `0.2.0` never reached the registry, so nothing consumed it.
