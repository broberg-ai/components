# F035.20 — Mistral's new «mstr…» key format

## Problem
Christian (7/10 2026): when he stores a new Mistral key in cardmem's vault, it gets no type. cardmem classifies through `@broberg/secret-scan` `classify()` (v0.11.1, exact pin, `apps/server/src/vault/detect.ts`) and has no table of its own, so the fix lands here.

Today secret-scan recognises Mistral **only from context**: the `mistral-api-key` pattern requires a `mistral(-api)-key/token = …` field, because the old keys had no prefix (~32 base62). A vault holds only the bare value, so it never matches. Mistral now issues keys starting with `mstr`, and a prefix like that lets us recognise the key **from the value alone**, which the old format could never support.

## Blocked on shape — deliberately
We do not know the separator (`mstr_` / `mstr-` / `mstr`), the length or the charset. D-453d89 rejects a guessed or anchorless value pattern: a confident wrong label gets acted on. cardmem measures the shape of the stored key (prefix + separator, total length, charset after the prefix) and reports it without the value.

## Build (once the shape is known)
1. New pattern `mistral-api-key` (same label, so consumers need no change), anchored on the exact measured prefix + separator, with the length range and charset that were measured. It is a prefix pattern, not a value-only pattern, so it runs by default.
2. Vitest with a SYNTHETIC value of the measured shape (never the real key). Negative controls: wrong length, wrong charset, `mstr` inside a word. The existing context-only Mistral pattern must still pass.
3. Mutation-check: removing the pattern turns the test red.
4. Bump secret-scan, publish via the `secret-scan-v*` tag, bump the roster, and send cardmem a release report (D-b7eb14) with the version to pin.

## Reuse
This IS the shared capability (`@broberg/secret-scan`, F035). It extends the package instead of adding a local rule in cardmem.
