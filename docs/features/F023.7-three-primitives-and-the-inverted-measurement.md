# F023.7 — Three primitives, and the measurement that inverts the intuition

**Status:** Backlog · **Epic:** F023 (Mail Templates) · **Written:** 2026-09-03

## Where this came from

vn-leker built a **third** local copy of the mail template layer, then measured
`@broberg/mail`'s exports, found no template layer, and proposed we build one.
The package already existed — `@broberg/mail-core`, shipped, ours. They had asked
the right question of the wrong artefact.

But the report they brought back is worth more than the duplicate cost. Three of
the gaps are real, and I verified each against 0.1.0's own signatures rather than
taking their word:

```
heading(text, { fontSerif?, textColor? })   no way to emphasise ONE word
(no eyebrow export at all)
factBox(rows: FactRow[], opts?)             key/value TABLE, not free prose
```

Each is five to ten lines here. The alternative is copy number four writing them
again.

## The two measurements (fd-sundhed's)

Morten Skjoldager's iPhone, Outlook iOS, 2026-08-19 18:28. Their hardware, their
customer paid for them.

### 1. Outlook maps a DARK source colour to a LIGHT rendered one

```
#1a1c2b  ->  #c1c2d1
#4a4d63  ->  #a7a9bf
```

So to make a too-faint line **more** readable at the recipient, the source colour
must be made **darker**.

That is the opposite of the intuition, and it is precisely the direction a future
"improvement" gets wrong — someone sees a washed-out line, lightens the source,
and makes it worse. **It belongs as a comment on the code that sets the colour**,
not in a plan-doc nobody opens while editing a hex value.

### 2. Three force-light techniques had ZERO effect — not partial

`only light` metas + CSS · `[data-ogsc]`/`[data-ogsb]` rules · `#fffffe` instead
of `#ffffff`.

```
asked #141969  got #484090
asked #fffffe  got #484848    card AND footer -> the same colour,
                              so the footer stopped being a zone
```

**The techniques stay** — Apple Mail honours them. What has to be written down is
the measured **zero**, or the next reader believes they carry something they do
not and builds on top of it.

What actually doubled legibility (2.0:1 → 4.9:1) was the four rules already
folded in: no mid-tones, structure from rule-and-space rather than fills, no
gradient, button with fill **and** border.

## Two design requirements, from mistakes their author caught himself

- **"Optional" must be first-class.** Their v1 existed only in its filled form
  (info box + button) and broke the first time someone had three lines to send.
  `mail-core` is already right here — everything is a primitive — so this is one
  README line, so a future `mail-templates` does not make a field required
  because the example had it.
- **A webfont is LAYERED, never removed.** They dropped the project's serif
  because Outlook does not guarantee webfonts — removing the design rather than
  letting Apple Mail show it. `BrandColors.fontSerif` is already the right hook;
  what is missing is saying the value must be a fallback **stack**.

## One thing the package already gets right, and under-sells

`makeLogoAttachment` (CID). vn-leker was about to ask cms for a permanent public
URL on webhouse.dk — but a mail fetches its logo **every time it is opened, for
years**, so a moved file breaks every mail we have ever sent, retroactively. A
CID attachment removes the class. That should read as the recommendation, not as
one of two options.

## Not in scope

**`@broberg/mail-templates` (layer 2) is not built here.** Three repos would
depend on it; that is Christian's decision and vn-leker has already routed it to
him. This card only closes gaps in a package that already ships.

## Verification

The assertions that matter are the negative ones: `heading` with no `emphasis`
must render byte-identically to 0.1.0, and an `emphasis` string that does not
occur in the text must leave the heading alone rather than appending it. Then a
clean install of the published tarball with the new exports actually called —
not a read of `src`.
