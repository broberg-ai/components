# F061.6 — A commit hook is our ONLY secret guard, and trail solved this first

**Status:** Ready · **Epic:** F061 (build hardening) · **Written:** 2026-08-31

## Motivation

After fixing [F061.5](./F061.5-the-format-layer-is-off-in-every-fresh-clone.md) I
checked whether the same defect was fleet-wide. It is not — and the audit turned
up two things worth more than the answer.

### 1. There is no CI backstop

```
$ grep -rln "secret-scan|scan-secrets|redactSecrets" .github/workflows/
.github/workflows/publish.yml
```

One file, and every hit in it is the job that **publishes** the
`@broberg/secret-scan` package. Nothing scans this repository's own contents.

So `.githooks/pre-commit` is the only guard, and a hook is:

- **absent** on any clone that has not run `pnpm install` (which is what sets
  `core.hooksPath`),
- **bypassable** with `--no-verify`,
- and until F061.5 landed, **silently off** whenever secret-scan was not built.

Our own Harness-kontrakt says a load-bearing chain is sealed only when a RED
automated test BLOCKS the release *and* a probe alarms live. A credential
reaching a public npm package is about as load-bearing as this repo gets. It has
neither. It has one bypassable local convenience.

### 2. trail already solved this, and wrote down why

```sh
# /Users/cb/Apps/broberg/trail/.githooks/pre-commit
if ! command -v bun >/dev/null 2>&1; then
  # Fail loudly rather than pretending the check ran. A silent skip is exactly
  # how a key stayed in this public repo for four months.
```

Same defect, same shape, already diagnosed — by a session that had lived the
consequence. F061.5 rediscovered it from scratch today because nothing carried
the lesson across a repo boundary.

And their file header goes further than ours in exactly the place this card is
about:

> CI runs the same scan so a machine without the hook installed still cannot land
> a secret — **the hook is the fast feedback, not the only guard.**

We built the fast feedback and called it the guard.

## Open question, deliberately not assumed

A grep of trail's own workflows did not locate their CI half. Either it lives
under a name the grep missed, or the sentence is aspirational. **Ask them.** If
it exists we copy it; if it does not, they are told plainly that their hook's
header promises a guard they do not have — which is the same class of defect as
ours and worth more to them than a compliment.

## Scope

**In:** a workflow job that runs `@broberg/secret-scan` across the full tree,
honouring `.secretscanignore`; `needs:` wiring so it blocks publishes; a planted
key on a scratch branch to prove the job goes RED before it is trusted green.

**Out:** any change to the pre-commit hook (it stays — second guard, not
substitute); any new pattern (F035 owns those); any change to what counts as a
secret.

## Reuse

components owns `@broberg/secret-scan`, so this job is the reference the fleet
copies. If it generalises cleanly it should ship as a reusable
`workflow_call` workflow the way `fly-server-deploy` did (F033.7), and be added
to Discovery's infra tips — rather than being pasted into thirteen repos and
drifting.

## Verification

1. Planted AWS-format key on a scratch branch → job **RED**, log names file+line.
2. Same branch with the key removed → job green.
3. A path in `.secretscanignore` → not scanned, asserted by fixture, so CI and
   the hook cannot disagree about what is allowed.
4. First full-tree scan result recorded in the card **whatever it says**.
5. The publish job's `needs:` verified on the rendered graph, not the YAML.
