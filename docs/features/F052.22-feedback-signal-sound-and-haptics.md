# F052.22 — Sound + haptics: the package emits the SIGNAL, each app wires what it has

**Status:** in progress · **Parent:** F052 (@broberg/bodymap) · **Filed:** 2026-08-28
**Requested by:** Christian (owner), who then answered the design question himself.

---

## What he asked

> "Kan vi sætte lyd på og bede mobile om noget taktilt som vibration — hvad er det
> nu det hedder i mobile lingo?"  → **"Haptisk feedback"** →
> "Haptisk er vel primært via native apps som vi har i fd-sundhed."

His last sentence is correct, and it is the fact the whole design hangs on.

---

## The measurement that decided the shape

Taken **with a control**, before any code:

| Engine | `navigator.vibrate` |
|---|---|
| WebKit — Safari, and **every** browser on iPhone | **absent** |
| Chromium — Android web | present |

So:

- On an **iPhone web page there is no route to a buzz at all.** Not a permission we
  have not asked for — the API is not there.
- The only thing that produces real Taptic on iOS is the **native app**:
  fd-sundhed's Capacitor build calling `Haptics.impact()`.

A package that imported Capacitor to deliver that would drag an app-only dependency
into a component that also renders on ordinary web pages, and in read-only journal /
PDF views where a buzz would be absurd.

**Therefore: the package emits the SIGNAL; the app wires the EFFECT.**

```
onFeedback({ outcome, region })  ──▶  fd-sundhed native app : Capacitor Haptics  (real Taptic, iOS)
                                 ──▶  any web app           : @broberg/soundkit  (sound)
                                 ──▶  nothing wired         : still fine
```

Web vibration is the one effect cheap enough to ship *inside* the package: zero
dependency, one API call, and it is inert where the API does not exist.

## Reuse check (mandatory, F217)

## Reuse

- **Sound → `@broberg/soundkit@0.1.0` ALREADY EXISTS** and bodymap does not use it.
  Web Audio synth, autoplay-policy handling (lazy `AudioContext` gated on the first
  user gesture), mute/volume persisted to localStorage, React + Preact adapters.
  **Sound is therefore NOT re-rolled here.** The README documents the four-line
  wiring from `onFeedback` to `soundkit.play(...)`.
- **Not added as a dependency, deliberately.** bodymap is frequently rendered
  read-only (F052.9 display mode, journals, PDFs, the clinician view). Pulling Web
  Audio into that is a cost every consumer pays for a feature most of them will not
  turn on. The callback costs them nothing.
- **Haptics → no fleet package exists**, and none should: the effect is
  platform-specific (Capacitor on native, `navigator.vibrate` on web, nothing on iOS
  web). What is shareable is the *signal*, which is what this card ships.

## Where the signal comes from

F052.20 already funnelled **both** click paths through one core decision:

```
react.tsx  applyPick(key)     → decidePick(key, report, config) → "select" | "clear" | "ignore"
three.tsx  pickRef.current(k) → decidePick(k,   report, config) → "select" | "clear" | "ignore"
```

The feedback signal is emitted **from that outcome**, not from the tap. Three
consequences fall out for free, in both renderers, without either knowing about the
other:

1. A tap on a **locked** region can never buzz as though it cleared something.
2. A tap **suppressed by the pan/pinch guard** emits *nothing at all* — it never
   reaches `decidePick`.
3. The signal vocabulary **cannot drift** from the pick vocabulary, because it *is*
   the pick vocabulary. `PickOutcome` is reused; no second enum is introduced.

---

## The honesty constraint

`navigator.vibrate(...)` returning `true` means **the request was accepted** — not
that the phone moved. All of these return `true` and produce nothing:

- the device is in silent / do-not-disturb mode
- the device has no vibration motor at all (most laptops)
- the page has not yet had a qualifying user gesture

So the outcome word is **`requested`**, never `delivered`. This is the same lesson
`@broberg/webpush` 0.3.1 recorded when xrt81 proved a push had **arrived** on a
device (`bytes:355`) that still never **showed** it: the right instrument, answering
honestly, still did not answer the question they needed — because *arrived* and
*shown* are two claims.

Three outcomes, never a boolean:

| | meaning |
|---|---|
| `unsupported` | the API is not there (iPhone web, most desktops) |
| `declined` | the browser refused it, or the call threw |
| `requested` | the browser accepted it — **the motor may still not have moved** |

## API

**Core** (`@broberg/bodymap`, zero new dependencies):

```ts
export interface FeedbackSignal { outcome: PickOutcome; region: string }
export type FeedbackFn = (signal: FeedbackSignal) => void;

export type VibrateOutcome = "unsupported" | "declined" | "requested";
export function requestVibration(pattern: readonly number[], nav?: unknown): VibrateOutcome;

export const VIBRATION_PATTERNS: Record<PickOutcome, readonly number[]>;
//   select [12]      a short tick — you marked something
//   clear  [8,40,8]  a double tap — you took something away
//   ignore []        nothing. a tap that did nothing must not feel like it did.
```

**Both renderers** gain two props:

```ts
onFeedback?: FeedbackFn;      // always called with what actually happened
haptics?: boolean;            // default TRUE — web vibration where the API exists
```

`haptics={false}` suppresses the buzz while `onFeedback` still fires: an app may
want sound without a vibration.

**Default ON, deliberately.** A fix behind a flag reaches only the people who read
changelogs — i.e. the people who did not need it (`@broberg/webpush` 0.2.0 shipped
three defaults ON for exactly this reason). The buzz is 12 ms, it only ever follows a
deliberate tap, and it does not exist on the platform where it would be most
intrusive.

---

## Non-goals

- **No sound in this package.** `@broberg/soundkit` exists; the app wires it.
- **No Capacitor / native import.** The app does that; the package must stay usable
  on a plain web page.
- **No audio assets.** Nothing is bundled.
- **The 2D and 3D bodies are unchanged.** This card adds a signal; it changes no
  colour, no geometry, no report.

---

## How it will be proven

The test that matters is the one with the **control**, because a stub that always
answered `requested` would otherwise pass everything:

- `unsupported` (no `vibrate` on the nav object) **and** `requested` (it exists,
  returns `true`) **and** `declined` (returns `false`) — all three in the same test.
- A `vibrate` that **throws** → `declined`, and the mark is still set or cleared.
- An **empty** pattern never calls the API at all.
- Per renderer — not once — the outcome passed to `onFeedback` for a marked, an
  unmarked and a locked region.
- The pan-guard case asserted **separately** from the locked case: "nothing happened
  because you were panning" and "nothing happened because it is locked" are
  different events, and a single assertion covering both would hide either one.
