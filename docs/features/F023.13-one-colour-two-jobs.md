# F023.13 — one colour doing two jobs

**Status:** Ready · **Epic:** F023 (`@broberg/mail-core`) · **Written:** 2026-09-05
**Filed by:** cms, found by Lens's contrast critic on a real form notification.

## Measured

WebHouse gold `#F7BB2E`. WCAG AA needs **4.5:1**.

```
accent AS TEXT on white (eyebrow)          1.74:1
accent AS TEXT on the footer's #f4f4f5     1.58:1
WHITE text ON the accent surface (cta)     1.74:1
black text on the accent surface          12.10:1   ← the fix
```

cms reported 1.73 / 1.58 / 1.74. I recomputed from scratch before answering and
got the same figures — so this is their measurement confirmed, not relayed.

### Confirmed in our own source

```
index.ts:599  cta()        color:#ffffff              HARDCODED
index.ts:457  eyebrow()    color:${accentColor}       accent used as TEXT
index.ts:341  footer link  color:${accentColor}       accent as TEXT on backdropColor
index.ts:393  top bar      bgcolor=${accentColor}     accent as a SURFACE
```

**The same value is a surface and a text colour inside one shell.** That is the
whole defect; everything else follows from it.

## The control that decides the design

An optional `textColor` parameter is the obvious remedy and it is the weaker one.
For a **dark** accent the current constant is *right*:

```
white on #0f7391    5.41:1   OK
black on #0f7391    3.88:1   UNDER
```

So a fixed choice is illegal in one direction or the other, always — white fails
on gold, black fails on teal. **Only the package can see both sides of the pair,
so the package has to pick.** A parameter leaves the default illegal, and the
default is what a hurried consumer ships.

## Why this is urgent rather than cosmetic

**It fails in the green direction.** A 1.7:1 mail renders, sends, and looks like
a deliberately pale style. Nothing errors. No test goes red. The only person who
finds out is the customer who cannot read the button.

## What it costs cms today

They shipped a local workaround (c5524c31 — 7 tests, mutation-proved, Lens run
b1bcbd5f with 0 findings) and it **costs them their brand colour**: to get
legible white text they must send a *darkened* colour as the button background,
so the button is no longer WebHouse gold. Same for the top bar.

They are trading colour for legibility in two places where **both could be
kept** — and that half is only fixable in here.

## Scope

`readableOn(background)` derived from luminance, applied where the accent is
**text** and never where it is a **surface**:

| site | today | after |
|---|---|---|
| `cta()` label | hardcoded `#ffffff` | derived from the accent it sits on |
| `eyebrow()` | raw accent | derived, measured against its surface |
| `renderShell` footer link | raw accent | derived, measured against `#f4f4f5` |
| `renderShell` top bar | raw accent | **unchanged** — it is a surface |
| `noteBox`, `factBox` borders | raw accent | **unchanged** — borders are surfaces |

### The detail that cost cms a round

**Do not measure against white.** The footer sits on `#f4f4f5`, so a colour that
just clears 4.5:1 against white lands at **4.18:1** there. Measure against the
surface the text will actually sit on — which is different per call site, and is
why this cannot be one global "darken the accent" helper.

### Non-goals

- **Not a theming system.** One derived value per site, no palette API.
- **Not touching the surfaces.** The whole point is that the brand colour keeps
  its exact value everywhere it is a background or a border.
- **Not removing `assertColor`.** The F023.9 colour-injection guard applies to a
  derived value exactly as to a supplied one.

## The thing that must not happen

**A silent change to mails that are fine today.** Every consumer with a dark
accent must get byte-identical HTML. That is an AC with a tarball diff behind it,
not a hope — and it is proven against the version on npm rather than our own
previous build, because those are different artefacts (measured the hard way on
`@broberg/auth` the same evening).

## Reuse

`@broberg/theme` owns design tokens and already does WCAG-AA contrast checking
for Tailwind generation. Worth reading before writing the luminance maths — but
mail-core deliberately has **no** dependency on it (a mail shell must render with
zero runtime deps), so the function is duplicated by design, not by oversight.
If the two ever disagree about a ratio, theme's is the reference.
