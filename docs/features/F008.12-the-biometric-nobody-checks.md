# F008.12 — the biometric nobody checks

**Status:** Backlog · **Epic:** F008 (`@broberg/auth`) · **Written:** 2026-09-05

## The question that produced it

Christian asked whether "Face ID in an iPhone PWA" fits one of our existing
packages or needs a new one, and guessed `@broberg/auth`.

**He is right, and half of it already exists.** `@broberg/auth/passkey` wraps
`@better-auth/passkey` (SimpleWebAuthn) and has since F008. Discovery already
routes `passkey`, `webauthn` and `biometric` to it. **No new package.**

What is missing is not a package. It is a *guarantee*.

## Measured, in the dependency's own dist

```
@better-auth/passkey 1.6.23

  dist/index.mjs:273   userVerification: "preferred"    authentication — HARDCODED
  dist/index.mjs:444   requireUserVerification: false   verification   — HARDCODED
  dist/index.mjs:174   userVerification: "preferred"    registration   — overridable

  PasskeyAuthenticationOptions = { extensions, afterVerification }
                                   ↑ no userVerification field at all
```

So the server accepts an assertion whose **UV flag is 0** — a sign-in that proves
possession of the device and *not* that a face or a passcode was checked. And the
authentication ceremony cannot be configured to ask for more.

## Why the severity is not what it first looks like

This is the half worth keeping, and it corrects the obvious reading.

**On iOS the UV flag is consistently `true`.** Apple's own reference
([passkeys.dev](https://passkeys.dev/docs/reference/ios/)) states that iOS
performs verification locally *before* it will produce an assertion at all, and
that `preferred` and `required` behave identically there. So on an iPhone you get
Face ID whether or not the server asked for it.

Which means: **the guarantee holds because of the platform, not because anything
enforces it.** That is the same shape this repo keeps finding — a green that
holds because of the data rather than because something is holding it. It is fine
until a security key, an Android device or a future browser behaves differently,
and for an *unlock-the-app* feature the guarantee **is** the value.

## The seam — no fork required

`authentication.afterVerification` receives
`verification.authenticationInfo.userVerified`, which SimpleWebAuthn 13.3.2 sets
straight from the raw flag:

```
@simplewebauthn/server 13.3.2
  esm/authentication/verifyAuthenticationResponse.js:162   userVerified: flags.uv
```

So the check can be enforced on top of the plugin rather than inside a fork.

## Scope

`requireUserVerification?: boolean` on our `PasskeyConfig`:

- **registration** → `authenticatorSelection.userVerification: "required"`
- **authentication** → an `afterVerification` hook that rejects `userVerified === false`

**Default OFF.** A released package that silently starts rejecting logins which
work today would be a breaking change wearing a patch's clothes.

### Non-goals

- **Not a fork or a vendored copy** of `@better-auth/passkey`. The hook is the
  supported seam and it carries the flag we need.
- **Not a client-side "lock screen" component.** Re-verifying on app open is
  `signIn.passkey()` called again — a recipe for the README, not package code,
  until a second consumer wants the same UI.
- **Not a biometric API.** There is none on the web. Every path here goes through
  a passkey ceremony.

## Two corrections for the README

Both are things a reasonable person would get wrong, so they belong written down
rather than re-derived.

**1. Face ID is not the only unlock.** With no Face ID or Touch ID configured but
a passcode set, iOS falls back to the passcode — and still sets UV. So this
feature is **device-owner verification**, not Face ID. A product that promises a
face and accepts a passcode has misled its user.

**2. The EU scare is stale and still being repeated.** Apple announced removing
standalone home-screen web apps in the EU under the DMA, then **reversed it
before iOS 17.4 shipped**; standalone PWAs work in Denmark. The first search
result found while researching this card still asserts the removal as current —
which is exactly why the correction goes in the README instead of being looked up
again by the next person.

## Reuse

Discovery checked (`passkey`, `webauthn`, `biometric`, `face id`): every one
already routes to `@broberg/auth`. `cardmem_search` for an existing card:
no results. So this extends the package that already owns the capability — the
reuse rule's preferred outcome, and the reason the answer to Christian's question
is "no new package".
