# F033.9 — A dead deploy token is reported as missing secrets

> Parent: [F033](F033-deploy-provider-core.md) · sibling of [F033.7](F033.7-fly-server-deploy-workflow.md) (built the workflow) and [F033.8](F033.8-deploy-workflow-git-sha.md) (the sha passthrough).

## Motivation

The `trail` session spent 2026-08-19 tracking down why none of their CI deploys had worked since mid-May. The answer was an expired `FLY_API_TOKEN`. Their read of it is the sharpest thing anyone said this week:

> **Rød så længe at rød ikke længere bærer information.** There was no green run to contrast against, so a red row meant nothing.

That prompted a look at our own shared workflow — and it has a *different* version of the same disease.

### What the check does today

```bash
PRESENT=" $(flyctl secrets list $APP_ARG 2>/dev/null | awk 'NR>1 {print $1}' | tr '\n' ' ') "
```

Measured with a deliberately invalid token (2026-08-19, this machine):

| | |
|---|---|
| exit code | **1** |
| stdout | 0 lines |
| stderr | `Error: failed to list app secrets: Authenticate: token validation error` |

`2>/dev/null` discards the only sentence that says what actually happened. `PRESENT` is empty. Every required secret is therefore judged absent, and the step fails with:

```
::error::Missing Fly secrets on the app: FOO BAR — set them with 'flyctl secrets set'
```

The secrets are all present. The token is dead. **The message names the wrong cause with complete confidence** — and sends whoever reads it to go set secrets that already exist. After that they are still broken, and now have *less* reason to suspect the token, because they just "fixed" the thing the error named.

## The failure form — third variant this week

We had named two:

1. **A claim that fails GREEN.** Never contradicted by use, because use is what would correct it. (`sha:"unknown"` accepted and locked — F033.8.)
2. **A RED that stopped carrying information.** Failing so long there is no green to contrast against, so the red means nothing. (trail's token.)

This is a third: **a check that fails loudly, in the right colour, naming the wrong cause.** It is the most expensive of the three to a reader, because a red that points somewhere *specific* is trusted **more** than a vague one. A confidently mislabelled failure costs more than an unclear failure.

The root of it is two states collapsed into one. "flyctl could not answer" and "flyctl answered, and the secret is not there" are different facts — and only the second one is about secrets. The exit code that separates them was available the whole time and was never read.

## Scope

**In scope** — the required-secrets step only:
- Read flyctl's exit status; on non-zero, fail naming authentication / app access.
- Stop discarding stderr, so the real message is readable.
- Keep the genuine missing-secret error exactly as it is for the case it actually describes.

**Non-goals**
- A token-validity health check on a schedule. trail built one for themselves (`fly-token-health.yml`) and their reasoning for keeping it *in GitHub Actions* rather than on cronjobs.webhouse.net is right: what is being tested is whether a **GitHub secret works from inside a GitHub runner**, and testing that anywhere else tests a different chain. If we want that fleet-wide it is its own story, not a rider on this one.
- Changing when the step runs, or making it non-optional.

## Why this step is worth keeping

Worth stating plainly: this step is also the reason a dead token surfaces **before** the deploy rather than during it. It is doing something valuable. The fix is not to remove it — it is to keep it failing and make it say the true thing.

## The trap in fixing it

The obvious repair — bail out early when flyctl fails — can quietly turn a working check into one that never fires. If the new code path swallows the genuine-absence case, nobody notices, because the check simply goes green forever. **That would be strictly worse than the mislabelled red we started with**: we would have traded a confusing signal for no signal.

So the acceptance criteria require **three** measurements, not one:

1. invalid token → names authentication, lists no secrets
2. valid token + genuinely absent secret → **still** the missing-secrets error
3. valid token + present secret → passes

Case 2 is the one that matters. A fix verified only against case 1 is a fix nobody proved can still fail.

## Reuse

Checked Discovery first. No `@broberg/*` package owns CI secret-presence checking; this is a workflow components already owns (F033.7). Nothing to adopt, nothing new to publish.

## Rollout

One commit to `.github/workflows/fly-server-deploy.yml`. Consumers pin `@main` and pick it up on their next run. No consumer action required — the behaviour only changes in the case that was already broken.
