# F064.1 — `evalAssertBody` + three distinct outcomes

> Story under **F064**. The fix itself.

## Motivation

See F064 for the measurement. In one line: **an assert written on the documented `{ pass, detail }` form can never fail**, because every object is truthy.

## Scope

Replace:

```ts
const result = await page.evaluate(step.js);
if (!result) throw new Error(`assert failed (falsy): ${step.js}`);
```

with a page-side evaluator returning a three-way outcome:

```ts
type AssertOutcome =
  | { kind: 'syntax'; message: string }   // never becomes valid by waiting
  | { kind: 'threw';  message: string }   // ran and exploded — not a verdict
  | { kind: 'value';  value: boolean; detail?: string };
```

- **Expression wrapper first** (`async () => (body)`), **block wrapper as fallback** (`async () => { body }`) — so `x === y` *and* `return x === y` both work, and `await` works in either.
- **`.pass` is read** when the value is an object carrying it; otherwise truthiness, unchanged.
- **`detail` is stringified page-side** — a DOM node would otherwise fail structured-clone and turn a working assert into a mystery error.
- Three outcomes → three messages. *"is false"*, *"threw X"* and *"is not valid JavaScript"* are different sentences.

### Non-goals

No polling loop (F064). No other step touched.

## Test plan — proven red

The defect is a test-shaped hole, so every test is first run against the **old** implementation and shown to fail. cardmem's three measured probes are the core; the object/detail/await/DOM-node/compile/throw cases surround them.
