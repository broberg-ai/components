# F102.2 — @broberg/seal 0.2.0: bytes for files, a key per customer

## Motivation
helpdesk (27/10, #5139, their F062.1) wants to move attachment encryption — images and PDFs up to 10 MB, today their own `createCipheriv` with a per-tenant HKDF key — onto @broberg/seal, and will not build a local workaround. Two gaps: seal/open only take strings (base64 round-trips cost 33 % and a 13 MB string per file), and seal has one key ring for all tenants (aad binds the row, the key is shared). The owner's requirement for helpdesk is «hermetisk lukket mellem kunder».

## Scope
1. `sealBytes(data: Uint8Array, { aad }) → Promise<Uint8Array>` / `openBytes(sealed: Uint8Array, { aad }) → Promise<Uint8Array>`. Binary layout: magic `SEB1` (4) · KEK version uint32 BE (4) · wrapIv (12) · wrapped DEK (48) · iv (12) · ciphertext+tag. Same DEK/KEK envelope and AAD rules as the string form.
2. `createSealer({ keys, current, scope })`: when `scope` is set, the KEK for each key-ring version is HKDF-SHA-256(ikm = key-ring key, salt = "seal1-scope", info = scope) instead of the raw key, and the wrap AAD includes the scope. A value sealed under one scope cannot be unwrapped under another.

## Non-goals
- `rewrapBytes` (rotation for byte values) — not asked for; the old version keeps opening as long as its key stays in the ring.
- Streaming encryption of very large files.
- Reading helpdesk's old HDB1 format (they keep that).

## Architecture
Inside `packages/seal/src/index.ts`: a `kek(version)` that derives per scope when configured; the byte functions share encrypt/decrypt/unwrap with the string ones. No new dependency (Web Crypto HKDF).

## Dependencies
F102.1 (0.1.0).

## Reuse
Extends @broberg/seal itself, the fleet's encryption-at-rest package.

## Rollout
Tests + mutations → 0.2.0 via CI (tag seal-v0.2.0) → release report to helpdesk.
