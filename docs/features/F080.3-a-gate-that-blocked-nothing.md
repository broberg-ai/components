**Status:** in progress · **Parent:** F080 (the repo's own gate) · **Priority:** critical · **2 SP**

## What happened

`@broberg/notifications` 0.3.0 was published to npm through a gate that had been

## Two defects, and the second is what makes the first dangerous

### 1. The red carried no information

`test` went red at 07:50 on `143e8a2` (the notifications React wrapper) and
stayed red for every push after it, **including the release**. No job in
`publish.yml` carries `needs: test`.

This repo's own CLAUDE.md says: *«the release job must depend on the test job so
one red test blocks deploy/merge».* It does not. **A gate nothing depends on is
a notification**, and this one was addressed to a session that was not reading
it. Eleven chances to notice, eleven missed — which is the honest measure of how
much attention an advisory red actually gets.

Related, same shape: `docs/features/F038.9` (a guard that cannot say it could
not ask) and the memory note *"Red that stopped carrying information"*.

### 2. The pin gate cannot reason about an exact version

```
? @broberg/notifications → @broberg/ui-controls-core "0.1.1"
  — this gate cannot reason about that range (npm latest 0.1.1).
  Refusing to call it fine.
```

A bare `"0.1.1"` is not an expression the gate should be confused by — it is the
**most** reasonable-about range there is: it can only ever resolve `0.1.1`. So
the verdict is decidable (`ok` iff `latest === "0.1.1"`, else `stale`), and
reporting it as UNKNOWN tells the reader *the gate is confused* when in fact
*the pin is the wrong shape*. A true finding wearing a misleading message.

The devDependency itself IS wrong, and is the immediate cause: an exact pin means
the conformance test proves our types match `0.1.1` forever while consumers
install whatever is current — a test that stays green for the wrong reason, which
is the exact thing the gate's own comment says devDependencies are in scope for.

## Non-goals

- Not touching what `test` runs. The suite is fine; its *authority* is the defect.
- Not adding a second deploy path or a new workflow.

## Approach

1. `packages/notifications/package.json` devDependency → `>=0.1.1` (a shape the
   gate understands **and** that tracks what consumers install).
2. `satisfiesLatest()` learns the bare exact version: decidable, not unknown.
   Keep every other form conservative — an expression it genuinely cannot read
   must still refuse.
3. `publish.yml` — every publish job gets `needs: test`, with a `test` job in
   that workflow running the same suite on the tag. A tag push does not trigger
   `test.yml` (it is `on: push: branches`), so a cross-workflow `needs` is not
   available; the gate has to run inside the publish workflow itself.
4. Prove the block: push a tag with a deliberately red suite and watch the
   publish job refuse to run. **A gate not observed refusing is not a gate.**
