# F084.185 — Native passkey helper in @broberg/sso (Face ID / fingerprint login in Capacitor apps)

## Why
Owner's order 27/10 2026, relayed by `bid` (#5234, BID card F084.203): «Byg et generisk FaceID login til iOS og Android der kan genbruges overalt». BID opens its embedded passkey login to native apps. The client half must live in ONE place so Buzz, Jam Mobile and the next native app reuse it instead of each wiring BID's four routes and PKCE by hand.

## Open questions (answer before/while building)
1. Which Capacitor passkey plugin do consumers use (Buzz first)? The design keeps it injectable so the package does not hard-depend on one.
2. Does BID's `options` return `allowCredentials`, or is it discoverable-credential only? Affects what we pass to the platform.
3. Token storage on device is the app's choice (secure storage); the helper returns tokens and does not persist them.

## BID contract (from bid #5234)
- `POST /embedded/passkey/start {client_id, code_challenge, redirect_uri?}` → `{flow_id}`
- `GET /embedded/passkey/options?flow_id` → `{challenge, rpId: "id.broberg.ai", timeout}`
- `POST /embedded/passkey/verify {flow_id, response: AuthenticationResponseJSON}`
- `POST /embedded/passkey/complete {flow_id}` → `{next: "done", code}` → `/oauth2/token` with PKCE
- BID serves AASA / assetlinks.json from each native client's registered iOS app ids / Android package + SHA-256 (BID's side).

## Design
- New export on the existing embedded surface, e.g. `embedded.passkeyNative({ baseUrl, clientId, redirectUri?, getAssertion })`.
- `getAssertion(options) => Promise<AuthenticationResponseJSON>` is injected: the app wires its Capacitor plugin (ASAuthorization on iOS, Credential Manager on Android). The package owns the protocol, PKCE and error mapping — not the native bridge.
- Named outcomes: `cancelled`, `no_credential`, `rejected`, `unavailable`, plus success with tokens.
- No new hard runtime dependency.

## Non-goals
- Native plugin code (Swift/Kotlin) — consumers use an existing Capacitor plugin.
- Registering a new passkey from the app (BID's setup flow covers creation).
- Persisting tokens.

## Reuse
Builds on @broberg/sso's existing embedded login and PKCE helpers; no separate package.

## Tests
Fake BID implementing the four routes + token endpoint with real PKCE verification; one test per named outcome; mutations on PKCE and flow_id.

## Rollout
Minor release of @broberg/sso; release report to broberg-id and every known consumer (D-4d0783); Buzz is first. Live proof on a real phone belongs to Buzz/BID and is named unverified until they report.
