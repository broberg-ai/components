# F078.4 — Permission facts, and why five states rather than two

> Story under **F078 — `@broberg/device-stats`**. Follows F078.1 (core), F078.2 (adapters), F078.3 (Tier-1 consent).

## What Christian asked

> *"En ting til vores device stats — kan den ikke også checke på om man på de forskellige devices har sagt ja til Push og Lokation og FaceID og hvad der ellers er af device specifikke godkendelser? Det ville være godt for statistikken."* — 2026-08-28

Yes. The value is obvious: knowing that 70 % of installed users have push enabled and 12 % have location is the difference between designing a feature and guessing at one.

But his list contains **three different questions that look like one**, and the naive implementation gets the most important one backwards on the platform most of his users are on.

## ⚠️ The finding that decides the design

**The Permissions API is not evenly supported, and the gap lands exactly where his users are.**

Safari/iOS does not answer `navigator.permissions.query({ name: "geolocation" })`. So a two-state read — granted or not-granted — records **every iPhone visitor as having REFUSED location.**

> That is not an incomplete statistic. It is a wrong one, in the direction that invites action, on the majority platform.

It is the same failure this whole week has been about, one layer out: **an unanswerable question must read as *unanswered*, never as an answer.** So:

```ts
type PermissionState = "granted" | "denied" | "prompt" | "unsupported" | "error";
```

Five, and `unsupported` (the browser has no opinion) and `error` (the query threw) are never folded into `denied`. A dashboard built on this can then say *"unknown on 61 % of devices"* — which is the truth, and is itself a useful finding about our user base.

**`prompt` is not `denied` either.** It means *not yet asked* — and for a product decision that is the most actionable state of all: those people can still say yes.

## The correction that splits his list in two

**Face ID is not a permission, and no browser exposes one.**

What exists is `PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable()` — *does this device offer Face ID / Touch ID / Windows Hello*. That is a **capability**, not a consent.

So his one question is really three:

| Question | Where the answer lives |
|---|---|
| **CAN** the device do it | the browser (WebAuthn availability) |
| **HAS THE USER ALLOWED** it | the browser (Permissions API) — for push/location/camera/mic only |
| **HAS THE USER SET IT UP** with us | **our own database** — did they register a passkey |

Reporting Face ID inside the permission map as `faceId: "granted"` would be read as consent by everyone who ever sees the field. It gets its own field name and its own state union, so the mistake is unavailable.

## And the one that matters most for push

**`Notification.permission === "granted"` does not mean a push will arrive.**

On iOS the PWA must *also* be installed and hold a live subscription — and a subscription can be dead (`410 Gone`) while the permission still reads `granted`. `@broberg/webpush` already tracks exactly that.

So *"who has said yes to push"* is answered by joining the browser's answer with **our own subscription record**, and where the two disagree, our record is the true one. The README says this out loud, because the browser's answer is the easier one to reach for and the weaker one to ship.

## What is read

```ts
interface PermissionFacts {
  notifications: PermissionState;
  geolocation: PermissionState;
  camera: PermissionState;
  microphone: PermissionState;
  /** CAPABILITY. The device offers Face ID / Touch ID — NOT that anyone allowed anything. */
  platformAuthenticator: "available" | "unavailable" | "unsupported" | "error";
}
```

`Notification.permission` is read directly (it is supported where the Permissions API is not, including Safari) and the Permissions API is used for the rest. Where both exist, the Permissions API wins — it distinguishes `prompt` from `denied`, and `Notification.permission`'s `"default"` maps onto `prompt`.

## Two rules the package must not be able to break

1. **It cannot prompt.** No `requestPermission()`, no `getCurrentPosition()`, no `getUserMedia()` anywhere in the source, asserted by a grep that runs as a TEST rather than as a review habit. Measuring a permission by asking for it would turn an analytics library into a consent dialog on somebody else's product — a bug that is invisible in code review and unmissable to the end user.
2. **The consent gate makes the READ impossible**, not discarded. F078.3's rule, unchanged: permission state is a fingerprinting vector, so with consent absent the query must never be issued — proved with a navigator whose `query` throws if called.

## Measured, not inferred

The support claims above come from documentation, so the card carries an AC that puts them in a **real WebKit browser via Lens** (`engine: "webkit"`) alongside Chromium, and records both results here with the date. If WebKit answers something the tables did not predict, this document says so rather than the table.

## Non-goals

- Not prompting, requesting, or nudging for any permission. Read-only, always.
- Not the passkey registry — whether a user set up Face ID *with us* is the consuming app's own data.
- Not per-user tracking. Same bucketed, identifier-free shape as the rest of F078.
- Not Bluetooth/NFC/clipboard/MIDI. Add one when a product actually asks; a permission we do not use is entropy we collected for nothing.
