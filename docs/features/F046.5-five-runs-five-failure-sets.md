# F046.5 — five runs, five failure sets

**Status:** In progress · **Epic:** F046 (`@broberg/lens-engine`) · **Written:** 2026-09-11

## The measurement

Five consecutive `npx vitest run` in `packages/lens-engine`, on a machine loaded by this session's own work (browsers, four publishes, six gate runs):

| run | result | failing test |
|---|---|---|
| A | 1 / 293 | F071.2 — a tag-named testid that EXISTS and fails for another reason gets no hint |
| B | 1 / 293 | F071.4 — remainingBudget floors at 1, never 0 |
| 1 | 1 / 293 | nth is honoured: "the third row is gone" is "fewer than three visible" |
| 2 | 1 / 293 | ALL layers must be gone — one layer still matching is a FAILURE |
| 3 | 5 / 289 | same instant, wrong settle order · label vs resolved_via · +3 |

**No overlap between any two runs.** The suite is not broken; it is non-deterministic. The reporter's own timings point at the cause: these are the tests carrying 300–500 ms waits.

## What it is not

Not this evening's change. The full repo gate — `pnpm test`, which runs this suite through turbo — went **green with the new close-browser test file present**, an hour earlier, on a quieter machine (`GATE_EXIT=0`).

And the natural first read was wrong. Two runs in, with two different failures, "my new test file broke something" was the obvious explanation — a module mock leaking across files is a real precedent in this fleet (cardmem's F131.29, where four files mocked the same module and execution order decided whether the suite passed). Three more runs killed it. **One or two runs would have had me fixing a bug that does not exist.**

## Why it earns a card

**A gate that fails randomly is a gate you stop reading.** cardmem paid two commits for exactly this today: their local suite was habitually red on a cleanup step, they learned to ignore it, and a genuinely red CI sat unnoticed behind the habit. Their sentence, which is better than mine:

> a local gate that is habitually red for a reason you learn to ignore is a gate you stop reading

**It blocks the mutation harness outright.** `test/mutations.mjs` refuses to run on a red baseline — correctly, because a mutation over a broken baseline proves nothing:

```
::error::1 tests already fail before any mutation:
  F071.2 — the negative controls … gets no hint
```

So while this flakes, the package's strongest guard cannot run **at all**. That is the concrete cost, and it is why this is not cosmetic.

## The trap this card must not fall into

Raising the waits. A longer sleep moves the failure rate; it does not remove it — and it makes every green slower for everyone, forever, in exchange for a red that now arrives monthly instead of hourly. That is the version that looks fixed.

The other trap is measuring the fix on an idle laptop. The bug lives in the loaded window; a clean run outside it proves nothing, which is precisely the mistake cardmem made bisecting their own intermittent wedge tonight — every one of their bisect steps ran in the window where the fault does not occur.

## Not diagnosed

I have not looked at why these particular tests depend on wall-clock, and I am not guessing. The tally is the finding; the cause is this card's job.
