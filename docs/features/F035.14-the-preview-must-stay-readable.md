# F035.14 — The preview that must NOT be redacted is the harder half

> Parent: [F035 — @broberg/secret-scan](F035-secret-scan.md) · filed by cardmem (#27031), shape measured by helpdesk on three real keys (#27034) · sibling of [F035.13](F035.13-the-dangerous-half.md).

**Status:** Backlog · **Priority: high** — a live flagship module's keys are unredacted today.

## The pattern

```
^hd_live_[0-9a-f]{64}$        72 characters, fixed
```

**Verified against our own source, not taken on report** — `packages/apikey/src/core.ts:10`:

```ts
export function generateKey(prefix: string, bytes = 32): string {
  return `${prefix}_${randomBytes(bytes).toString("hex")}`;
}
```

HelpDesk mints through `@broberg/apikey@0.3.1`, which is ours. 32 bytes → exactly 64 lowercase hex. No checksum, no internal structure to anchor on. Prefix plus fixed length plus hex is everything there is, and it is enough: `hd_live_` followed by exactly 64 hex characters does not occur by accident.

Measured on published 0.7.2: `classify('hd_live_…')` → `null`. The gap is real.

## Why cardmem sent no regex the first time

Worth recording, because the restraint is the lesson. Christian's example had a masked tail, and **a mask is not 1:1 with the real length.** A pattern derived from it would never have matched a real key — and would never have failed loudly, because *a pattern that matches nothing looks exactly like a pattern with nothing to find.*

They went and got the shape measured instead. That is the same failure class this package keeps meeting, caught before it was written rather than after.

## The negative control is the harder half

HelpDesk has a **preview** format, deliberately visible in their UI and their logs:

```
hd_live_f4b4cf              prefix + 6 hex
```

It is not a secret. It is what a human reads to see *which* key was revoked. Redact it and we break something designed to be readable — and the preview stops doing its job.

`{64}` already excludes it. **The point is not that it is at risk today.** It is that this is exactly what a well-meaning loosening hits in six months — *"let us catch the shortened ones too"* — and by then nobody remembers why the length was exact. A named test that `hd_live_f4b4cf` does **not** match is cheaper than that conversation.

This is the mirror of [F035.13](F035.13-the-dangerous-half.md)'s mutation requirement:

| | the risk | the seal |
|---|---|---|
| F035.13 (AWS) | a pattern that can only be **too narrow** | widening it must redden a false-positive test |
| **F035.14 (HelpDesk)** | a pattern that can only be **too broad** | loosening `{64}` must redden the preview test |

Both need a seal, and the seals point opposite ways.

## No publishable variant — measured

cardmem raised this before anything was built, and it is the right first question: **if a publishable key ships in every browser bundle, it must never enter the redaction set.** Redacting a value that sits in every checkout bundle is how a redactor gets switched off. The precedent is Stripe's `pk_live_`.

helpdesk measured it: HelpDesk is headless, the console is a client of the same API using a session token, and `grep -c "hd_" dist/assets/*.js` in the deployed bundle returns **0**. No key ever reaches a browser.

Our own pattern is already clean on that axis **by construction**, confirmed on 0.7.2:

```
sk_live_…  → stripe-secret-key
pk_live_…  → null
pk_test_…  → null
```

`/\b[rs]k_live_[A-Za-z0-9]{20,}/` — **s**ecret and **r**estricted only. `pk_` was never in it.

## Considered and rejected: a generic minter pattern

Since `@broberg/apikey` is ours and every key it mints is `<prefix>_<64 hex>`, the tempting move is one pattern covering HelpDesk and every future consumer at once.

**Rejected.** A 64-character hex tail is also a sha256, so `etag_<sha256>`, `cache_<sha256>` and every content-addressed identifier would match — a false-positive class large enough to get the redactor switched off, which is the outcome this whole package exists to avoid.

Narrowing it to a *list* of known prefixes buys one list entry instead of one pattern entry, and adds a list that goes stale silently. Per-prefix stays.

**What does generalise, and it is why this card was cheap:** every fleet key minted through `@broberg/apikey` has a 64-hex tail. The next prefix needs no measurement at all — only the prefix itself.

## Reuse

Nothing to check: `@broberg/secret-scan` is the fleet's single redaction primitive and this repo owns it. cardmem filed a report rather than writing a local regex, which is the reuse rule working — a second copy of a detection rule is the drift the package exists to prevent.

## Non-goals

- Detecting HelpDesk **session** tokens. Different lifetime, different shape, not measured. If they need it, it is its own card with its own measurement.
- Validating that a matched key is live. We detect shapes; we do not call HelpDesk.

## Rollout

Minor, additive. Output changes for real text: anyone logging a HelpDesk key will see it start coming back redacted. That is the fix working, and the release note says so in those words — otherwise it reads as the package having become noisy.

cardmem's coverage test goes red the next time we add a label they have no "where to get this key" page for, so this one announces itself to them when it lands. One less thing depending on someone remembering.
