# F039.9 — Behind on a security release looks healthy

**Status:** Backlog · **Epic:** F039 (Discovery auto-enrollment) · **Written:** 2026-09-01

## The case that raised it

buddy runs `@broberg/secret-scan` **0.5.0**. Current is **0.7.2**. The releases in
between fixed real redaction defects measured on the published package:

- `(\S+)` swallowed a value's trailing punctuation into the replaced span, so
  redacting **deleted** it — `config(password='hunter2')` lost its closing paren.
- A **quoted key never matched at all**: `{"password": "hunter2"}` was reported
  as clean. JSON is how a machine writes a secret, and it was the one shape the
  rule did not see.

Their roster row reads:

```
secret-scan  0.5.0 · uses
```

True, and it looks **healthy**. An adopted package; a version that exists.

## The asymmetry

Being behind on a feature release costs you a feature you never had. Being behind
on a **security** release means a check you are relying on is answering wrongly —
and the roster's silence reads as reassurance.

That is this epic's own recurring shape: F039.7 was about a gap that could not say
it had never been told anything. This is the same merge — *"nothing to report"*
and *"something you would want to know"* arriving as the same blank space.

The version numbers are already there. The missing bit is the one that says which
upgrade is not optional.

## Design

- The roster carries a **security-relevant** mark per release, with a one-line
  reason: what the older version gets *wrong*.
- A session below such a release is told so in its boot payload — reason, and the
  version to move to.
- A session that is current gets **no line at all**, so the line's presence means
  something instead of becoming furniture.

## Constraints

- **Announce a possibility, never issue an order.** Which repos upgrade, and
  when, is Christian's decision. buddy's own 0.5.0 → 0.7.2 is waiting on a
  planned window because an install hangs their daemon. The signal exists so the
  decision is informed.
- **The owner sets the flag at release time.** A heuristic over commit messages
  would mislabel in both directions, and a wrong *"not security-relevant"* is
  worse than no flag.
- **Silence must not mean safe.** An unmarked release reads as *unmarked*, not as
  cleared. The roster cannot know what nobody told it.

## Verification

The real case, not a fixture: buddy on 0.5.0 against 0.7.2 must produce the line,
with the reason. A current session must produce none. And a package with no marks
at all must not emit anything resembling *"no known security issues"* — that is
the negative control, and it is the assertion most likely to be eroded later.
