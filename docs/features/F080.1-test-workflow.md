# F080.1 — `test.yml`: run the workspace gate on every push and PR

**Parent:** [F080](F080-the-repos-own-gate.md) · **Status:** in progress · 2026-08-28

---

## Why (short — the full finding is in F080)

No workflow in this repo has ever run the workspace-wide test. The 38 publish jobs
each run **one** package's tests. The root script that runs all 39 is something
only a human runs by hand — and today `main` was red for hours because a *different
service* (`cronjobs.webhouse.net`) improved a sentence in its published API
contract, and nothing said so.

---

## The workflow

```yaml
name: test
on:
  push: { branches: [main] }
  pull_request:
```

Two steps that matter, kept separate on purpose:

| Step | Why separate |
|---|---|
| `pnpm typecheck` | a type error and a failing assertion are different problems; one red X for both makes you open the log to learn which |
| `pnpm test` | the root script — `check-internal-pins` · `test-fly-deploy-workflow` · `turbo run test` across 39 packages |

**No separate `pnpm build` step.** `turbo run test` already builds what a test
needs through its task graph. Adding one would double the work *and* blur which
stage actually failed.

**Same toolchain as `publish.yml`** — `pnpm/action-setup@v4` (version resolved from
the root `package.json` `packageManager`) and `actions/setup-node@v4` with node 22.
A gate running a different toolchain than the release does not gate the release.

**`concurrency` with `cancel-in-progress`** so a second push does not queue behind
a run nobody wants any more, and an explicit **`timeout-minutes`** because
`contract-drift.mjs` makes a network call and a hung connection must not hold a
runner open.

## The external-service failure mode, written into the file

`@broberg/cron`'s test script ends with:

```
vitest run && (node scripts/contract-drift.mjs || [ $? -eq 2 ])
```

That `|| [ $? -eq 2 ]` is doing real work and it is worth understanding before
someone "simplifies" it:

| exit | meaning | CI |
|---|---|---|
| 0 | reachable, and our schema matches | pass |
| 2 | **could not reach the service** | tolerated — pass |
| 1 | reachable, and our schema **has drifted** | **fail** |

Three states, and only the middle one is a real failure. Without the split, an
outage at `cronjobs.webhouse.net` would redden every PR in this repo and someone
would eventually delete the check to get their work merged.

The consequence a contributor needs: **a PR you did not cause can go red here**,
and the fix is `pnpm --filter @broberg/cron gen` — not a revert. That sentence
lives in the workflow file, not only in this doc.

## How it is proven

A workflow that has only ever been green is a light nobody has proved is connected
to anything — [[signals-indistinguishable-from-silence]]. So:

1. Branch. Break **one** assertion in a real test.
2. Push. **Record the run failing**, and check the log names the package.
3. Revert the break on the same branch. Push. **Record it passing.**
4. Delete the branch.

Step 3 is not decoration: without it, a red proves only that *something* is wrong,
possibly the workflow itself. The pair — red with the break, green without — is
what attributes the failure to the break.

## Reuse

Discovery searched for `github actions`, `workflow`, `test`: as in the parent
epic, no shared test workflow exists and one would be a wrapper around a
per-repo command.

The reuse inside this repo is real though, and it is what made the workflow one
file instead of thirty-nine: the root `pnpm test` already fans out through Turbo
to every package, plus `check-internal-pins.mjs` and
`test-fly-deploy-workflow.mjs`. The finding that motivated the card is that
nothing had ever RUN it — all 38 publish jobs run only their own package via
`working-directory`, so the workspace-wide script existed and was never
executed by CI.
