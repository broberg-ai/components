# F005.11 — "Did it arrive?" has no answer in the fleet

**Status:** In progress · **Epic:** F005 (`@broberg/mail`) · **Written:** 2026-08-31

## Motivation

A peer session filed one sentence and it is exactly right:

> `@broberg/mail` er «delivery only» — der findes ingen status-primitiv i flåden.

Christian relayed it as an order, and in the same turn removed the thing that
had made it impossible:

> Mail har full access adgang i Resend nu.

That matters, because this gap has already cost the fleet real time **twice**,
and both times the wall was the send-only key:

- **F005.6 / xrt81, 11 Aug.** Fourteen club mails, zero errors, and the ids lost
  to a socket timeout. `GET /emails` answered `401 restricted_api_key`, so they
  could not reconcile afterwards. They refused to re-send blindly — correctly —
  and six of the fourteen are *still* unknown.
- **F005.9 / moovyy, 22 Aug.** Christian locked out of moovyy.com. Every link in
  the chain measured green. With no way to ask what happened to three message
  ids, they reasoned from DNS records instead — and reached the wrong
  conclusion (spam-folder, not reject). One query would have settled it.

The key is no longer the blocker. The primitive is simply not there.

## What is actually missing — measured, 2026-08-31

### 1. There is no lookup of any kind

```
packages/mail/src/index.ts    createMailer · createMailerFromEnv · mailAllowed · buildFrom
packages/mail/src/webhook.ts  verifyWebhook · parseMailEvent · handleMailWebhook
packages/mail/src/verify.ts   verifySendingDomain · senderDomain
```

Send, receive-a-push, check-the-domain. Nothing that asks a question.

### 2. The provider can answer

Read off the live spec rather than recalled — the API with the most examples
online is often the retired one:

```
GET https://api.resend.com/emails/{id}      Authorization: Bearer re_…
→ { object, id, message_id, to, from, created_at, subject,
    html, text, bcc, cc, reply_to, last_event, scheduled_at, tags }
```

### 3. Four of eleven events are dropped on the floor

One payload per event type Resend documents, run against our own published
`dist`:

```
email.sent               -> sent
email.delivered          -> delivered
email.delivery_delayed   -> delivery_delayed
email.bounced            -> bounced
email.complained         -> complained
email.opened             -> opened
email.clicked            -> clicked
email.failed             -> NULL (dropped)
email.received           -> NULL (dropped)
email.scheduled          -> NULL (dropped)
email.suppressed         -> NULL (dropped)
```

`parseMailEvent` refuses to guess at a type outside its union — deliberate, and
right. But the union was written before Resend had these four, and **two of them
(`failed`, `suppressed`) are precisely the ones that mean the mail did not
arrive.**

A consumer who wired only `onEvent` — the documented happy path — never sees
them. A non-delivery nobody was told about is indistinguishable from a webhook
that never came, which is this repo's recurring shape landing in the one place
where the silent branch hurts a named human being.

## The design

### The shared part is the VERDICT, not the fetch

The HTTP call is four lines and any repo can write it. What each repo would
write *differently* is the mapping from eleven provider strings onto the only
question anyone asks:

| verdict | means | from |
|---|---|---|
| `delivered` | it reached the recipient | `delivered`, `opened`, `clicked`, `complained` |
| `failed` | it did not, and will not | `bounced`, `failed`, `suppressed` |
| `pending` | still moving | `sent`, `scheduled`, `delivery_delayed`, `received` |
| `unknown` | **we could not look** | 401 · 404 · network · unrecognised shape |

Two rows carry the whole argument for putting this in the package:

- **`complained` is `delivered`.** The mail arrived; the recipient pressed
  "spam". A repo that files it under failure will tell a customer their address
  is wrong when it is fine.
- **`suppressed` is `failed`.** It was never attempted, because the address is
  on a suppression list. A repo that files it under pending will wait forever.

Nobody gets both of those right by intuition, and the cost of getting one wrong
is a wrong sentence sent to a real person.

### `unknown` is a state, not an error code

A send-only key answers 401. A wrong id answers 404. The network answers
nothing. **None of those is "the mail failed"** — and if a permission problem
renders as a bounce, the consumer emails the customer to say their address is
bad. Found / not-found / could-not-look, with the reason carried all the way to
the caller.

### The body is dropped by default

`GET /emails/{id}` returns `html` and `text` — the entire message. A status
object is the first thing a consumer logs. So the body is absent unless the
caller explicitly asks for it, and the README says why in the same breath.

### Where it lives

On the mailer, reusing the key and the **injectable `fetch`** that `MailerConfig`
already carries. Zero new dependencies, no `node:*` import, so it works on
edge/workers like the rest of the core — the line F005.9 already drew when the
DNS check had to move to its own entrypoint.

## Non-goals

- **No datastore, no polling loop, no retry engine.** F005.6 drew this line and
  it holds: one call, one answer. Where the answer is kept is the consumer's.
- **No change to `send()`**, the webhook surface, or any existing type. Purely
  additive; nobody has to touch a line to take the release.
- **No auto-reconciliation.** Re-sending is a decision, not a repair — xrt81 was
  right to refuse it, and a primitive that re-sends on its own would have made
  fourteen mails into twenty-eight.

## Reuse

Checked Discovery before writing this (`/api/search?q=mail+status+delivery`).
Nothing in the fleet owns mail delivery status: `@broberg/mail` is the mail
chokepoint and this belongs inside it, which is the whole point of the ask —
the alternative is seventeen repos each mapping eleven strings their own way.
`@broberg/notify` is chat-only (Discord/Slack) and deliberately fenced away from
mail. No new package.

## Risks

- **A recorded response shape drifts.** The tests assert against a fixture of
  Resend's documented body; if they change it, our fixture agrees only with
  itself. Mitigated the way `@broberg/cron` does it — the fixture is quoted from
  the live spec in this doc, with the date, so a future reader can diff it.
- **`last_event` is a snapshot of the newest event, not a history.** It cannot
  tell you a mail was delivered *and later* complained about; it shows the
  latest. The webhook stream is the history, and the README must say which
  question each surface answers rather than implying they are interchangeable.
