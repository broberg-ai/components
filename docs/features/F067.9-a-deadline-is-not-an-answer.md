# F067.9 — A deadline is not an answer

> Parent: [F067 — @broberg/webpush](F067-webpush-sw-distribution.md) · continues [F067.4](F067.4) · filed by cardmem, intercom #27209, 2026-09-09.

**Status:** Backlog · current published version 0.5.0

## The report was stale; the ask was not

cardmem reported that `getSubscription()` calls `getRegistration()` directly and so answers "not subscribed" for a device that is subscribed, at cold start.

**That code has not existed since 0.3.0.** [F067.4](F067.4) shipped `resolveRegistration()` — `.ready` raced against a deadline, falling back to a direct lookup — for exactly this defect, found by xrt81 in August. cardmem were reading `dist/client.js` from **0.2.1**, pinned in two of their `package.json` files. They measured their own tree when told and confirmed it.

Their own naming of the failure form is worth keeping:

> *"`node_modules` er hvad VI kører, ikke hvad pakken ER — samme forskel som mellem arbejdstræet og repoet. Ét `npm view` er hele kontrollen."*

## What survives — and it is the sharper half

```ts
const winner = await Promise.race([sw.ready, deadline]);
if (winner !== timedOut) return winner;
// deadline hit — try a direct lookup
return (await sw.getRegistration()) ?? null;
```

If the deadline fires **and** the direct lookup finds nothing, the answer is `null`. So today:

| situation | value |
|---|---|
| we did not manage to find out | `null` |
| there is no subscription | `null` |

The hang is gone and the wrong-answer window is much narrower. **The distinction was never added** — F067.4's task was *"one shared resolver, must not hang"*, and it delivered precisely that. This is the piece it did not cover, and it is this epic's recurring shape one layer in: an answer that collapses two facts.

## cardmem's shape is better than a third return value

```ts
getSubscription()                    → PushSubscription | null      // unchanged
getSubscriptionState({ timeoutMs? }) → { state: 'subscribed', subscription }
                                     | { state: 'none' }
                                     | { state: 'unknown', reason: 'worker-not-ready' }
```

A **discriminated union**, not `| 'unknown'` bolted onto the existing return type. Their argument is the reason, and it is correct:

> A consumer writing `if (!sub)` gets a **type error** instead of bucketing `unknown` into the wrong branch.

That is the whole defect: a falsy test swallows the distinction silently. A sentinel string would still be falsy-safe, but it can be cast away; a union cannot be ignored. **Prefer a shape that cannot express the error over a check that forbids it** — the same principle ai-sdk applied to `classify` the day before (they took `label: string | null` alone rather than adding a `matched` boolean, because *there is no field to hardcode when the absence itself is the signal*).

`reason` earns its place because it is the one thing a consumer can **act** on: `'worker-not-ready'` means *ask again*, not *show an error*.

## Not in scope

- **The `visibilitychange` re-check.** cardmem keeps it in their own UI and we agree it belongs there. Their measurement is worth recording regardless: **iOS suspends the page when the app backgrounds**, so the answer from open-time can be stale by the time the user returns. That is a consumer-lifecycle concern, not a package one.
- Changing `getSubscription()`. It stays `PushSubscription | null`; this ships as a minor and nobody is carried into a new shape by upgrading.

## Reuse

Nothing to check — this extends a function in a package this repo owns. cardmem filing it rather than keeping their local guard is the reuse rule working, even though the report turned out to be against an old version: the tri-state ask was real and we would not have had it otherwise.

## Rollout

Minor, additive. cardmem offered the PR and verifies on their real iOS device before this closes — they have the phone, the cold-start path, and 11 iOS subscriptions. A fake `serviceWorker` can prove the branch exists; it cannot tell us the deadline is right in practice.

They are upgrading 0.2.1 → 0.5.0 as its own card first, deliberately not mid-rollout. Their current UI waits on `serviceWorker.ready` directly, so it is version-independent and does not break on the upgrade — it simply becomes redundant the day the package can answer `unknown`.
