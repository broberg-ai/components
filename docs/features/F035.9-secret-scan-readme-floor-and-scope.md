# F035.9 — README: the length floor + the publishable-key scope

> Story under **F035 — @broberg/secret-scan**. Motivated by two consumer reports on 2026-08-24/25 that were **both false in the same way**.

## Motivation

`classify()` returns `null` for two completely different reasons, and the caller cannot tell them apart:

1. no pattern matches this string;
2. a pattern exists, but the sample is shorter than its `{20,}` floor.

That ambiguity cost real time twice in two days, from the same session:

- **`rk_live_`** — cardmem probed `rk_live_51ABCdef` (8 chars after the prefix) → `null` → filed as *"the description names `rk_live_` but the pattern does not match it, and it is security-relevant via redaction"*. **They retracted it themselves** when their own production vault showed a real `rk_live_` key correctly labelled `stripe-secret-key`, contradicting the probe.
- **`whsec_`** — filed as the one genuine remaining gap. It is not one.

### Measured against the PUBLISHED tarballs (not the source tree)

```
whsec_ occurrences in dist/index.js:   0.2.2 → 0    0.3.0 → 0    0.4.0 → 3    0.5.0 → 3

redactSecrets(), realistic key (whsec_ + 32–44 random chars), three contexts
(bare value · inside prose · WEBHOOK=<key>):

  0.5.0  →  redacted   redacted   redacted
  0.1.7  →  LEAKED     LEAKED     LEAKED
```

So **there is nothing to fix in the package.** `whsec_` shipped in 0.4.0 and works.

Their `null` had **two independent causes pointing the same way**, which is exactly why neither could reveal the other: the probe was below the floor (it would return `null` on 0.5.0 too), *and* their installed version is **0.1.7**, which does not carry the pattern at all.

### The real finding (reported separately, not this story)

Per Discovery's self-reported roster: cardmem **0.1.7**, beacon **0.1.8**, trail **0.1.5**, buddy **0.1.4** — latest is **0.5.0**. On 0.1.7 a realistic `whsec_` **leaks through redaction in every context tested**, including `WEBHOOK=<key>` — the exact shape someone pastes into a chat while debugging. That is a live, security-relevant drift for those repos, and it is the caret-on-0.x trap (`^0.1.x` can never resolve `0.4.0`) that Discovery's npm tips already document — biting a second time the same day, after buddy's `ai-sdk` finding. All four were notified.

### A correction I made mid-investigation, kept because it is the lesson

My first pass diffed the exported `SECRET_PATTERNS` **labels** between 0.1.7 and 0.5.0 and found **nine** missing — which read as nine redaction holes. Probing them **functionally** showed eight of the nine (`sk_live_`, `rk_live_`, `xoxb-`, `sbp_`, `sb_secret_`, `trail_`, `uk_`) are redacted on **both** versions by broader patterns. Only `whsec_` actually leaks.

**A label diff is not a behaviour diff.** I was one step from sending the fleet a message that overstated the risk by 9×.

## Scope

README only, three short sections:

1. **The length floor** — what a `null` actually means, the instruction to re-probe with a realistic-length value, and why the floor is deliberate.
2. **Publishable keys are out of scope** — stated as a *decided boundary*, so it is not re-filed.
3. **Measure the version you run** — one line: patterns are added over time, a caret on a 0.x locks the minor.

### Non-goals

- **No pattern changes.** `whsec_` works; do not "fix" it.
- **Do NOT add `pk_live_`/`pk_test_`.** Publishable keys are not a leak risk, and redacting one would corrupt copy-pasted setup instructions for no gain. The decision is to decline — the README records it rather than leaving it open.
- **Do not lower the floor.** It is load-bearing: without it the literal string `sk_live_` in prose, a doc or a code comment gets flagged, and a redactor that fires on prose gets switched off.
- No version bump; a README-only change rides the next release.

## Reuse

Nothing to reuse — documentation on a package `components` owns. Same family as F019.7 (i18n): a description that was accurate and still left the reader unable to act on it.
