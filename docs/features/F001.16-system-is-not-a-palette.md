# F001.16 — "system" is not a palette, it is a WAY OF CHOOSING one

**Status:** Ready · **Epic:** F001 (`@broberg/theme`) · **Written:** 2026-09-07
**Asked for by:** Christian, relayed by cardmem — *«Udvide @broberg/theme til at
kunne køre system. Få components til det.»*

## Measured in our own source

cardmem sent three claims about our package. All three verified in
`packages/theme/src/index.ts` rather than accepted:

```
 76  export function initTheme(options) {
 78    const stored = readStored();
 79    if (stored) { current = stored; }              <- a stored value wins FOREVER
 81    else if (options.followSystem) { current = systemTheme(); }

 33  THEME_KEYS = [light, dark, light-cool, light-warm, dark-cool, dark-warm]
 96  setTheme(theme) { if (!isThemeKey(theme)) return; … }    <- "system" is a silent no-op
 60  systemTheme()  reads matchMedia ONCE; nothing anywhere listens
```

So `followSystem` is in force only until the first click, there is no way to
say "system" at all, and an OS that flips while the app is open changes nothing.

## The design, and why a seventh key is the wrong shape

`ThemeKey` currently conflates **which palette** with **how it was chosen**.
Adding `"system"` to `THEME_KEYS` would make `getTheme()` able to return
something that is not a theme — and every consumer reading it to paint would
need a special case.

```
preference   ThemeKey | 'system'    persisted; the user's CHOICE
theme        ThemeKey               derived; what lands on <html>
```

`getTheme()` keeps returning a `ThemeKey` and nothing else. `getPreference()` is
the new verb, and it returns `'system'` — not the resolved value, because
returning the resolved value is exactly what makes a setting look like it did
not stick.

## One correction to cardmem's sketch

They proposed `preference: 'light' | 'dark' | 'system'`. That **drops the four
variant palettes** — `light-cool`, `light-warm`, `dark-cool`, `dark-warm` — so a
consumer on one of them would lose it on the first `setPreference`. It has to be
`ThemeKey | 'system'`.

Found by reading our own `THEME_KEYS`, which is the half they could not see.

## The part that is easy to miss (theirs)

**The `matchMedia` listener must be attached regardless of the current
preference, and must re-read the preference on every change.** Attach it only
while the preference *is* `'system'` and the app goes deaf after a trip through
light → dark → system.

That implementation passes every other criterion in this card. It is the one
that needs its own named test.

## Backward compatibility, in both directions

| | |
|---|---|
| old stored `"dark"`, new code | a valid preference — nothing to migrate |
| new stored `"system"`, **old** code | `isThemeKey('system')` is false → `readStored()` returns null → falls back to `defaultTheme`/`followSystem` |

The second row is the one nobody checks, and two versions **will** coexist across
the fleet during rollout. It degrades rather than throwing — assert it.

## Scope

- `setPreference` / `getPreference`, persisted under the existing storage key.
- A `matchMedia` listener that stays attached and re-reads.
- `initTheme` resolves preference → theme.

### Non-goals

- **Not a seventh `THEME_KEY`.** See above — it would put a non-palette into the
  value consumers paint from.
- **Not removing `followSystem`.** It is shipped and consumers pass it. Deprecate
  it in the README in favour of `defaultPreference: 'system'` and leave the
  behaviour untouched. Replace, prove, then remove.
- **Not a UI.** The picker belongs to each app; this is the runtime underneath.

## Reuse

None — this is `@broberg/theme`'s own runtime, in the repo that owns it.
cardmem's `apps/web/src/lib/theme.ts` (their F313.2) is a **sketch we were
shown**, not a dependency: they delete their layer the day this ships, rather
than migrating it.
