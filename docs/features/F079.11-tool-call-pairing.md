# F079.11 — `ChatMessage` cannot carry a tool call

> Story under **F079 — `@broberg/chat`**. Reported by **cms** from a live production outage, 2026-08-28, hours after they swapped onto the package.

## What happened to a real user

For about 40 minutes, every question in cms's admin chat that required a tool ended in an error message.

```
event: tool_call    site_summary
event: tool_result  (correct: 48 posts, 22 pages, …)
event: error        mistral 400 — "Unexpected role 'tool' after role 'user'"
                    type=invalid_request_message_order code=3230
```

**The tool ran. The answer came back. The round that would have turned it into a sentence was rejected.**

Christian asked whether *he* should try the chat. cms said no and ran it themselves from inside the Fly machine. Good thing they did.

## Reproduced in our own loop before acting

Not taken on their word — run against our own built `dist/`, with a model that calls a tool without writing anything first:

```
round 1 sent: ["user"]
round 2 sent: ["user","tool#c1"]     <-- exactly the payload the provider rejected
```

## Two faults, and the second is the real one

```ts
interface ChatMessage { role: "user" | "assistant" | "tool"; content: string; toolCallId?: string }
```

**A. No assistant turn at all.** `if (text) messages.push({role:"assistant", content:text})` — the model called a tool without speaking, so `text` was empty, so nothing was pushed and `tool` followed `user` directly.

**B. An assistant turn cannot record what it asked for.** There is no field for it. Only the following `tool` message knows its own id, and *nothing* knows the name or the arguments. Mistral, OpenAI and Anthropic all require a tool result to answer an assistant turn that requested it.

A is what fired. **B is why it could not be repaired downstream** — and B hits every consumer with tools against any real provider.

## The part that is about us, not about the type

cms asked the question this card is really named after:

> *"Jeres røgtest sendte 37 beskeder uden værktøj og 27 med — mod HVAD? Hvis det er en fake ModelFn, kan den per konstruktion ikke se denne fejl, og den ville have bestået hele vejen gennem 0.4.0 også."*

**Answered honestly: a fake `ModelFn`.** All 181 tests and the entire clean-directory smoke of the published tarball ran against a stub. **None of them could have caught this.** Neither could cms's 1,283 green tests, for the same reason.

> **The broken condition belongs to the PROVIDER. Nothing in either repo had ever spoken to one.**
>
> cms: *"Attrappen var tro mod GRÆNSEFLADEN og ikke mod VERDEN."*

This is a rule already written down in this repo — *check whether your test doubles are shaped like the code or like reality* — failing one storey above where it was written. The double was not a stubbed function; it was a whole fake implementation of an external party, so it agreed with our interface instead of checking it. A stub cannot disagree with you.

**So the type fix is ten lines and is not the deliverable.** The deliverable is a test double that *refuses* what a provider refuses.

## What we build

1. **`toolCalls?` on an assistant message** — id, name, args per call. Optional, so the type change is additive.
2. **`run()` always emits the assistant turn that owns the calls**, with or without text. This is a behaviour change and the release note says so.
3. **A strict `ModelFn` test double** that enforces the providers' documented ordering rule, with the existing loop tests run through it. Proven by reverting the fix and watching the strict double go red where the permissive one stayed green.
4. **An unknown call id is never repaired.** cms's rule, adopted verbatim: an invented pairing is a second wrong answer, and the provider's own error is more useful than our guess.

## What we cannot do, said plainly

**No live provider round-trip.** There is no key outside production — ours or cms's — so the strict double encodes the providers' *documented* rule, not a measurement. **A live tool round-trip against the cheapest model remains the outstanding test**, and it is the one that would have caught this. It is recorded as outstanding rather than quietly absent.

cms proved theirs live after their own fix (`020c7c30`): `tool_call → tool_result → 10 streamed text frames → ONE done`, answering *"Der er **136 dokumenter** i alt på sitet."* — our loop, our tool registry, our permission gate, their translation, through a real Mistral conversation. **That is the first time today any of it was proven against a real provider rather than an imitation of one.**

## Also from the same report

cms emitted their own `done` after our loop, so the stream carried two per turn. Harmless for their client, load-bearing for the next one. The README must state that `done` **is** a frame the loop emits.

## Their method, worth copying

They could not prove it in a browser: Lens is a read-only principal and the chat route correctly answers 403 for it, because a chat message can trigger tools that write. So they ran `node -e` *inside the production container* against localhost, with the service token from the container's own environment. **The secret never left the machine and never entered their context.** That is how to exercise an authed, mutating route in production without opening a door to get a green tick.

## Non-goals

- Not a provider adapter. The model stays injected; we describe the transcript correctly and the consumer translates it.
- Not rewriting a caller's malformed transcript into something plausible.
- Not assuming cms upgrades. They are explicitly not taking a version jump on the day production went down, and they are right.
