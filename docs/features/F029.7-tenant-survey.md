# F029.7 — Survey before code: five tenant implementations side by side

> Story under F029 · research + plan revision · M · no package code

## Summary
Before we build a shared tenant package, we measure how the five apps that already handle organisations do it, and put that next to cms. Only what is genuinely the same in several apps goes into the package. The result is a revised F029 plan and one short decision question for Christian.

## Motivation
Christian 6/10 asked whether a shared tenant module is worth having, and decided that organisations and memberships do NOT live in Broberg ID. F029 was planned in June from cms' model alone (registry.json, a site pool). Since then at least five apps have built their own: xrt81 (F013), cardmem (orgs and team roles), trail (tenant-pool, key-index, plan limits), helpdesk (tenant/platform) and Scout (one Postgres database per organisation). A package designed from one of them would not fit the others, and the plan has to say which parts actually repeat.

## Solution
For each app, read the code (or ask its session), then fill one row per dimension: resolution, membership and roles, invitation, isolation model, switcher UI and per-tenant limits. Mark what is identical in three or more apps. Revise F029 so that the package owns the identical parts, and the app supplies storage through an adapter (like sso's TokenStore).

## Reuse
The survey itself needs none. Candidates to reuse in the package: @broberg/sso (session identity), @broberg/db-sdk (storage adapters), @broberg/app-shell (switcher and member list UI).

**Organisations in Broberg ID: nowhere** (6/6). This matches D-5345a2. One exception: Scout's `PLAN.md:345` says roles come from BID, which contradicts both its own F001 and D-5345a2. Scout has been told.

### Identical in ≥3 apps: these go into the package

1. **A tenant has an id, an immutable unique slug and a name.** 6/6.
2. **Membership is (user, tenant, role), unique per pair, and a user can be in several tenants.** cardmem, trail, helpdesk and cms (4), plus Scout's plan. **The role vocabulary differs** (owner/admin/member, owner/operator/viewer, admin/editor/viewer), so the package takes the roles as app data and does not define them.
3. **Choosing the active tenant, checked against membership.** 5/6 do it, **and it is where the bugs are**: cardmem falls back to the first membership without ORDER BY and without telling anyone, cms falls back to the first site, and xrt81 looks a member up by email without a tenant. Two answers are right: helpdesk refuses an explicit choice hard, and trail lets a stale preference fall back WITHIN the user's own memberships. The package needs both rules, kept apart (see F029).
4. **Invitation:** token → expiry → accept → membership. 5/6. The best parts are already in the fleet: hashed token and single use (helpdesk), email must match and idempotent accept (cardmem), cannot escalate to the platform (helpdesk).
5. **Capability check** (role → allowed actions, audit on denial): cardmem has it as a matrix, helpdesk as an allowlist, cms as `requirePermission`. The package gives the shape, the app gives the matrix.
6. **Switcher UI:** 4/6. This belongs in `@broberg/app-shell`.

### Different: stays in the app

- **Isolation model**: shared DB with `tenant_id` (3), DB per tenant (trail, Scout), directory per site (cms). The package must not choose, so it gets the tenant from a `TenantStore` adapter that the app implements.
- **Levels under the tenant** (site, project, unit, brain group): app-specific.
- **Plan/limits**: stored in 4 apps and **enforced in none**. That is not a pattern to share. It is a pattern of not getting it done.
- **The credential → tenant index** (trail's key-index): only trail needs it, because it is the only app with one DB per tenant behind a bearer token.

### Security findings along the way (reported to the owners; not ours to fix)

- **cardmem:** card lookup by id, slug or F-number has no org filter (`get-card.ts:220-236`, `update-card.ts:200-208`, `card-reviews.ts:319-327`). `cardmem_get_settings` reads any project by id. `api/org.ts ctxOf` ignores `active_org_id`.
- **xrt81:** `findMemberByEmail` is not tenant-scoped (`lib/auth.ts:13-20`). `DEFAULT_TENANT_ID` as a column default lets a forgotten `tenantId` land in X RT 81.
- **cms:** `resolveToken("oauth")` step 3 can use another site's GitHub token (`site-pool.ts:114-132`). `/api/cms/registry` treats an unknown user as admin.
- **trail:** a forged `trail-active-tenant` cookie falls back to the user's own first membership, whereas the header is a hard 401. **trail's answer (#1976): deliberate, and right.** The header is an explicit choice for one request; the cookie is a standing preference that goes stale innocently, and a 401 there would lock the user out. This was adopted into the F029 design (`requested` strict, `preferred` falls back within the user's own memberships with `fellBack: true`). So it is not a bug, and the pattern is the one to copy. The only thing missing is clearing the stale cookie.
