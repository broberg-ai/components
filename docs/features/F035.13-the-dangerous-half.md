# F035.13 — We redact the harmless half and leave the dangerous one

> Parent: [F035 — @broberg/secret-scan](F035-secret-scan.md) · filed by cardmem, intercom #26988, 2026-09-09.

**Status:** Backlog · **Priority: high** · published version at filing: 0.7.2

## The measurement

Re-run here against our own source before accepting the report, and the real output is worse than the summary:

```
redactSecrets('aws_access_key_id=AKIAIOSFODNN7EXAMPLE\n' +
              'aws_secret_access_key=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY')

aws_access_key_id=[REDACTED:aws-access-key-id]
aws_secret_access_key=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
```

Per value:

| input | classify |
|---|---|
| `AKIAIOSFODNN7EXAMPLE` | `aws-access-key-id` ✓ |
| `AWS_SECRET_ACCESS_KEY=wJalrX…EXAMPLEKEY` | `null` ✗ |
| `ASIAIOSFODNN7EXAMPLE` | `null` ✗ |

We ship exactly one AWS pattern — `/\bAKIA[0-9A-Z]{16}\b/` at `src/index.ts:117`. No secret-key pattern, no session-token pattern.

## Why this is worse than no redaction at all

cardmem's argument, and it is correct:

> An AWS access key ID alone is useless to an attacker. The **secret** access key is the credential.

So the output masks the half that does not matter, leaves the half that does, and stamps `[REDACTED:…]` right beside it. **A reader sees a redaction marker and concludes the text was cleaned.**

That is a false green produced by the one package in the fleet whose entire job is to not produce one. It is the same shape this repo has now named repeatedly — a signal that looks like an answer to a broader question than it actually answers — except here the signal is a security control and the reader's wrong conclusion is *"this is safe to paste"*.

Not hypothetical: cardmem took AWS on board yesterday (SES + IAM for cardmem.com).

## The design question, which is ours

cardmem filed the gap and explicitly declined to prescribe the fix — *"I own the trade-off false-positives vs coverage"*. Right call. A bare 40-character base64 string **cannot** be matched: it is the shape of every git object hash, every base64 body and every JWT segment in every repo we own.

Two workable shapes, and they are complements rather than alternatives:

**(a) Context anchor.** `AWS_SECRET_ACCESS_KEY=…` / `aws_secret_access_key: …`. This is exactly the form already shipped for mistral, deepseek and cloudflare, so it is proven in this codebase rather than novel. Catches a lone secret in a config file, an env dump, a `.env` pasted into a chat.

**(b) Pair proximity.** A 40-character base64 value near an *already matched* `AKIA`/`ASIA` id. The false-positive cost is close to zero **because it requires the ID to be present** — and the pasted pair is precisely the dangerous case this card exists for. It also catches the pair when the variable is named something we did not anticipate, which is the failure mode (a) alone still has.

Build (a) first: it is the smaller change, it reuses a proven form, and it closes the config-file case on its own. (b) is where the interesting testing lives, and its window must be a **measured** number with a boundary fixture on each side — a proximity threshold nothing can move is a magic number wearing a measurement's clothes, which is the exact mistake F035.12 had to come back and fix for the 16-character floor.

## The false-positive control is the half that decides whether this ships

A secret-scanner that cries wolf gets switched off, and then it protects nothing. So the negative fixtures are not an afterthought here — they are the acceptance condition. They must be drawn from **shapes this repo actually contains** (git hashes, base64 bodies, JWT segments) rather than invented, because an invented negative is chosen by the same author who chose the pattern and tends to agree with it.

That is helpdesk's lesson from the same week, in a different package: their residency test could not tell `regionOfHost(u) === "eu"` from `u.includes("mistral")`, because every fixture they had made the two agree. **A predicate is only tested by a case where the right answer and the plausible-wrong answer differ.**

## Reuse

Nothing to check — this repo owns `@broberg/secret-scan` and it is the fleet's single redaction primitive. That is exactly why cardmem filed a report instead of writing their own AWS regex: a second copy of this rule is the drift the package exists to prevent. The right response is to extend it, which is what this card does.

## Not in scope

- **F035.12's AC#4** already recorded `hasAnnouncedSecret` and `redactSecrets` disagreeing on `password: AKIA…`, and settled it correctly: the format pass runs first and holds the better attribution. That is a different question — this card is about a value we have **no pattern for at all**.
- Validating that a matched key is live. We detect shapes; we do not call AWS.
- The `classify()` label surface. cardmem noted they use it to *tag* a stored secret and that a label without a pattern is just a label — true, and it follows for free once the patterns exist.

## Rollout

Minor version, additive — new patterns, nothing removed. But the **output changes for real text**: consumers who have been storing or logging AWS pairs will see previously-visible values start coming back redacted. That is the fix working, and the release note must say so in those words, or it reads as the package having become noisy.

cardmem confirms against their own AWS credentials before this closes. They filed it, they have AWS live, and a fixture we wrote ourselves cannot tell us whether a real credential shape matches.
