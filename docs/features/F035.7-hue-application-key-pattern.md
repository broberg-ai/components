# F035.7 — Adopt the Hue application-key pattern (SHA-safe) + `classify()` support

> Story under **F035 — @broberg/secret-scan**. Consumer-filed gap from **beacon** (#18982), with a working pattern supplied.

## Motivation

beacon adopted the package and **measured before wiring it in**. Reproduced here against the shipped `dist`:

```
const key = 'FAKEfakeAbCdEf0123456789AbCdEf01234TEST5'   // 40 chars, Hue form
hasSecret(key)                 // false
classify(key)                  // null
redactSecrets('key: ' + key)   // unchanged, findings: []
```

A Philips Hue v2 application key is 40 characters of `[A-Za-z0-9-]` with **no prefix**. There is nothing to anchor on, so it falls between our 37 curated patterns. That is not a criticism of the curation — it is exactly as conservative as it should be.

But it makes adoption *dangerous* for a repo like beacon, where that key is the only one worth anything: wiring the package in unmeasured yields a redactor that scrubs every credential **except** theirs — and an acceptance criterion reading *"verified with secret-scan redaction"* over a key that sails straight through. A guard that cannot fire looks like a guard that passes.

Context beacon supplied: Christian's real Hue key was committed into a test whose subject is that credentials do *not* escape. Rotation is complete and the old key is dead. While rotating, beacon caught themselves writing a script that printed seven characters of the **new** key "so it can be recognised" — caught by Christian, not by anything mechanical. Hence closing this for the whole fleet rather than for one repo.

## Scope

Add one pattern to the canonical list and teach `classify()` to name it.

```ts
{
  label: 'hue-application-key',
  description: 'Philips Hue v2 application key (40 chars, no prefix)',
  regex: /\b(?![0-9a-f]{40}\b)[A-Za-z0-9-]{40}\b/g,
}
```

**The lookahead is the whole design, and it is load-bearing.** A bare `[A-Za-z0-9-]{40}` also matches a **git commit SHA**. Telemetry and error messages are full of them; a redactor that eats commit hashes gets switched off within a week, after which it protects nothing. Hue keys are mixed-case, SHAs are lowercase hex — that asymmetry is what the guard exploits. beacon reports zero false positives on real Beacon output; verified independently here against SHAs from this repo's own history, standalone and in prose.

Known, accepted edge: an **all-uppercase** 40-char hex string still matches. Git SHAs are lowercase, and such a string is genuinely ambiguous, so erring toward redaction is correct.

### Non-goals

- No change to any existing pattern or to the ordering (first-match-wins is preserved).
- Not a general "unprefixed high-entropy token" heuristic — that is how a redactor starts eating IDs and gets disabled. One specific, tested shape only.

## Dependencies

None. Pure addition to the pattern table + the `classify()` map.

## Reuse

The extension path worked exactly as designed: beacon used the documented `extraPatterns` hook rather than forking, and filed the pattern for adoption. Landing it canonically lets them delete their local copy. `classify()` support matters beyond beacon — cardmem's Secrets Vault (F214) uses it for "paste a key → detect the type", where a Hue key currently returns `null`, and beacon has already put one into a vault-like context. No Discovery search applies — we own the package.
