# F080.2 — Seven packages had a publish job that could never fire

## Found by a release that did not happen

Shipping `@broberg/ui-controls-core@0.1.1` (F016.7): committed, pushed, tagged
`ui-controls-core-v0.1.1`, tag confirmed on the remote with `git ls-remote`.

No workflow run appeared. Nothing failed. Nothing was skipped. npm still served
`0.1.0`.

## The cause

The job existed, and its condition was correct:

```yaml
publish-ui-controls-core:
  if: startsWith(github.ref, 'refs/tags/ui-controls-core-v')
```

But `ui-controls-core-v*` was **not in the workflow's `on: push: tags:` list**, so
the workflow could not *start* for that tag at all. A job's `if:` is only
evaluated once the workflow is already running.

## Measured across the whole file, not just the one that bit

```
38 publish jobs
31 tag triggers

jobs with NO trigger:
  cmdk  consent-cookie  event-log  http  i18n  soundkit  ui-controls-core
```

Seven packages, every one of which looks fully configured to anyone reading the
jobs section.

**`@broberg/http` is the one that shows the cost.** Its Trusted Publisher was set
up on npmjs.com specifically so `0.1.1+` would auto-publish on a tag — and that
belief has been recorded as fact in this repo's notes since July. A tag would have
done nothing, and the first person to learn otherwise would have been whoever was
mid-release.

## Why it survived, and this is the part worth keeping

**A tag push that matches no trigger is not an error.**

GitHub does not start the workflow, does not report a skip, and shows nothing on
the commit or on the tag. The *absence* of a run looks exactly like a run that has
not started yet. Every signal a person would think to check is silent, so the only
way to notice is to already suspect it.

Same shape as everything else closed this week: a failure indistinguishable from
silence. The fix cannot be *remembering* — it has to be a check that runs.

## The guard

`scripts/check-publish-triggers.mjs`, wired into `pnpm test` so the F080.1 CI
workflow runs it on every push and PR.

It derives **both** sets from `publish.yml` itself — the `on: push: tags:` block
and the jobs' `if:` conditions. A hardcoded list of expected packages would be a
second thing to keep in sync, which is precisely the defect being fixed.

### It checks both directions

| defect | what you see |
|---|---|
| job with no trigger | **no run at all** — silent |
| trigger with no job | **a GREEN run** that published nothing |

The second is the more dangerous one. A green tick claiming a release happened is
a stronger false signal than no tick at all.

### And it names names

```
✗ publish.yml: job/trigger mismatch

  publish job(s) that can NEVER fire — no matching tag in `on: push: tags:`:
    http  (add: - "http-v*")
  Tagging these silently does nothing: GitHub does not start the workflow and reports no skip.
```

A gate that just says "mismatch" sends the reader back into a 2,000-line YAML
file.

## Reuse

Discovery searched `github actions`, `workflow`, `release gate`. No shared
primitive exists for this and one would not make sense — the check reads *this*
workflow's own structure.

The reuse that applies is internal and is the precedent this follows:
`scripts/test-fly-deploy-workflow.mjs` already tests a workflow file from
`pnpm test`. This is the second of its kind, which is the point at which the
pattern is worth naming rather than repeating a third time by accident.

## Non-goals

- Touching the job definitions. Seven trigger lines is the whole change; the jobs
  were already correct, and rewriting a release path to fix a list is a bad trade.
- Validating what the jobs *do* (working-directory, provenance, OIDC). Separate
  question, and one the successful publishes already exercise.
