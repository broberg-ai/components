# F033.11 — We put the sync secret on the command line

> Parent: [F033 — Deploy provider core (@broberg/deploy-core)](F033-deploy-provider-core.md) · reported by helpdesk, intercom #26994, 2026-09-09.

**Status:** Backlog · **Priority: high** · a real secret leaked and was rotated · affected version 0.1.0

## What happened

helpdesk is the first consumer of `flyLiveRebuildInfra`. On their first run, their 32-byte HMAC sync secret ended up in their log in plaintext — **before the secret had been used for anything.** They rotated it.

`packages/deploy-core/src/deploy/fly-live.ts:270`:

```ts
runFlyctl(["secrets", "set", `SYNC_SECRET=${config.syncSecret}`, "--app", …]);

function runFlyctl(args: string[], cwd: string): void {
  execFileSync("flyctl", args, { cwd, stdio: "inherit" });
}
```

An argument list is readable via `ps` by any process on the machine, and it lands in the shell history of whoever ran it. Neither of those is how helpdesk found it: **the thrown error printed the whole command line back**, secret included.

## Their remedy was half right, and the wrong half matters

helpdesk suggested two things. One is correct. The other would have shipped a fix that leaves the leak, and it is worth writing down why.

> "Og fejlhåndteringen bør ikke gengive kommandolinjen når den indeholder en hemmelighed — `execFileSync` med `stdio:"inherit"` giver den gratis."

**We already pass `stdio: "inherit"`.** It has been there all along, and it does not help. `stdio` governs the *child's* streams; the leak is in Node's own thrown `Error`. Measured:

```
execFileSync('false', ['SECRET=hunter2','--app','x'], { stdio:'inherit' })
→ error.message = "Command failed: false SECRET=hunter2 --app x"
```

Had we taken that suggestion at face value, we would have changed nothing and closed the card.

**Their primary fix is right, and it closes both halves at once:** `flyctl secrets import --stage` reads `KEY=value` from stdin. The value never enters argv, so `ps` cannot see it, the shell history cannot keep it, and the error message has nothing to reproduce. One change removes three exposures — which is the argument for fixing the *source* rather than scrubbing the *output*.

A scrubbed error message would still leave the value in `ps`. Redaction at the reporting layer treats the symptom; not putting it there treats the cause.

## The second finding

`fly-live.ts:230` promises:

> *Provision (or re-provision) the Fly.io app **from scratch**.*

Confirmed: the only flyctl subcommands in the file are `deploy` and `certs add`. No `apps create`, no `launch`.

Against an app that does not exist, helpdesk got:

```
Error: Could not find App "broberg-helpdesk-console"   (appbasic-query)
Error: Could not find App "broberg-helpdesk-console"   (appcompact-query)
error: Command failed: flyctl secrets set … --app broberg-helpdesk-console --stage
```

So "from scratch" means "from an empty app that already exists", and nothing in the failure says so. They created the app by hand and re-ran.

Either behaviour is defensible; **the silence is not.** Create the app (needs an `org` on `FlyLiveConfig`), or fail early naming the exact command. What must not survive is a doc-comment promising something the code does not do — the same shape this repo keeps meeting, where an explanation and the thing it explains have drifted apart.

## Reuse

No Discovery check needed: this is a defect in a function this repo owns, in the package that IS the fleet's deploy primitive. Nothing to reuse and nothing to converge with — helpdesk reported it here rather than working around it locally, which is the reuse rule working as intended.

## What works, recorded on purpose

A report containing only defects is a biased sample, so helpdesk's confirmation belongs in the record too: `--remote-only` is in the shipped dist, and they checked it **before** running anything, because Decision Register `01a08100` forbids a local docker build on the owner's M1. We had it right.

## Non-goals

- A general secret-scrubber over every error this package throws. That is the symptom layer, and it would still leave values visible in `ps`. Keep secrets out of argv instead.
- Managing Fly organisations, volumes or regions beyond what `FlyLiveConfig` already carries.

## Rollout

Patch release. The observable behaviour of a *successful* run is unchanged; what changes is where the secret travels and what a *failing* run prints. helpdesk re-runs against their real Fly app before this closes — including the app-does-not-exist path they hit — because they found it by using it, and a stub we wrote cannot confirm the fix on the surface that burned them.
