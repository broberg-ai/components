# F078.2 — Stack A + B adapters

> Story under **F078 — @broberg/device-stats**. Follows F078.1 (core, `5a5c3c8`).

## The decision that shapes everything: no vendor types

This repo has already paid for the alternative. **F008.8** in `@broberg/auth`: Better Auth's `Auth<O>` is *invariant*, so a plugin-narrowed instance did not satisfy a parameter typed as the vendor's own type, and every consumer had to write a cast. The fix was to take a **structural slice** of what the function actually touches.

This package touches `.headers`, and sometimes `.url`. Typed structurally, **one** function serves:

- Next.js middleware (`NextRequest`)
- Next.js route handlers (`Request`)
- Hono (`c.req.raw`)
- `Bun.serve`
- a plain `fetch` `Request`

… and it cannot break when a vendor renames or re-parameterises its request type.

### The honest consequence

Because of that, **"two adapters" is really one structural function plus two small idiom wrappers.** That is the correct outcome, not a shortfall. Two parallel implementations of the same reading would be duplication with a drift date on it — and this week already produced a worked example of that failure (a helper written once, converted at one of four call-sites, class left open, cost paid on a customer's launch day).

## The one genuine asymmetry

Next's `headers()` inside a server component returns headers with **no URL**. So the launch marker cannot be read there.

The tempting default is `'browser'`. That is wrong, and specifically wrong in the direction that hurts: it would report every RSC render as a browser visit and make **installed-PWA traffic invisible** — in the surface most likely to be measured. So that path returns `'unknown'` unless the caller supplies `searchParams`, and the README says why.

This is the same rule the core already follows: *an unrecognised marker is `unknown`, not silently `browser`.*

## Shape

```ts
// core (framework-free) — the whole reading
deviceFromRequest(req: { headers: HeaderInput; url?: string }, opts?): DeviceFacts

// ./next
deviceFromNextRequest(req)                       // middleware + route handlers
deviceFromNextHeaders(headers, searchParams?)    // server components (no URL)

// ./hono
deviceMiddleware({ onDevice })                   // mounts on a Hono app
deviceFromContext(c)                             // direct read
```

## Ship dark, and it is not a formality here

The Hono middleware **must never throw into the request path**. A device statistic is not worth a 500 on a user's page. AC#5 proves it adversarially with a sink that throws — and asserts the throwing sink *was actually invoked*, so the test cannot pass by the sink never running. A guard that reports success because it never ran is this house's most repeated failure shape.

## Testing against the real frameworks

`hono@4.12.25` and `next@16.2.9` are already in this monorepo, so the tests drive a **real** `new Hono()` and a **real** `NextRequest`.

A mock of a framework tests my idea of the framework — the exact shape that produced three separate corrections in the fleet this week (a README written from memory, a Tailwind class that was never generated, a probe below a pattern's length floor). Where a real object is available, use it.

## F061 bites here for the first time

The package becomes **multi-entry** with this story — precisely the configuration that shipped `@broberg/pwa` 0.2.1 without its react `.d.ts` and blocked a consumer's adoption. The seal is already in place from F078.1; AC#7 proves it still covers the *new* entries by deleting one and watching the build refuse.

## Non-goals

- No sink, no aggregation, no dashboard (F078.4).
- No Tier-1 client collector (F078.3).
- **No publish.**
