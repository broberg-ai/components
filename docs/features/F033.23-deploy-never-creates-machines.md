# F033.23 — Udrulning opretter aldrig maskiner af sig selv

> **Ordre:** ejeren 1/11 2026, ordret: «Jeg vil have styr på udrulning til fly og jeg vil IKKE have vi failer og laver nye maskiner hvert eneste forsøg det er noget fucking rod. Og hvis fly bare ikke dur længere og er blev for ustabilt må vi finde en anden løsning.» Og: «OK til forslaget, ryd op og sørg for at ALLE repos anvender samme flyctl og de andre ting og send hele opgaven til cardmem som info».

## Målt (1/11 2026)
- `flyctl machine list --json` og Flys dashboard viser jævnligt for få maskiner med exit 0 (broberg-id 5 5 1 5 5 1; jam 6 vist, 14 reelt).
- `flyctl deploy` laver så nye maskiner i stedet for at opdatere: Discovery 1 → 3, jam 2 → 4, BID 3 releases på 5 maskiner. Discovery var vokset til 20.
- F033.21/.22 opdager det bagefter og rydder op — men årsagen er at flyctl selv bestemmer hvilke maskiner der findes.

## Rettelse
- Nyt trin **Machine-plan** før udrulning (kun når `expected_machines` er sat og appen har maskiner): tæl pålideligt (3 læsninger, foreningsmængde); fjern overskud ud over `expected_machines` når alle er i én region og én gruppe (stoppede først, så ældste; aldrig maskiner med volumes — de stopper rødt).
- Udrulning: `flyctl deploy … --only-machines <ids> --update-only` — flyctl opdaterer image OG fly.toml-opsætning på netop de maskiner og opretter ingen.
- Færre maskiner end forventet eller en ny app (0 maskiner) → almindelig udrulning som før; Machine-verify efterfølgende er uændret som sikkerhedsnet.

## Flåden
- Oprydning udført 1/11 på ejerens OK: buddy-voice, cardmem-lens, trail-docs, claudestatus-proxy, cms-docs, fd-redirect, trail-widget, webhouse-mail-mcp, webhouse-old → 1 maskine hver. trail-db-001 rørt ikke (begge maskiner har volumen trail_db_data — trail spørges). BID rydder selv (to regioner).
- Alle Fly-repos over på `fly-server-deploy.yml` med `expected_machines` (ejerens ordre) — besked via cardmem_broadcast; cardmem får FYI.
- Én flyctl-version: `flyctl_version` i det fælles workflow (0.5.1) er det ene sted; Macs tjekkes for flyctl/gh (Intel-gh i /usr/local/bin «Bad CPU type» målt af jam).

## Hvis Fly stadig fejler
Måles efter denne ændring: antal røde udrulninger og ekstra maskiner pr. uge. Er Fly stadig ustabil, vurderes alternativ (EU-VM eller anden PaaS) med tal — eget kort.
