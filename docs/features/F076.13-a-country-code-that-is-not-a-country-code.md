# F076.13 — `normalisePhone(n, 'DK')` returns `+DK22680880`

**Status:** in progress · **Parent:** F076 (@broberg/sms) · **Priority:** critical · **2 SP**

Reported by **fd-sundhed** on 2026-08-29 against 0.11.0, measured in the published
package. Reproduced here before anything was written:

```
normalisePhone('22680880')          → '+4522680880'    ✔
normalisePhone('22680880', '45')    → '+4522680880'    ✔
normalisePhone('22680880', 'DK')    → '+DK22680880'    ✗ no error
normalisePhone('22680880', 'dk')    → '+dk22680880'    ✗
normalisePhone('22680880', 'da-DK') → '+da-DK22680880' ✗
normalisePhone('22680880', '+45')   → '++4522680880'   ✗
```

## Why this one matters more than it looks

The second argument is a **dialling code without a plus**. The parameter is named
`defaultCountry`, and an ISO country code is exactly what a reader writes when
they see that name. The type is `string`, so nothing catches it, and **the result
does not fail** — it looks like a phone number, a gateway accepts it, it is
**billed**, and it is never delivered.

This function's own doc says:

> *Refusing matters more than accepting: a guessed number is accepted by the
> gateway, billed, and never delivered — and nothing in the chain reports it.*

Here it is `normalisePhone` itself producing that number.

The value is interpolated in two places with no validation at all:

```ts
if (digits.length === 8) return `+${defaultCountry}${digits}`;
if (digits.startsWith(defaultCountry) && digits.length === defaultCountry.length + 8) …
```

## Decision — and why not the alternative

fd-sundhed offered two shapes: **throw** on anything that is not 1–3 digits, or
**accept both** by looking ISO-2 up in a table.

**Throw.** A country table is a maintenance surface that goes stale, and the
invitation to write `'DK'` comes from the parameter NAME — remove the invitation
and the table is unnecessary. A caller passing `'DK'` has made a programmer error,
not entered bad user input, so an error is the correct answer.

**Rename the parameter to `defaultDiallingCode`.** It is positional, so this
changes nothing at runtime and everything for the reader — the cheapest and
highest-value half of the fix.

**Strip one leading `+`.** `'+45'` is unambiguous and currently yields `++45…`.
Accepting it costs one line and removes a second way to hold it wrong.

**And a postcondition**, which is fd-sundhed's third suggestion and the one that
generalises: the returned string must be `+` followed by digits only. It catches
all four cases above *and* anything neither of us thought of. A guard on the input
proves what I anticipated; a guard on the output proves the property.

## Non-goals

- No ISO country table. No libphonenumber. The package normalises Danish-shaped
  input and refuses everything else on purpose (F076.1).
- Not touching the 8-digit national rule or the E.164 length window.
