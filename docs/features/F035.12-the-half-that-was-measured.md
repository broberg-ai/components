# F035.12 — 0.6.0 fixed the half that was measured

**Status:** Ready · **Epic:** F035 (`@broberg/secret-scan`) · **Written:** 2026-08-30

## Motivation

0.6.0 shipped the announced-secret rule with a plausibility test:

```ts
function plausibleSecretValue(candidate: string): boolean {
  return /\d/.test(candidate) || candidate.length >= 16;
}
```

buddy measured the **digit-free** half (35 of 49 candidates separated cleanly on
length, so the 16-char floor was earned). I then implemented the **converse** —
*any digit means secret* — which nobody had measured, and reported to buddy that
we had broken their corpus with noise like `Kodeord: 2`.

**I was about to make it worse.** buddy went and measured the digit branch on
41,095 texts (24,049 announcements + 17,046 LSD runs, everything from 29/8
excluded so our own night of test strings could not set the floor on our own
fixtures), running *our* regex verbatim out of 0.6.0's `dist` rather than a
re-typing of it:

```
digit candidates, unique, before 29/8   92
  under 16 chars                        35
  16+ chars                             57   (26 plain · 22 JSON · 8 markdown · 1 sk-*)
```

The one line that settles it: **`Sommer2026!` — 11 characters.** An ordinary
Danish password. A 16-char floor on the digit branch leaks it. It is not alone:
`Fejl-ugl!23` (11), `App!1234` (15 with markdown around it), `hunter2` (7). And
in the *same* length band sits unambiguous prose: `35).` · `**404**,` · `base64`
· `AC1).` · `"0.1.0"` · `buddy-1e64c3` · `36+1+32`.

The populations **overlap**. buddy tried two independent form rules
(trailing-punctuation ⇒ prose; letter+digit+symbol ⇒ secret) and both misfiled
cases across the boundary — evidence that this branch is not form-separable, not
that a third rule is waiting to be found.

**Decision: the digit branch stays conservative — no floor.** We keep redacting
`35).` and accept the noise, because the alternative costs a real password. The
asymmetry only points one way on this branch. This is the same *code* 0.6.0
already ships; what this card adds is the **reason**, a named regression fixture
(`Sommer2026!`), and a test that goes red if anyone reintroduces a floor here.

## Reuse

Checked `discovery.broberg.ai/api/search?q=secret+redaction+scanner` — the
capability is `@broberg/secret-scan`, which **this repo owns**. Nothing to adopt;
this is the owner extending its own package. No raw provider integration

## The two defects measured on the PUBLISHED 0.6.0

Probed against a clean install of `@broberg/secret-scan@0.6.0`, resolved version
printed by the probe. Both were reachable only with `{ announced: true }` — my
first probe forgot the flag and reported "nothing is redacted", which is exactly
the trap the package's own docstring warns about. The instrument was wrong
before the code was.

### D1 — the redaction destroys the surrounding text

`(\S+)` runs to the next whitespace, so trailing punctuation is swallowed **into
the replaced span** and disappears from the output:

| input | output |
|---|---|
| `config(password='hunter2')` | `config(password=[REDACTED:announced-secret]` |
| `` `password: hunter2` `` | `` `password: [REDACTED:announced-secret] `` |
| `Se koden (password: hunter2) i filen` | `Se koden (password: [REDACTED:announced-secret] i filen` |
| `password: hunter2, og derefter` | `password: [REDACTED:announced-secret] og derefter` |

The closing paren, the closing backtick, the comma — all gone. A consumer
re-redacting a corpus gets **syntactically broken text back**, and buddy is
holding 41k texts waiting to do exactly that.

This is also buddy's upstream point about the numbers: they hold `hunter2` in 14
variants (`hunter2"`, `hunter2')`, `hunter2\"*.`) where only the first 7
characters are the candidate. That inflates the unique count, shifts every
length distribution upward, and makes any floor measured on raw matches
systematically too low — **including the digit-free 16 we already shipped.**

### D2 — a QUOTED key is never matched at all (a leak, not noise)

The rule requires the label to be followed by `\s*[:=]`. A closing quote or
bracket between the word and the colon breaks it:

| input | detected |
|---|---|
| `{"password": "hunter2"}` | **no** |
| `'password' => 'hunter2'` | **no** |
| `<password>hunter2</password>` | **no** |
| `{password: "hunter2"}` | yes |
| `password = "hunter2"` | yes |
| `PASSWORD=hunter2` | yes |

JSON is the shape a *machine* writes a secret in, and it is the one shape we do
not see. `hasAnnouncedSecret()` returns `false`, which is indistinguishable from
clean: the house failure form, in the guard named after it.

**A correction to my own first reading, from buddy (#24227).** I cited "22 of
their 57 long candidates are JSON fragments" as evidence *for* D2. It is the
opposite: those 22 are fragments our regex **caught**, where `(\S+)` ran on into
the next field — D1 seen from the other side. The leak is the form that never
matches at all, and it is not in that count.

**buddy then measured the actual leak on their whole corpus, and the instrument
was proven before the result was believed.** Positive control: four planted
secrets (an `sk-ant-api03-…`, a Pitch-Vault-shaped key, a PHP hash, an XML value)
were all caught *and* judged secret-shaped. Negative control: `den er hemmelig`,
`et api key felt`, `password reset` were all correctly rejected. Only then the
count — 41,099 texts, 46 quoted-form hits, 43 unique values, **0 secret-shaped**.

So the hole is real and **no leak was realised**. That is why 0.6.1 is not being
rushed out on anyone's behalf, and why D1 — which would hand them back broken
text on a re-redaction — is the one that has to be right first.

## The three findings that came from the gate, not from buddy

These were measured by the auto-review gate on F035.11 against published `0.6.0`
and are carried over from this card's first plan-doc, so consolidating the two
files loses nothing.

**(2) A quoted format-recognised key is flattened — and this PRE-DATES 0.6.0.**

```
'API key: "sk-ant-api03-AAAA…"'  ->  'API key: [REDACTED:announced-secret]'
findings: anthropic-api-key, announced-secret
```

The format pass correctly produces `[REDACTED:anthropic-api-key]` inside the
quotes; the announced pass then matches the whole quoted token and overwrites it
with the generic marker, because the `(?!\[REDACTED:)` lookahead only fires when
the marker is the FIRST character of `\S+`. The redacted text no longer says what
kind of key it was. README:163 states the opposite as fact.

**Fix the lookahead, never special-case the quote.** The defect is that the guard
tests only the first character. A fix that lists quote characters leaves brackets,
parentheses, and every delimiter nobody thought of — and D2 above is the same
lesson from the other direction.

**(3) `hasAnnouncedSecret` and `redactSecrets` still disagree.**

```
hasAnnouncedSecret('password: AKIA…EXAMPLE (elided: our own pre-commit gate correctly refuses the literal form)')  -> true
redactSecrets(same).findings                          -> [aws-access-key-id] only
```

Routing both through `plausibleSecretValue` fixed ONE of the two reasons they
diverge. The other is that `hasAnnouncedSecret` runs on RAW text while the
announced pass in `redactSecrets` runs AFTER the format pass has substituted a
marker. The comment claims they agree; the claim is broader than what was fixed.
Either make them agree, or narrow the comment to the invariant that IS true and
assert that one — never leave a comment broader than the code.

**(4) A README sentence is now factually inverted, and the threshold is pinned by
nothing.**

```
redactSecrets('Adgangskode:\nJeg glemte den', {announced:true})  -> untouched, []
README:160  "One visibly-marked word, never a silent miss — and both halves are tested."
```

It is now precisely a silent miss. There is no "Upgrading to 0.6.x" section at
all, though 0.3.0 and 0.4.0 both have one and 0.4.0's exists for this exact shape
of change. And changing `16` to `24` leaves all 141 tests green: every announced
fixture carries a digit so it never reaches the length branch, the only length
fixture is 25 characters, and the longest rejected one is 6. The harness then
prints "0 uncaught" — a completeness claim it cannot support.

## (8) The exported regexes carry `/g`, so measuring them corrupts them

**Found by cardmem, confirmed here independently, and it is the most dangerous of
the set because it fails in the GREEN direction.** Every `SECRET_PATTERNS[i].regex`
is shared, mutable module state carrying the `g` flag, so `.test()`/`.exec()`
advance `lastIndex` on the object itself:

```
sweep all 39 with lastIndex reset each time   1 match
sweep on the shared /g objects                0 matches   <- silently wrong
sweep with the g flag stripped                1 match
```

Any consumer reading the patterns directly — exactly what you do to AUDIT what
this package detects — gets false negatives and corrupts the objects for every
later caller in the same process. **0.6.1 must export patterns that cannot be
damaged by being read:** strip `g` from the exported copy, or expose an accessor
returning a fresh `RegExp`.

**Reassuring half, also measured: the package's own functions are unaffected.**
`classify` six times interleaved with another value, `hasSecret` and
`redactSecrets` four times each — identical answers throughout. No consumer's
runtime behaviour is wrong today; only direct pattern-reading is.


## (7) `classify` consults a list that `SECRET_PATTERNS` does not contain

**Found by cardmem contradicting my count. We were both right, about different
VERSIONS — and that is worth more than either finding on its own.**

```
0.5.0  exported hue pattern = the BARE 40-char rule, description
       "Philips Hue v2 application key (40 chars, no prefix)" — byte-identical
       to what classify returns                                  <- cardmem right
0.6.0  exported hue pattern = context-anchored (hue/bridge-named field);
       classify STILL answers "(40 chars, no prefix)", a description that
       appears in NO exported entry                              <- this finding
```

0.6.0 moved the bare rule OUT of the exported list into an unexported one, so
cardmem's concern did not go away — it went OUT OF SIGHT. A reader auditing 0.6.0
the documented way would conclude the bare rule was removed. It was not.

cardmem also diagnosed my "0 of 39" as the `/g` trap in (8). It was not: my sweep
reset `lastIndex` before every test, and re-running it both ways on both versions
shows 0.5.0 finds hue WITH the reset while 0.6.0 finds nothing either way. Their
defect is real and my zero was a real absence — two true things that looked like
one contradiction.

```
SECRET_PATTERNS       39 entries, 38 unique labels — what the package EXPORTS
VALUE_ONLY_PATTERNS   not exported — what classify() ALSO consults
```

Measured on published 0.6.0 with the 40-char string `aBcDeF…abcd`:

```
no exported pattern matches it              (checked all 39 by hand)
classify(bare)      -> hue-application-key  "Philips Hue application key (40 chars, no prefix)"
redactSecrets(bare).findings -> []          not redacted
```

**Three surfaces of one package give three different answers about the same
input, and the description `classify` returns does not appear anywhere in the
exported list.** A consumer auditing this package by reading `SECRET_PATTERNS` —
the documented, exported way to see what it detects — cannot see what `classify`
will actually do.

**The design itself is defensible and should be kept.** `VALUE_ONLY_PATTERNS` is
`^…$`-anchored, so it only fires when the WHOLE input is the value. That is right
for `classify` (a vault hands it one value) and would be catastrophic in
`redactSecrets` (an unanchored 40-char rule loose in free text). The split is
correct; **its invisibility is the defect.**

**cardmem's substantive point stands regardless, and is the sharper half:** as a
value-only discriminator, "40 characters, mixed case" is weak. Any 40-char id,
slug, nonce or short hash classifies as a Philips Hue key — confidently. Their
concrete case is not hypothetical: had Christian's Recraft token happened to be
40 characters, it would now be labelled `hue-application-key` rather than
`generic`, and **a wrong label is acted on where a missing one is not.** That is
the exact rule this card's Recraft section states, live in our own package.

**Scope for 0.6.1:**

- **The requirement is a PROPERTY, not a mechanism, and cardmem's phrasing is the
  one to build to: "what does this package detect?" must have exactly ONE answer,
  not two.** Exporting the second list is one way; folding both into one list with
  an explicit `mode: "value" | "text"` field is another. What must not survive is
  a reader being able to consult the documented surface and get a true-looking
  answer that is incomplete. **That property is what was lost between 0.5.0 and
  0.6.0, and it matters more than which list any single rule sits in** — the same
  requirement as `RedactionResult.scanned`, one level up.
- Export patterns that cannot be damaged by being read (finding 8): strip `g` from
  the exported copy, or expose an accessor returning a fresh `RegExp`. An audit
  that corrupts what it audits is worse than no audit.
- Decide the Hue value-only rule on its merits: keep it (accepting that 40-char
  mixed-case will mislabel), gate it behind the caller opting into low-confidence
  value-only guesses, or drop it to the context-anchored form only. **This is a
  judgement about false-label cost, so it is Christian's, not an agent's.**
- Whatever is chosen, `classify` and `redactSecrets` must not be able to disagree
  silently — that is already finding (3) on this card, and this is its second
  instance from a different cause.

**And the method note, which is theirs:** I classified `hue-application-key` by
its INTENT — the name contains "application_key", so it must be name-anchored —
instead of running it. In the SAME message I had described exactly that failure
in myself (a guessed field name returning a confident zero). Reading a regex is
not a measurement; the behaviour test is.

## DECIDED — the Hue value-only rule (Christian, 2026-08-31: "tag begge")

The question was: keep a rule that identifies a Philips Hue key from its length
alone, or require the key's name beside it?

**Neither. Keep the capability, remove the CONFIDENCE.** Deleting the value-only
rule loses something real — a vault only ever holds the bare value, so
context-anchored patterns can never help it. Keeping it as-is produces a
confident wrong label, and this package's own position, written two sections
above about Recraft, is that a confident mislabel is worse than no match because
a wrong label gets acted on and a missing one does not.

**So the weak axis becomes opt-in, and its name states what it is:**

```ts
classify(value)                          // format + context patterns only
                                         //   a bare 40-char string -> null
classify(value, { valueOnly: true })     // also consults the length-based guesses
```

**Why opt-in rather than a confidence field.** A `confidence: "weak"` on the
result is more information, but it is information a caller can ignore by
destructuring `label` — and every caller that ignores it is back where we started.
An opt-in cannot be ignored: a caller who did not ask for weak guesses cannot
receive one. The parameter name is the warning, at the only place it cannot be
skipped.

**The default MOVES, deliberately, and that is a breaking change for `classify`.**
A bare 40-char value that answered `hue-application-key` will answer `null`.
cardmem is the only known caller, they are pinned to 0.5.0, and they have already
written an assertion that will go red exactly here — which is the point: the
decision surfaces rather than slips past. Ship it in the 0.6.1 notes as a named
break, not a footnote.

**This does not resolve the "one answer" requirement — it depends on it.** Once
the value-only axis is opt-in, `SECRET_PATTERNS` under-describing it becomes
worse, not better: a reader would see no length-based rule at all and conclude
none exists. Both ship together in 0.6.1, or neither.

**WHO gets to receive a weak signal — cardmem's rule, and it is better than the
one I wrote.** They declined `{ valueOnly: true }` outright, and the reason is not
about our rule: their vault renders the type as a **fact** — a chip beside the
name, with nowhere to say "low-confidence guess". So a guess they accepted would
become an assertion the owner reads and acts on. Generalised: **the decision to
accept a weak signal belongs to whoever can render the uncertainty. A surface that
cannot show "guess" must not be given guesses.** Write that beside the flag, so the
next consumer does not have to re-derive it.

They also wrote "do not silence this canary with `valueOnly`" *next to the canary*,
which is the right place — it is the tempting fix precisely when CI goes red, and
it would mute the one signal the check exists to deliver.

**One mismatch found while reading their reply, and it is ours to state:
`generic` is NOT a label this package returns.** Measured on published 0.6.0:

```
SECRET_PATTERNS contains a "generic" label   false
classify("abc123")                           null
classify("")                                 null
```

`generic` is cardmem's own fallback for "classify said nothing". Harmless today
because they map it themselves — but at upgrade time a reader who takes the word
from the conversation would expect the string `"generic"` from us and get `null`.
The 0.6.1 notes must say `null`, in those characters, rather than repeat the word
the discussion settled on.

**Not decided here, and left for whoever builds it:** whether `valueOnly` should
also gate the OTHER length-based rules if any exist. The audit that answers that
is "which patterns can fire with no anchor at all", and it has not been run — only
Hue was measured. Run it before writing the flag, not after.

### The measurement that settled it — two repos, opposite answers (2026-08-31)

beacon pushed back on the opt-in design and proposed instead that **lockfiles be
exempted at FILE level**, keeping the broad value-only rule on everywhere else.
Their reasoning was good: the collision that broke the pattern was `pnpm-lock.yaml`'s
base64 digests, so move the exemption to where the problem actually was.

I ran 0.1.8's value-only pattern — `/\b(?![0-9a-f]{40}\b)[A-Za-z0-9-]{40}\b/g`,
lifted from the published tarball, not retyped — over both trees.

| | lockfiles | everything else |
|---|---|---|
| **components** | 1 file, 33 hits | **15 files, 35 hits** |
| **beacon** | 8 hits | **0 prose** (12 deliberate test fixtures) |

A file-level lockfile exemption reaches **half** of our hits and **none** of the
interesting ones. The non-lockfile matches here are not exotic:

```
WebStandardStreamableHTTPServerTransport      a CLASS NAME
gate-the-submit-button-on-status-not-on-      prose from a README
-not-log-a-request-body-and-assume-this-      prose from generated HTML
5-the-format-layer-is-off-in-every-fresh      a FILENAME fragment
```

The charset is `[A-Za-z0-9-]` and it **includes the hyphen**, so any 40-character
run of kebab-case slug or hyphenated English matches. That is not a lockfile
problem and no file-level exemption reaches it. beacon's instinct that digests
would not be the only collider was right; the bigger collider turned out to be
prose.

**And the two trees give opposite answers to the same question**, which is the
whole argument for a parameter rather than a fix:

> **The right default depends on the CALL SITE, not on the quality of the pattern.**
> beacon redacts logs — a false positive costs a masked word in telemetry, a false
> negative costs the bridge key. The commit gate blocks commits — a false positive
> costs a developer a blocked commit on a README. Same pattern, opposite cost.

beacon withdrew #2 on this measurement and accepted the opt-in knowingly, with
their own numbers in hand. Recorded because a consumer who opts in should also
expect false positives on their side if a bridge error message ever carries 40
characters of hyphenated text — they were told that explicitly, and took it.

**Also measured while confirming their report:** 0.6.0's field-anchored form is a
genuine REGRESSION for beacon and they are right not to upgrade. Their two call
paths — `redactDeep()` masking each string separately, and `bridge/errors.ts:48`
passing free text — structurally cannot supply a `hue`/`bridge`-named field in the
same string. They stay on 0.1.8 until 0.6.1, and the whsec half that 0.5.x added
does not reach them (0 occurrences of `whsec` in their repo; their webhook signing
uses their own format).

## Recraft — deliberately NOT given a pattern (now SEVEN, and measured)

cardmem asked whether Recraft has a documented signature. **We do not know of
one**, and their reasoning for not building around it is correct and is now this
package's stated position: a bare mixed-case token with no prefix could only be
matched by a rule that also matches any base64-ish string, which would label other
providers' keys — confidently and wrongly. **A confident mislabel is worse than no
match**, because a wrong label is acted on and a missing one is not.

If a provider's key has no distinguishing shape, the way it gets protected here is
the LABELLED form (`RECRAFT_API_KEY = "…"` in source), which is exactly what the
six patterns above already do — making Recraft the **seventh**, and the cleanest
example of the class: there is no version of a value-pattern for it that works.

**ai-sdk measured the form (never the value) and checked the authoritative source
first, and the conclusion is against building it:**

```
prefix            NONE
separator         NONE
charclass         base62
length            64      (the whole key; no random part to isolate)
case mix          32 upper · 24 lower · 8 digit
samples           1
Recraft's docs    no key format documented at all — only
                  `Authorization: Bearer $RECRAFT_API_TOKEN`
```

**My own suggestion was wrong and is recorded as wrong.** I proposed that with
n=1 we ship a deliberately looser rule — a length RANGE instead of a fixed number
— until more samples arrive. That treats the problem as sample size. It is not.
An anchorless `[A-Za-z0-9]{64}` has a high false-positive rate **by construction**,
so a looser version of it is strictly worse, not safer.

**Measured against this repo (778 tracked files), because their argument deserved
a number rather than agreement:**

```
[A-Za-z0-9]{64}                        8 matches
same, REQUIRING upper+lower+digit      6 matches   ← barely discriminates
```

The mixed-case requirement was my attempt to save the pattern — a hex hash has no
uppercase, so requiring mixed case should have excluded hashes. It drops 8 to 6.
What survives is `pnpm-lock.yaml` integrity hashes and base64 embedded in a
mockup: mixed-case, base62, exactly 64. **So the discriminator does not
discriminate**, and the surviving matches are 100% wrong — every one of them is a
hash or an asset, none is a credential. The failure is not volume; it is that
everything it catches is a false positive.

**Do not ask Christian for a second Recraft token.** ai-sdk offered to, so we
could see whether 64 is fixed. It cannot change the decision: even a
*confirmed*-fixed 64 is unusable as a bare-value rule, so the sample would buy a
fact we would not act on.



## Open question — is `announced` opt-in the wrong default?

Raised by ai-sdk and buddy independently, on the same night, both pointing at the
same thing: **my own probe forgot `{ announced: true }` and got back "nothing is
redacted".** ai-sdk's wording is the one to keep — *"if a forgotten flag gives a
calm 'nothing to do', it is not a warning that is missing, it is the default that
is wrong."* A docstring is not a control, and this package's docstring warns about
exactly this trap because buddy nearly filed the same false report in August.

**Not decided here, and deliberately not decided by an agent.** The reason to
leave `announced` opt-in today is measured, not preference: the digit branch still
eats prose (`Kodeord: 2`), so flipping the default now would corrupt text for every
consumer at once. The order is therefore fix first, default second — this card
ships 0.6.1, and only then is the question real.

What already exists and would have prevented my own error: **`RedactionResult.scanned`
reports whether the axis ran at all**, so "we looked and found nothing" is
distinguishable from "we never looked". Nothing forces a caller to read it. Both
peers were told to assert on `scanned`, not only on `findings`.

Christian's call when 0.6.1 is out: flip the default (a breaking change every
consumer must be told about), or keep opt-in and make the un-scanned axis visible
in the result in a way a caller cannot ignore.
