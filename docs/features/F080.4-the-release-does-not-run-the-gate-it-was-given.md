# F080.4 — the turbo fix closed the half that was named

**Status:** In progress · **Epic:** F080 (the repo's own gate) · **Written:** 2026-09-10

## What happened

Three publishes failed today on the same line while every local run was green:

```
error TS2307: Cannot find module '@broberg/apikey' or its corresponding type declarations.
```

The cause I found was real: `turbo.json` gave `typecheck` no `dependsOn`, so nothing built the sibling whose types the F035.14 fixture imports. Locally `packages/apikey/dist` was lying there from an earlier build, which is why the green was ambient rather than earned. Fixed:

```json
"test":      { "dependsOn": ["build", "^build"] },
"typecheck": { "dependsOn": ["^build"] }
```

Proven on the task graph and then in CI: `test.yml` step 7, *Typecheck (39 packages)*, went **green on main for the first time today** on commit `d164f8e`.

**And the publish failed again anyway**, 18:33, same error, same file, same line.

## Why — there were two mechanisms and I fixed one

```yaml
- name: Typecheck
  working-directory: packages/secret-scan
  run: pnpm typecheck            # → the PACKAGE's script: `tsc --noEmit`
```

`working-directory` makes pnpm run the package's **own** script. Turbo is never invoked, the task graph is never consulted, and no dependency is ever built. The same is true of the job's `Build` and `Test` steps.

So the workspace gate and the release ran different commands, and only one of them was fixed. That is the shape this whole session has been about — *a guard shaped by the REPORT closes only the half that was named* — arriving in my own work: the report was "typecheck fails in CI", and I never asked whether the release runs the same command.

It is also the exact argument `publish.yml` already makes about itself, one section over, for `workflow_call`:

> *"a gate and the release it guards must not be able to drift apart, and the way they drift is that somebody fixes one of the two."*

That comment was written about the *suite*. The same drift was sitting in the typecheck and build steps directly beneath it.

## Scope — measured, not assumed

Exactly **one** of the 40 packages declares a `workspace:` dependency:

```
@broberg/secret-scan  →  @broberg/apikey@workspace:*
```

So the narrow fix is today's complete fix. That is precisely the reason it needs a seal rather than only a patch: the **second** package to grow one gets no warning, and finds out when a release goes red.

The pin itself is right and stays. `workspace:*` is the tightest pin there is — it resolves to this repo's own source, which is what makes the F035.14 fixture minted by the *real* minter and unable to drift from it. The pin was never the problem; the pipeline was.

## Design

### 1. The fix

One step, before `Typecheck`, in `publish-secret-scan`:

```yaml
- name: Build workspace dependencies
  run: pnpm turbo run build --filter="@broberg/secret-scan^..."
```

`^...` is "the dependencies of, **excluding** the package itself". Verified on the task graph rather than by re-running a release:

```
$ npx turbo run build --filter="@broberg/secret-scan^..." --dry=json
@broberg/apikey#build
```

One task. Not the package's own build (that is the next step, and doubling it would blur which stage failed).

### 2. Why not convert all 40 jobs to turbo

It is the tidier answer — one task graph, no second mechanism — and it is rejected here. Forty jobs edited at once, in a workflow whose failure mode is *a job that silently never runs*, on a file this repo has already been bitten by twice (F080.2: seven jobs that could never fire; a dedent that registered no triggers at all). The blast radius of the tidy fix is every release; the blast radius of the narrow one is a package that is already broken.

The seal below is what makes the narrow fix safe to keep.

### 3. The seal

A check that reads both sides and compares them:

> **Every package declaring a `workspace:` dependency must have a dependency-build step in its publish job.**

Both halves are derived, neither is a list: the packages come from `packages/*/package.json`, the jobs from parsing `publish.yml`. A hand-written list of "packages that need this" is the thing that goes stale silently, which is the failure being sealed.

### 4. Both directions, because a rule that reddens correct jobs gets deleted

- **RED when it should be:** remove the step from `publish-secret-scan` → non-zero, and the message names the package *and* the job.
- **GREEN where it should be:** the 39 packages with no `workspace:` dependency are not required to have the step. Without this half the check would redden every correct job on the day it shipped, and a gate switched off on day one still *looks* like coverage.

### 5. Where it runs

In `pnpm test`, so it blocks locally and in CI — the same gate `publish.yml` calls through `workflow_call`. A check that only ran inside the job it guards could not warn anyone before they tagged, which is the whole complaint above.

## The version is bumped, never re-pointed

`secret-scan-v0.9.2` exists and failed. The fix ships as **0.9.3**.

Re-pointing a tag is what cost `0.8.0` this morning: the tag was moved, pointed at a 0.7.2 commit, and the version guard correctly refused it. A tag is a claim about a commit; moving it makes every earlier statement about that tag false.

## Non-goals

- Converting the other 39 publish jobs to turbo. See §2 — the seal covers the risk without the blast radius.
- Adding `^build` to turbo's `build` task. A package whose *build* reads a sibling's types would need it; none does today, and widening the graph on a hypothesis is how a build gets slow for no measured reason.
