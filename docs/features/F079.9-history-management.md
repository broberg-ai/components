# F079.9 — History management: an overflowing conversation must not become a dead one

> Parent: [F079 — `@broberg/chat`](./F079-chat.md)

## The defect, measured by cms in their own code

Christian asked them *"why does the chat grow per message?"* The answer was that it has **no history handling at all**:

| Measured | |
|---|---|
| `chat-interface.tsx:166` | builds the request from the **whole** conversation — no slice, no window, no compaction, in neither client nor route |
| `route.ts:149` | `maxTokens` is the **output** limit. Nothing handles input overflow |
| `route.ts:244` | on an exceeded context window the provider 400s and **the raw error text is passed to the user** |

**The one sentence that has to survive everything else here:**

> Because nothing truncates, **a retry resends the same oversized payload.** The conversation is not expensive, it is **dead** — and it dies after a long session, which is precisely when there is most to lose. The user can only start over.

So the first acceptance criterion is not *"the message was shortened"* — that can be passed by something that still leaves the conversation dead. It is: **after an overflow, the next turn on the SAME conversation succeeds.**

## Scope: all four — Christian, 2026-08-27

> *"Vi skal have ALT med i components udgaven og de detail udgaver der senere arver components udgaven."*

## But they are not four items in one menu

cms's structural point, and it is the one that decides whether the module is coherent:

**Three are mutually exclusive strategies.** You pick one per conversation.

| Strategy | |
|---|---|
| **Sliding window** | keep the last N turns |
| **Compaction** | summarise the old, keep the recent verbatim (à la `/compact`) |
| **RAG over history** | store everything, retrieve only what is relevant |

**One is a layer underneath all three.** Prompt-caching is not an alternative: the provider remembers the unchanged prefix. **It stops the price growing, never the conversation**, and it applies whichever strategy is chosen.

> Build caching as a sibling choice and a consumer can select *caching and no strategy* — and the conversation still grows until it dies. **That is exactly the state cms is in today.**

So: a consumer may choose a **different** strategy from the default, but can never end up with **none**. The default is one of the three, never "none". And the acceptance criterion that catches it is one that **fails on "caching configured + no strategy"**.

## Delivery order — Christian

> *"Og vi slutter med RAG da vi skal have noget i drift med FD Sundhed FØR vi har RAG klar."*

1. **Sliding window** — the simple floor.
2. **Compaction** — the one that preserves context.
3. **Prompt-caching** — live, not dark (see below): it works today on 0.30.0.
4. **RAG over history** — **last**, after FD Sundhed is in production.

Each of 1–3 is useful and shippable alone. The card records which are done rather than implying the set.

## Compaction changes what the MODEL sees, never what the USER can read

cms's sharpest contribution, and it was not in the acceptance criteria until they said it:

> Compaction replaces old turns with a summary. If a user expects to read a session back **verbatim** — and a content assistant is exactly the kind of thing people go back into — then *"the conversation lives on"* is not enough.

**They are two different things, and a module that conflates them deletes people's work in good faith.**

So: the original transcript stays retrievable word for word after a compaction, and a test asserts the exact original turns survive a compaction that shrank what was *sent*.

This is not hypothetical, and the picture is bigger than it first looked. cms's own correction, after the sanne session measured it: **there are three chats in that world, not one.**

| | |
|---|---|
| **cms's chat** (`webhouse.app/admin`) | Sanne uses it as her internal content helper. No coupling — `api/cms/chat` 0 hits, `cms-chat-client` 0 hits, `webhouse.app/api` 1 hit and it is `/api/upload`. An internal swap cannot break a contract. |
| **sanneandersen's OWN admin chat** | `/api/admin/chat/conversations`, its own prompt, its own tools, its own SQLite on their Fly volume. 100% self-hosted. |
| **Eir** | their public chat. A third system again. |

sanne's own words, worth keeping verbatim: *"Regn os ikke med som afhængig af jer, og regn os heller ikke som urørt af components' modul."* They are not a **consumer** of cms's chat; they are the **owner** of two others, each with its own prompt, tool set and history table.

Two consequences: there is one more potential consumer than assumed, and **"cms adopts" does not prove the inheritance path for them** — their chats have a different shape.

Volume, measured rather than sensed: 14 conversations / 56 messages in their admin chat, last touched 26/8; Eir has 28. Low volume, so low risk in a swap — but it is a number, not a feeling. And people may still expect to re-read those conversations word for word.

## cms is the first consumer, and they are now waiting on us

Christian approved it. The consequence is a real dependency rather than a courtesy: **cms have cancelled their temporary floor** rather than build something they know they will throw away. Their own F177.3 keeps only the half that is genuinely theirs — the ceiling on the system instruction's size, which grows with the site's schema and not with the conversation, and which we cannot solve for them.

## Two things already measured — do not repeat the work

### The context window does not exist in the model registry

Measured by cms, confirmed by ai-sdk. A model object's fields are **exactly**:

```
["id", "alias", "provider", "available", "status", "note", "source"]
```

No `contextWindow`, no `maxInputTokens`, on any of the 10 models. So this cannot be the single source today — **whatever the alias problem does.**

> **And the trap is sharper than an absence.** The only number that *looks* like it is `maxTokens`, which is a **per-call OUTPUT limit**. Look it up as "the window" and you get a number for something else entirely — worse than no number, because it looks like an answer.

The limit is therefore **declared by the consumer**, and the gap is filed with ai-sdk. A test asserts nothing here derives a limit from the registry.

### Mistral DOES cache — we were never asking for it

**Corrected the same day, and the correction is the interesting part.**

ai-sdk's first answer was *"measured: no caching"* — two identical calls, a 2,411-token shared prefix, `cached_tokens = 0` both times. **cms rejected it**, correctly: that showed caching did not *happen*, not that Mistral *cannot*. Their a/b/c taxonomy was the whole contribution, and the answer turned out to be (c): **the adapter was discarding `prompt_cache_key`.**

Re-measured live through `ai.chat` on **0.30.0**:

```
WITHOUT a key:  call 1 cached=0   call 2 cached=0      (still 0 at 57,210 tokens)
WITH a key:     call 1 cached=0   call 2 cached=8,784  call 3 cached=8,784
                $0.004411 → $0.000458   —   90% cheaper
```

Cached tokens bill at 10% of the input price, now in `pricing.ts` for every Mistral row.

**And this module is the best case there is.** A fixed system instruction, identical on every message, is exactly the shape prompt-caching was built for — and exactly the shape a shared chat module has. So caching **ships live, not dark**:

```ts
ai.chat({ system, messages, promptCacheKey: conversationId })
```

**The key is ours to generate, deliberately.** ai-sdk does not invent one: only the caller knows what "the same conversation" means, and an SDK-invented key would either collide across tenants or never hit.

> ⚠️ **A cache key IS a shared-prefix identity.** Never reuse one across tenants. So the key is derived from the conversation *and* the tenant, and a test asserts two tenants with identical transcripts get **different** keys — the same isolation rule as `kbId` in [F079.2](./F079.2-trail-retriever.md).

**And no guard is built on `cacheReadTokens`.** ai-sdk wrote the ambiguity down rather than papering over it: `0` means both *"no cache hit"* and *"this provider does not report it"*. The price is right either way; the field cannot answer *"did caching happen?"*. An absence read as a verdict — this week's shape, one more time.

## The other two things the module owns

- **A comprehensible warning *before* overflow** — a typed frame, not prose the widget has to pattern-match, and not the provider's raw 400.
- **Nothing dropped silently** — what was removed or compacted is reported, so nobody is quietly answered from half a conversation.

## Why it belongs here and not in cms

cms drew the line themselves, correctly:

- **Theirs:** the size of the *instruction*. Their schema, their prompt builder — 6,619 tokens on sanneandersen, 56% schema.
- **Ours:** history handling is **completely generic**. Every chat in the fleet has the identical problem, and if cms hand-rolls a window, trail does something else and sanne a third, we have drift on the most load-bearing part of a conversation.

While this is unbuilt, cms keeps a temporary floor in their own repo and will remove it when this lands — **and their card says explicitly that the floor is not the fix.** Worth copying.

## Non-goals

- Not summarisation as a product feature. Compaction keeps a conversation alive; it is not a digest for users.
- Not persistence. What is stored and for how long is F079.6.
- Not the instruction's own size — that belongs to whoever writes the prompt.
