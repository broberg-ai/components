# F079.9 — History management: an overflowing conversation must not become a dead one

> Parent: [F079 — `@broberg/chat`](./F079-chat.md)

## Filed by cms, measured in their own code

Christian asked them *"why does the chat grow per message?"* The answer was that it has **no history handling at all**:

| Measured | |
|---|---|
| `chat-interface.tsx:166` | builds the request from the **whole** conversation — no slice, no window, no compaction, in neither client nor route |
| `route.ts:149` | `maxTokens` is the **output** limit. Nothing handles input overflow |
| `route.ts:244` | on an exceeded context window the provider 400s and **the raw error text is passed to the user** |

## The part that makes this urgent

**Because nothing truncates, a retry resends the same oversized payload.**

So the conversation is **permanently unusable** from the moment it tips. The user can only start over and lose everything.

> It is not an expensive conversation. It is a **dead** one — and it dies after a long session, which is precisely when there is most to lose.

That is the defect this story exists to make impossible, and it is what the first acceptance criterion asserts: after an overflow, **the next turn on the same conversation succeeds.**

## Why it belongs in the package and not in cms

cms drew the line correctly themselves:

- **Theirs:** the size of the *instruction*. Their schema, their prompt builder — 6,619 tokens on sanneandersen, 56% schema. They fix that.
- **Ours:** history handling is **completely generic**. Every chat in the fleet has the identical problem, and if cms hand-rolls a sliding window, trail does something else and sanne a third, we have drift on the most load-bearing part of a conversation.

Reuse-first, in its literal form.

## The three things the module owns

1. **A strategy that is chosen, not assumed** — sliding window *or* compaction (à la `/compact`), never one hard-coded. They behave differently enough that guessing is wrong for somebody, so there is no silent default. The test asserts both bring an overflowing transcript within the limit **and that they produce different transcripts** — otherwise the choice is decorative.
2. **One source for the limit** — not a number copied into every consumer's chat, where a model change leaves it wrong somewhere nobody looks.
3. **A comprehensible warning *before* overflow, and a way forward that keeps the work** — a typed frame, not prose the widget has to pattern-match, and not the provider's raw 400.

## ⚠️ The registry is the obvious source and it is not yet trustworthy

cms's second request — read the context window from the model registry as one source — is right in shape and **blocked on a defect measured the same day**.

fd-sundhed found `@broberg/ai-sdk` 0.21.1 disagreeing with itself:

```
resolveModel('smart')      → claude-sonnet-4-6      (aliases)
ai.chat({ tier: 'smart' }) → mistral-large-latest   (DEFAULT_TIER_MAP)
```

Same word, two answers. So before the registry becomes the single source of the *limit*, ai-sdk must be asked whether its context-window numbers are authoritative **for the model that actually answers** — not for the one the alias table names. If the answer is no, the limit is declared by the consumer and the gap is filed.

Reading a number from a table that is wrong about *which model runs* is how you get a limit that is correct for a model nobody called.

## An open question, asked rather than assumed

**Does Mistral support prompt caching?** cms's SDK usage already reports `cacheReadTokens`, so the field exists — but nobody has measured whether Mistral actually caches. It does not change the overflow defect; it changes the **price** of resending the same instruction 200 times. Asked of ai-sdk, recorded here either way.

## While this is unbuilt

cms is building a temporary floor in their own repo — a warning before overflow and a way forward — and will remove it when this lands. **Their card says so explicitly, so nobody mistakes the floor for the fix.** That is the right shape and it is worth copying.

## Non-goals

- Not summarisation as a product feature. Compaction here exists to keep a conversation alive, not to give users a digest.
- Not persistence. What is stored, and for how long, is F079.6.
- Not the instruction's own size — that belongs to whoever writes the prompt.
