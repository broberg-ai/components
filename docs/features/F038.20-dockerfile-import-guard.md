# F038.20 — Discovery down: a module the Dockerfile never copied

## What happened
7 Oct 2026, ~15:10–15:47 dansk tid. F098.1 (7fc847e) added `apps/discovery/webmcp-lab.ts` and imported it from `server.ts`. The Dockerfile copies app sources **one file at a time**, and nobody added a line for the new file. The image built fine; the server crashed on boot with `Cannot find module './webmcp-lab'`. Fly restarted both machines 10 times each, then left them stopped. Every request timed out, and `cardmem_session_start` served `discovery_reuse.unavailable` to the whole fleet.

Service was restored by redeploying the previous image (v364) — the WebMCP lab is offline until the fix ships.

## Why nothing caught it
- The discovery vitest suite imports `server.ts` from the source tree, where the file exists. It cannot see what the image lacks.
- The discovery deploy job ran even though the `test` workflow was red on the same push (unrelated failures in app-shell + greppable). The deploy is not gated on tests — a separate hole, noted below, not fixed here.

## Fix
1. Add `COPY apps/discovery/webmcp-lab.ts ./webmcp-lab.ts`.
2. `apps/discovery/dockerfile-imports.test.ts`: walk the local (`./`) import graph from `server.ts` and require a `COPY apps/discovery/<f> ./<f>` for every file. Control test asserts the walk finds the known modules. Mutation: delete the new COPY line → red with `['webmcp-lab.ts']`.

## Not in scope (flagged to owner)
- Gating the discovery deploy on the test workflow (harness rule 2). Right now the test workflow is red for unrelated reasons, so gating it would also block this fix.

## Reuse
No shared capability involved — a repo-local build guard. Checked: no `@broberg/*` package covers Dockerfile/import consistency.
