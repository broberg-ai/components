# F033.12 — every SPA 404s on its own routes, and four test layers say it works

**Status:** Ready · **Epic:** F033 (`@broberg/deploy-core`) · **Written:** 2026-09-11 (dansk tid)
**Filed by:** helpdesk · **Confirmed here against the source before accepting**

## The report

Measured in production on `broberg-helpdesk-console` (helpdesk.broberg.ai):

```
/                        200
/velkommen               404
/velkommen/              404
/velkommen/index.html    404
/assets/                 404
```

Their invitation and forgot-password links — the entire path into the product for
user number two — were dead in production.

## Confirmed, with the line

`src/deploy/fly-live-assets.ts` is the server we generate and deploy. `serveStatic`
has three fallbacks, and none of them is an SPA fallback:

```js
if (rel === "") rel = "index.html";            // the bare root ONLY
...
if (s.isDirectory()) → index.html inside it    // needs a real directory on disk
catch: `${full}.html`                          // /velkommen → velkommen.html
catch: 404.html, served with STATUS 404
else:  404
```

An SPA route matches none of them: there is no `velkommen` directory and no
`velkommen.html`, because the route exists only inside the client bundle.

`FlyLiveConfig` has no field for it either — `appName`, `region`, `volumeName`,
`syncSecret`, `customDomain`. Read, not recalled.

## Why this is a card and not a README note

helpdesk's own argument, and it is the strongest part of the report:

> **Vite's dev server answers `index.html` on any path.**

So every local check is green on a surface that 404s live — including a full Lens
run in a real browser, which is the strongest verification this fleet has. Four
layers green, production dead. It cost a deploy to find, not a test.

That is this repo's recurring shape with a new source: not a check that lies, but
a test ENVIRONMENT whose behaviour differs from production in exactly the way the
test is supposed to rule out. The dev server is kinder than the real one, so the
happy path is the only one anyone ever sees.

And every SPA in the fleet deployed this way has it.

## What they did not find, and it changes the design

**A partial escape hatch already exists.** Ship a `404.html` that is a copy of
`index.html` and the SPA boots on any route. But line 70 serves it with
**status 404**:

```js
try { await access(join(CURRENT, "404.html")); return fileResponse(join(CURRENT, "404.html"), 404); } catch {}
```

So the route works for a human and lies to everything that reads the status: a
crawler, an uptime probe, a `fetch` branching on `res.ok`, any consumer treating
404 as "this page does not exist". It is the week's failure form inverted — not a
failure reported as success, but a **success reported as failure**.

So the fix is not "add a fallback". The mechanism is there. It is: *let a consumer
say this is an SPA, and then answer 200.*

## The trap in the obvious implementation

If the fallback catches everything, a missing `/assets/app-abc123.js` returns
`index.html` with status 200. The browser then fails on an HTML file it expected
to be JavaScript — a parse error naming the wrong problem — and **a deploy that
dropped a file looks like a working deploy.**

That trades a visible 404 for an invisible one, which is strictly worse than the
bug being fixed. AC#3 and the extension guard in AC#4 exist for exactly this, and
AC#6 requires the mutation that proves it.

## Reuse

Discovery checked per F217 (`discovery.broberg.ai/api/search` for `spa fallback`,
`static hosting`, `deploy`). Nothing to adopt: the server being fixed is a string
this package GENERATES and ships to Fly, so no dependency can reach it. The fix
is in `@broberg/deploy-core` or nowhere.

The reuse that matters here is the one helpdesk already honoured: they did **not**
fix it locally. See Rollout.

## Design

```ts
export interface FlyLiveConfig {
  …
  /** Answer index.html (200) on an unknown ROUTE. Default false. */
  spaFallback?: boolean;
}
```

and in `serveStatic`'s existing catch, BEFORE the `404.html` branch:

```
unknown path
  ├─ `${full}.html` exists            → serve it            (unchanged)
  ├─ spaFallback && looks like a ROUTE → index.html, 200   (new)
  ├─ 404.html exists                  → serve it, 404      (unchanged)
  └─ 404                                                   (unchanged)
```

**"Looks like a route" is the whole design, and it is two clauses:** the request
ACCEPTS html, and the path has no file extension. Either alone is not enough — an
Accept-header check alone would hand `index.html` to a `fetch()` for a missing
JSON file, and an extension check alone would hand it to a curl for `/velkommen`
that wanted a 404.

## Non-goals

**Defaulting it ON.** Tempting — the consumers who need it are exactly the ones who
will not read the field — but this package deploys live fleet sites, and a
static-site consumer relying on a real 404 (or on `404.html`) would silently start
serving a 200 for every typo. Not worth it on a patch. The README and this
plan-doc carry the warning instead, and helpdesk's measurement is the argument for
any future owner who wants to revisit it.

**A `notFound?: "index.html"` shape.** More general-looking and worse: it invites
`notFound: "/some/other.html"`, which is a second code path with no consumer, and
it does not say whether the answer is 200 or 404 — which is the entire defect.

## Rollout

1. Build + seal here, mutation-proven both directions.
2. Publish as a MINOR (new optional field, default preserves today's behaviour).
3. helpdesk sets the flag, measures `/velkommen` → 200 **in production**, and only
   then drops their `/?velkommen=<token>` query form (AC#7).
4. Tell the fleet it is a POSSIBILITY, never a task — Christian alone decides
   adoption.

**Nothing of theirs needs undoing.** They put the link on the root as a query,
which needs nothing from the host, and their console still reads the path form —
so the prettier link starts working the day this ships, with no coordinated change
on their side. That is what not-building-around-it looks like when it is done
well, and it is worth copying.
