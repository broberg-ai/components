# F010.8 — Per-route rate-limit max, `X-RateLimit-Limit`, record projection

> Story under **F010 — @broberg/apikey**. Consumer-filed gap from **beacon** (#18998), reported while adopting F010.7's error hooks.

## Motivation

beacon adopted `honoApiKeyMiddleware` in 0.2.0 and deleted their own copy. They could **not** adopt `honoRateLimit`, and the reason is worse than a missing feature — **the adapter hides a capability the core already has**:

```ts
// rate-limit.ts — since v0.1.1
check(key: string, opts: number | { now?: number; max?: number } = {})

// hono.ts — never passes it
const r = await limiter.check(key);
```

So one limiter cannot serve admin 600/min and write 300/min, and beacon reaches **around our adapter to our own core** to get it. That is the adapter failing at its one job.

Second: the adapter sets `X-RateLimit-Remaining` but never `X-RateLimit-Limit`. A client can see how much is left but not *of what* — which makes the remaining count uninterpretable. With a per-route max this gets worse, because the cap now varies by route.

Third, and beacon was careful to classify it correctly: `c.set(ctxKey, record)` puts the **whole** record on the context, `hash` included. A sha256 is not a usable credential, so this is **not a vulnerability** — but it is more than any handler needs, and a future `c.json(caller)` somewhere would serve it. They added a local narrowing plus a test proving it, and suggest the package offer a `project(record)` option.

All three apply identically to the **Next** adapter, which beacon does not use — unreported, same defect.

## Scope

1. **`RateLimitResult.limit`** — the *effective* max used for that check. The result is the only place that knows whether a per-call override was in play, so the header can be honest without the adapter reading the limiter's `private readonly max`.
2. **`keyFn` returns `string | { key, max? }`** in `honoRateLimit` **and** `nextRateLimit`. A plain string keeps working.
3. **`X-RateLimit-Limit`** on both the allowed path and the 429, from `result.limit`.
4. **`project?: (record: T) => unknown`** on `HonoApiKeyOptions` and `ApiKeyAuthOptions`. Default identity — unchanged behaviour — but a consumer can hand the handler a narrowed caller instead of the storage row.
5. README: per-route max, both headers, and an explicit note that the full record (hash included) reaches the handler unless `project` narrows it.

### Non-goals

- **Not** retrofitting F010.7's `onUnauthorized`/`onForbidden`/`onLimited` hooks into the Next adapter. That asymmetry is real and now documented, but it is a separate parity story — folding it in here would hide a second change inside a filed fix.
- Not owning route policy. beacon keeps their role rules in `authorize`, correctly — the package must never own which roles may call what.
- No change to the sliding-window algorithm or the store contract.

## Architecture sketch

```ts
export interface RateLimitResult {
  allowed: boolean;
  remaining: number;
  resetAt: number;
  limit: number;          // NEW — the effective cap for THIS check
}

type RateLimitKey = string | { key: string; max?: number };

honoRateLimit(limiter, keyFn?: (c) => RateLimitKey, opts?: { onLimited? })
// admin route:  keyFn: (c) => ({ key: tokenId(c), max: 600 })
// write route:  keyFn: (c) => ({ key: tokenId(c), max: 300 })   — one limiter
```

`limit` is additive on an interface consumers only ever *read*, so it is not a breaking change in practice.

## Dependencies

None.

## Reuse

beacon filed instead of forking — again — and was precise about severity (they explicitly said the record exposure is *not* a vulnerability, which is why it is a documentation + option story and not a security fix). Fixing the Next adapter at the same time is the reuse rule applied to ourselves: the defect was reported in one adapter and exists in two. Precedent: F010.7, F008.8, F053.7.

3. `pnpm typecheck` + `pnpm test` green.
