# F035.19 — `announced: 'code'`: the announced axis for SOURCE CODE

## Problem

pitch (intercom #1328, 30/9 2026) wanted secret-scan as a pre-push gate against GitGuardian findings. GitGuardian flagged «Generic Password» on

```ts
body: JSON.stringify({ currentPassword: 'a', newPassword: 'abcdefgh' })
```

0.11.1 with `{ announced: true }` returns `findings: []` on that line, reproduced 1/10. Two reasons, both deliberate for PROSE:

1. `\bpassword` needs a word boundary, so `newPassword` (a compound identifier) never matches.
2. `plausibleSecretValue` rejects a value with no digit and under 16 chars (buddy's prose measurement: 35/35 such candidates were words). `abcdefgh` is exactly that shape.

And the reverse: `apiKey: nanoid(32)` and `apiKey: process.env.RESEND_API_KEY` ARE flagged, because in prose `\S+` after a label is the value, while in code it is an expression.

The prose rule is right for prose. It is the wrong rule for code, and the package documents that precision "depends entirely on WHAT IS BEING SCANNED" and that only the caller knows. So the caller says so.

## Design

`announced?: boolean | 'code'`. `true` keeps today's prose rule, byte for byte. `'code'` swaps the rule for:

- **label** = an identifier CONTAINING a credential word (compound allowed: `newPassword`, `DB_PASSWORD`, `clientSecret`, `apiKey`, `KODEORD`), optionally quoted as an object key.
- **separator** `:` or `=` (not `==`/`===`).
- **value** = a QUOTED string literal (`'…'`, `"…"`, `` `…` ``), no whitespace, no `${`, at least 4 chars. Quoted is the whole point: an unquoted value is a call, a variable or an env reference, never a hardcoded secret.

Noise guards, each from a measured hit (below): label ending in a descriptor (`Path`, `Name`, `Id`, `File`, `Url`, `Label`, `Field`, `Env`, `Type`, `Hint`, `Placeholder`, …); a value that is itself a credential WORD (`"Adgangskode"`, `"Password"`); a value equal to the label (`PASSWORD_TOO_SHORT: "password_too_short"`); the branch of a ternary (`? "wrong_password" : …`); a `type X = '…'` alias.

`hasAnnouncedSecret(text, mode?: 'prose' | 'code')` and `hasSecret(text, { announced: 'code' })` route through the same predicate, keeping the existing invariant (true ⇒ redaction happens).

## Measured, draft rule, 1/10 2026

2,848 tracked TS/JS files across 13 local fleet repos: 315 hits, 280 of them in test/spec/fixture files (`apiKey: "re_x"`, `password: "hunter2"`). Those are exactly GitGuardian's class and correct for a pre-push gate. 35 outside tests: most are hardcoded defaults/fixtures in scripts (also GitGuardian-class); ~12 were noise, and each noise shape has a guard above. Final numbers are recorded in the release commit.

## Out of scope, stated

- `.env` files (unquoted literals). Code mode reads unquoted as an expression, so `DB_PASSWORD=hunter2` in `.env` is NOT caught by `'code'`. Use prose mode for env files.
- Comparisons (`password === 'x'`).
- Parity with GitGuardian in general. This closes the reported class, not their whole detector.

## Reuse

This IS the shared package (`@broberg/secret-scan`). The alternative, pitch keeping `lib/no-literal-passwords.test.ts`, is the local workaround the reuse rule exists to retire. No new dependency.
