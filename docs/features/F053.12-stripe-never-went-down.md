# F053.12 — Stripe never went down. It moved a field, and everything kept answering 200.

**Status:** In progress · **Epic:** F053 (`@broberg/stripe`) · **Written:** 2026-09-08
**Ordered by:** Christian, 2026-09-08 — «Der skal bygges et Stripe API tester der skal køres som et cron job»

## Motivation

Twice in two months Stripe broke sanneandersen in production. **Neither time was an outage.**

| | what happened | what a health check would have said |
|---|---|---|
| F098.4 | `current_period_end` moved off the Subscription onto its **items** | Stripe is up ✅ |
| F102 | `invoice.subscription` was **removed** in `2026-04-22.dahlia` | Stripe is up ✅ |

Both failed in the **green direction**: no exception, no log, a webhook branch that quietly did not run. One of them was `invoice.payment_failed` — a declined card triggered literally nothing, and the customer kept full access without paying.

So the thing to monitor is **not** whether Stripe answers. It is whether **the fields we read are still where we read them.**

## Who owns it, and why not Upmetrics

The knowledge of *which fields we read* lives in `@broberg/stripe` — that is the entire reason the package exists (F053.10: otherwise every repo digs the fields out itself and each API change is discovered one repo at a time, always by a customer).

A tester anywhere else would have to **duplicate that list**, and a duplicated list is wrong the day one of the two is updated. That is the drift this package was created to remove, reintroduced one layer up.

| who | what |
|---|---|
| **components** | owns the probe — it ships beside the fields it guards |
| **cronjobs.webhouse.net** | runs it on a schedule |
| **Upmetrics** | receives the failure as an incident |

Upmetrics owns *noticing*, not *knowing what Stripe calls things*. sanneandersen must not own it either: they would be testing on the fleet's behalf by accident, and discover it on their own paying customer.

## Scope

`packages/stripe/src/probe.ts` — `probeStripeShape({ stripe })`:

1. Create a **test-mode** product, price, customer and subscription. Real API calls, Stripe's test environment, no money.
2. Read the subscription back and run **our own readers** — `readPeriod`, `readSubscriptionId` — over the real payload.
3. Assert each reader **resolves**, and report **which location it resolved from**. A reader that silently fell through to the deprecated location is a warning that the new one moved again.
4. Clean up what it created.

**Three outcomes, never two:**

```
ok       every reader resolved, and from the location we expect
drift    a reader resolved from an UNEXPECTED location, or not at all   → incident
unknown  could not reach Stripe / no key                                → NOT a verdict
```

The third is the one that gets collapsed by accident, and collapsing it is how a monitor becomes noise: an unreachable API reported as drift wakes someone for Stripe's outage, and reported as ok hides a real move.

### Non-goals

- **Not testing that Stripe works.** Their status page does that.
- Not touching live mode. The probe refuses a key that is not `sk_test_`.
- Not scheduling itself. The schedule is `cronjobs.webhouse.net`, and it is a separate step Christian owns.

## Reuse

Checked Discovery: `@broberg/stripe` is the fleet's only Stripe primitive, and no `@broberg/*` package does contract-drift probing generically. `@broberg/cron` has a `contract-drift.mjs` for *its own* service's OpenAPI document — a different shape (a published contract to diff) and not reusable here, because Stripe publishes no machine contract for where a field lives. Its **three-outcome split** is reused as the design, and named as the precedent.

## Acceptance criteria

1. `probeStripeShape` returns one of exactly three statuses, and `unknown` is reachable — asserted by a test that makes the client throw a network error and requires `unknown`, never `drift`.
2. A payload where `current_period_end` sits ONLY at the removed top level reports **drift**, naming the reader and the location it fell through to. Not a boolean.
3. A payload where every field is in the current location reports **ok**, and states which location each reader used — so "it resolved" and "it resolved from where we expect" stay separate claims.
4. The probe REFUSES a non-test key. Asserted with `sk_live_` and mutation-proven: removing the guard must redden a NAMED test.
5. Every assertion above proven RED before being trusted.
6. The probe cleans up what it created, and says so in its result. A monitor that leaks a subscription per run is a monitor someone turns off.
7. **NOT CLAIMED until measured:** these run against a fake Stripe client. That the probe catches a REAL future field move is unproven until it runs against test-mode Stripe with a real key — which needs a key this repo does not have. Stated on the card, not ticked past.
