# F033.10 — the shared deploy workflow starts TWO copies by default

> Reported by the **coverletter** session. Ordered by Christian, 2026-08-27.

## The defect, in one line

`flyctl deploy` runs the app on **two machines** by default. For an app whose database is a file on one attached volume, that is silent data loss — and our shared workflow gives the caller no way to say otherwise.

There is no error and no failed deploy. The job goes green. That is the whole problem: **a default that is correct for a stateless web app is a data-corruption default for a stateful one**, and nothing in the pipeline distinguishes them.

## Reuse check (F217)

Searched Discovery for `deploy` · `fly` · `ha` · `high availability` · `health check` · `commit`. `@broberg/deploy-core` exists and is **not** the right home: it does static content-sync and Fly Machines REST, while this is a CI concern — the reason F033.7 chose a reusable GitHub Actions workflow over a JS function in the first place. This is a change to the workflow we already own. No new package.

## An input is not enough — the guard has to read the config

An `ha: false` input alone only helps someone who already knows the problem exists, which is precisely not the person about to hit it. The workflow is already handed the caller's `fly.toml`. If that file declares `[mounts]`, the app has a volume, and running two copies of it is never what the caller meant.

So: **`[mounts]` + `ha: true` is a hard stop, before `flyctl` runs.** Not a warning — a warning in CI output is read by nobody until after the damage. The error names the exact input to set.

### Two states, not one

The failure form this epic keeps meeting (F033.8: an empty sha written as `unknown`; F033.9: a dead token reported as missing secrets):

> **"There is no `[mounts]` section"** and **"I could not read the config"** are different facts.

A guard that collapses them is a guard that reports success because it never ran. When the config is absent the step says **SKIPPED**, in words, in the log.

And the mount detection matches a real TOML section header, not the substring `mounts` — a commented-out `# [mounts]` or the word inside some other value must not trigger the stop, or the guard becomes something people route around.

## Health-verify has the same shape as the mounts bug

Today the poll exits on the first HTTP 200. If the new release fails to boot, **the old version is still serving 200** — so the check passes, the deploy is declared healthy, and what shipped is what was already there.

`health_commit_path` (a jq path, e.g. `.commit`) makes the poll keep going until the served commit matches the sha *this run* deployed. F033.8 already stamps that sha into the build, so the two halves finally meet.

The comparison normalises to the 7-char short form, since an app may report either the short or the full sha, and F033.8 chose 7 chars deliberately so a CI deploy and a local ship of one commit produce one id.

Three outcomes, three different messages — collapsing them is how F033.9 sent someone to fix secrets that were already set:

| Situation | Reported as |
|---|---|
| never returned 200 | timeout, unchanged |
| 200, commit field absent/null | the field is missing at `<path>` — names the path, not a timeout |
| 200, commit is someone else's | served `X`, expected `Y` |

## The negative control IS the acceptance

coverletter named it, and it is the sharpest thing in the exchange:

> *A green verify that would also be green without the fix is not a verification.*

So pointing `health_commit_path` at a stale build **must turn the job red**, and that is an acceptance criterion rather than a nice-to-have. Same for the mounts guard: removing it must turn a named test red.

## Testing the bash that actually ships

A reusable workflow runs inside the **caller's** checkout, so this logic cannot move into a script file in this repo — it has to stay inline in the YAML. Re-typing it into a test would test a copy, which is exactly how a fix and its proof drift apart.

Instead the test **extracts the `run:` blocks from the shipped workflow file** and executes them against fixtures with a stubbed `flyctl` and `curl` on `PATH`. Edit the YAML, and the test either follows or goes red.

## No naked cutover

`ha` defaults to **true**, so every existing consumer sees a byte-identical `flyctl` command until it opts out. coverletter keeps its own hand-rolled guard job until ours is proven **in their pipeline** — replace, prove, then remove.

## Non-goals

- Not a general Fly config parser. We detect one section.
- Not choosing `ha` for the caller. We refuse an unsafe combination; we never silently flip it.
- Not a rollback mechanism. A red health-verify tells you the new version is not serving; undoing it is a separate decision.
