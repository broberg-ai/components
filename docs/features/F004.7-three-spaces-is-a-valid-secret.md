# F004.7 — three spaces is a valid production secret

**Status:** Ready · **Epic:** F004 (`@broberg/config`) · **Written:** 2026-09-11 (dansk tid)
**Filed by:** helpdesk · **Confirmed here against our own dist before accepting**

## Measured

`@broberg/config` 0.2.0:

```
productionGuard({ SESSION_SECRET: "" },     ["SESSION_SECRET"], "production")  → refused
productionGuard({ SESSION_SECRET: "   " },  ["SESSION_SECRET"], "production")  → BOOTED
productionGuard({ SESSION_SECRET: "a"*64 }, ["SESSION_SECRET"], "production")  → BOOTED
```

**The guard that exists to stop the first state lets the second through, and the
second is worse.** An empty secret stops the service loudly. Three spaces STARTS
it — and every session cookie in production is then signed with a three-character
secret.

## The cause

`src/index.ts:134`

```ts
const missing = requiredKeys.filter((key) => !config[key]);
```

`!"   "` is false. The check cannot tell *“somebody set a key”* from *“somebody set
whitespace”*, and one of those two states disappears silently.

Same family as `findings: []` without a denominator, **inverted**: here an empty
result says “everything is in place” rather than “I did not look”.

## Why the obvious fix is wrong

This is what makes it a design question and not a one-line patch.

helpdesk has exactly one key where trailing whitespace is **legitimate content**:
`PLATFORM_OWNER_PASSWORD`, the owner's own password. A human may choose a password
with space around it, and **a guard that silently trims it locks the owner out of
his own system.** That is worse than the hole.

So the distinction is not *secret vs not-secret*. It is:

> **machine-issued vs human-chosen.** A hex token may be trimmed. A password may
> not.

And `productionGuard` cannot make that call — it sees key names and values,
nothing else. The caller knows; the guard does not.

## The proposal — a choice, not a behaviour change

helpdesk's shape, ours to decide:

```ts
productionGuard(config, keys, nodeEnv, { blank: (v) => v.trim() === "" })
```

with today's `!v` as the **default**, so no existing consumer moves without
meaning to.

**Open, and recorded rather than decided quietly (AC#4):** should the default
change? *“Most consumers have a machine key on the required list”* argues yes.
*“A silent behaviour change in a boot guard, across fifteen repos, on a patch”*
argues no. Both are real; the answer is the owner's.

## Reuse

Discovery checked per F217 (`env validation`, `config guard`, `boot check`).
`@broberg/config` is the fleet's only env-guard primitive and this is a defect
inside it — nothing to adopt, and nowhere else the fix could live.

## What helpdesk did on their own side

They did not wait, and they did not patch around us: one `maskinnoegle()` helper
over the eight machine-issued values and **not** over the password, with three
mutations each reddening its own test — including a negative control that goes red
if someone “simplifies” it into trimming everything. Their card: `helpdesk-F003.4`.

That negative control is the interesting one, and this card copies it as AC#5:
the dangerous fix here is not the missing one, it is the **complete-looking** one.

## Non-goals

- **Trimming values.** The guard reports; it must never mutate what a consumer
  passed. A silently trimmed password is a worse failure than a rejected boot,
  because it looks like it worked.
- **Inferring machine-vs-human from the key NAME.** `*_PASSWORD` would be a guess,
  and a guess that decides whether the owner can log in.
