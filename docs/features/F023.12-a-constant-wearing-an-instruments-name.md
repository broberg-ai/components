# F023.12 — A constant wearing an instrument's name

**Status:** Ready · **Epic:** F023 (`@broberg/mail-core`) · **Written:** 2026-09-03

## Measured against the published tarballs, not the source

```
0.2.1  SHELL_VERSION = "1"   footer rule: rgba(0,0,0,0.08)
0.3.0  SHELL_VERSION = "1"   footer rule: #0f7391          <- rendering CHANGED
0.4.0  SHELL_VERSION = "1"
```

Between 0.2.1 and 0.3.0 the footer rule changed colour, the footer text went from
an opacity to a real colour, `cardBg` moved off exact white, and `signOff`'s
emphasis moved. Every one of those changes what a recipient sees. **The marker
did not move.**

## Filed by cardmem, and their sentence is the specification

> *If it tracks the rendering CONTRACT rather than the package, then an
> output-changing release has to bump it, or it is a constant wearing an
> instrument's name.*

## Why this is worse than a wrong number

cardmem's template store is being built **on this marker, right now**, to answer
*"did my template change, or did their shell change?"* A marker that never moves
answers that question with a confident, wrong **"not us"**.

And it fails in the reassuring direction: **nobody investigates a stable version
number.** A marker that jumped around would get checked. One that sits at `"1"`
looks like a healthy instrument reporting no change.

I shipped it, and I documented it as an instrument — the docstring says it lets a
consumer tell *"my template changed"* from *"your shell changed"*. It could not do
that on the day it shipped.

## The second finding, same audit, same shape

`index.ts:568` — `factBox` renders `opacity:0.65` on every label cell.

F023.8's AC#3 read *"No `opacity` on any text in the shell"* and I **ticked it**.
The test rendered `renderShell`, which is clean; a sibling primitive forty lines
away in the same file still carries it. **The test rendered one function and the
claim covered the file** — one card after writing that exact lesson down.

## Design

**Two numbers, because there are two questions**, and cardmem already returns
both: `SHELL_VERSION` (did the rendering contract change) and the installed
package version (which build am I on). Collapsing them loses the distinction that
makes either useful.

**The seal is the deliverable, not the bump.** A convention that says *"remember
to bump this"* is exactly what produced three releases at `"1"`. So:

> Render a fixed set of representative mails; compare against a fixture stored
> under the current `SHELL_VERSION`. Output differs while the version is
> unchanged → **fail**, naming the marker.

That converts "remember" into "cannot forget": the only ways to green are to bump
the version or to not change the output.

**No retroactive renumbering.** 0.2.1, 0.3.0 and 0.4.0 all shipped as `"1"` and a
consumer may have stored it. Rewriting history would make those stored values
wrong in a new way. The fix is forward: the next output-changing release moves
it, and the README says the marker was unreliable before this version.

## Reuse

Discovery checked (`?q=snapshot+test`, `?q=contract+version`, `?q=rendering`).
Nothing in the roster owns a rendering-contract marker, and it would be a poor
fleet package — the fixture is inherently per-package. Stays here.

## Verification

- Change one rendered byte without bumping `SHELL_VERSION` → the seal reddens.
  That mutation IS the test's reason to exist; without proving it, the seal is a
  fixture comparison that happens to pass.
- Re-introduce `factBox`'s opacity → the invariant reddens.
- The invariant must render **every** text-emitting primitive, derived from the
  export list rather than hand-written — a new primitive with an opacity has to
  fail without anyone editing the test. Hand-written coverage is what let
  `factBox` sit under a ticked AC.
