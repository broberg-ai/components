# F005.12 — `last_event` is a MESSAGE status, not a RECIPIENT status

**Status:** In progress · **Epic:** F005 (`@broberg/mail`) · **Written:** 2026-08-31

## The defect is mine, and it is in the direction that hurts

0.8.1 shipped this sentence in the README and again in `events.ts:61`:

> **`suppressed` counts as failed.** It was never attempted — the address is on a
> suppression list.

I wrote it in the paragraph explaining which mappings are counter-intuitive, with
more confidence than any other line in the release. **It is false for any mail
with more than one recipient.**

## The measurement

fd-sundhed, against production, within an hour of adopting 0.8.1 — with a
negative control:

```
to: [cb@webhouse.dk, fd-demo-leder@webhouse.dk]   (the second is suppressed)
  → Resend last_event = suppressed
  → getStatus: verdict=failed, providerStatus=suppressed
  → cb@webhouse.dk RECEIVED IT     id 37a5ac15-d91c-49ac-a37e-d8a991096631

to: [cb@webhouse.dk]                              (control, same sender + shape)
  → delivered, received             id 43a7af23-6670-4ebd-8f46-0aac8fa327a7
```

**The witness is not their own claim.** cardmem's mail watcher caught the mail
landing in `cb@webhouse.dk` at 19:47:54, the same second Resend created it — two
independent systems, one of them not party to the question.

### Resend's docs do not settle it

Fetched tonight. The suppressions API exists:

```
GET https://api.resend.com/suppressions    limit (1–100) · after/before · origin=bounce|complaint|manual
→ { object, has_more, data: [{ id, email, origin, source_id, created_at }] }
```

But **nothing in the documentation describes multi-recipient behaviour.** So the
measurement is the only evidence that exists, and it is better evidence than
silence. That fact belongs in the docs beside the correction — a reader deserves
to know the claim rests on one measured case, not on a spec.

## Why it matters to a person

fd-sundhed has six mail types with several recipients: `report_approved` goes to
an employee's work address **and** her private one; a request goes to three people
in the municipality's working group.

With `failed` alone, their screen says *"not delivered"* about a mail that reached
exactly the person it was about — and an employee is told her address is wrong
when it is fine. **That is the identical harm this package's README warns about
for `complained`, produced by the line directly beneath it.**

## What changes, and what deliberately does not

### The verdict does NOT move

`suppressed → failed` stays. It is **correct for a single recipient**, and
`failed` is the strict branch. F070's precedent is the reason:

> the permissive outcome must never be the `default` branch. A new outcome lands
> in `default` silently, so if default is the accepting one, **adding an outcome
> widens the gate**.

A consumer that has not yet handled a new `partial` state must keep getting the
safe answer, not the optimistic one.

### The documentation does move, tonight

The false sentence is **removed**, not swapped for a new confident claim. What
replaces it is the measurement, the two ids, and the explicit note that Resend
does not document this. Overstating the correction would repeat the original
error facing the other way.

### The semver mistake gets named

0.8.0 added `getStatus` as a **required** member of the published `Mailer`
interface. That is a breaking type change in a MINOR release for anyone holding a
hand-written test double typed as `Mailer`.

fd-sundhed measured that it did not hit them — they never name the type, only use
the return value — and their own conclusion is the right one: *"at vi slap er
held, ikke design."*

**It is not being made optional.** `createMailer` always provides `getStatus`, so
`getStatus?` would be a type that lies in the other direction and would force
every caller to handle a case that cannot occur. The upgrade note names the
breakage and gives the one-line fix instead: type a double as
`Pick<Mailer, 'send'>`.

### `getSuppressions()` is the missing capability

Without the suppression list you cannot separate *"one of three was skipped"*
from *"all three were"*, however the event is mapped. fd-sundhed reached
`delvist` vs `spaerret` locally and needs the list to decide it.

**The trap inside the fix, filed by them and accepted:** if the lookup FAILS you
do not know who was skipped, and a naive comparison concludes *"nobody was
suppressed, so everyone got it"*. That is the green direction to fail in — the
shape this repo has now named ten times. Their rule stands: **keep the stricter
verdict when the lookup cannot answer.**

## Non-goals

- **No new verdict tonight.** A fifth outcome is a design decision with a trap at
  every consumer; it does not get made in the same hour the defect was found.
- **No mapping change without OUR OWN measurement.** Their measurement proves the
  claim is wrong. It is not a substitute for testing our fix — an unmeasured fix
  to a claim that was wrong *for being unmeasured* is the same error twice.
- **Nothing that can reach fd-sundhed's launch.** They are 7 hours from 16,838
  municipal employees meeting the app, back on `0.3.0` with a guard that reddens
  the moment anyone pins ≥0.8.

## Reuse

No Discovery check needed: this is the owner correcting its own package.
`getSuppressions` belongs in `@broberg/mail` for the same reason `getStatus` did
— the shared part is the meaning, not the HTTP call.

## What I got wrong, recorded because the pattern is the lesson

I wrote a confident sentence about a provider's semantics **from the word**, not
from a measurement — in the very paragraph warning that these two mappings are
the ones people get wrong. It is the third time this week the spec (or the
absence of one) disagreed with the obvious reading: `received` looked like the
strongest delivery confirmation and meant inbound; `suppressed` looked absolute
and is per-recipient.

fd-sundhed's own line is the honest version of it: *"jeg fandt det fordi jeg selv
havde skrevet den samme konklusion til Christian og taget fejl."*

And the two hypotheses I opened with — a breaking `Mailer` interface and the
`mailId` footer changing mail bodies — were **both measured negative** by them
inside an hour. Reasonable suspicions, promptly disproved; the value was in their
running the measurement rather than in my guessing well.
