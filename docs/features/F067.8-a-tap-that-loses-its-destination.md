# F067.8 — A notification tap lands on the wrong screen on iOS

**Status:** Backlog · **Epic:** F067 (`@broberg/webpush`) · **Written:** 2026-09-07
**Raised by:** trail (intercom #26338), against 0.5.0

## Motivation

trail's owner, with the phone in his hand:

> «Når jeg trykker på denne APN så kommer jeg godt nok ind i PWA, men jeg kommer ikke til en relevant skærm.»

Their engine sent a correct address (`/kb/<id>/sources`). The last link — ours — dropped it.

trail measured it in our published `dist`. **I verified it in the source myself** (`packages/webpush/src/sw.ts:151-178`) rather than taking a peer report at face value. It holds, and it is worse than reported.

```ts
for (const c of all) {
  const wc = c as WindowClient;
  if ('focus' in wc) {
    await wc.focus();
    if (navigate && 'navigate' in wc) {          // ← PATH A
      try { await wc.navigate(navigate); }
      catch { /* cross-origin or detached — ignore */ }   // ← PATH B
    }
    return;
  }
}
if (navigate) await clientsApi.openWindow(navigate);
```

## Two silent paths, not one

| | what happens | what a consumer sees |
|---|---|---|
| **A** | `'navigate' in wc` is **false** — iOS does not implement `WindowClient.navigate`, so the call is skipped entirely | nothing. No throw, no catch, no log |
| **B** | the method exists and **rejects** | nothing. The empty `catch {}` swallows it |

**Both end identically.** "It routed" and "it did nothing" are the same observable outcome, on every platform, for every consumer. That is why nobody found this by reading the code: it looks perfectly sensible.

Which of A or B fires on iOS does not change the fix — but it does change the *claim*, so this plan does not assert one. trail's own caveat, kept.

## Scope

**Post the destination to the app before falling back.**

```ts
for (const c of all) {
  const wc = c as WindowClient;
  if ('focus' in wc) await wc.focus();
  wc.postMessage({ type: 'webpush:navigate', navigate });   // NEW
}
// then the existing navigate() / openWindow() fallback, unchanged
```

An app with a router handles the message and routes itself — faster everywhere, and the only path that works at all on iOS.

### Non-goals

- **Not removing `navigate()`/`openWindow()`.** Replace, prove, then remove — and there is nothing to remove here anyway: they are the fallback for a consumer that does not listen.
- **Not a breaking change.** A consumer who ignores the message gets exactly today's behaviour.
- Not solving iOS badge or subscription-expiry behaviour. Separate cards.

## Two clients is necessary and NOT sufficient — trail measured it

trail hit our second bug in their own local copy, in a **different form**:

> Min `sw.ts` await'ede `focus()` MIDT i løkken, før postMessage. Et afvist focus ville have kastet ud af den async-blok, så vinduerne bagefter aldrig fik ruten.

**A fixture with two clients that both focus fine PASSES their broken code** — it reached both windows; it would only have failed if the first had rejected. So two clients catches *our* `return` and misses *their* `await`, and the two live in the same three lines.

**The fixture must have two clients AND the first must reject `focus()`.** They have it measured and mutation-proven both ways (`apps/admin/src/sw-notificationclick.test.ts`, commit `398bb39`) and offered it — take theirs rather than writing a weaker one.

### Their three caveats

1. **It rejects in the FIXTURE, not in the code.** So it covers a focus that *rejects* and not one that *hangs*.
2. **Strict equality on the whole message**, never "contains" — a contains-check passes on a mangled route, i.e. it fails in the green direction.
3. **`matchAll` order is not guaranteed anywhere.** Not only about the test: if the order is not guaranteed, "the first focusable client" is itself non-deterministic — an independent argument for posting to **all** clients, which holds even where `navigate()` works.

## The third door: a `focus()` that never resolves

`await` on a never-resolving promise does not throw. It simply never continues — no error, no catch, no signal, and the `waitUntil` sits until the browser kills it. That is worse than a rejection, because a rejection at least *could* have been observed.

**The fix covers it** — posting before the `await` means a hang costs nothing. **No test covers it**, in either repo. trail said so explicitly rather than letting the fixture imply more than it proves. AC#8.

## The `return` is also wrong, and it is a second bug

The loop `return`s after the **first** focusable client. With several windows open, the rest are never told. The message must go to **all** of them.

The general shape, worth keeping: *the post that carries the payload must happen before anything that can fail.* `return`, `throw`, and an `await` that rejects are three doors to the same room.

## Reuse

Nothing to reuse — this IS the shared package. Checked Discovery for a second push primitive that might already own click-routing: `@broberg/webpush` is the only one, and `@broberg/notifications` (F074) is deliberately about counting, not delivery.

## What is NOT claimed

Nobody here has an iOS debugger. AC#1–#4 are provable in a test harness with a fake `WindowClient`; **that iOS then lands on the right screen is trail's to confirm on the device**, and until they do, this fix is reasoned rather than observed.

buddy's version of the same trap, from their own incident: they once had a branch matched against a field that existed only in a fixture they had shaped themselves. The branch could never fire in production, and the test was green because it was fed the author's own assumption. **Test the branches against a real response, not against a mock you shaped.**
