# F053.10 — Every repo reads Stripe's moved fields itself

**Status:** Shipped — `@broberg/stripe@0.3.0`
**Parent:** F053 — `@broberg/stripe`
**Filed by:** sanne, with two measured production failures two months apart

---

## The pattern, measured twice

### 1 · F098.4 — the period moved down a level

Stripe moved `current_period_end` from the Subscription top level onto
`items.data[0]`. They read the top, got `undefined`, wrote `null`.

Their only paying subscriber then had **no renewal date** — and because *no date*
means *gift without expiry* in their access rule, a **cancelled paying
subscription would have kept access forever**.

### 2 · F102 — `invoice.subscription` is gone

Stripe **removed** it in `2026-04-22.dahlia`. Measured on a real live invoice:
`hasOwnProperty(invoice, 'subscription') === false`. The id now lives at
`invoice.parent.subscription_details.subscription`, with
`lines[0].parent.subscription_item_details.subscription` as the alternative.

Two branches of their webhook read the old place and fell out with `break`. One
was **`invoice.payment_failed`** — so **a declined payment triggered nothing**. No
status change, no message, the customer keeps access for free, and neither they
nor the customer finds out.

## Why it is ours

We already own the webhook chain — we deliver the payload. But reading a field
*out* of that payload is every repo's own code. So each time Stripe moves
something, **one repo discovers it at a time, and always because something has
already gone wrong for a customer.**

**Both failures fail in the GREEN direction:** no exception, no log, just a branch
that quietly does not run. No test catches it, because the code "works".

## The fixture is the most valuable part

Theirs, and their reasoning is the sharp bit:

> an **anonymised copy of a real dahlia invoice**, fetched rather than written,
> deliberately — *a hand-written imitation confirms the author's understanding of
> the shape, and a wrong understanding of the shape WAS the bug.*

Take it as ours.

## Reuse

Discovery searched for `stripe` and `invoice subscription field` before writing
a line. One hit both times, and it is this package: **F053 / `@broberg/stripe`**,
owned by `components`, already shipped at 0.2.0.

**Decision: EXTEND, do not build.** The reads go into the package that already
owns the webhook chain, as two new exports on the existing entry point — no new
package, no new subpath, no second Stripe dependency anywhere. That is exactly
the case the reuse-first rule names: the capability is missing *from a package we
own*, so it is extended rather than worked around, and every consumer gets it.

Nothing else in the roster reads a provider payload, so there was no adjacent
primitive to fold this into. The two functions sanne wrote locally are the thing
being **removed**, not a third copy being added — AC#8 makes their deletion part
of this card.

## Design

```
readPeriod(subscription)   → { start, end } in ms   items.data[0] first, top level as fallback
readSubscriptionId(invoice) → string | null        parent.subscription_details
                                                   → lines[0].parent.subscription_item_details
                                                   → legacy invoice.subscription
```

**New location first, old as fallback, in both.** A stored event from an older
API version must still resolve, or a webhook replay becomes a second outage.

**Null on foreign input, never throw.** These run inside a webhook handler; an
exception means the event is never acknowledged and Stripe retries it forever.

**English identifiers.** Their functions are `laesPeriode` / `laesAbonnementsId`.
The behaviour is theirs, the names are the package's.

## What we must NOT inherit as truth

They flagged it themselves, which is the right way to hand something over:
whether `customer.subscription.updated` actually fires on every renewal — and has
therefore been a safety net for the renewal branch all along — is **an inference
from Stripe's documentation, not something they have watched happen.** Their
subscription is a month old; the first real renewal is **2026-09-27**. Unproven
until someone sees it.

## Rollout

1. Lift the behaviour + the real fixture; rename to English.
2. Assert each fallback branch separately, and assert the dahlia fixture does not
   carry the old field — so the new path is exercised for the reason it exists.
3. Reproduce their actual outage shape (`invoice.payment_failed`, dahlia), proven
   RED against the old field read.
4. Mutation pass — removing either fallback, and swapping precedence, each turn a
   distinct test red.
5. Publish, verify from the tarball, tell sanne so they delete their two files.

## What shipped

`@broberg/stripe@0.3.0` — `readSubscriptionId(invoice)` and
`readPeriod(subscription)`, plus `SubscriptionPeriod`.

**Two deliberate differences from sanne's original, both stated to them:**

1. **Every invoice line is scanned, not `lines.data[0]`.** A renewal invoice can
   carry a proration credit, and nothing guarantees the subscription line is
   first — index 0 alone would fall through to the *removed* field and answer
   null, the same silent no-op F102 was. Recorded honestly as **inferred**: we
   have not observed a proration-first invoice.
2. **`has_own_subscription_key: false` is gone from the fixture.** That key does
   not exist on a real Stripe invoice, and a fixture whose entire value is that
   nobody wrote it must not carry a fact somebody wrote in it. The test asserts
   the stronger thing against the object itself:
   `hasOwnProperty(invoice, "subscription") === false`.

**The caveat that is the consumer's real takeaway**, now in the package docs:
`null` from `readPeriod` means *could not read it*, never *no expiry*. That
translation is the whole of F098.4 — an access rule read a missing end date as an
unlimited gift, and an unreadable field became free lifetime access for a
cancelled paying subscription.

**Provenance, kept separate rather than blurred:** the invoice fixture is fetched
(real, anonymised). The subscription shapes are constructed — sanne measured the
timestamp but never saved the object, so the period tests carry a weaker claim
than the id tests and say so. A real subscription fixture is requested.

**12 mutations, 0 uncaught, 0 identical red sets** — each asserting its anchor
applied, the harness refusing an uncommitted file. Wired into `pnpm test`, which
`turbo run test` runs in the `gate` job that `publish-stripe` depends on, so a
surviving mutant blocks the release rather than being a report nobody reads.
