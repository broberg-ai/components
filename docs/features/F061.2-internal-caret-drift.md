# F061.2 — a caret on 0.x locks the minor, and it is in our own monorepo twice

> Found while answering a question about something else entirely. coverletter asked *where does the secret-scan gate live?* — and looking up who actually depends on it found this.

## The defect, measured on the published package

```
npm i @broberg/logger          → resolves @broberg/secret-scan 0.1.8   (latest: 0.5.1)
redactSecrets('whsec_…')       → LEAKS. No finding. Value untouched.
```

`@broberg/logger`'s own description says it **"cannot leak a secret … every message and metadata value run through `@broberg/secret-scan` before it leaves the process."**

Today that sentence is false for any Stripe webhook secret, and for everything else the four minors since 0.1.8 added.

**The guarantee is the dangerous part, not the gap.** A promise like that is exactly why someone stops checking what they log. (This package has been here before: F063's own README once claimed "a secret cannot reach the log by accident", and the claim was corrected to a measured table precisely because a guarantee makes people stop looking.)

## The mechanism

On a `0.x` version a caret locks the **minor**. `^0.1.8` can never resolve `0.2.0`, let alone `0.5.1`. **Every `@broberg/*` package is 0.x**, so an internal dependency never updates by itself — ever.

Twice in our own monorepo:

| | pinned | npm latest | behind |
|---|---|---|---|
| `@broberg/logger` → `@broberg/secret-scan` | `^0.1.8` | 0.5.1 | 4 minors, **and it leaks** |
| `@broberg/lens-engine` → `@broberg/ai-sdk` | `^0.21.1` | 0.28.0 | 7 minors |

Discovery's own npm tips already document this trap **for consumers**. Nobody had pointed it at us.

## Why nothing caught it

Every angle we normally look from reports green:

- the **roster** says logger is shipped and current — and it is; the version that is stale is the one *inside* it
- its **tests** pass — against the 0.1.8 that is installed
- its **typecheck** passes
- the **consumer** installs one package and gets a transitive dependency they never chose and cannot see

This week's shape once more: **a property that reads as enforced and is only true by luck.**

## The fix is the gate, not the two bumps

Bumping both pins fixes today. A gate is what stops the third one. It reads every `@broberg`→`@broberg` dependency across `packages/*/package.json`, asks npm what latest is, and fails when a pin can never resolve it.

**And it must have three states, not two** — *current* · *stale* · **could not ask**. A registry that does not answer must print that it could not look, and must never produce a clean result. Getting that wrong would be this very card's defect, one level up: a check that reports success because it never ran.

## What this means for consumers

Per Discovery's enrollments, measured rather than assumed:

| repo | secret-scan | |
|---|---|---|
| trail | 0.5.1 | current |
| cardmem | 0.5.0 | one patch behind |
| **beacon** | **0.1.8** | **leaks `whsec_`** |
| **buddy** | **0.1.4** | **leaks `whsec_`** |

For beacon and buddy that is a live finding about their own redaction, not a version-number nag — and it is the same caret trap, from the consumer side.

**coverletter is not affected**, and measured it rather than assuming: no pre-commit hook, no `core.hooksPath`, no secret-scan dependency. The gate trail spoke of is per-repo — components runs it from `.githooks/pre-commit`; trail runs their own.
