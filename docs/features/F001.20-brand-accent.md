# F001.20 — Brand accent: a customer app gets its own colour

**Source:** appkit, intercom #1669 (5/10 2026), Lens-measured at 1440px.

## The gap (verified in palettes.css)

Only `broberg` sets its own `--accent` (#EC4E27 light / #F3522C dark). `cool` and
`warm` do not set `--accent` at all and fall through to classic's #E8A87C. So a
palette is a *surface tone*, not a brand: appkit's demo with three fictional
customers (Nordlys Energi = cool, Havnens Bageri = warm) gets identical orange
buttons. A customer app cannot have its own brand colour without hand-overriding
`--accent`, which D-a84d0a forbids (no copied/override code in appkit).

## Design

A fourth, independent axis beside theme / palette / surfaces: **accent**.

- `setAccent(hex | null)` — writes `--accent`, `--accent-fg`, `--accent-soft` as
  inline custom properties on `:root` (inline beats every palette selector, so it
  survives palette and theme switches without per-palette rules).
- `--accent-fg` = dark ink or white, whichever gives the higher WCAG contrast on
  the accent; must reach 4.5:1.
- `--accent-soft` = the accent at low alpha (0.14), same as the palettes.
- `prePaintScript({ accent })` — same writes before first paint.
- Optional `accentKey` for persisting a user choice is NOT in scope: a brand
  colour is set by the app, not chosen by the end user. Add later only if asked.

Open question for later: whether one hex should be lightened for dark mode. v1
uses the same hex in both modes (the broberg palette's own two values differ by
only a few %); the fg contrast check runs per value.

## Reuse

- WCAG contrast: `@broberg/theme/design-md` already has the contrast maths
  (F001.10 notes it is only reachable through a DESIGN.md). Reuse that internal
  function; do not write a second luminance implementation.
- Discovery check: no fleet package owns runtime accent derivation; theme is the
  owner of the token axes. Build here.
