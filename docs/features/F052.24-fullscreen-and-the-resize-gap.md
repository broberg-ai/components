# F052.24 — Fullscreen the body, and the resize gap underneath it

**Parent:** F052 · **Priority:** high · 2026-08-28
**Requested by:** Christian, in session: *"Kan du lave så API kan få komponentet (den
sorte boks) til at vises i fullscreen."*

---

## Why this, rather than a framing knob

It arrived next to fd-sundhed's report that the figure is small and its lower legs
are clipped on a phone. Fullscreen is the better answer: the body is small because
the box is **36vh of a phone**, and no amount of camera fitting turns a 300px-tall
box into a good place to examine a knee.

---

## The gap that would have made it useless

Measured **before** building:

```
src/three.tsx:457
  const onResize = () => { W = el.clientWidth || 520; H = el.clientHeight || 600; … }
  window.addEventListener("resize", onResize)

ResizeObserver in the file:  0 occurrences
```

The canvas is measured from the element **once at mount**, and re-measured only on
a **window** resize. Entering fullscreen changes the **element**, not the window.
So would:

- a consumer switching `canvasHeight` at a breakpoint (fd-sundhed does exactly this)
- a container animating open
- a phone's URL bar collapsing, changing what `vh` means

Ship fullscreen on top of that and **the box goes fullscreen while the picture
inside stays 393×304** — worse than not shipping it. The ResizeObserver is not
scope creep; it is what makes the requested feature work.

---

## The framing report: NOT root-caused, and not guessed at

The same message reports the figure sitting too low with the lower legs clipped.
What is actually known:

| checked | result |
|---|---|
| `git diff bodymap-v0.2.6..HEAD -- src/three.tsx` | nothing about camera, position, framing, lights, materials — **one comment line** |
| repro at `iphone-15`, fd-sundhed's exact props | body framed **correctly**, head to feet, nothing clipped |
| camera | hardcoded: `PerspectiveCamera(32)`, pos `(0, 1.05, 4.4)`, target `(0, 0.95, 0)` |

Vertical FOV is fixed, so canvas **aspect** does not change what is visible
vertically — which is why a short box alone does not explain clipped legs.

**Strongest remaining hypothesis, NOT confirmed:** `H = el.clientHeight || 600`.
If `clientHeight` reads `0` at mount (a height that resolves after first paint),
the renderer is sized **600px tall inside a 304px box** with `overflow: hidden` —
so you see the **top** of a taller render: empty space above, legs cut below. That
is exactly the screenshot. The ResizeObserver here would close it **if** that is
the cause; a `fit` option is the fallback if it is not. Raw screenshot and their
container requested.

No camera change on a guess — that would move the problem and destroy the evidence.

## Design

**Both ways in**, because Christian asked for the API and a forced button would
repeat a mistake this component has already made twice (F052.14 `showSexToggle`,
F052.18 `showRegionCode` — both added because the package imposed chrome a
consumer had to CSS-hide):

- a handle the consumer can call from their own button
- a built-in control that can be switched off

**iOS Safari does not support the Fullscreen API on arbitrary elements.** The
iPhone is this component's primary surface, so the fallback — expand to fill the
viewport with CSS — is **the main path, not an edge case**, and the control must
never be a dead button. Verified in Lens under `engine: webkit`.

---

## How it is proven

- A test that changes the **element's** height with no window resize and asserts
  the renderer re-measured — and that test must be shown going **red** without the
  observer.
- Lens at `iphone-15`: enter fullscreen, measure **more body pixels** than before,
  leave, and the layout returns.
- The serialized pain report read back **before and after** — fullscreen is a view
  change and must never touch the record.

## Reuse

Discovery searched for `fullscreen`, `viewport`, `resize`: the only hit is
bodymap itself. No `@broberg/*` package owns viewport behaviour.

The decision that came out of the check is worth more than the null result: we
deliberately did NOT reuse the browser's own Fullscreen API. iOS Safari does not
support fullscreen on an arbitrary element at all, and a phone is this
component's primary surface — so a good path plus a fallback nobody exercises
loses to one `position: fixed; inset: 0` mechanism that behaves identically
everywhere.

`ResizeObserver` is a platform primitive, not a dependency, and needs no
polyfill on any browser we support (the code still guards for its absence so a
server render cannot throw).
