# F053.13 — A stub cannot disagree with us

> Parent: [F053 — @broberg/stripe](F053-stripe.md) · split out of [F053.12](F053.12-stripe-never-went-down.md) on the owner's order, 2026-09-09.

**Status:** Backlog · **Blocked** on an `sk_test_` key for this repo · **Priority: low, deliberately**

## Why this card exists separately

F053.12 built the thing that guards the fleet, and it runs every morning at 08:17. One of its acceptance criteria said:

> the probe catching a REAL future field move is unproven until it runs against test-mode Stripe with a real key, which this repo does not have

True, and **unsatisfiable in a repo with no Stripe key.** Left where it was, a finished, running, verified card would have sat in Review forever behind a criterion no work in this repo could meet — and a permanently open flag on finished work teaches everyone to stop reading flags.

Christian's call, verbatim: *"flyt det til eget kort"*.

## What is already proven, and is NOT this card's job

The **primary** path needs no account at all. `checkSpecDrift()` reads Stripe's own published OpenAPI spec — no key, nothing created, nothing to clean up. Measured against the real spec (run 34288141389):

```
status: "ok"   specVersion: "2026-08-26.dahlia"
  readPeriod         primary   subscription_item.current_period_end   present: true
  readPeriod         fallback  subscription.current_period_end        present: false
  readSubscriptionId primary   invoice.parent                         present: true
  readSubscriptionId fallback  invoice.subscription                   present: false
```

Two true, two false. **An instrument fabricating a green answers four trues**; this one discriminates on real input. It would have caught both incidents that broke sanneandersen — and Stripe's status page was green through both, which is the whole reason the check asks about fields rather than uptime.

## What this card is

`probeStripeShape()` asks the same question of a **real account** instead of a document. Every one of its tests drives a fake Stripe client.

A stub is kind by construction: it returns what we told it to. So the existing tests prove the probe's **logic** — three outcomes, drift naming the location, cleanup reported, a live key refused — and prove **nothing** about whether a real Stripe payload matches the fixtures we wrote for it.

That is the gap, and it is narrow but real: our fixtures came from a live account once, months ago, and nothing re-checks them.

## The most valuable outcome is a disagreement

The interesting result is not "the probe works". It is whether the **live account** and the **published spec** resolve the same way.

If they diverge, that is a fact no instrument we currently own can detect — the spec describes Stripe's newest shape, an account answers on the pinned API version, and F053.12's README already states that those are two different documents. A measured disagreement would turn a stated limitation into a known quantity.

So AC#2 requires the comparison to be **written down rather than reconciled away**.

## The safety already built

Nothing needs adding before this can run:

- `probeStripeShape` refuses any key that is not `sk_test_` **before it creates anything** (`LiveKeyRefused`), mutation-proven — removing the guard reddens the named test.
- It reports `cleanedUp` and `leaked` rather than swallowing a failed cleanup.
- Cleanup order is asserted separately (`subscription → customer → price → product`), corrected once already to the order a live run actually required.

AC#3 still verifies the account is clean **by listing it afterwards**, not by trusting the probe's own report — a leak is exactly the condition that would corrupt that field.

## The key

Store it with `cardmem_create_secret`, which takes the value server-side and returns only an id. It must never appear in a chat, an argv, a log or a commit: that failure is one-way, and this repo has the precedent on the books.

## Reuse

Nothing to check — this runs an existing function in an existing package against a real account. No new capability, no new dependency, nothing another `@broberg/*` package could provide.

## Non-goals

- **Making this a scheduled job.** One run, recorded. A daily run against an account costs a key somebody must hold and rotate, which is precisely what Christian's question removed from the design in the first place.
- Replacing `checkSpecDrift`. The keyless check stays the primary; this is a second opinion.
- Relaxing an assertion to make the live run pass. If reality disagrees with a fixture, the **fixture** is wrong — correct it and record the difference. A test loosened until it goes green proves nothing afterwards.

## Why low priority, said plainly

So nobody later mistakes this for neglect: the keyless check answers the same question **earlier** (the day Stripe publishes a move, possibly before it reaches us), costs nothing, and cannot leak a credential. This card buys an independent second reading. Worth having; not worth blocking anything on.
