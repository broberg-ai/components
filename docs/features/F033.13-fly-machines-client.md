## Design

```ts
const fly = new FlyClient({ token?: string /* default FLY_API_TOKEN */, fetch?: typeof fetch })
```

**Machines REST** (`https://api.machines.dev/v1`): `listApps(org)`, `getApp(name)` (null ved 404), `createApp`, `deleteApp`, `listMachines`, `getMachine`, `createMachine`, `startMachine`, `stopMachine`, `destroyMachine`, `updateMachine`, `waitForState(app, id, state, timeoutSec)` (serverens `/wait` har et loft pr. kald — løkken forlænger), `waitForExit(app, id, {maxMs})`.

**GraphQL** (`https://api.fly.io/graphql`) — kun det repoerne bruger: `listOrgs`, `listAllApps` (paginering via cursor, ingen stille loft), `setSecrets`, `allocateIp`.

**Fejl:** `FlyApiError { status, method, path, body }`. Body afkortes og tokenet redigeres ud. Genforsøg KUN på netværksfejl, 408, 429, 5xx (samme klassificering som ai-sdk lærte dyrt 23/9). En 4xx fejler med det samme.

**waitForExit** returnerer `{ state, exitCode }` og overlader succes-dommen til kalderen — `exitCode: null` er en oplysning, ikke et «ok».

## Afgrænsning

**Ikke her:** adoption i cms/whop/buddy (Christians beslutning pr. repo) · event-bussen (bliver på F033.3) · Cloudflare/GitHub Pages (F033.2) · Prometheus-metrics (buddy F391 bygger lokalt) · log-streaming (cms' `/logs`-kald er ikke verificeret mod Fly's API).

## Verifikation

1. Enhedstests med injiceret fetch: request-form + fejlklassificering fra begge sider, mutationsbevist.
2. **Live read-only** mod det rigtige Fly: org'er, alle apps, maskiner på en eksisterende app — sammenlignet med `flyctl`.
3. **Live skrive-sti i en engangs-testapp** som testen selv opretter og sletter: create → start → resize (læst tilbage) → stop → destroy → app væk. Aldrig mod en eksisterende app.

## Reuse

Discovery 24/9: `fly`, `fly machines`, `prometheus`, `cost`, `observability` — intet der taler Fly Machines API. `@broberg/deploy-core` er det rigtige hjem (registret nævner den som deploy-eksekveringslaget, og F033's plan havde den). Ingen ny afhængighed: ren `fetch`.
