# F005.15 — The check looks one level beside where the records are, and asks presence where it means value

> Parent: [F005 — Mail sending (Resend)](F005-mail.md) · fixes [F005.9](F005.9-sending-domain-readiness.md) · sibling of [F005.14](F005.14-dns-is-not-permission.md), filed by the same consumer an hour earlier.

**Status:** Backlog · **Filed:** 2026-09-08 · Defect 1 reported by helpdesk (#26865), defect 2 found while verifying it.

## Both measured against live DNS

```
support@support.fdsundhed.dk   ok=false  spf=missing  dkim=ok  mx=missing   ← FALSE RED
noreply@broberg.ai             ok=true   spf=ok       dkim=ok  mx=ok        ← FALSE GREEN
x@send.broberg.ai              ok=true   spf=ok       dkim=ok  mx=ok        ← correct
```

Nothing here is reasoned about. Every line is the shipped function run against the real resolver.

## Defect 1 — the wrong place

Resend's layout:

```
send.<domain>                      SPF (TXT) + MX
resend._domainkey.<domain>         DKIM
```

`verifySendingDomain` looks up SPF and MX on **the sender domain's own apex**. So it finds DKIM — which genuinely lives at `resend._domainkey.<domain>` — and calls SPF and MX missing. Confirmed with `dig @8.8.8.8`:

```
support.fdsundhed.dk                     no TXT, no MX
send.support.fdsundhed.dk                v=spf1 include:amazonses.com ~all
                                         MX 10 feedback-smtp.eu-west-1.amazonses.com
resend._domainkey.support.fdsundhed.dk   p=MIGfMA0GCSqG…
```

Resend reports that domain `verified`. We report two records missing, permanently.

**It is worse than a false alarm, and helpdesk named exactly why.** `missing` carries the *fix* — the best property that field has. Here it instructs the customer to add SPF at the apex. They add it. Nothing changes, because Resend reads the `send.` subdomain. The warning stays. And they now hold a DNS record that does nothing.

> A fix that does not fix is more expensive than no fix, because it spends the customer's trust.

### Why it survived three months

F005.9 was built and measured against `send.broberg.ai` and `send.webhouse.dk` — domains that **are already the `send.` subdomain**. The lookup landed in the right place by construction of the fixture, not by correctness of the code. The convenient fixture was accidentally safe.

And it is not a helpdesk peculiarity: any domain added through Resend's normal flow has this shape. helpdesk is simply the first consumer sending from a domain that is not already `send.<something>`.

## Defect 2 — the wrong question, and this is the false green

Found while verifying defect 1, unreported by anyone, and it fails in the direction that hurts.

```ts
} else if (mx.state === 'found' && mx.value.length > 0) {
  mxState = 'ok';
```

**MX is judged by presence, never by value.** `broberg.ai`'s MX is Google Workspace (`alt3.aspmx.l.google.com`) and the check reports `mx: 'ok'`.

The comment directly above that branch states the purpose:

> *Its absence does not stop delivery — it stops BOUNCES coming back, so you never learn that a send failed.*

A Google MX does not carry SES bounces. So the check reports *bounces will come back* about a domain where they will not. It clears the exact property it exists to report.

**SPF has the same shape, structurally.** Only the `v=spf1` prefix is tested, never whether the sending provider is authorised. `v=spf1 include:_spf.google.com ~all` — a perfectly real SPF record — reads as `ok` while every SES send fails SPF. Recorded as **structural, not measured**: `broberg.ai`'s SPF happens to include `amazonses.com`, so it is right there by luck of the data rather than by the predicate.

## The two directions are not equally bad

| | who notices | consequence |
|---|---|---|
| **1 — false red** | immediately | refuses a working domain; the customer is told to make a change that does nothing; someone switches the check off |
| **2 — false green** | nobody | clears a domain whose bounces vanish — the precise failure the check was written for |

Fix both. Defect 2 carries the higher risk despite being the one nobody complained about, and that asymmetry is the reason it is written down here rather than folded into defect 1's fix.

## Design constraints

**Do not hardcode `send.`.** helpdesk raised this themselves and they are right: Postmark and SES place records elsewhere, so a fixed prefix is a general rule that is wrong for most providers. The layout becomes a *named* option — the same treatment `dkimSelector` already got in F005.9, and for the same stated reason: an unstated provider assumption produces a confident false alarm about a domain that is fine.

**More lookups means more ways to fail silently.** The fix multiplies the hostnames visited, and the three-state discipline (`ok` / `missing` / `unknown`, where `unknown` never counts as ok) has to hold on every one of them — not only on the ones that existed before.

**Say where the record was found.** With several hostnames in play, `spf: 'ok'` that does not name the hostname that carried it is the same unfalsifiable claim F005.10 already fixed for the normalised domain. The report must stay checkable by a reader who disagrees with it.

## Reuse

No Discovery search needed for a fix to an existing function in this package; the capability is already ours. Nothing else in the `@broberg/*` inventory performs DNS record checks, so there is no second implementation to converge with. (`@broberg/mail` remains the single chokepoint — the reason helpdesk filed a report instead of writing their own resolver.)

## Non-goals

- Resend's `/domains` verdict — that is [F005.14](F005.14-dns-is-not-permission.md). This card only makes the DNS half tell the truth.
- Validating the DKIM key material. A malformed key is the provider's problem; an absent record is ours. Unchanged from F005.9.
- Supporting every provider's layout today. One named layout with Resend as the default, built so a second can be added without another false-alarm class.

## Rollout

Patch or minor — no signature change, but the *answers* change for real domains, in both directions. Consumers currently gating on `ok` will see a domain flip from false to true (defect 1) and, more importantly, may see one flip from true to false (defect 2). That second flip is a correction, not a regression, and the release note has to say so in those words or it reads as the package breaking.

helpdesk confirms on their real tenant domain before this closes. They found it; the fix has to answer correctly on the thing they measured, not on our copy of it.
