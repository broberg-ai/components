# F019.7 — README: state the CONSEQUENCE of the `detect:true` default, not just the mechanism

> Story under **F019 — i18n / Language Switch**. Filed by **fd-sundhed, 2026-08-24**, after a production incident.

## Motivation

`@broberg/i18n` detects the locale from `navigator.language` when nothing is stored. Measured in the source (not from memory):

```ts
// src/index.ts:90
const detect = config.detect !== false;   // → default TRUE

// detectInitial(): stored → navigator exact → navigator prefix → defaultLocale
```

During a steering-group demo for Aalborg Kommune, a municipal leader got the **entire leader surface in English** ("For approval", "Awaiting your decision") because her browser was `en-US`. Nothing was broken. No error fired. The engine did exactly what it was configured to do — and the configuration was our default.

fd-sundhed fixed it in one line with `detect: false`. The flag was there, and that part worked.

### Why this is a documentation DEFECT and not a footnote

The decisive evidence is not the incident. It is that fd-sundhed built **five separate workarounds** against this same behaviour over several weeks **without once recognising the default as the cause**:

```
tools/fd-sundhed-mail-tests/e2e/onboarding-e2e.mjs:84   localStorage fd-sundhed-locale = 'da'
tools/fd-sundhed-mail-tests/e2e/rejse-skud.mjs:94       — same —
tools/fd-sundhed-mail-tests/e2e/rejse-skud.mjs:168      — same —
tools/fd-sundhed-mail-tests/e2e/pwa-skud.mjs:170        — same —
tools/fd-sundhed-mail-tests/e2e/workflow-e2e.mjs:102    (deliberate — this one CHOOSES a language)
```

Their own ADR wrote the mechanism down verbatim — *"appen følger telefonens sprog når brugeren ikke selv har valgt et"* — and they still filed it as a test quirk rather than as a product property they had never chosen.

So the failure mode is **not** "consumers don't discover the default". They discover it four times and fix the symptom each time. The field name `detect` describes the **mechanism**, and no reading of a mechanism prompts the question *"do we even want this?"*.

That is why the fix is a **consequence sentence**, not a better mechanism description. The current README is already mechanically accurate and useless for the decision:

> **Detection** — stored locale → `navigator.language` prefix-match → default, all SSR-guarded.

## Scope

- Rewrite the README's **Detection** bullet + add a short **"Which default do you want?"** subsection: the consequence in product terms, a worked example the reader can recognise, the copyable `detect: false` opt-out, and when each choice is right.
- Add the same consequence to the **JSDoc on the `detect?` field** in `src/index.ts` — that is where the reader actually is at the moment of deciding, and it is what an editor tooltip surfaces.
- Keep every existing factual statement about ordering; **add**, don't replace.

### Non-goals

- **Do NOT flip the default.** fd-sundhed's proposal #1 (`detect: false` as the default) is a genuinely better default for a single-primary-language product, but it is **breaking** for any consumer relying on today's behaviour. It needs its own story, a minor/major call and a consumer notice — never a silent flip. Deliberately out of scope here so the safe half ships now.
- No version bump or publish in this story; a README-only change rides the next release.
- No change to `detectInitial()` ordering.

## Reuse

Nothing to reuse — this is a documentation change to a package `components` owns. Discovery check not applicable (no new capability). Related consumer-filed gaps captured the same day on `@broberg/auth`, `@broberg/stripe` and `@broberg/secret-scan`.
