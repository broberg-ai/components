# F078.5 — The web cannot name Face ID, and Android cannot either

**Status:** Backlog · **Epic:** F078 (`@broberg/device-stats`) · **Written:** 2026-09-02

## The ask

Christian, 2026-09-02:

> «I den device-stats pakke der mangler vi at kunne aflæse FaceID tilslutninger —
> hvis det ikke kan lade sig gøre så er det måske min app der native skal kunne
> sige at den er tilsluttet.»

The app is **fd-sundhed, iOS and Android**.

## His instinct is right, and this is not a gap in the package

Measured in `packages/device-stats/src/permissions.ts`. The only question a
browser will answer is:

```ts
PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable()
```

It says *"a built-in authenticator that can verify the user exists"*. **[Certain]**
It returns the same `true` for Face ID, Touch ID **and a plain passcode**. The
spec hides the modality on purpose — exposing it would fingerprint the device.
There is no web API that names Face ID, and there will not be one.

## The half that changes the design

This only surfaced once the app was named as iOS **and** Android:

| | enrolment | modality |
|---|---|---|
| **iOS** | `LAContext.canEvaluatePolicy` **[Certain]** | `LAContext.biometryType` → `.faceID` / `.touchID` **[Certain]** |
| **Android** | `BiometricManager.canAuthenticate(BIOMETRIC_STRONG)` **[Certain]** | **no public API** **[Likely]** |
| **Web** | — | — |

Android's `PackageManager.hasSystemFeature(FEATURE_FACE | FEATURE_FINGERPRINT)`
reports **hardware present**, not what is enrolled and not what the prompt will
actually use. Reading it as modality would be a guess wearing a measurement's
clothes.

**So enrolment is answerable on both platforms; modality is answerable on iOS
only.** A single field `biometry: "face" | "touch"` would be a measurement on one
platform and a guess on the other — one field doing two jobs, with nothing in the
data to tell them apart.

## The number he probably wants works everywhere

- *"How many users have biometric login switched on?"* → **enrolment**, both platforms.
- *"How many use Face ID specifically?"* → **iOS only, by construction.**

Worth choosing knowingly rather than discovering it in a chart that silently
under-counts Android.

## Shape

```ts
biometrics: {
  enrolled: "yes" | "no" | "no-hardware" | "unknown";
  modality: "face" | "fingerprint" | "other" | "unknown";
  source:   "native-ios" | "native-android" | "web-cannot-tell";
}
```

`source` is the load-bearing field. Without it `unknown` means both *"the user has
none"* and *"we could not ask"*, and those are opposite facts — the merge this
repo has spent the week finding everywhere else.

## Not in scope

- **Redefining `platformAuthenticator`.** It is correct; only its *name* misleads.
  It gets a docstring saying `available` is also true of a passcode — on the
  **exported** symbol, or it is stripped from the published `.d.ts` and reaches
  nobody (measured on `@broberg/mail` 0.10.0).
- Prompting for biometrics. This reads what is already configured; it never shows UI.

## Verification

The assertions that matter are the ones about what CANNOT be known: the Android
adapter must not be *able* to emit a modality, proven by a compile failure rather
than a convention, and a missing native report must read `web-cannot-tell` and
never `none`. Plus a real device on each platform, read back from the stored
record rather than from the request that wrote it.
