# F061.3 — No `@broberg/*` package can tell a consumer what version it is

**Status:** in progress · **Parent:** F061 (build hardening) · **Priority:** high · **1 SP**

Found by **fd-sundhed** on 2026-08-29, while auditing their own Discovery
enrollments after we audited ours. Verified here across the whole workspace
before anything was written.

## The measurement

```
packages with an exports map          39
  CAN be probed (./package.json)       0
  CANNOT be probed                    39
```

```js
require('@broberg/sms/package.json')   // ERR_PACKAGE_PATH_NOT_EXPORTED
```

Every one of our packages ships an `exports` map, and none of them export
`./package.json`. Node then refuses the deep import — so the ordinary way to ask
*"what version of this do I actually have installed?"* throws.

## Why it matters more than it sounds

**The throw is indistinguishable from the package being absent.** fd-sundhed's
probe reported *"NOT INSTALLED"* for all seven packages they tested, and all
seven were installed. Their words:

> *Measured through a layer, and the layer answered.*

That is today's failure form again, and this time it lands on the one question
the whole reuse loop depends on. Discovery's value is that a repo can say what it
has adopted; **our packaging makes an accurate answer impossible to compute.**

The consequences were both real and both found the same afternoon:

| | |
|---|---|
| **components** | our own enrollment on `@broberg/sms` said 0.2.0 while npm served 0.12.0 — ten minors of drift in our self-report about our own package |
| **fd-sundhed** | reported 7 packages, actually used 14; 3 of the 7 named the wrong version |

Neither was carelessness. Neither repo had a reliable way to look.

**And `package.json` is not the answer either** — fd-sundhed makes this point
explicitly. A declared range and an installed version can disagree, so a probe
must read what is in `node_modules`, which is exactly the read this blocks.

## The fix

`"./package.json": "./package.json"` in every `exports` map. It is the standard
convention precisely because tooling needs it. No behaviour change, no new
surface — it exposes a file that is already in `files`/the published tarball.

## Non-goals

- Not exporting anything else. `./package.json` only.
- Not writing a version-probe helper. The fix is to stop blocking the probe every
  consumer already knows how to write.

## Also worth recording, from the same report

fd-sundhed found **two** `DISCOVERY_ENROLL_KEY` values in their repo (`.env` and
`apps/web/.env.local`). The wrong one 401s on everything, and their note is the
sharp part:

> *Had I only run one package and seen a 401, I would probably have concluded
> "Discovery is down" instead of "I used the wrong one of two keys".*

**Measured on our side, and this one needs no fix:** `/api/enroll` already
answers with the reason in the body —

```
401 {"error":"session_key_mismatch — this session is already bound to a
     different key (use the one in your .env, or ask components to reset it)"}
401 {"error":"x-enroll-key required (min 32 chars — generate your own …)"}
```

So the information is there for anyone who reads the body. The ambiguity is in
the status code alone. Recorded rather than "fixed", because inventing a change
here would be theatre.
