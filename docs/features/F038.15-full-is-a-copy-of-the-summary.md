# F038.15 — "full" is a byte-for-byte copy of the summary

**Status:** Ready · **Epic:** F038 (Discovery) · **Written:** 2026-09-06
**Found while:** filing cardmem's note that Lens video recording is *not* in
`@broberg/lens` — and then checking whether the note reaches anyone.

## Measured

```
cmp docs/llms.txt docs/llms-full.txt   →  BYTE-IDENTICAL
67,393 bytes each
```

`build-onboarding.mjs:264-265` writes the same string to both, with a comment
calling `llms-full.txt` *"a convention alias for the same content."* And the
content is built from `oneLiner(p)` — everything before the first `. ` or ` — ` —
so every package line is truncated:

```
@broberg/lens v0.1.3 — A headless POST /api/lens-session mint endpoint (+ thin
Next.js / Hono adapters) that issues a short-lived, read-only Playwright session
so Cardmem…
```

**That `…` is where the note lives.** The video-recording warning. The F051
`next-auth` sub-path. And, on every other row, whatever was learned after the
first sentence.

## Why this is worse than a missing file

The canonical Discovery block — copied verbatim into ~30 repos — says:

> `GET https://discovery.broberg.ai/ai` — the ENTIRE inventory as a single
> llms.txt: every `@broberg/*` package grouped by layer AND all 107 fleet tips
> **inline** (packages + every tip in one response, **nothing behind a further
> link**).

**"Nothing behind a further link" is true for the tips and false for the package
descriptions.** So a session follows our instruction exactly, reads a truncated
line, and concludes that is all there is. The full text exists only in the
dashboard HTML and the JSON API — behind precisely the further link the sentence
promises there is none of.

A file named *full* that is a copy of the summary is not a gap a reader can
notice. It is the same shape this repo keeps finding: **a name that answers a
narrower question than the one it is used for.**

## The precedent, one level in

`cms-inline-edit` grew a capability that lived in sentence four of its `desc`,
and the one-liner hid it from exactly the audience the roster is for. The fix
then was to **rewrite the opening segment** — correct for that row, and it scales
to one row at a time. There are 54.

The real hole is not that a description was badly ordered. It is that **no
surface serves the full text at all** to the audience told to read first.

## Scope

- `llms-full.txt` serves each package's **complete `desc`**.
- `llms.txt` is **unchanged** — it is the map, and a map carrying 54 full
  descriptions would be the same failure from the other side.
- A CI guard that fails if the two are ever byte-identical again. It is one line
  to re-alias them; without a guard it will come back.
- CLAUDE.md's sentence is made true, or corrected. It is currently a promise to
  ~30 repos.

### Non-goals

- **Not rewriting descriptions to fit the one-liner.** That is the F051 remedy
  and it does not scale.
- **Not changing `oneLiner()`.** The short form is right for `llms.txt` and for
  the dashboard cards; the problem is that nothing serves the long form.
- **Not a new endpoint.** `/llms-full.txt` already exists and is already
  advertised. Making it do its name is cheaper than teaching the fleet a new URL.

## The thing that must not happen

**Fixing this by making `llms.txt` longer.** The map's value is that it fits in
one read. If the remedy is "put everything everywhere", the next session pays for
54 full descriptions to learn that a package exists.

## Reuse

None — this is Discovery's own generator, in the repo that owns it.

## What shipped

```
llms.txt         67,675 bytes   the MAP — one line per package (was 67,393)
llms-full.txt   304,446 bytes   every sentence of all 54 descriptions
```

`llms.txt` did **not** grow by a package line. Its entire diff is one pointer
bullet, and that bullet was itself part of the defect: it advertised
`llms-full.txt` as *"every one of the 124 tips, inline"* — a difference that did
not exist, because `llms.txt` already carried every tip. The one line telling a
reader to fetch the full file described nothing. Following it exactly, you had
no reason to go and nothing to find on arrival.

`oneLiner()` is untouched. The short form was never wrong; nothing served the
long one.

## The check cardmem sharpened, and why it matters

Their correction, mid-build: **`cmp` reporting a difference is necessary and not
sufficient.** Remove the truncation from only ONE of the two package renderers
and the files differ while the full one is still cut.

So `scripts/check-llms-full.mjs` asserts the **invariant** — every one of the 54
complete descriptions present in `llms-full.txt` — and keeps byte-identity only
as a cheap first signal. It asserts the opposite failure too: no full description
may leak into `llms.txt`, because "put everything everywhere" is the same defect
from the other side.

**The floor.** With no row carrying content past its first sentence, both checks
are vacuous — every desc would equal its own one-liner and the file would pass
while telling a reader nothing. That exits 3 and says so. Measured: 54 of 54 rows
are tailed; longest is `@broberg/lens-engine` at 31,717 chars, of which 70 reach
`llms.txt`.

**Proven RED on three mutations** before being trusted:

| mutation | result |
|---|---|
| re-alias: write the same string to both | red — names both files, then all 54 rows |
| truncate the full renderer only (files still DIFFER) | red — all 54 rows |
| put the full text into the map as well | red — 54 leaked into `llms.txt` |

The seal in the app's own suite reddens on the first two, and on nothing else —
one named test, not "something failed".

## Two things found on the way, both larger than the card

### The deploy gate had been red for twelve runs

`discovery` had failed on every run since 5 September. Correctly: three roster
rows named a version older than npm served, **two of them published by this
session earlier the same night** without bumping the roster. Nothing had shipped
in that window. AC#4 — verify on the live site — was unreachable until this was
fixed, and would have looked like a deploy problem rather than a stale roster.

The gate worked. Nobody read it.

### `apps/discovery` was in no gate at all

`pnpm-workspace.yaml` lists `packages/*` only, so the app that SERVES all of this
is invisible to the workspace gate:

```
turbo run test --dry   ->  78 tasks, ZERO from apps/discovery
```

Its 60 tests and its typecheck have never run in CI. The only use any workflow
made of its path was deciding whether to deploy it. The consequence was already
on main — `server.ts` imported `readFileSync` twice (b0503fc, 3 September), which
`tsc --noEmit` rejects and nothing ever ran. It was found because a shell
happened to be inside that directory, which is not a mechanism.

Wired into the `check` job rather than by adding `apps/*` to the workspace: that
job is what the deploy `needs`, so the gate sits on the thing it guards, and the
install topology of 39 published packages does not move to fix a CI hole.

**And it is the reason the seal above is worth anything.** A test in a suite CI
never runs is not a gate; the card's own evidence would have been theatre.
