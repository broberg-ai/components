# F038.15 — "full" is a byte-for-byte copy of the summary

**Status:** Ready · **Epic:** F038 (Discovery) · **Written:** 2026-09-06
**Found while:** filing cardmem's note that Lens video recording is *not* in
`@broberg/lens` — and then checking whether the note reaches anyone.

## Measured

```
cmp docs/llms.txt docs/llms-full.txt   →  BYTE-IDENTICAL
67,393 bytes each
```

`build-onboarding.mjs:264-265` writes the same string to both, with a comment
calling `llms-full.txt` *"a convention alias for the same content."* And the
content is built from `oneLiner(p)` — everything before the first `. ` or ` — ` —
so every package line is truncated:

```
@broberg/lens v0.1.3 — A headless POST /api/lens-session mint endpoint (+ thin
Next.js / Hono adapters) that issues a short-lived, read-only Playwright session
so Cardmem…
```

**That `…` is where the note lives.** The video-recording warning. The F051
`next-auth` sub-path. And, on every other row, whatever was learned after the
first sentence.

## Why this is worse than a missing file

The canonical Discovery block — copied verbatim into ~30 repos — says:

> `GET https://discovery.broberg.ai/ai` — the ENTIRE inventory as a single
> llms.txt: every `@broberg/*` package grouped by layer AND all 107 fleet tips
> **inline** (packages + every tip in one response, **nothing behind a further
> link**).

**"Nothing behind a further link" is true for the tips and false for the package
descriptions.** So a session follows our instruction exactly, reads a truncated
line, and concludes that is all there is. The full text exists only in the
dashboard HTML and the JSON API — behind precisely the further link the sentence
promises there is none of.

A file named *full* that is a copy of the summary is not a gap a reader can
notice. It is the same shape this repo keeps finding: **a name that answers a
narrower question than the one it is used for.**

## The precedent, one level in

`cms-inline-edit` grew a capability that lived in sentence four of its `desc`,
and the one-liner hid it from exactly the audience the roster is for. The fix
then was to **rewrite the opening segment** — correct for that row, and it scales
to one row at a time. There are 54.

The real hole is not that a description was badly ordered. It is that **no
surface serves the full text at all** to the audience told to read first.

## Scope

- `llms-full.txt` serves each package's **complete `desc`**.
- `llms.txt` is **unchanged** — it is the map, and a map carrying 54 full
  descriptions would be the same failure from the other side.
- A CI guard that fails if the two are ever byte-identical again. It is one line
  to re-alias them; without a guard it will come back.
- CLAUDE.md's sentence is made true, or corrected. It is currently a promise to
  ~30 repos.

### Non-goals

- **Not rewriting descriptions to fit the one-liner.** That is the F051 remedy
  and it does not scale.
- **Not changing `oneLiner()`.** The short form is right for `llms.txt` and for
  the dashboard cards; the problem is that nothing serves the long form.
- **Not a new endpoint.** `/llms-full.txt` already exists and is already
  advertised. Making it do its name is cheaper than teaching the fleet a new URL.

## The thing that must not happen

**Fixing this by making `llms.txt` longer.** The map's value is that it fits in
one read. If the remedy is "put everything everywhere", the next session pays for
54 full descriptions to learn that a package exists.

## Reuse

None — this is Discovery's own generator, in the repo that owns it.
