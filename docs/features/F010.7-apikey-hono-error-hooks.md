# F010.7 — Hono adapter: pluggable error responses

> Story under **F010 — @broberg/apikey**. Consumer-filed gap from **beacon** (#18981).

## Motivation

beacon closed their HTTP surface with bearer tokens + roles and adopted the parts of this package that are genuinely dangerous to hand-roll — `generateKey`, `hashKey`, `verifyKey`, `makeKeyPreview`, `SlidingWindowRateLimiter`. Those worked.

They could **not** use `honoApiKeyMiddleware`, for a small and entirely mechanical reason (`packages/apikey/src/hono.ts:23`):

```ts
c.json({ error: "missing_api_key" }, 401)   // `error` is a STRING
```

Beacon's whole surface answers `{ error: { code, message, at?, hint? } }`. Their clients — typically an LLM — switch on `error.code` and never read prose. Adopting the adapter would make precisely the two responses a client most needs to handle, **401 and 403**, differently shaped from every other response on the API. `honoRateLimit`'s `{ error: "rate_limited" }` has the same problem.

So they wrote ~40 lines of middleware on top of our core primitives. It works — and it is exactly the local workaround the reuse rule exists to prevent. The next repo with its own error contract will make the same call.

The package's own stated principle is *"own the primitives, never your storage/tenancy/rate-backend"*. A hardcoded error envelope is the same category mistake: **the response contract is the app's, not the package's.**

## Scope

Three optional hooks. Defaults untouched, so no existing consumer notices.

```ts
interface HonoApiKeyOptions<T> {
  // …existing
  onUnauthorized?: (c: Context, reason: 'missing' | 'invalid') => Response
  onForbidden?:    (c: Context, record: T) => Response
}

function honoRateLimit(
  limiter: SlidingWindowRateLimiter,
  keyFn?: (c: Context) => string,
  opts?: { onLimited?: (c: Context, r: RateLimitResult) => Response },
): MiddlewareHandler
```

`reason` is worth passing through even though both cases answer 401 today. beacon's own distinction is the argument for it: **401 = "I don't know who you are"** (no token, unknown token, revoked a second ago) vs **403 = "I know exactly who you are, and this isn't yours"**. The first is fixed by fetching a token, the second by requesting a different role — and the response is the only thing that tells the caller which.

Also from beacon's use, worth documenting rather than changing: `clientIp()` falls back to `"unknown"` when there is no `x-forwarded-for`. On a loopback-bound service with no proxy that means **every caller shares one bucket**. Not wrong, but surprising — the README should say so and point at keying on token id instead, which is what beacon does.

### Non-goals

- No change to what the middleware **decides** — 401/403/429 semantics are unchanged. The hooks shape the rendering only.
- Headers (`X-RateLimit-Remaining`, `Retry-After`) stay owned by the middleware; `onLimited` shapes the body.
- No new error-envelope abstraction shipped by us — we hand the consumer the `Context` and get out of the way.

## Dependencies

None. `hono` remains the only (peer) dependency of this adapter.

## Reuse

beacon filed rather than forked, and offered a PR. Landing the hooks lets them delete their 40 lines and every later repo skip writing them. Precedent: F008.8 (happy-little-place), F053.7 (sanne), F052.x (fd-sundhed) — consumer-filed gaps that grew the package. No Discovery search applies — we own the package.
