# F005.18 — a check that only sees what is already leaving

**Status:** Ready · **Epic:** F005 (`@broberg/mail`) · **Written:** 2026-09-11 (dansk tid)
**Filed by:** sanne (#27435), out of their own F116.2 cutover · **Verified here before accepting**

## The report, and why it is a good one

sanne did not send a bug. They ran our package through a real cutover, measured what
happened, and came back with two findings and a correction to their own earlier claim.
Both findings are ours. Both are confirmed.

They also caught something about themselves first — four call sites that bypassed their
own guard — and the honest consequence was that our check sits *deeper* than theirs, not
that theirs was redundant. That is the report that makes the next one worth reading.

## Finding 1 — the check runs after the gates

`src/index.ts` `send()`, in the order it actually executes:

```ts
if (config.disabled || !config.apiKey)  return { ok: true, skipped: true };   // no check
if (!mailAllowed(...))                  return { ok: true, skipped: true };   // no check
const integrityReport = checkMailIntegrity(message);                          // only here
```

So `checkMailIntegrity` never runs:

| environment | why not |
|---|---|
| local dev | no `RESEND_API_KEY` |
| CI | no `RESEND_API_KEY` |
| staging, to a real test address | recipient not on the allowlist |

Those are exactly the three places a broken template is cheap to find and free to fix.
The check only ever sees mail that is **already on its way to a person**.

### The comment above it is false, and that is the part worth recording

```
// It runs on every send, including report-only, because the report is the
// point: a finding nobody can read before enforcement is turned on is a
// guard nobody can trust turning on.
```

It runs on every send **that passes two gates**. I wrote that sentence in F005.16, and
it is the same shape this repo spent the night finding in other people's code and twice
in its own tonight (F005.17's `dmarcHosts`, F080.4's empty-reader exit 0): *a claim
broader than the code, in a comment that reads as a guarantee.*

The second half of the comment is the argument AGAINST its own placement — "a finding
nobody can read before enforcement is turned on is a guard nobody can trust". That is
precisely what a dev environment is for, and it is the one place the finding is never
produced.

### What it cost the consumer

sanne's words: a test with no key gets `{ ok: true, skipped: true }` for a mail that is
**broken**, and proves nothing. They now set key + `live` + a stubbed `fetch` in every
test, and wrote down why, so nobody simplifies it away later. That workaround exists
only to make our check run at all.

And the stakes are on the record: all three of the production defects F005.16 was built
to prevent reached a paying customer. A check that only sees real deliveries catches
that class at the most expensive possible moment.

## Finding 2 — three causes, one answer

`{ ok: true, skipped: true }` is returned for three different situations, and two of
them share a single `return` — only the log line tells them apart:

| cause | what it means | how bad |
|---|---|---|
| `disabled` | deliberate kill-switch | fine, intended |
| `no-key` | ship-dark, nothing configured | fine, intended |
| `not-live` | a key IS set, `live` never was — only the allowlist gets mail | **this is an outage wearing a success** |

`live` defaulted to `!!apiKey` in 0.1.0 and is `config.live === true` in 0.13.3. sanne
never passed the field. Measured with their real config on 0.13.3:

```
mode = "allowlist-only"
send({ to: "<a customer>" }) -> { ok: true, skipped: true }
```

Every customer mail stopped, silently, with a success-shaped answer — booking
confirmations, Stripe receipts, magic links, all at once. None of their ~25 call sites
reads `skipped`. Their own gate caught it. **Nothing in this package would have.**

### It is not a one-off: cms hit the mirror image

F005.8, recorded at the time: cms set `live` from `NODE_ENV`, which meant they opted out
of the only signal the package had, and swapped one silent failure for its opposite —
prod quietly delivering to the allowlist only. Two repos, opposite causes, same outcome.

The shared part is not the default value. It is that **the result cannot say which of
three things happened**, so a caller has no way to tell a deliberate no-op from an
accidental one.

### `mailer.mode` is not enough, and cms said why

`mode` answers this at BOOT: `"live" | "allowlist-only" | "disabled" | "no-key"`. That
is a good readback and it stays. It does not cover the failure that matters most in a
multi-tenant consumer — a key that falls out for ONE tenant is a per-send fact, and the
other ninety-nine look perfectly healthy from boot.

## Reuse

Discovery checked per F217 (`discovery.broberg.ai/api/search?q=mail send result`): the
only fleet package that owns mail transport is this one. Nothing to adopt — the defect
is in `@broberg/mail`'s own `send()` and can only be fixed here. That is the point of
the card: sanne explicitly refused to patch it locally, because copying their
`findMailFejl` into four more files would be four new duplicates of the thing the switch
exists to remove.

## Design

```ts
export type MailSkipReason = "disabled" | "no-key" | "not-live";

export interface MailResult {
  ok: boolean;
  id?: string;
  error?: string;
  skipped?: boolean;
  /** WHICH of the three no-op causes. Present exactly when `skipped` is true. */
  reason?: MailSkipReason;
  /** The integrity report for this message — present on skips too, which is the card. */
  integrity?: IntegrityReport;
}
```

and the order in `send()` becomes:

```
checkMailIntegrity(message)          // ALWAYS, first, on the finished message
  ├─ skip gates → { ok:true, skipped:true, reason, integrity }   ← never refused
  └─ delivering → refuse if enforcing and there are findings
```

**Signal where it is cheap, enforcement where it matters.** sanne's phrasing, and it is
the right shape: a dev environment gets to SEE a broken template without a no-op turning
into a hard error.

### The one rule this must not break

**A skip is never refused.** Not even under `integrity: "enforcing"`. A dev machine that
suddenly returns `{ ok: false }` where it used to return a harmless no-op is a worse
outage than the one being fixed, and it would arrive in every repo at once. AC#2 asserts
it rather than trusting it.

## Non-goals

**Making `live` REQUIRED when `apiKey` is set.** sanne proposed it and the argument is
good — it is our own `not-configured` argument, that the permissive reading must not be
the silent default. It is not in this card because it is **breaking in the direction
nobody would test**: a staging deployment that runs allowlist-only on purpose, and never
bothered to write `live: false`, stops booting. Fifteen repos install this package.

That is a major-version decision and it is Christian's, not mine and not a peer's. The
additive half here removes most of its urgency anyway: once a caller can read
`reason: "not-live"`, the silent state is no longer silent, and the remaining question is
only whether we also want it to be fatal.

**Changing the `live` default back.** Same reason, worse: it would flip fifteen repos
from allowlist-only to delivering, which is the one direction that reaches real people.
