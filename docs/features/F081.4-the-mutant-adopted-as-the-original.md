# F081.4 — The mutant adopted as the original

**Status:** Backlog · **Epic:** F081 (mutation-harness safety) · **Written:** 2026-09-01

## The hole

A mutation harness writes broken code, runs the tests, and writes the original
back. Every safety mechanism this epic has built so far watches the **restore**:

- the **marker** announces that a run is in progress, so a diff read during the
  window is not mistaken for a defect;
- **`assertRestored`** reads the file back afterwards and proves it matches what
  the harness meant to put there.

Neither can see a run that was wrong **before it started**. If the tree already
carries a mutant when the harness begins, that mutant is read as `original`, it
is written back as the restore target, and `assertRestored` passes — because it
compares the file against the same corrupted bytes it just adopted. The
corruption becomes permanent and every instrument reports success.

## Measured

`grep -c porcelain` across all eleven harnesses, 2026-09-01:

```
refuses on a dirty tree   discovery · mail · notifications · pwa · secret-scan · stripe · theme
does NOT                  greppable · mail-identity · webpush · lens-engine
```

And lens-engine carries a worse version of the same thing —
`packages/lens-engine/test/mutations.mjs:262`:

```js
for (const m of MUTATIONS) {
  const original = readFileSync(m.file, 'utf8');   // <- INSIDE the loop
```

The seven clean harnesses read it once, outside (`packages/stripe/test/mutations.mjs:145`).
Inside the loop, each iteration re-baselines against whatever is on disk *now*.

## Why it was only caught by luck

The leftover mutant that exposed this (`packages/lens-engine/src/flow.ts`, from
an interrupted run) happened to make the suite red, so lens-engine's baseline
check fired and refused to continue.

A leftover mutant that does **not** redden the suite is adopted in silence. And
that is not the rare case — it is precisely the case a harness leaves behind,
because an **uncaught** mutation is by definition one where nothing goes red.
The guard we have fires on the mutants we do not need it for.

## Fix

1. The four missing harnesses get the refuse-on-dirty guard the other seven have,
   naming the dirty files. "Commit first" without a file list sends the reader to
   `git status` during the one window when `git status` must not be trusted.
2. lens-engine's `const original = …` moves out of the loop. One line. The other
   26 mutations in that file are fine and are not being rewritten.
3. A discovered test (`git ls-files "*mutations.mjs"`, zero-length guard) asserts
   every harness refuses on a dirty tree, so a new harness cannot ship without it.

## Non-goals

- Not a rewrite of any harness. Rule 3.
- Not auto-cleaning a dirty tree. A harness that repairs what it finds would hide
  the very evidence that something went wrong earlier.

## Verification

Both directions per harness — dirty tree refuses and names the file, clean tree
still completes with its usual mutation count — plus a mutation on the new test
itself: remove the guard from one harness and the test must go red naming that
harness. And the check is run against a **non-reddening** leftover mutant, not
only against the reddening one that exposed this.
