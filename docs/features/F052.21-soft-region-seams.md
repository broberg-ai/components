# F052.21 — The sharp edges are the paint, not the model

> Story under **F052 — `@broberg/bodymap`**. Reported by Christian, 2026-08-28.

## What he said

> *"se på figuren der er lidt skarpe overgange i renderingen … prøve med det samme tool at lave en endnu mere smooth og menneskelignende. Måske der er kommet nye AI renderings tools til den konverter du brugte."*

**The observation is right. The diagnosis is not** — and building a new model would have been real work that changed nothing he can see.

## Measured before answering

```
body-male.glb / body-female.glb   21,160 triangles · 12,010 vertices each
NORMAL attribute                  present, 1/1 primitives
meshes                            1  ← NOT the ~15-20 segmented region meshes F052.5 planned
body.glb                          byte-identical to body-male.glb (legacy alias)
```

The body itself renders smooth — visible in every screenshot taken today. What is sharp is `three.tsx:277-282`:

```js
// for each vertex: the single closest of 20 anchors wins, outright
for (let a = 0; a < anchorVecs.length; a++) { const d = v.distanceToSquared(anchorVecs[a]); … }
vertexRegion[i] = ANCHOR_KEYS[best];

// and every vertex with that key is painted ONE flat colour
colorRegion = (key, hex) => { … if (vertexRegion[i] === key) colorAttr.setXYZ(i, …) }
```

**A boundary between two regions is a mathematically hard plane through the mesh.** It is sharp *by construction*, and would be exactly as sharp on a model ten times better. The file's own comment says as much: *"true per-zone mesh segmentation is a later refinement"*.

## What actually helps, in order of effect per unit of work

1. **Blend the colour between the two nearest anchors near a boundary** — this card. Cheap, and it makes a marked area look like a sore region rather than a sticker stuck on a mannequin.
2. **A denser mesh** — but for the **gradient**, not for looking human. A per-vertex blend across 12,010 vertices will still be slightly faceted. That is a real argument for a new model, and it is a *different* argument from the one given.

## On the AI-tool question, answered rather than dodged

Text-to-3D generators have improved a great deal. Two reasons they are the wrong move here:

- They produce an **unsegmented** mesh, which we would then process exactly as we process this one — so the sharp seams would come back unchanged.
- **Provenance.** F052 chose Blender Studio Human Base Meshes (CC0) deliberately, over CC-BY-SA atlases and NonCommercial models, because the customer is a public authority. An AI-generated body trades away the one property that decided the original choice.

## The design

Keep the hard assignment for **hit-testing** — a tap must map to exactly one region and produce the same clinical record. Store the *second* nearest anchor and a blend weight, and paint each vertex as a mix:

```
w = d1 / (d1 + d2)      0 at an anchor · 0.5 where two anchors are equidistant
colour = lerp(colour(nearest), colour(second), w)
```

Well inside a region `w ≈ 0`, so a marked chest is fully its heat colour at the centre and only fades at the edges. **A soft LOOK must never become a soft ANSWER.**

It is also *faster*: one pass over the vertices per repaint, where `refresh()` currently walks every vertex once per region (20×).

## Also found, not fixed here

`three.tsx:271` calls `geo.computeVertexNormals()`, discarding the normals the file ships. Harmless on this mesh (mostly welded — 12,010 vertices for 21,160 triangles), but it is authored data thrown away for no stated reason. Recorded, not touched.

## Non-goals

- Not replacing or deleting the models. Christian said so explicitly, and the licence is the reason.
- Not touching the 2D renderer. Its regions are authored SVG shapes with real outlines — a different mechanism with a different look.
- Not true per-mesh segmentation (still F052.5's later refinement).
