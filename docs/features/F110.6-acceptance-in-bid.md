# F110.6 — Accept af vilkår og GDPR-samtykker gemmes ét sted: i BID

> **Ordre:** ejeren 1/11 2026, ordret: «Vi gemmer, hvilken version af vilkårene du har accepteret, og hvornår. Gør vi det og hvordan? Ideen er FUCKING god men det skal virke. Jeg foreslår at det gemmes et sted i BID så det også kan aflæses via BID både i UI og via et API de forskellige apps kan trække ud». Og: «ja til GDPR-samtykker i BID også - alle samtykker gemmes i BID for de apps vi laver der har login logger ALLE ind med BID».
> **Erstatter** F110-planens linje «Storage stays in each app». «Bed straks Jam om at vente på BID løsningen» — jam har fjernet sin egen lagring (51911c2); deres tabel legal_acceptances (migration 0057, få rækker) står urørt og flyttes til BID senere.

## Målt (1/11 2026)
Vilkårene lover: «Vi gemmer, hvilken version af vilkårene du har accepteret, og hvornår.» Intet system gjorde det.

## To ting, holdt adskilt (juridisk forskellige)
- **Accept af vilkår** (aftale): `terms`, `dpa`. Aldrig `privacy` — privatlivspolitikken er information og accepteres aldrig.
- **GDPR-samtykke**: frivilligt, kan trækkes tilbage når som helst, aldrig en betingelse for brug (fx fysio-appsenes del 4-samtykke). Egen type og egen rute — aldrig en doc-værdi.

## Aftalt form med bid (#47367/#47368)
- Credential: brugerens access token fra appens SERVER. BID får sub og clientId af tokenet; sub eller produkt i kroppen læses aldrig.
- Produkt: udledt af clientId via et register (jam-web, jam-clipper, jam-ios → «jam»), sat af driften. En klient uden registrering → product = clientId.
- **Accept:** `POST /api/app/terms-acceptance { doc, version, contentHash: "sha256:<hex>" }` → 201 med rækken læst tilbage; `GET /api/app/terms-acceptance?doc=terms` → seneste eller null. doc ∈ {terms, dpa}. Lager: BID's termsConsent-tabel + product/doc/contentHash, append-only.
- **Samtykke:** `POST /api/app/consents { purpose, granted, version, contentHash }` → rækken læst tilbage; `GET /api/app/consents?purpose=` → gældende tilstand eller null. purpose fra et register. Tilbagetrækning = ny række med granted=false.
- UI på BID-kontoen: «Vilkår du har accepteret» (kun læsning) og «Dine samtykker» med en kontakt til at trække tilbage direkte i BID (lige så let at trække tilbage som at give, art. 7(3)).

## Uden for scope
Cookie-samtykke for besøgende, der ikke er logget ind (@broberg/consent-cookie), bliver i browseren.

## Ejerens svar (via bid, 2/11 2026)
1. **Ingen «gammel version vs. ny»-visning** på kontosiden: den viser kun den version, brugeren accepterede. Om brugeren skal acceptere igen, afgør appen selv (`getAcceptance` + `needsReaccept`).
2. **Accepter og samtykker bliver ved kontosletning**, med kun sub. De slettes ikke.

## Leveret i components (@broberg/legal 0.4.0)
`recordAcceptance`/`getAcceptance`, `recordConsent`/`getConsent`, `needsReaccept`, `BidConsentError` — kalder BID's live-ruter med brugerens token; en record-kald afviser et svar, der ikke ekkoer det sendte. Live-tjek: alle tre ruter svarer `401 invalid_token` på et forkert token (adresse og fejlformat passer).

## Tilbage: kun spørgsmål 2 (ikke-væsentlig ny version kræver ikke ny accept) — løst i `needsReaccept`: kun `material: true` + nyere version.

## Uden for scope
Cookie-samtykke for besøgende, der ikke er logget ind (@broberg/consent-cookie), bliver i browseren.

## Reuse
BID (broberg-id) som lager, API og «Samtykke»-side — én kilde for hele flåden (D-ae49a8); @broberg/legal for tekster, versioner og hashes. Ingen app bygger egen tabel til accepter eller samtykker.
