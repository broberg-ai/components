# F035.15 — the redaction library could not reach its own new patterns

**Status:** In progress · **Epic:** F035 (`@broberg/secret-scan`) · **Written:** 2026-09-10

## What the gate said, the minute 0.9.3 landed

```
✗ @broberg/logger → @broberg/secret-scan is pinned "^0.8.1", which can NEVER
  resolve npm latest 0.9.3.  (a caret on 0.x locks the MINOR)

A consumer installing the outer package gets the pinned version, not the current one.
```

The gate is `scripts/check-internal-pins.mjs`, and this is the exact defect it was built for (F061.2). It fired within a minute of the publish, unprompted, and named both versions.

## Why it is not bookkeeping

`@broberg/logger` does not merely depend on `@broberg/secret-scan` — it **delegates its entire promise** to it:

```ts
import { redactSecrets } from "@broberg/secret-scan";
// "...every metadata value goes through @broberg/secret-scan BY DEFAULT"
```

So a range that stops at `0.8.x` means every consumer of logger redacts with the **old pattern list**, while the package's own documentation promises current redaction.

Today that is concrete: F035.14 added the HelpDesk key pattern in 0.9.x. A repo logging through `@broberg/logger` writes `hd_live_<64 hex>` to its logs **in the clear** — and nothing says so. The redaction ran. It simply did not know that shape.

That is the failure form this whole epic keeps meeting from the other side: **a guard that silently covers less than the caller believes is worse than no guard, because it closes the question.**

## The caret is the bug, not the version

On `0.x`, `^0.8.1` means `>=0.8.1 <0.9.0`. The **minor** is the lock — which is not what a caret does on `1.x` and is exactly why people write it by accident.

It is also the only internal range in this repo still written that way. Measured, not assumed — all four others resolve today's latest:

| package | internal range |
|---|---|
| `@broberg/auth` | `mail >=0.3.0` |
| `@broberg/chat` | `apikey >=0.3.1 <1` · `forms-turnstile >=0.3.0 <1` |
| `@broberg/lens-engine` | `ai-sdk >=0.34.0 <1` |
| `@broberg/notifications` | `ui-controls-core >=0.1.1` |
| **`@broberg/logger`** | **`secret-scan ^0.8.1`** ← stuck |

## Reuse

Discovery checked per F217 — `discovery.broberg.ai/api/search?q=secret redaction logging`
returns `@broberg/secret-scan` and `@broberg/logger` as the top two rows.

**The reuse is the card.** `@broberg/logger` already delegates its entire promise —
"every message and metadata value run through `@broberg/secret-scan` before it leaves
the process" — to the fleet's one redaction package, exactly as this repo's rules
require. Nothing was re-rolled and nothing new is adopted here.

**What this card fixes is reuse that had silently STOPPED working.** A dependency
declared is not a capability received: `^0.8.1` on a 0.x package locks the minor, so
logger kept consuming the shared package at a version that predated the pattern it
needed. The package was still the single source; the consumer just could not reach it.

**The generalisable note, worth more than the fix:** reuse-vs-build is not settled once
at plan time. A correctly-reused dependency can drift out of reach through its version
range alone, with every architectural rule still satisfied on paper.
`scripts/check-internal-pins.mjs` is what turns that from a thing to remember into a
thing the gate refuses — and it is the mechanism that found this, unprompted, one minute
after 0.9.3 reached npm.

## Design

`>=0.9.3 <1`, matching the house pattern. Forward within `0.x` so a new pattern list reaches consumers without a release here; capped below `1.0.0` so a deliberate breaking change still requires a decision.

**A wide range is the right shape for THIS dependency specifically.** The thing being tracked is a list of secret shapes; a consumer being slightly ahead is the desired direction, and being pinned behind is the failure. That is the opposite of the argument for exact-pinning a prod-auth dependency, and the difference is worth stating rather than applying one rule to both.

## The half that is easy to skip

**Changing the range in this repo reaches nobody.** A consumer installs the *published* logger, so the fix does not exist anywhere that matters until logger is republished. The card's AC requires an install in a clean directory to resolve `>=0.9.3` — not a registry page listing a version, which is a different claim (`published-is-not-installable`).

And the capability check goes **through logger's own API**, never by calling `secret-scan` directly. The question is what a consumer of *logger* gets; reaching past it would answer a question nobody asked.

## Non-goals

- Auditing every fleet repo's own pins. Discovery's roster covers that ground and this card is about the one range this repo owns.
- Changing the other four ranges. They resolve latest today and there is no defect to fix.
