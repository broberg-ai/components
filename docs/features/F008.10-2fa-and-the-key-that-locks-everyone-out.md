# F008.10 — 2FA via authenticator app, and the encryption key that would lock every user out

**Status:** Backlog · **Epic:** F008 (`@broberg/auth`) · **Written:** 2026-09-03

## The first thing to say: there is nothing to integrate

Microsoft Authenticator and Google Authenticator implement **the same open
standard** — TOTP, RFC 6238. A 6-digit code derived from a shared secret and the
current 30-second window. **We never talk to Microsoft or Google.** We generate a
secret, show it as a QR code, and verify codes. Any authenticator app works,
including ones nobody has heard of.

That makes the job much smaller than the request sounds — and moves the risk
somewhere else entirely.

## What the plugin already does, read out of its own types and source

```
issuer · totpOptions · otpOptions · backupCodeOptions · schema
skipVerificationOnEnable   DEFAULT FALSE  ← enrolment already requires a valid code
allowPasswordless          for passkey-only users
twoFactorCookieMaxAge      600s to complete the challenge
trustDeviceMaxAge          30d "trust this device"
account-level lockout      on consecutive failed second-factor attempts
secret encrypted at rest   symmetricEncrypt        (index.mjs:90)
backup codes encrypted     storeBackupCodes: "encrypted"
totpURI returned           for the QR
```

**Every hand-rolled-TOTP trap worth warning about is already handled** — replay,
lockout, verified enrolment, encrypted secret, recovery codes. Hand-rolling this
would be strictly worse, and that is the whole argument for the wrapper shape.

## What is actually ours — three things

### 1. The wiring, and where it must NOT go

F008.9 established this the hard way: **dark-ship is a property of the import
graph, not just the configuration, because the import graph runs first.** A
consumer with no passkeys could not even load the package. `passkey` now lives
behind `@broberg/auth/passkey`.

So 2FA goes behind **`@broberg/auth/two-factor`**, and the existing
`verify-clean-install.mjs` guard enforces the install cost automatically — it
reads the `exports` map rather than a hand-written list, so a new entry cannot
slip past it.

### 2. The QR code — the part actually asked for

Better Auth returns `totpURI`, a **string**:

```
otpauth://totp/Issuer:user@x.dk?secret=…&issuer=…
```

It renders nothing. Somebody has to turn that into a scannable image, and
without a shared helper every repo picks its own library and pushes the secret
through it differently. That is exactly the drift the reuse rule exists to stop.

**The URI is a credential, not a display string** — it contains the shared secret
in plain text. It must never reach an application log.

### 3. The one with no way back — measured, not suspected

`better-auth/dist/crypto/index.mjs:41`

```js
const symmetricEncrypt = async ({ key, data }) => {
  if (typeof key === "string") return rawEncrypt(key, data);    // ← no version envelope
  const secret = key.keys.get(key.currentVersion);
  …
  return formatEnvelope(key.currentVersion, ciphertext);         // ← rotation survivable
};
```

Two key shapes. The **string** shape writes ciphertext with no version marker, so
nothing can decrypt it once the key changes. The `{ keys, currentVersion }` shape
writes an envelope, and old ciphertext keeps working across a rotation.

**Our own type makes the dangerous shape the only shape:**

```ts
packages/auth/src/index.ts:39     secret?: string;
```

So every consumer of `@broberg/auth` is on the un-versioned path today. The day
`BETTER_AUTH_SECRET` rotates — a leak, a new environment, a re-provisioned Fly
app, someone tidying secrets — every stored TOTP secret becomes undecryptable.
And **the recovery codes are encrypted with the same key**
(`backup-codes/index.mjs:19`), so the escape hatch is gone with it.

Every 2FA user is locked out of their own account, with no self-service path
back.

**It fails in the worst available direction:** nothing breaks at rotation time.
The *next login* breaks — for the users who did the responsible thing and turned
2FA on.

**And it cannot be retrofitted.** Migrating un-versioned ciphertext requires the
old key, which is precisely what is missing in the scenario this protects
against. So the widening lands **before the first user enrols**, or not usefully
at all.

## Design

```ts
import { twoFactor } from "@broberg/auth/two-factor";

createAuth({
  secret: { keys: new Map([[1, process.env.AUTH_KEY_V1]]), currentVersion: 1 },
  plugins: [twoFactor({ issuer: "WebHouse" })],
});
```

```ts
import { totpQr } from "@broberg/auth/two-factor";
totpQr(totpURI)            // inline SVG string — browser or server
totpQr(totpURI, "dataUri") // for an <img src> or a mail
```

## Non-goals

- **SMS as a second factor.** SIM-swap makes it weaker than the password it
  protects, and `@broberg/sms` exists for messages, not for auth.
- **Email OTP.** Better Auth ships `email-otp` separately; if wanted it is its
  own story, routed through `@broberg/mail` like magic-link already is.
- **Re-abstracting Better Auth's API.** The thin-wrapper invariant from F008
  stands: register the plugin, expose its types, add fleet opinions only.

## Verification

- **Prove the lockout RED first.** Enrol under a string secret, rotate it, and
  show the secret *and* the backup codes are both undecryptable. Without that
  measurement the versioned key is a theory, and this is the one claim on the
  card that would be embarrassing to have assumed.
- **Decode the QR back to the URI.** An unscannable QR renders perfectly and
  fails only in someone's hand — looking at the image proves nothing.
- **Read enrolment back from the record**, not from the response: a wrong code
  must leave 2FA *off* in the stored row.
- **Read the backup codes from the row directly**, not through the API that wrote
  them, to prove they are encrypted.
- Mutation: break the version envelope · the enrolment verification · the replay
  guard · the QR payload — each must redden a DISTINCT test.
