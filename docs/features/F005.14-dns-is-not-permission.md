# F005.14 — Correct DNS records are not permission to send

> Parent: [F005 — Mail sending (Resend)](F005-mail.md) · builds directly on [F005.9](F005.9-sending-domain-readiness.md) (the DNS half) and [F005.10](F005.10-sender-domain-normalisation.md) (its first consumer's correction).

**Status:** Backlog · **Filed:** 2026-09-08, by helpdesk via intercom #26860 · **Not started**

## How this arrived

helpdesk asked for domain verification in `@broberg/mail`, following the reuse rule rather than hand-rolling a raw `fetch` to `api.resend.com`. That was the right call and it produced three findings, only one of which is the feature they asked for.

**Half of it already shipped, in the version they run.** `@broberg/mail/verify` has exported `verifySendingDomain` since v0.6.0; they are on 0.10.1. It already does the thing they asked us to be careful about — `missing` and `unknown` are separate fields and an `unknown` never counts as `ok` — which they requested by citing our own secret-scan 0.2.2 lesson back at us.

So they can unblock their F007.2 today. Told them so (#26864).

## The gap that is real

| | asks | answers |
|---|---|---|
| `verifySendingDomain` | DNS | are the SPF/DKIM/MX records there? |
| **missing** | Resend `/domains` | does Resend say `verified`? |

**These disagree in the dangerous direction.** A domain can have all three records correct and still sit at `pending` in Resend, which then refuses to send from it. DNS is necessary and not sufficient.

For a single-tenant app that is a boot-time annoyance. For helpdesk it is the product: they are multi-tenant, each tenant sends from its own subdomain (`support.fdsundhed.dk`), and **onboarding a customer is not finished when the DNS records are added — it is finished when Resend says `verified`.** Without the lookup they send from a half-configured domain, and the failure is silent: the mail looks sent and lands in spam.

Both halves are needed, for different jobs:

- **DNS** tells the customer *what to create*. It is the only half that can produce an actionable instruction, and `verifySendingDomain` already carries the fix alongside each missing record.
- **Resend's verdict** tells us *when we may start sending*. Only the provider knows that.

## The trap in the obvious implementation

helpdesk proposed the status union directly:

```ts
status: "verified" | "pending" | "not_started" | "failure" | "temporary_failure"
```

That is **Resend's** closed list, and it can grow. Write it into our type and a status Resend adds tomorrow falls through to every consumer's `default` branch — and **if that branch is the permissive one, a single provider release widens the gate at every consumer simultaneously.**

This is on the books. F070 hit it exactly: adding a fourth outcome (`conflicted`) landed it in the `default` branch, and that branch was the accepting one, so the new outcome silently reopened a hole. The rule written then still applies — *the permissive outcome must never be the `default` branch.*

And the second half of helpdesk's own request is the same shape one level up: **a lookup we could not perform must not be expressible as any Resend status.** `not_started` is the one that would be reached for, and it is the worst possible collision — a consumer reads it as "the customer has not added their DNS records yet" when the truth is "we never asked". One sends the customer a to-do they have already done; the other is a bug in us.

## Design sketch

Three things, and the third is the one that prevents the fleet-wide version of this bug.

1. **A reporter** — the raw Resend verdict, with the could-not-ask case as a distinct `ok:false`, not a status value.
2. **Unknown-status preservation** — a status outside today's vocabulary is carried verbatim and classified as unknown. Never coerced, never permissive.
3. **A decider** — one call that answers *may I send from this domain* as a three-state, so no consumer writes its own switch over provider statuses. helpdesk asked for a reporter; a reporter alone means every consumer rebuilds the `default`-branch trap independently. That is precisely the drift this package exists to remove.

Ship-dark like the rest of the package: no key → a defined could-not-ask result, never a throw.

## Reuse

Checked Discovery before writing this (`discovery.broberg.ai/api/search?q=domain+verification`, and the roster). Nothing in the `@broberg/*` inventory covers a provider-side domain verdict; `@broberg/mail` already owns the DNS half, so the provider half belongs beside it rather than anywhere else. No raw `fetch` to `api.resend.com` is acceptable in a consumer — that is the anti-pattern the reuse rule names explicitly, and helpdesk correctly refused to write one while waiting.

## The discoverability defect, which caused the request

Measured, and it is ours:

```
packages/mail/src/index.ts doc-comment:  "It owns DELIVERY only"  — /verify not mentioned
README lines 1-40:                        names no subpath at all
verifySendingDomain's own section:        README line 180
```

helpdesk enumerated exactly what the root entry exports plus the webhook subpath — which is what an editor shows a TypeScript user — and correctly concluded the capability was absent. They were reading right; the package was presenting wrong.

**Third instance of this shape in one evening**, which is why it is an acceptance criterion rather than a footnote:

| where | what was invisible |
|---|---|
| `@broberg/stripe` README | the API table still documented a function 0.4.0 had removed |
| `@broberg/stripe` | everything F053.12 shipped — `checkSpecDrift`, `probeStripeShape` — documented nowhere |
| **here** | `/verify`, absent from both the entry doc-comment and the README opening |

The summary is what gets read. A correction or a capability that lands only in the body has not landed.

## Non-goals

- **Creating** or configuring domains in Resend. This reads a verdict; provisioning is a console/DNS operation and DNS changes go through buddy.
- Replacing `verifySendingDomain`. Both halves stay, separately readable — the combination *DNS ok + Resend pending* is exactly the state that produces a confusing support conversation, so it must be visible rather than collapsed into one boolean.
- A generic multi-provider domain abstraction. One provider, today.

## Rollout

Minor version. Additive: a new export on the existing `/verify` subpath, nothing removed. helpdesk is consumer #1 and confirms on their multi-tenant path before this closes — they are the first to run the domain check **per tenant** rather than once at boot, which is a caller shape none of the existing tests were written for.

They offered a PR. Reasonable, but the return type gets designed here first, because the failure modes above are the whole content of the feature and a PR that gets them wrong is harder to correct than one that starts from the contract.
