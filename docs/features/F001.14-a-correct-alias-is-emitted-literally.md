# F001.14 — A correct alias is emitted as a literal brace string

**Status:** Backlog
**Parent:** F001 — `@broberg/theme`
**Reported by:** cardmem, 2026-08-29, against a clean `0.5.0` install

---

## The measurement

```
colors.a: "#ZZZZZZ"           → REFUSED, names colors.a           ✓
colors.a: "{colors.missing}"  → REFUSED, names the alias          ✓
colors.a: "{colors.ink}"      → ACCEPTED, emitted as --a: {colors.ink}
```

0.5.0 checks that an alias resolves to *something* and then **never substitutes
the value**. So a *correct* alias — what you write on purpose when two tokens
share a value, using DESIGN.md's own reference syntax — becomes a custom property
whose value is a literal brace string. No browser understands it, no error
mentions it, and the generator reports success.

**cardmem's phrasing is the sharp one: the invalid case now shouts and the valid
one is silent.** It is *harder* to spot than the bug it succeeded, because the
input is right — nobody debugging starts with the token they wrote correctly.

## I named this and deferred it

F001.12's constraints, verbatim:

> *Do not resolve aliases to their values — that is a real feature and a separate
> card. This one only refuses to emit a reference that names nothing.*

The deferral was reasonable. Not writing the card was not: "a separate card" that
does not exist is a promise, and the context that motivated it decays. It took a
consumer asking, three hours later, for the other half to get written down.

## Why this is not low priority

**Measured: 0 aliases in our DESIGN.md, 0 in cardmem's.** Nobody is hurt today.

But that is an inventory of the present, not a claim about the future.
cardmem-F280.4 has just handed **~15 repos a generated DESIGN.md whose entire
purpose is to be edited**, and an alias is the obvious thing to write the first
time two tokens share a value. The exposure is new and growing, not theoretical.

## Design

**Substitute, do not merely validate.** The 0.5.0 refusals stay exactly as they
are — an alias naming nothing is still a hard error with the same message. This
adds the step that was missing.

**Resolve transitively; refuse a cycle by name.** `a → b → a` must fail with both
names in the message. Recursing until the stack dies would put someone else's
error text in place of ours — which is precisely the crash F001.12 removed from
the contrast checker, reintroduced one function along.

**Refuse a cross-kind alias that cannot hold the value.** A radius aliasing a
colour is a new success-shaped non-answer, not a feature.

## Non-goals

- **No widening of the reference syntax.** `{namespace.name}` as DESIGN.md
  defines it. No expressions, no fallbacks, no defaults.

## What cardmem did on their side

Worth recording, because it is the pattern the reuse rule asks for: their local
`assertResolvable` was **halved, not deleted**. The colour half is ours now — a
second copy is the drift the rule exists to prevent. The alias half stays,
renamed `assertNoUnresolvedAliases` for what it actually does, and disappears the
day we substitute.

**And one observation worth carrying into our own work:** they first reported the
guard had shipped untested, having grepped for the *function* name. It had a test
— named after the *property*, not the function — and it went red on the upgrade
exactly as designed. **A test that announces an obsolescence is rarely named
after the thing it retires.**

## Rollout

1. Prove RED against published 0.5.0: `{colors.ink}` emits the literal string.
2. Substitute, with transitive resolution and a named cycle error.
3. Keep the 0.5.0 refusals as negative controls, so the fix cannot pass by
   loosening validation.
4. Mutation pass — removing substitution, and removing the cycle guard, each
   turn a test red, each mutation with a receipt that it applied.
5. Tell cardmem the version so they delete `assertNoUnresolvedAliases`.
