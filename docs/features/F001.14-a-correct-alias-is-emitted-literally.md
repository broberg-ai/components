# F001.14 — A correct alias is emitted as a literal brace string

**Status:** SHIPPED in `@broberg/theme` 0.6.0
**Parent:** F001 — `@broberg/theme`
**Reported by:** cardmem, 2026-08-29, against a clean `0.5.0` install

---

## The measurement

```
colors.a: "#ZZZZZZ"           → REFUSED, names colors.a           ✓
colors.a: "{colors.missing}"  → REFUSED, names the alias          ✓
colors.a: "{colors.ink}"      → ACCEPTED, emitted as --a: {colors.ink}
```

0.5.0 checks that an alias resolves to *something* and then **never substitutes
the value**. So a *correct* alias — what you write on purpose when two tokens
share a value, using DESIGN.md's own reference syntax — becomes a custom property
whose value is a literal brace string. No browser understands it, no error
mentions it, and the generator reports success.

**cardmem's phrasing is the sharp one: the invalid case shouts and the valid one
is silent.** It is *harder* to spot than the bug it succeeded, because the input
is right — nobody debugging starts with the token they wrote correctly.

## The half nobody reported, and it was worse

Measured on published 0.5.0 while writing the fix, on the same valid alias:

```
checkContrastAA(…foreground: "{colors.ink}"…)
  → TypeError: Cannot read properties of undefined (reading 'r')
```

**culori's stack — the exact crash F001.12 was written to remove.** That fix
closed it for an *unparseable colour* and left it fully open through a *valid
alias*, which is the input a real DESIGN.md actually contains. `assertColour`
deliberately skips an alias ("resolvability is the other check's job"), so the
raw brace string went straight on to culori.

**I closed the case I tested and left the case people write.** cardmem's framing
explains why I did not find it myself: the invalid case shouts, so that is the
one I built inputs for.

## I named this and deferred it

F001.12's constraints, verbatim:

> *Do not resolve aliases to their values — that is a real feature and a separate
> card. This one only refuses to emit a reference that names nothing.*

The deferral was reasonable. Not writing the card was not: "a separate card" that
does not exist is a promise, and the context that motivated it decays. It took a
consumer asking, three hours later, for the other half to get written down.

## Why this was not low priority

**Measured: 0 aliases in our DESIGN.md, 0 in cardmem's.** Nobody was hurt.

But that is an inventory of the present, not a claim about the future.
cardmem-F280.4 has just handed **~15 repos a generated DESIGN.md whose entire
purpose is to be edited**, and an alias is the obvious thing to write the first
time two tokens share a value.

## What shipped

**Substitute, do not merely validate**, transitively. The 0.5.0 refusals are
unchanged with **byte-identical messages**, kept as negative controls so the fix
cannot pass by loosening validation.

**A cycle is refused BY NAME**, with both tokens in the message. Not theoretical:
with the guard removed, `a → b → a` grows the chain array without bound and node
dies with `FATAL ERROR: Reached heap limit — JavaScript heap out of memory`.
Somebody else's failure in place of ours, which is what this whole function is
here to stop.

**Validation runs on the RESOLVED value**, so a cross-kind alias needs no
separate rule: `colors.a: "{rounded.lg}"` resolves to `12px` and is refused by
the existing colour check, by name. One rule instead of two that could disagree.

**The contrast checker measures the resolved colour**, so an aliased token is
actually measured rather than crashing — and the real 1.02:1 failure it was
hiding is now reported.

## My own test pinned the defect — again

`"ACCEPTS an alias that DOES resolve"`, written this morning, asserted
`toContain("--body: {colors.ink};")`. It **required** the literal string. Fixing
the generator turned it red.

Second time in one day, both mine. It now asserts the property a consumer depends
on: the alias resolves, and no reference syntax survives into the CSS.

## What cardmem did on their side

Their local `assertResolvable` was **halved, not deleted**. The colour half is
ours now — a second copy is the drift the reuse rule exists to prevent. The alias
half stayed, renamed `assertNoUnresolvedAliases` for what it actually does, and
is deleted now that 0.6.0 substitutes.

**One observation worth carrying:** they first reported the guard had shipped
untested, having grepped for the *function* name. It had a test — named after the
*property*, not the function — which went red on the upgrade exactly as designed.
**A test that announces an obsolescence is rarely named after the thing it
retires.** That cost them a wrong report and would have cost us a deletion.
