# F033.14 — FlyClient: en maskine vi aldrig så er ikke «destroyed» + volumes + Prometheus

Parent: F033. Rapporteret af cms (#637) og buddy (#638), 24/9 2026.

## Målt før design (24/9, read-only mod rigtige Fly)

| kald | svar |
|---|---|
| forkert token, ukendt maskine | 404 `machine not found` |
| godt token, ukendt maskine | 404 `machine not found` (identisk) |
| forkert token, app | 401 token validation error |
| forkert token, volumes | 401 |
| Prometheus med `Bearer <token>` | 401 |
| Prometheus med `FlyV1 <token>` | 200 |

## 1. waitForExit

`getMachine` → null på 404 → `waitForExit` returnerede `{destroyed, null}`. For en maskine vi aldrig har set, er det ikke et svar — det er to mulige fejl (forkert id, forkert token) med en success-lignende form. Regel: **404 på første poll kaster** `FlyApiError(404)` med besked der navngiver begge årsager. 404 EFTER at maskinen er set = `destroyed` (auto_destroy fjerner den). Kendt kant: en auto_destroy-maskine der er væk før første poll vil nu kaste — målt af cms at Fly stadig returnerer den som `destroyed` lige efter, så kanten er smal, og en fejl dér er bedre end en falsk slutning.

## 2. listVolumes(app)

`GET /apps/:app/volumes` via samme `rest` (30 s tidsgrænse, retry kun 408/429/5xx). Filtrering af `destroyed` overlades til forbrugeren — klienten returnerer hvad Fly siger.

## 3. promQuery(org, query, { time? })

`GET https://api.fly.io/prometheus/:org/api/v1/query`. Auth-fælden skjules: `FlyV1 <token>`, og hvis tokenet allerede starter med `FlyV1 ` sendes det som det er. Prometheus kan svare 200 med `status:"error"` → kastes. Returnerer `data` (`resultType`, `result`).

## Reuse
