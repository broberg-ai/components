# F078.1 — Headless core: `deriveDevice(headers, launchCtx)`

> Story under **F078 — @broberg/device-stats**. First build step.

## Why this story carries the risk

The adapters are thin. If the buckets or the UA parsing are wrong, **everything downstream is confidently wrong** — and a device statistic has no natural contradiction to catch it. A dashboard showing 40% iOS looks exactly the same whether it is true or whether the parser mis-assigned a family. There is nothing to notice.

So the correctness lives here, and two of the acceptance criteria exist purely to make it disprovable.

## Real User-Agent strings are an AC, not a preference

A UA table tested against strings *I invent* tests my idea of the format. The fleet lost time to exactly that shape **three times this week**:

- the `@broberg/i18n` README documented a detection chain from memory and had dropped a whole step;
- a Tailwind class was in the markup while the plugin that generates it was missing — every source-reading guard stayed green;
- a `secret-scan` probe below the pattern's length floor was read as a missing pattern, twice, and both reports were withdrawn.

So: capture the strings from something **real** — the fleet's own request logs, Lens runs on both engines, published UA corpora — and **record in the fixture file where each one came from**. Provenance is part of the artifact.

## The one that will bite: frozen versions

Modern Chromium **freezes the OS version** in the plain `User-Agent`; the iOS/Android major version is no longer reliably in there. Safari drifts in its own way.

So Tier 0 will legitimately return `unknown` for some OS versions, **and that is a correct answer, not a gap**.

This is the reason for AC#3. The tempting failure is a plausible default:

> A derived stat that quietly reports a *wrong* version is worse than one that reports it does not know. **The first gets used. The second gets investigated.**

The real version needs `getHighEntropyValues()` — Tier 1, consent-gated, F078.3.

## `launchCtx` — how PWA-vs-browser is answered without touching the device

The web manifest's `start_url` carries `?src=pwa`. When the user opens the app from the home screen, the browser navigates there — so **the app declares its own launch context in the URL**. Nothing was read from the terminal equipment, which is precisely why this sits in Tier 0 and needs no consent.

It answers the exact question that prompted the epic (*"er det mobil web (pwa)"*), and it degrades honestly: absent the marker, the answer is `browser`, which is what an un-installed visit actually is.

## Shape

```ts
deriveDevice({ headers, launchCtx }) → {
  formFactor:  'desktop' | 'mobile' | 'tablet' | 'unknown',
  os:      { family: string, majorVersion: number | 'unknown' },
  browser: { family: string, majorVersion: number | 'unknown' },
  launch:  'browser' | 'installed' | 'unknown',
  screenBucket?: '<=360' | '361-768' | '769-1024' | '1025-1440' | '>1440',
  source:  'ua' | 'client-hints' | 'mixed',
}
```

`source` is deliberate: a consumer reading a statistic should be able to see **which evidence produced it**, because Client-Hints-derived and UA-derived facts have different reliability. Same principle as the `build.source` convention in the fleet's health-stamp tip — say how much to trust the value you just returned.

## Anti-fingerprinting is enforced, not documented

AC#5 is adversarial on purpose: a test **attempts** to obtain a full version string, a raw pixel width, a persistent id and a hash of the combination, and asserts each is impossible — at type level and at runtime. Buckets as a *setting* would mean the guarantee lasts until the first consumer who wants more detail. Buckets baked in mean it holds.

## Non-goals

- No adapters (F078.2), no client collector (F078.3), no sink (F078.4).
- **No publish.** Nothing goes to npm in this story.
- No sessionisation, ever, without its own decision and legal review.
