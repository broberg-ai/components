# F005.13 — A verdict that was not a verdict

**Status:** In progress · **Epic:** F005 (`@broberg/mail`) · **Written:**
2026-09-01 · **Filed by:** cardmem, from F288.25

---

## Measured on the published package

Clean install of `@broberg/mail@0.9.1`:

```
verdictForEvent("delivered")                        -> "delivered"
verdictForEvent("bounced")                          -> "failed"
verdictForEvent("received")                         -> "unknown"
verdictForEvent("something-resend-adds-next-month") -> undefined   <-
verdictForEvent("")                                 -> undefined   <-
verdictForEvent(null)                               -> undefined   <-
```

The signature says `MailVerdict`. **It returns `undefined`.** Every type in the
chain says that cannot happen, so a consumer switching on the result gets a
silent `undefined` instead of a verdict — and *a mail whose delivery is unknown*
becomes *a mail with no verdict at all*.

## It is not hypothetical, and the proof is in this module's own header

`src/events.ts` records that the event list **"had been written before Resend
grew four more types"**, two of which meant the mail did not arrive.

The vocabulary going stale is the thing that **already happened**. This is what
happens the next time it does — and next time it will be silent, because the
type says it cannot be.

cardmem is carrying a local `?? "unknown"`. That is a workaround in a consumer
for a lie in the package, and it protects only the consumers who thought to write
it.

## The lesson was already written down in this repo

`@broberg/mail-identity`, F070:

> **a package that defends itself with `never` alone defends half its
> consumers.**

An exhaustive `switch` is a **compile-time** proof about the union. The input
here is a string off the wire, and a JavaScript consumer has no types at all.
Both layers are needed; only one was built.

## Why `default: return "unknown"` is the WRONG fix

It silences the compiler in exactly the case the exhaustive switch exists for:
someone adds a member to `MailEventType` and forgets to give it a verdict. The
new event would quietly answer `"unknown"` — which for a `bounced`-like event
means a failed delivery reads as undecided. **Trading a loud undefined for a
quiet wrong answer.**

A `Record<MailEventType, MailVerdict>` keeps the missing-key compile error AND
gives a safe runtime fall-through.

## The trap in the fix itself

A plain object literal inherits `Object.prototype`, so:

```ts
VERDICT["toString"]   // a FUNCTION, not undefined
```

Without an own-property check, `verdictForEvent("toString")` returns a function
where a string is promised — the same class of defect, one layer down. It gets
its own test.

## Reuse

The Discovery check (`discovery.broberg.ai/api/search?q=mail delivery status`)
returns **`@broberg/mail` itself** — this card is a defect fix *inside* the shared
package, so there is nothing to reuse and nothing to build alongside it. Recorded
rather than skipped, because "no reuse decision" and "no reuse check" are the same
two things this whole card is about not merging.

The reuse fact worth stating is the one pointing the other way: a repo that reads
Resend's `last_event` itself, rather than calling `verdictForEvent`, re-derives
this mapping — including the two rows nobody gets right by intuition
(`complained` arrived, `suppressed` is a MESSAGE status). That is the duplication
the package exists to prevent, and it is why the fix belongs here and not in a
consumer's `?? "unknown"`.

**Not reused, deliberately:** nothing from `@broberg/mail-identity`, although its
F070 supplied the argument (a package defending itself with `never` alone defends
only the consumers that compile). That is a lesson, not a dependency — importing
anything for it would couple two packages over a shared idea.
