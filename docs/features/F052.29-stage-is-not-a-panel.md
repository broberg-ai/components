# F052.29 — A stage is not a panel

**Filed by:** the `fd-sundhed` session, who are running a CSS `!important` wedge in
production because our prop cannot express what they need.

## The defect, measured in our own source

| line | surface | painted with |
|---|---|---|
| `three.tsx:667` | the **fullscreen root** | `chrome.panelBg` |
| `three.tsx:747` | the intensity/quality **card** | `chrome.panelBg` |
| `index.ts:344` | default | `panelBg: "#fff"` |

One field, two surfaces, opposite needs.

Outside fullscreen their screen looks right: a dark canvas box with a white card
beneath it. In fullscreen the **whole surface turns white** with a dark body
floating in the middle of it. Christian saw it as two screenshots side by side:
*«det ser ikke godt ud»*.

**And the prop cannot fix it.** Set `panelBg` to their dark colour and the card
goes dark too — where `text` is `#1e293b`, so the 0–10 buttons vanish. There is no
value of this single field that is correct for both surfaces. That is what a field
doing two jobs looks like from the outside.

## What they are running instead

```css
[data-bodymap-stor='1'] > * { background: #0e1424 !important }
```

Their own assessment, and it is the right one: it works, but it is a wedge under
our inline style and it breaks the day we change the structure. A consumer
maintaining a wedge against our package is precisely the drift the reuse rule
exists to stop — **extend the package, never let them work around it.**

## The half they did not ask for, and why the prop alone is not enough

`#0e1424` is a **literal in three places**:

- `three.tsx:330` — `scene.background = new THREE.Color(0x0e1424)`
- `three.tsx:740` — the canvas div
- `three.tsx:723` — the WebGL-unsupported placeholder

So a `stageBg` prop that only repainted the backdrop would leave the **three.js
scene still hard-coded**. A consumer choosing any other stage colour gets their
colour around a canvas that is still ours — and that seam is invisible on a
desktop monitor and obvious on a phone.

Which is exactly the trap fd-sundhed said they were avoiding when they chose to
read our number out of `dist` rather than pick their own near-identical navy. It
would be a poor joke to hand them a prop that reintroduces it.

**One source, or the prop is a half-measure with a visible edge.**

## The default changes, and that is the fix

The fullscreen backdrop goes from **white** to **`#0e1424`** for everyone.

Fullscreen is a *stage around the model*, not a panel. It defaulted to white only
because it inherited a field named for something else — a white void around a dark
canvas was never a considered choice, it was an accident of reuse. fd-sundhed's
framing is the correct one and is worth quoting: *fuldskærm er en scene om
modellen, ikke et panel.*

Anyone who wants the old look passes `ui: { stageBg: '#fff' }`. Fullscreen shipped
12 hours ago (0.6.0), so fd-sundhed is realistically its only consumer — but the
change is stated plainly to Christian and to them regardless, because a visible
default change shipped quietly is how a consumer discovers their own product
looks different without knowing why.

## The placeholder goes the other way, deliberately

The WebGL-unsupported box is a **message**, not a stage. It moves onto
`panelBg` + `mutedText` — a pair the contrast test already asserts at 7.58:1.

Leaving it hardcoded (`#cbd5e1` on `#0e1424`) would make it unreadable the moment
someone chose a light stage, and **no prop could rescue it**. Following `stageBg`
would need luminance-derived text, which is machinery this does not warrant.

## Scope

3D only. The 2D renderer has no fullscreen and no canvas, so `stageBg` is declared
on the shared palette type (it describes the stage, which is a shared concept) but
consumed only by `BodyMap3D`. Documented as such rather than silently inert.

## Reuse

Discovery searched `theme`, `palette`, `background token`. The relevant hit is
**`@broberg/theme`**, and it is deliberately not adopted here: `bodymap` takes a
consumer-supplied `BodymapPalette` precisely so a consuming app can pass its own
tokens in — fd-sundhed is doing exactly that. Binding the component to
`@broberg/theme`'s variables directly would make it require that package rather
than cooperate with it.

The reuse that DOES apply is the house rule the card is an instance of: one source
per value. Three literals of the same colour in one file is the violation this
repo exists to prevent, and it was ours.

## Non-goals

- Theming the three.js **lighting**. Only the background colour is in scope.
- A dark mode for the panel. `panelBg` keeps its meaning, its default, and every
  measured contrast ratio.
- Anything in the 2D renderer.
