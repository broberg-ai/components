# F038.10 — A guard that has never run, and a roster nothing compares to npm

**Status:** ready · **Parent:** F038 (Discovery) · **Priority:** high · **2 SP**

## What was found

Release-testing the Discovery automation on 2026-08-29 (publish
`@broberg/notifications` 0.3.0, deliberately without bumping the roster, so the
release was the only possible trigger). The automation fired correctly and
`check` blocked the deploy. But two things came out of it that the run itself
would not have shown:

### 1. `scripts/check-featured-fresh.mjs` is wired into NO workflow

```
$ grep -rn "check-featured-fresh" .github/ package.json
(nothing)
```

It is the **only** script in the repo that asks npm what the newest release
actually is. It was written for F038.7, hardened for F038.9 (it now distinguishes
"the site did not answer" from "the card is stale"), and it **has never once
run in CI**. A guard nobody has watched fail is not a gate — and this one has not
even been watched *pass*.

### 2. Nothing compares the roster to npm PER PACKAGE

`live-fresh` compares the **live site** to **this repo**. Those two agreeing
proves the deploy landed. It says nothing about whether the repo is right.

So the forgotten-roster case is caught only by luck: the hero card is generated
from npm, so publishing the **newest** package changes the generated HTML and
`check` sees it. Publish a patch to a package that is *not* the newest and:

- the hero card does not move,
- nothing asks npm about that row,
- `live-fresh` goes green,
- and Discovery tells every repo in the fleet to install a version that is behind.

That is the direction that has already burned us: for three days Discovery
pointed at `@broberg/webpush` 0.2.1 — the version whose icon path renders nothing
on iOS, silently — and it cost xrt81 a full day.

## Non-goals

- Not making the roster auto-write itself from npm. `ver` is checkable; the
  **role text and maturity are the owner's to speak to**, and npm can prove a
  version exists but cannot prove what a package now does (precedent: the
  2026-08-17 sweep, and `cms-inline-edit` growing a capability its one-liner hid).
- Not failing a release because the roster is behind. The publish already
  happened; the roster is what needs to catch up.

## Approach

1. A check that asks npm for **every** shipped `@broberg/*` row and compares it
   to `ver` in `scripts/inventory-data.mjs`. `npm-latest.mjs` already does the
   fetching.
2. Three outcomes, not two — the F038.9 lesson, applied at birth: *could not
   ask npm* is a third state and must never read as a pass.
3. Run it in the `discovery` workflow. Decide deliberately whether a behind-roster
   is a hard red or an annotation: it must be **visible**, and it must not be able
   to block an unrelated push forever if npm is unreachable.
4. Wire `check-featured-fresh.mjs` into the same job, against the LIVE url — the
   thing it was built to check and has never been pointed at.
5. **Prove each one red before trusting it green** (roster row set behind on
   purpose, then restored).
