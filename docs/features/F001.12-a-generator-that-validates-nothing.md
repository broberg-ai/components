# F001.12 — The generator validates nothing, and the contrast checker crashes instead of naming the token

**Status:** ready · **Parent:** F001 (@broberg/theme) · **Priority:** high · **3 SP**

Reported by **cardmem** (#23754 via cms, then directly in #23764) as defect 3 of
four. Defects 1, 2 and 4 shipped in 0.4.0; this is the remainder.

**A correction I owe first:** I told cardmem this was "carded separately as
F001.12" before the card existed. It did not, for about an hour. This is that
card, written the moment the gap was noticed rather than left as a promise
someone else was relying on.

## Measured against 0.4.0, not assumed

```
input                          emitted
colors.brand  "#ZZZZZZ"    →   --brand: #ZZZZZZ;
colors.alias  "{colors.missing}" → --alias: {colors.missing};
rounded.lg    "not-a-length" →  --radius-lg: not-a-length;
```

`designMdToTailwindV4` throws on missing YAML front matter **and on nothing
else**. So "the generator ran" and "the generator checked nothing" are the same
observation — cardmem's phrasing, and it is exact.

The alias case is the worst of the three: `{colors.missing}` is DESIGN.md's own
token-reference syntax naming a token that does not exist, and it lands in the CSS
as a literal string. It does not look like corruption; it looks deliberate.

## And a finding cardmem did not report, because it needs a specific input

`checkContrastAA` does not silently pass an unreadable colour — **it crashes**,
with someone else's stack trace:

```
TypeError: undefined is not an object (evaluating 'c.r')
  at luminance (node_modules/culori/src/wcag.js:12:18)
```

Measured across all four cases, because "it throws" and "it passes" are opposite
failures and only one of them is true here:

| foreground | verdict |
|---|---|
| `#777777` on `#FFFFFF` | correctly reported as failing 4.48:1 |
| `#000000` on `#FFFFFF` | correctly `[]` |
| `#ZZZZZZ` | **culori TypeError** |
| `{colors.missing}` | **culori TypeError** |

I assumed at first that it would report `[]` — a silent pass — because that is
the day's pattern and I was pattern-matching rather than measuring. It does not.
It is still wrong: a consumer sees a third-party stack trace instead of *"your
DESIGN.md's `foreground` is not a colour culori can parse"*, and the WCAG checker
is exactly the tool whose failure must be legible.

## Approach

1. **Validate on the way out, not by inventing a CSS parser.** A colour must
   parse (culori already tells us); a length must look like one; a
   `{token.reference}` must resolve against the tokens actually present.
2. **Refuse or report — decide per case and write down which.** An unresolvable
   alias is a hard error (nothing sensible can be emitted). An unparseable colour
   is a hard error. An odd-looking length is a warning, because CSS accepts more
   than a regex knows and a generator that refuses `clamp(...)` is worse than one
   that lets it through.
3. **`checkContrastAA` names the token and the value it could not read**, and
   never lets a dependency's TypeError reach the caller.
4. **The report is the same `skipped`-shaped channel 0.4.0 added**, not a second
   mechanism — one way to ask "what did you not do with my file".

## Non-goals

- No CSS value parser. Validate the shapes DESIGN.md actually specifies.
- Not resolving aliases to their values (that is a real feature, and a separate
  card). This one only refuses to emit a reference that names nothing.

## Coordination
