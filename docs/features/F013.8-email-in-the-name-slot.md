# F013.8 — 0.2.0 regressed an email in the name slot, and my own AC was narrower than its claim

> Parent: [F013](F013-gravatar.md). A regression introduced by [F013.7](F013.7-gravatar-three-outcomes-and-initials.md), reported by **moovyy** within the hour of adopting it.

## The regression

```
0.1.0:  getInitials("cb@webhouse.dk")  →  "CB"
0.2.0:  getInitials("cb@webhouse.dk")  →  "CD"
```

One argument, so the address goes down the **name** branch. The new unicode split turns `cb@webhouse.dk` into `['cb','webhouse','dk']` — three words, so first + last gives `c` + `d`.

0.1.0 split on whitespace, got a single word, and took its first two characters. Right for the wrong reason — **but the user saw the right result.**

Measured after their report, and worse than described. **Every** address in the name slot now ends in the TLD's first letter:

```
"jens.hansen@firma.dk"  →  "JD"
"christian@broberg.dk"  →  "CD"
"x@webhouse.dk"         →  "XD"
```

Systematic, not an edge case. And it degrades in the worst available way: no type error, no exception, no red test. A repo upgrades and its avatars quietly start showing the wrong letters.

## Why my own test did not catch it

This is the part worth keeping.

F013.7's AC#6 reads:

> *The existing `cb@webhouse.dk` → `'CB'` still holds — it must, or the fix is a regression for the common case.*

I proved exactly that string. I proved it in the **email argument**:

```ts
getInitials(null, "cb@webhouse.dk")  // 'CB' ✓
```

moovyy's call-site passes it in the **name argument**, because their display value is `navn = bruger.navn || bruger.email` — an utterly ordinary shape.

So the AC's **claim** was about the common case, and the **test** was about one argument position. Both green. The gap between them is where the regression lived.

That is this week's failure form arriving inside my own acceptance criteria rather than in someone's code: **a check that answers a narrower question than the one it is read as answering.** The same shape as a `dig` line read as a pass, a `mode: 'live'` that was true and insufficient, and a mutation whose anchor matched nothing.

## The fix

Detect an email in the name slot and send it down the email path.

moovyy's alternative — return `'??'` — is worse **here**, and the reason is specific: 0.1.0 produced the *right* answer and users saw it. Degrading a previously-correct case to "don't know" is still a regression, just a more honest-looking one.

Detection is deliberately **conservative**: exactly one `@`, non-empty and whitespace-free on both sides. A name containing an `@` is not a name.

## The test that should have existed from the start

Not a case. An **invariant**:

```ts
for (const addr of EMAIL_FIXTURES) {
  expect(getInitials(addr)).toBe(getInitials(null, addr));
}
```

A table of individual cases can be complete and still miss the *relationship* between two arguments. That relationship is the thing that broke, and nothing in a per-case table was ever going to look at it.

## The same shape, from their side

Worth recording because it happened in the same hour, in the guard written to prevent this exact class of call:

> moovyy added a guard requiring two-argument calls. **The guard was green on a bug**: its regex matched `getInitials(navn, email)` inside their own doc comment, so a one-argument call passed. They now strip comments before matching.

The instrument looked at the wrong thing and answered green. Both halves of this exchange produced one, an hour apart.

## Reuse

Nothing to adopt — a fix to a package `components` owns, correcting a regression `components` shipped.

## Rollout

Patch, `0.2.1`. moovyy is on 0.2.0 in production **right now** with wrong initials rendering, so they are told directly rather than left to read a changelog.
