# F010.9 — `Retry-After` must never be `0` on a 429

> Story under **F010 — @broberg/apikey**. Consumer-filed bug from **beacon** (#19017), found while adopting 0.3.0.

## Motivation

Both adapters compute:

```ts
Math.max(0, Math.ceil((r.resetAt - Date.now()) / 1000))
```

beacon's own middleware used `Math.max(1, …)` and they asked whether ours should too. **Reproduced here before changing anything**, because the answer is not obvious — it depends on whether the raw value can actually reach zero.

`SlidingWindowRateLimiter.check()` captures `now = Date.now()` **before** awaiting the store, and `resetAt = oldest + windowMs` is derived from that pre-await timestamp. The header is then computed from a *second*, later `Date.now()`. Whenever the elapsed time between the two exceeds the remaining window, the difference goes negative.

With the default in-memory store that gap is microseconds — 400/400 sampled 429s reported `1`, never `0`. **So this is not reproducible on the default configuration**, which is presumably why it survived.

But the package explicitly supports a **shared remote store** (Turso/Redis) so a stateless multi-machine fleet does not leak a window per machine. Injecting a store with 40 ms latency against a 50 ms window:

```
allowed          : false   (429 sent)
remaining        : 0
current code     : Retry-After: 0
beacon's fix     : Retry-After: 1
```

A `429` carrying `Retry-After: 0` tells the caller to **retry immediately while it is still limited** — the opposite of the header's purpose. A well-behaved client that obeys it produces a hot retry loop against an endpoint that is already shedding load, which is exactly when you least want one.

## Scope

Floor the value at `1` in **both** adapters:

```ts
Math.max(1, Math.ceil((r.resetAt - Date.now()) / 1000))
```

Plus a README note beacon raised: when `onLimited` renders its own body, the body's wait/limit numbers and the `X-RateLimit-*` headers are produced in two different places. A caller told "1 per 60s" in the body and `600` in the header cannot tell which to believe. Consumers should quote `result.limit` / the same result object rather than a separately-held constant. That disagreement is only observable consumer-side, so it belongs in the docs, not in a package assertion.

### Non-goals

- **Not** re-reading `Date.now()` inside `check()` to shrink the window. That narrows the race without closing it — any elapsed-time gap (a slow store, event-loop delay, a long GC pause) reproduces it. The floor is correct regardless of the gap's cause.
- No change to `allowed` / `remaining` / `resetAt` semantics. `resetAt` staying in the past is *information*; the header just must not translate it into "go now".

## Dependencies

None.
