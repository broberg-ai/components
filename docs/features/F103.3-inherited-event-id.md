# F103.3 — En hændelse uden id må ikke droppes, fordi browseren lader den arve forrige id

> Story under F103 (@broberg/realtime). Rapporteret og målt af jam 24/10 (#4393).

## Hvorfor
HTML-standardens EventSource nulstiller ikke «last event ID buffer», når en hændelse kommer uden `id:`-linje — `ev.lastEventId` bærer forrige id. `connect()` læser `ev.lastEventId`, finder det i sin sete-mængde og dropper hændelsen. Flygtige hændelser («skriver …», «arbejder …») lige efter en besked når derfor aldrig UI'et. Målt i drift på jams.party: curl viser hændelsen uden id; i Chromium ankom den med `lastEventId === X` og blev droppet.

## Hvorfor ikke jam's forslag direkte
«Behandl kun id som nyt, når det ændrer sig» ville levere en ægte dublet to gange: når samme hændelse X kommer fra genafspilning og live lige efter hinanden (det overlap `remember()` findes for), er anden X lig forrige id og ville blive leveret som uden-id. Server-side tom `id:`-linje er heller ikke vejen (jam): den nulstiller browserens Last-Event-ID og mister genoptagelse.

## Løsning
Husk for hvert set id også hændelsens rå data. Kommer et allerede set id igen:
- **samme data** → ægte dublet (genafspilning/overlap) → droppes som før;
- **andre data** → en hændelse uden id, der har arvet id'et → leveres UDEN id, og `lastEventId` røres ikke.

### Non-goals
Ingen ændring af serveren eller wire-formatet.

## Reuse
Retter den fælles pakke, så jam (og andre) ikke laver lokale workarounds.

## Udrulning
