# F079.13 — A tool that answers nothing

> Story under **F079 — `@broberg/chat`**. Reported by **cms** after their second production crash of the day, 2026-08-28, found while hunting an unrelated error.

## What broke

```js
JSON.stringify(undefined) → undefined,  NOT the string "undefined"

let result = typeof frame.result === "string" ? frame.result : JSON.stringify(frame.result);
if (result.startsWith(…))     // ← throws
```

A tool handler that returned nothing — an early `return;`, a void function, a caught error path — produced `undefined`. The error escaped to their route's outer catch, which ended the SSE stream with *"Chat error"* **on top of a half-written answer that was fine.**

**One tool answering nothing took the whole turn down.**

## The third of the day in one family

cms's framing, and it is the useful part — **a missing value degrading into something that does not look like a missing value**:

| | |
|---|---|
| `!t.permission \|\|` | missing permission = **access** |
| `ChatMessage` without `toolCalls` | missing pairing = **an accepted shape** |
| `JSON.stringify(undefined)` | missing answer = **a value that throws three lines later** |

All three shipped from this package or its consumer in a single day.

## Measured in our own published 0.6.1 before acting

```
frame.result                      : undefined   (typeof undefined)
what WE write into the transcript : "undefined" (the STRING)
JSON.stringify(undefined) is a string : false
```

Two separate facts fall out of that, and only one of them is what cms reported.

### 1. Our internal path is already safe — the hazard is at the frame

`serialise()` has `JSON.stringify(value) ?? String(value)`, so the transcript never receives a non-string. **The hazard exists only for a consumer serialising the `tool-result` FRAME** — which is exactly what cms did, and what the next consumer will do.

So: **document, do not normalise.** cms is right that we must not guess what an empty answer means — and their own fix proves why. They chose `?? ""` and **explicitly not** `|| ""`, because a tool answering `0` **has** answered, and `||` would merge *"zero documents"* with *"no answer"*. Six tests on exactly that distinction. Different consumers need different semantics; ours is not theirs.

One sentence at `tool-result` turns the next reader's **surprise** into their **choice**.

### 2. And a finding of my own, which nobody asked about

**We write the literal string `"undefined"` into the transcript the MODEL reads.** That is a JavaScript artefact leaking into a prompt. A model told that a tool answered *"undefined"* may well pass that on to a user — the same class as the English developer note reaching a Danish customer in F079.12.

**I am not changing it in this card.** It is a behaviour change nobody requested, and cms's own rule cuts both ways: *we* must not guess what an empty answer means either. `""`, `"(no result)"` and `"undefined"` are three different messages to a model, and picking one for every consumer is the mistake this package keeps declining to make.

Raised with cms, and recorded here as an **open question** rather than silently decided.

## Non-goals

- Not normalising `result`. Not choosing `?? ""` for anybody.
- Not changing the transcript string in this card.
- Not adding a helper. cms hand-rolled one and got it right; the sentence they needed was documentation, not code.
