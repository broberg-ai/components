# F008.11 — the signing secret nobody set

**Status:** In progress · **Epic:** F008 (`@broberg/auth`) · **Written:** 2026-09-03

## Motivation

cardmem measured their own exposure and found they set **neither** `secret` **nor**
`secrets`, so the key falls through to the environment. I went to measure what
Better Auth then uses. Chain (better-auth 1.6.23,
`dist/context/create-context.mjs:70,78`):

```
options.secret || BETTER_AUTH_SECRET || AUTH_SECRET || "better-auth-secret-12345678901234567890"
```

The last term is a **hardcoded literal in Better Auth's own source** — it ships in
every copy on npm, so it is public.

**Measured, with `NODE_ENV` set before process start:**

```
NODE_ENV unset                boots  -> the public default
NODE_ENV=development          boots  -> the public default
NODE_ENV=production           THROWS   <- the only protection
NODE_ENV=production + TEST=1  boots  -> the public default
NODE_ENV=test                 boots  -> the public default
```

The defence is `validateSecret`'s `isDefaultSecret && isProduction`, itself behind
`if (isTest()) return`, where `isProduction === (NODE_ENV === "production")` and
`isTest() === (NODE_ENV === "test" || truthy TEST)` (`env-impl.mjs:32,36`). So the
whole protection rests on **two environment variables the platform owns**, and a
stray `TEST=1` in a container removes it.

cardmem then measured their **running** container: `NODE_ENV=production`, `TEST`
absent, `BETTER_AUTH_SECRET` set. They are covered. Their framing is the right
one: *the guard is the backup, the set secret is the defence.* This card is about
moving the protection from an env var the platform owns to an assertion the
package can hold itself.

**Our own contribution to the silence:** `buildAuthOptions` and `createTypedAuth`
forward `secret`/`secrets` **only when set** and we have no boot check, so a
consumer inherits all of the above without a line of code to look at.

## Two instrument notes

1. **My first probe was wrong on the axis it was built for.** It assigned
   `process.env.NODE_ENV` *inside* the script, after a hoisted static import — so
   the module-load `const isProduction` was already `false` and the probe reported
   "production boots fine". Env for this class of test must be set **before**
   process start.
2. **`if (!secret)` at `create-context.mjs:42` is unreachable.** Line 78's fallback
   means `secret` is never falsy, so the error message that names the missing
   variable can never print. The only live branch is default+production.

## Scope

A `resolveSecretOrThrow(config)` used by **both** live factories (`createAuth`,
`createTypedAuth`). It reads the same four terms Better Auth reads and throws when
the result is the published constant, or when nothing resolves at all. Independent
of `NODE_ENV` and `TEST` — that independence is the entire point.

### Non-goals

- **Not** touching the short/low-entropy checks. Better Auth warns on `< 32` chars
  and low entropy; duplicating that is noise, and a warning is the right severity
  for "probably fine".
- **No env-readable escape hatch.** An escape that can be set from the environment
  reintroduces exactly the `TEST=1` hole. The code-level escape already exists and
  is the correct one: pass a `secret`.
- **Not** guarding the pure `buildAuthOptions`. It assembles options without
  booting anything, and unit tests that only inspect the assembly (magic-link,
  passkey) should stay green.
- **Not** generating a random per-boot secret when none is set. That trades a loud
  failure for sessions that silently die on every restart.

## Reuse

Discovery checked (`/api/search`) for `secret validation`, `boot check`,
`startup guard`, `auth secret`, `default secret`. Nearest existing patterns:

- **`@broberg/secret-scan`** — redacts secrets in text. Different job; it cannot
  tell whether a *configured* key is the vendor default. No reuse.
- **`@broberg/mail`** — the closest shared pattern: it exposes a `mode` field and
  lets the consumer decide whether to throw. **Deliberately not reused here.**
  Mail's failure is "no mail sent" — visible and recoverable — and cms showed a
  boot assert would be false precision there because they resolve a key *per
  tenant at send time*. Auth's failure is "sessions signed with a public key":
  invisible, security-relevant, and our wrapper has exactly one key at boot. A
  field the consumer may ignore is the wrong shape for a hole nobody can see.

So: extend `@broberg/auth` itself, which is the package that owns this.

## Rollout

0.4.0. Not breaking for production code — anything with a real secret is
unaffected, and anything without one is already broken. It **is** breaking for
test setups that boot auth with no secret at all: three of our own test files do
this, and they get a real test secret rather than an exemption. The consumer
report must say so in those words, with the one-line fix.
