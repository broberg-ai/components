# F114.1 — MailProvider contract as a shared package

Parent: F114 (mail packages, from mailworker to Mail). **Not ordered yet:** built only when Mail's Build Contract is signed and the order arrives (the epic's own note, 19 Nov 2026). This story exists so the epic is not empty and the next session does not have to guess what comes first.

## Why
Mail builds on code that today lives in mailworker (OAuth connection, noise filters, tone, triage, read adapters gmail/graph/imap). D-d3c8c9: no copy of code between repos — only packages. The seam between "a mail source" and everything above it is the MailProvider interface, and it is already agreed.

## What is already settled (19 Nov)
Mail sent the MailProvider spec (broberg-ai/mail 7fa0033); components accepted it with three changes, all landed in broberg-ai/mail 9e5104c:
1. `send` is out of MailProvider. A reply is `saveDraft({ replyTo })` plus sending through `@broberg/mail` `createMailer({ transport })`; the send rules (old R11/R12) move into `@broberg/mail`'s own suite when the extraction happens.
2. `isMailProviderError` matches on `name` and a string `code`, with a test that a foreign copy of the class is recognised.
3. Factories take `AccessTokenSupplier = () => Promise<string>`; no personal data in logs.
The contract suite is `runMailProviderContract(name, make, { describe, test, expect })`, vitest-ready; 36 green at Mail.

## Out of scope here (later stories under F114, when ordered)
graphTransport, smtpTransport (implicit TLS 993/465), edgeTransport (Proton via Mail Edge), the calendar package (Mail's epic G), the gmail harness (Mail asks mailworker).

## Reuse
Discovery check before coding: `@broberg/mail` (send/transport chokepoint) is reused, not rebuilt. Nothing in the roster owns a mail-READING interface.

## Proof
Contract suite green against an in-memory provider; one mutation per rule; no personal data in any error/log; send path through `createMailer` only; Discovery row; release report as a possibility, not a task.
