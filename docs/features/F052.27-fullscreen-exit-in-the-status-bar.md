# F052.27 — The fullscreen exit landed in the iOS status bar

**Parent:** F052 · **Priority:** critical · 2026-08-29
**Reported by:** fd-sundhed, measured on a real iPhone. **The owner was stuck in
production**, on code I shipped an hour earlier.

---

## What I got wrong

The control renders in a row **above** the canvas. In a page that is correct.

In fullscreen, "above the canvas" is the top of a `position: fixed; inset: 0`
surface — and in a standalone / Capacitor webview that surface covers the **status
bar**. So the «Luk stor visning» pill sat on the clock, the wifi icon and the
battery: unreadable, and overlapping the system's own text.

**And there was no second exit.** I built `Escape` as the keyboard way out in
F052.24 and was satisfied with that. **A phone has no Escape.** So the component
had exactly one exit, and I had put it under the status bar — a trap with no way
out, on the platform this component's own cards call its *primary surface*.

> Building the accessible path and then placing the only other one where it cannot
> be reached is not two mistakes. It is one: I never asked what a phone user does.

---

## The fix

| | |
|---|---|
| **Safe area, all four sides** | top for the notch, **bottom for the home indicator**, left/right for landscape |
| **Compact × in fullscreen** | 40×40. The text pill is right in a page, where discoverability matters, and wrong at the top of a phone, where it is wide enough to cover half the status bar. Label moves to `aria-label`. |

Bottom inset included deliberately: the home indicator hides content exactly as
well as the notch does, and fixing only the reported half is the mistake this
package has made three times this week.

---

## Their second finding is a docs gap, and it is the one that bites next

fd-sundhed switched our button off and supplied their own — the API path working
as designed — but placed it `absolute` inside the **original** box. The fullscreen
surface is `fixed`, so their × ended up **underneath** it. With our button already
disabled, there was **no exit at all**.

Their sentence is the documentation:

> a consumer's own control must be a **sibling of the fullscreen surface**, not a
> child of something below it.

That goes in the README next to `showFullscreenButton`.

---

## What is proven, and what is not

**Proven** (Lens, WebKit, iphone-15, 9/9):

- computed padding carries the inset expression on all four sides and never
  collapses below the 12px base
- the control is `×`, ≤56px wide, keeps its `aria-label`, and reverts to the pill
  outside fullscreen
- **`elementFromPoint` at the control's centre returns the control** — the exit is
  not covered. This is the assertion that would have caught fd-sundhed's own
  overlay bug, and it is now ours too.

**NOT proven:** the actual notch clearance. A headless viewport reports
`env(safe-area-inset-*)` as **zero**, so Lens can confirm the CSS is applied and
cannot confirm it clears the clock. fd-sundhed verifies on the device. Saying the
CSS is there is not the same claim as saying the button is readable.
