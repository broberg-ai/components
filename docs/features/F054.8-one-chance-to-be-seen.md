# F054.8 — `updateReady` is event-sourced and latches once

**Status:** Ready · **Epic:** F054 (`@broberg/pwa`) · **Written:** 2026-09-06
**Filed by:** cardmem, explicitly as a *question* about our package — they found
it in their own hand-rolled glue and said they had not read our dist. I read it.
They are right.

## Measured in our own source

`packages/pwa/src/index.ts`, every write to the flag:

```
 72   let updateReady = false;
109   updateReady = true;      <- inside markReady, the ONLY writer
```

`markReady` is reachable from exactly two places:

```
174   if (registration.waiting) markReady(...)    one-shot, at attach
139   markReady(installing)                        statechange -> "installed"
```

And the two recurring checks:

```
178   registration.update().catch(...)   the interval        — and nothing else
147   registration.update().catch(...)   focus/visibility    — and nothing else
```

**Neither ever reads `registration.waiting`.** The answer is *remembered*, not
*read*. So the only routes from "a worker is waiting" to a banner are one read at
attach and an `updatefound` this tab happens to observe.

## The second half, which cardmem did not name and which is worse

```ts
const markReady = (worker) => {
  waitingWorker = worker;
  if (!updateReady) {      // <- once true, never entered again
    updateReady = true;
    emit();
  }
};
```

`emit()` fires **at most once for the life of the updater**. Both adapters drive
their state from `subscribe()` plus a single `getState()` at mount. So a consumer
who dismisses the banner does not have a stale channel — they have no channel at
all.

## One correction to their report

cardmem wrote that a consumer "has no way to ask *is one still waiting?*". They
can: `getState()` returns the flag and would answer `true`. But it is a **latch,
not a reading** — it says true because it once became true, so it would also say
true after the waiting worker was gone. A workaround built on it is stale-safe by
luck. Worth stating precisely, because someone will reach for it today.

## What I have NOT verified

That `registration.update()` fires **neither** `updatefound` **nor**
`statechange` when a worker is *already* waiting. That is cardmem's production
measurement; I have not driven a real service worker to confirm it.

It does not change the fix. **Re-deriving from `registration.waiting` is strictly
more robust than listening for an event**, whatever `update()` does or does not
fire — so the remedy does not rest on the unverified half.

## Why it is urgent rather than tidy

cardmem measured the consequence: they shipped a feature, verified it live in a
real browser on the deployed sha, and the owner reported it missing. It was on
his screen's newer sibling; his tab had no way to learn a version was waiting.

Deploy green · server on the new sha · feature live — and the only symptom
available to anyone was **a person saying something was broken**. The green
direction, in a package whose entire job is telling a client a new version
exists.

**And the consumer who is not cardmem.** fd-sundhed has run this in production
since 1 September for **16,838 municipal employees**. cardmem hit it in their own
copy — they have not adopted us yet (their F113.4 is queued). fd-sundhed hits it
in ours.

## Scope

- Re-derive from `registration.waiting` on every interval / focus /
  visibilitychange tick.
- A pure `shouldOfferUpdate({waiting, controller, snoozedUntil, now})` holding
  the decision, provable with no service worker.
- `updateReady` may go **false** and rise **again**.
- "Later" is a snooze with a documented default, not a mute.

### Non-goals

- **Not another event listener.** The defect is that the answer is remembered
  rather than read; a second listener is the same design with more surface.
- **Not a shorter poll default.** A shorter interval would mask the bug by making
  the one-shot read happen more often — the opposite of a fix.
- **Not a redesign of the banner.** `PwaUpdateBanner` is already unstyled and
  consumer-owned; only `onDismiss`'s meaning changes.

## Two test traps, handed over by cardmem

Both let an empty component agree with every assertion:

1. Under happy-dom, Preact's rAF-scheduled effects need **real timer ticks** — a
   `setTimeout(…,0)` loop never runs the effect.
2. `readyState` is `'interactive'` and `load` never fires, so a `load`-deferred
   `register()` never happens.

They now throw unless `register()` was actually called. Ours must too, or the
adapter tests prove nothing.

## Reuse

None — this is `@broberg/pwa`'s own core, in the repo that owns it. cardmem's
`shouldOfferUpdate` is a *sketch we were shown*, not a package to depend on;
their F113.4 has them adopting ours, not the reverse.
