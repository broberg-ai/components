# F005.9 — `mode` said `'live'` and it was true. The sending domain was half-configured.

> Parent: [F005 — Mail sending (Resend)](F005-mail-sending-resend.md) · sibling of [F005.7](F005.7-delivery-webhook.md) (did the mail arrive?) and [F005.8](F005.8-mailer-delivery-mode-readback.md) (will this mailer deliver as configured?).

## The case

2026-08-22. Christian could not log in to **moovyy.com**. The magic-link mail never reached him.

moovyy measured the entire chain and every link was green:

| Link | Result |
|---|---|
| Better Auth mints the token | ✅ verified in the DB |
| A token really mints a session | ✅ 302 + `Set-Cookie` |
| `@broberg/mail` mode | ✅ `live` |
| `send()` | ✅ `{ok:true, id:…}` |

Resend accepted the mail. The user still could not get in.

## Why this is not F005.8 again

This distinction is the whole card, because "we already shipped a boot readback" is exactly how this gap gets closed as a duplicate.

**F005.8 answers: given how this mailer was CONFIGURED, will it deliver?** For moovyy it answered `live` — and that was **correct**. The mailer *was* live. It *did* send. Nothing about the configuration was wrong.

What was wrong was the **domain it sends from**. Measured with `dig @8.8.8.8`:

```
send.broberg.ai     DKIM ok   SPF MISSING   MX MISSING
send.webhouse.dk    DKIM ok   SPF ok        MX 10 feedback-smtp.eu-west-1.amazonses.com
```

Same Resend account. One domain finished; the other stopped after DKIM.

So `mode: 'live'` was **a green that was TRUE and still insufficient** — a different axis of readiness that no existing signal covers. Not a false green. A green answering a question nobody had thought to ask a second one alongside.

moovyy's framing is the right one:

> *Det er ikke en manglende log; det er en manglende sans.*

Every measurable thing stopped at "Resend said yes". No line of code in the chain **could** have shouted, because none of them can see into an inbox — or, until now, into DNS.

## The workaround that does not exist

moovyy tried the obvious escape: send from the fully-configured `send.webhouse.dk` using their own key.

```
{"ok":false,"error":"This API key is not authorized to send emails from send.webhouse.dk"}   403
```

Correct security posture — no complaint. But it means **"switch to a sender domain that works" is not available** to a repo whose own domain is half-set-up. Once enrolled on a half-configured domain, there is no way around it but to wait for DNS.

That is what makes catching this **at enrolment** rather than at first failure worth real effort: the cost of missing it is not a slow fix, it is a blocked one.

## Scope

A domain-readiness check a consumer calls at boot, reporting whether the From domain has SPF, DKIM and MX.

**Where I differ from the literal ask.** moovyy proposed the package check DNS *itself, automatically, at boot*. It cannot — not from the core entrypoint. `@broberg/mail` has **zero runtime dependencies** and is framework-agnostic; it runs on edge/workers where `node:dns` does not exist. Importing DNS into the main entry would break portability for every consumer in order to serve the ones on Node.

So: a **separate Node-only subpath** the consumer calls, at the same boot moment and next to the existing `mode` assertion. Same log line, no cost to the universal core.

**Non-goals**
- Checking deliverability *outcome* — that is [F005.7](F005.7-delivery-webhook.md), the delivery webhook. This card catches a sender that should never have been put into service; F005.7 catches the mail that **was** sent. Opposite ends, both needed.
- Making the check automatic or blocking. See ship-dark below.
- Fixing DNS. Records go through buddy; the package reports, it does not mutate.

## The trap: three states, not two

The failure form this package keeps meeting. A DNS lookup has **three** outcomes, not two:

1. record present
2. record absent
3. **the lookup failed** — no resolver, timeout, NXDOMAIN on the whole zone

Collapsing 3 into 2 turns a network hiccup into a confident false alarm about a domain that is perfectly fine — and a false alarm at boot is how a check gets ignored, which is how it stops being a check at all. Asserted with a lookup that throws.

## Ship dark

It never throws and never blocks a send. It is a **report**, and the consumer decides what to do with it. A repo that does not call it is entirely unaffected; a repo that calls it on a broken resolver still boots.

## A note kept for the record

moovyy's own diagnosis of *why* the mail vanished was wrong, and it is instructive. They read SPF=none plus `p=quarantine` as "DMARC quarantines it". But the DKIM record is complete (218 chars, valid RSA-1024, ends `IDAQAB`) and `adkim=r` means `send.broberg.ai` aligns with `broberg.ai` — so **DMARC passes on DKIM alone**. Spam folder, not reject.

A plausible chain of reasoning about DNS sent them to the wrong place to look. One delivery-log query would have settled it. That is the argument for F005.7, and it is why these two cards are siblings rather than alternatives.

## Reuse

Checked Discovery before writing. No `@broberg/*` package owns DNS inspection, and this belongs in the mail package rather than a new one — it is meaningless outside the question "can this mailer's domain deliver?". `@broberg/mail` is ours; the extension goes here so the whole fleet gets it, which is the rule that produced this card in the first place: a consumer hit a gap and filed it instead of working around it locally.

## Rollout

Additive minor. New subpath export, core untouched, existing consumers unaffected until they choose to call it.
