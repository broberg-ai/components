# F011.8 — appendInSync: an audit write that fails inside a synchronous transaction must throw synchronously

## Why
Measured by beacon, 22 Oct 2026 (intercom 3924). `createAuditTrail().appendIn` is `async`, so a synchronous throw from the host's `appendTx` becomes a rejected promise. Drizzle on bun:sqlite (and better-sqlite3) run `db.transaction(cb)` with a SYNCHRONOUS callback that cannot await. The callback returns normally, the transaction COMMITS, and the audit row is missing — the exact failure F011.7 was built to prevent. F011.7's title even promised a synchronous throwing path; what shipped was async.

## Scope
- `AuditTrail.appendInSync(tx, input): LogEntry` — builds the entry (layer `audit`), calls `appendTx(tx, entry)` synchronously, lets a throw propagate synchronously, returns the entry.
- If `appendTx` returns a thenable, `appendInSync` throws a named error: a synchronous transaction cannot wait for it, and silently not waiting is the bug.
- `appendIn` unchanged.
- Minor release 0.3.0 + release report to beacon.

### Non-goals
- `at` as epoch-ms (beacon's second wish). `LogEntry.at` is ISO in the frozen v1 contract; `Date.parse(entry.at)` gives the number in the host. Changing the type would break every adapter.

## Reuse
This is the shared package (`@broberg/event-log`).
