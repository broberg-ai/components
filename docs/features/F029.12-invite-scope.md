# F029.12 — Invitation to a UNIT: optional `scope`

## Why
scout (pilot, 7/10 #2034): Scout's roles sit per unit. An invitation today carries `{tenantId, role}` only, so the write side (invite → accept → unit membership) has no way to say *which* unit. Read side is already solved by the store deriving org membership from unit memberships (F029.8 note).

## Design (proposed to scout, pending their read)
- `scope?: string` — opaque to the package. Added to `CreateInviteInput`, `StoredInvite`, `Membership`.
- Carried into `store.addMembership({ userId, tenantId, role, scope })`, not merely returned. Reason: `acceptInvite` already heals a half-finished accept by re-calling `addMembership`; if scope were only returned, a crash between org- and unit-write would leave a member without a unit and the heal path could not repair it.
- Also returned from `acceptInvite` so the app can redirect into the unit.
- **Authorisation of scope is the app's**, because only the app knows the unit tree: a unit_lead of A must not invite to sibling B. Core `createInvite` is called by the app, which checks first. `/hono` POST /invites gets an optional `authorizeScope(inviter: Membership, scope, role) => boolean | Promise<boolean>`; no hook + scope in body → 400; hook says no → 403. Never silently drop the scope.
- `invitableRoles` unchanged on both create and accept.
- Single string, not `meta: Record` — one field the app owns is enough; a free-form bag invites a second hidden data model.

## Rejected
- Encoding scope in role (`unit_lead@<id>`): breaks invitableRoles and can() matching.
- Returning scope only from acceptInvite: loses the heal guarantee (above).

## Reuse
Extends @broberg/tenant itself; no new package.

## Release
Additive → @broberg/tenant 0.2.0 via publish.yml (tenant-v*).
