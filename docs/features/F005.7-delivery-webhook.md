# F005.7 — Delivery webhook: the send response cannot tell you it arrived

> Story under **F005 · @broberg/mail**. The second half of the gap xrt81 filed on
> 2026-08-11. F005.6 makes the *send* receipt durable; this one is about what
> happens **after** the handoff.

## The distinction that matters

A send receipt proves the provider **accepted** the mail. It says nothing about
whether it arrived.

```
send() succeeded          →  Resend has it
delivered / bounced /     →  only ever arrives on the webhook stream
complained
```

Nobody in the fleet receives that stream today. So we send mail to real
customers, club members and patients with **no idea what fraction lands**.

And the two outcomes demand opposite responses: a bounced onboarding mail looks
exactly like a delivered one the recipient ignored. One means *fix the address
and resend*; the other means *leave them alone*. Without the stream you cannot
tell them apart, so you either nag people who got it or abandon people who
didn't.

## Measured state

`packages/mail/src/index.ts` exports `createMailer`, `createMailerFromEnv`,
`mailAllowed`, `buildFrom` + types. The only observability is a `logger` that
fires on skipped/failed sends. **There is no webhook receiver and no delivery
log.** xrt81 asked; that is the answer.

## The change

Framework-agnostic, three pieces, thin:

1. `verifyWebhook(rawBody, headers, secret)` — signature verification. Pure.
2. `parseMailEvent(rawBody)` → typed union: `delivered` · `bounced` ·
   `complained` · `opened` · `delivery_delayed`, each carrying the provider id
   and recipient so it joins to an F005.6 receipt.
3. Thin `@broberg/mail/hono` + `@broberg/mail/next` handlers that wire 1+2 to a
   consumer callback.

## Verification is the load-bearing part

An **unverified** webhook endpoint is an open write-surface where anyone can
assert that anything was delivered. That is *worse than having no delivery data
at all*, because it looks like evidence. So:

- Verify **before** parsing, never after.
- A missing or malformed signature is a rejection, not a warning.
- **A missing secret must refuse to serve** — it must not degrade into
  accept-everything. (Same rule as `chainIsEuOnly([]) === false`: absence must
  never satisfy a predicate that asserts safety.)

## Non-goals

- No storage. Same as F005.6 — the package hands you the event; where it lands
  is yours.
- No retry/backfill engine, no reconciliation against `GET /emails`.
- Not provider-abstract on day one. Resend is what the fleet uses; a second
  provider can generalise it when there is a second provider.

## Open question

Whether the webhook secret is per-app or fleet-wide. Leaning per-app: one leaked
secret should not let someone forge delivery events for every repo. Settle
before building.
