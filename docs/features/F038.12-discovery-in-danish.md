# F038.12 — Discovery, in the language the fleet actually works in

**Status:** In progress · **Epic:** F038 (Discovery) · **Written:** 2026-09-05

## How it was found

Christian asked whether the Face ID spellings were covered on `@broberg/auth`:
`FaceID`, `face id`, `id`, `face`, `bio`, `biometric`. All six were.

But the words **he** would type were not:

```
fingerprint · fingeraftryk · ansigt · ansigtsgenkendelse    MISS
```

Fixing that one row took a minute. The next question is the card: was that row
unusual, or is the roster like this everywhere?

**11 of 30 return nothing.**

### And it is worse than 11 of 30

This is the half a summary would drop. Several of the apparent successes are
successes for the wrong reason:

- **`post` scores 37** — because it matches HTTP POST, not Danish *post*.
- **`session`, `test`, `chat`, `video`, `sms`, `upload`** are the same word in
  both languages. They score identically and prove nothing about Danish
  coverage.

Strip the cognates and the false friends, and genuine Danish coverage is a
handful of rows where somebody happened to write a Danish word into a
description.

## Why this is not "a missing search result"

CLAUDE.md orders every session to consult Discovery **before** building a
capability, and to work in Danish. Those two instructions currently contradict
each other.

The failure mode is not an empty list. It is a session concluding **we have no
Stripe package** and wiring a raw Stripe SDK, or asking for `formular` and
rebuilding `@broberg/forms-turnstile` from scratch — the exact drift the roster
exists to prevent. A roster that answers "nothing found" is worse than no roster,
because it **closes the question**.

## Scope

1. **Danish keywords on every shipped row**, beside the English ones — never
   instead of them. Package names and API surfaces are English, and a session
   switches language mid-sentence.
2. **A CI guard** that fails a **new** row without Danish keywords, with an
   explicit cognate list so a row whose only "Danish" word is `test` does not
   pass. A guard that merely reports a total lets the roster drift back one row
   at a time.
3. **Per-word verification on the LIVE site.** Measured twice today: a term can
   HIT from another package's text while the deploy that added it failed. The
   build output is not the surface anyone reads.

### Non-goals

- **Not machine translation of `desc`.** That field is prose a human reads;
  translating it doubles the maintenance and halves the accuracy. Keywords are
  the search surface, and keywords are what this touches.
- **Not other languages.** The fleet works in Danish and English. A third is a
  different card with a different reason.

## The trap this must not fall into

Adding words until everything hits is not the goal — a search that matches
everything is as useless as one that matches nothing. Hence the **negative
control**: a coined non-word must still return zero. Without it, "every word now
hits" cannot be told apart from "the search stopped discriminating".

## Reuse

No package involved — roster data plus a check, in the repo that owns Discovery.
The guard belongs beside `check-roster-versions.mjs`, which already enforces the
other property a roster row must have: a version npm actually serves.
