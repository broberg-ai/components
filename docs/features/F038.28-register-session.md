# F038.28 — Register new Discovery sessions again

> Story under F038. Priority high. 2 SP.

## Summary
New repos cannot get into Discovery: every call answers 401 until components registers the session's key, and the tool for doing that was never written. This story writes it, registers the two repos that are waiting (jam, firstcoat), and hands each its key through the cardmem vault.

## Motivation
jam #2965 and firstcoat #2999 (12/10) have no DISCOVERY_ENROLL_KEY, so `/ai`, `/api/search` and enroll all answer 401. Since F038.21/22 (8/10) Discovery refuses unknown sessions (no trust-on-first-use) and `server.ts` says «components registers new sessions (scripts/register-session.ts)» — the fleet CLAUDE.md block says the same. Measured 12/10: that file does not exist and never did (`git log --all -- '*register-session*'` → nothing). Only `register-speech-editor.ts` exists. So the documented path ends in a missing file, and every new repo is locked out of the reuse check the fleet rules require at plan time.

## Solution
`apps/discovery/scripts/register-session.ts`, modelled on `register-speech-editor.ts`: session name in argv, key on stdin, `bindSessionKey(session, sha256(key))` through the existing `EnrollStore`, refuse if the session is already bound (rotation stays `reset-session-key.mjs`). Run where the Turso credentials are (locally from the vault, or `fly ssh console`). Keys are generated with `openssl rand -hex 32`, written straight into cardmem's vault for the receiving project, and never printed.

## Reuse
- `EnrollStore.bindSessionKey` / `sessionKeyHash` (apps/discovery/enroll.ts) — no new SQL.
- cardmem Secrets Vault (`cardmem_create_secret`) for handing over the key.

## Design
None — no visual surface.

## Scope
### In scope
- The script + a test in the discovery suite + Dockerfile COPY line.
- Registering jam and firstcoat; their keys in their vaults.
- Fixing the server.ts comment if the path differs.
### Out of scope
- Broberg ID login for Discovery (the planned replacement for keys).
- An HTTP route for registration — deliberately none (same reasoning as reset).

## Architecture
```
bun scripts/register-session.ts <session> < keyfile
  → sessionKeyHash(session) exists → refuse ("already bound — reset first")
  → else bindSessionKey(session, sha256(key)) → "registered <session>"
```

## Acceptance criteria
1. Script exists, key from stdin, binds sha256, refuses an already-bound session with the old hash unchanged (read back from the store) — discovery test suite.

3. Each key is in the receiver's cardmem vault as DISCOVERY_ENROLL_KEY; the value never appeared in argv, chat or intercom.
